# Генератор нагрузки `loadgen`

Модуль 14 («Высокие нагрузки»). Генератор нагрузки для REST «Заказов» и
нагрузочный разбор итогового проекта одной командой. Только стандартная
библиотека: свой HTTP-клиент, своя гистограмма задержек, свой разбор
метрик Prometheus.

```
labs/loadgen/
├── cmd/loadgen/main.go      подкоманды run и analyze, флаги
├── internal/
│   ├── load/                модели нагрузки (открытая, закрытая), сценарии, статистика, отчёт
│   ├── hist/                гистограмма задержек: лог-линейные корзины, ошибка перцентиля ≤ 3%
│   ├── promtext/            разбор текстового формата /metrics
│   └── analyze/             разбор: база → кеш → реплика → перегрузка, сводная таблица
└── Dockerfile               scratch, не root; контекст сборки — labs/
```

## Нагрузочный разбор

При запущенном профиле `labs`:

```sh
docker compose --profile labs run --rm loadgen analyze
```

Сервис `loadgen` в `docker-compose.yml` — в профиле `loadtest`, поэтому
`up` его не запускает; `run` включает профиль сам. `depends_on` у него
нет: `run` не трогает уже запущенные базы, а генератор сам ждёт
`/readyz` «Заказов» (до 90 с). Адреса — `LOADGEN_TARGET=http://orders:8080`,
`LOADGEN_OPS=http://orders:8081` (сеть docker `default`).

С машины, без Docker-образа генератора:

```sh
cd labs/loadgen
go run ./cmd/loadgen analyze -target http://127.0.0.1:8090 -ops http://127.0.0.1:8190
```

### Как переключаются кеш и реплика

Перезапустить контейнер «Заказов» изнутри другого контейнера нельзя (и
давать генератору доступ к Docker незачем), а пересборка ради флага
растянула бы разбор и сбросила прогрев. Поэтому у «Заказов» есть
служебный эндпоинт `/admin/features` (`ORDERS_ADMIN_FEATURES=true`, только
служебный порт): разбор читает исходное состояние, перед каждым шагом
выставляет нужное, а в конце (и при Ctrl+C) возвращает как было. Метрики
снимаются с `/metrics` того же порта до и после шага, в отчёт идёт
прирост — по каждому ряду отдельно, как `increase` в Prometheus (сброс
счётчика после рестарта считается от нуля). У каждого шага своё зерно
случайности (из `-seed`): смесь та же, а ключи новые — иначе шаг повторил
бы несуществующие товары предыдущего и их отдал бы отрицательный кеш.

### Шаги

| Шаг | Что включено | Что смотреть |
|---|---|---|
| 1 база | ничего | «запросов каталога в базу» ≈ частота запросов каталога; вся история с основной базы |
| 2 +кеш | кеш каталога | запросов в базу почти нет (промахи по несуществующим товарам и раз в TTL), попаданий — почти все |
| 3 +реплика | кеш и реплика | «история: с реплики» — большая часть; «реплика отставала от токена» — чтения по токену, ушедшие на основную; read-your-writes: «не виден без токена» > 0, «с токеном» = 0 |
| 4 перегрузка | как в шаге 3 | только заказы, 1500/с: исход `429` у части, `p99 отказов` много меньше `p99 принятых` |

Шаги 1–3 — одна и та же смесь `catalog=6,orders=1,history=3` с частотой
150 сценариев/с по 15 с (плюс 3 с прогрева, его статистика не входит). В
сценарии `orders` разбор после создания заказа дважды читает историю
покупателя — без токена и с токеном — и считает, виден ли новый заказ
(операция `orders.list_ryw`).

### Как читать отчёт

Отчёт шага:

```
сценариев запущено: 2250 (150.1/с), длительность 14.995s
операция        запросов    в сек       p50       p90       p99     p99.9       max  исходы
catalog.get         1329     88.6    1.01ms    1.70ms    3.01ms    3.77ms    6.21ms  200:1268 404:61
orders.create        235     15.7    2.94ms    4.86ms    6.78ms    7.47ms    7.47ms  200:235
...
read-your-writes: проверок 235, заказ не виден без токена: 235, с токеном: 0
метрики «Заказов» за шаг:
  запросов каталога в базу: 0 (0.0/с); кеш: попаданий 1503, «нет такого» из кеша 61, промахов 0, ошибок Valkey 0
  история: с реплики 921, с основной 235 (из них реплика отставала от токена: 235)
  отброшено ограничением CreateOrder (429): 0
```

- **сценариев запущено (в сек)** — фактическая частота. Если она заметно
  ниже заданной или есть «не запущено (лимит генератора)», генератор сам
  не успевал — результатам шага верить нельзя.
- **исходы** — HTTP-коды и транспортные ошибки (`timeout`, `conn_error`).
  `404` у `catalog.get` — нарочно: 5% запросов идут к несуществующим
  товарам (отрицательный кеш). `429` — load shedding, `400` — не хватило
  товара.
- **p50…max** — перцентили задержки. Среднего нет нарочно: у задержек
  тяжёлый хвост, и среднее его прячет. Задержка первого запроса сценария
  считается от **запланированного** момента отправки (см. ниже).
- **реплика недоступна** — строка появляется, если чтения с реплики
  падали и ушли на основную (`reason="replica_error"`): сервис
  деградировал, клиенты ошибок не видели, но доля реплики в шаге 3 будет 0%.
  Проверьте `docker compose ps postgres-replica`.
- **сводная таблица** в конце — шаги рядом: частота, p50/p99 каталога, p99
  создания заказа и истории, ошибки (`5xx/сеть`, `429`, `400`), запросы
  каталога в базу в секунду, доля попаданий кеша, доля чтений истории с
  реплики и проверки read-your-writes «без токена/с токеном».

Числа зависят от машины и её загрузки: на ноутбуке с маленькими таблицами
база отвечает за доли миллисекунды, и разница в задержках шагов 1–3
небольшая. Смотрите на направление, а не на значения: запросы в базу
падают почти до нуля, доля реплики растёт, «с токеном» всегда 0, в
перегрузке появляются быстрые 429.

## Один прогон: `loadgen run`

```sh
# открытая модель: 300 сценариев/с, 30 с, своя смесь
docker compose --profile labs run --rm loadgen run -rate 300 -duration 30s -mix catalog=8,history=2
# закрытая модель: 50 пользователей, пауза 200 мс ±50%
docker compose --profile labs run --rm loadgen run -model closed -users 50 -think 200ms
```

| Флаг | По умолчанию | Что |
|---|---|---|
| `-target` | `$LOADGEN_TARGET` или `http://127.0.0.1:8090` | REST «Заказов» |
| `-model` | `open` | `open` — заданная частота прихода; `closed` — N пользователей |
| `-rate`, `-max-in-flight` | 100, 10000 | open: сценариев в секунду; предохранитель генератора |
| `-users`, `-think` | 20, `100ms` | closed: пользователей и пауза между их сценариями |
| `-duration` | `15s` | длительность |
| `-mix` | `catalog=6,orders=1,history=3` | сценарии и веса |
| `-customers`, `-products`, `-missing` | 1000, 3, 0.05 | покупатели 1..N, товары каталога 1..N, доля несуществующих товаров |
| `-order-products` | `4` | что заказывать: 4 — «Кабель USB-C», на складе миллион |
| `-ryw` | `false` | orders: проверять read-your-writes |
| `-timeout`, `-seed` | `5s`, время | таймаут запроса, зерно случайности |

У `analyze` те же общие флаги и свои: `-ops`, `-rate` (150), `-duration`
(15s на шаг), `-warmup` (3s), `-mix`, `-overload-rate` (1500, 0 — без
шага 4), `-overload-duration` (3s).

Сценарии:

- `catalog` — `GET /v1/products/{id}`;
- `history` — `GET /v1/orders?customer_id=…&page_size=10`;
- `orders` — `POST /v1/orders` (одна штука товара), затем
  `POST /v1/orders/{id}:cancel`: отмена возвращает товар, остатки не
  убывают от прогона к прогону. Задержка отмены — от её фактической
  отправки.

## Открытая и закрытая модели, coordinated omission

**Открытая модель** — как пользователи из интернета: приходят с заданной
частотой независимо от того, успевает ли сервис. Расписание фиксировано
заранее (i-й сценарий — в `start + i/rate`), каждый сценарий — своя
горутина. Задержка считается **от запланированного момента**: если
сервис затормозил, расписание не ждёт, а время, которое запрос «простоял»
из-за этого, входит в его задержку.

Генератор, который ждёт ответа перед следующим запросом и считает
задержку от фактической отправки, при деградации сервиса сам снижает
нагрузку и не видит, сколько запросов «должно было» уйти, — хвост
перцентилей выглядит красиво именно тогда, когда всё плохо. Это
coordinated omission (Gil Tene). Тест
`TestOpenModelMeasuresFromSchedule` проверяет, что зависание сервера
попадает в задержку всех запросов, запланированных за время зависания.

**Закрытая модель** — N пользователей, каждый делает сценарий, ждёт
think time и повторяет: так ведут себя пулы воркеров и батч-клиенты.
Частота подстраивается под сервис, задержка — от фактической отправки:
закрытая модель по природе недооценивает хвост при деградации.

## Гистограмма

`internal/hist` — лог-линейные корзины, как в HdrHistogram: до 64 мкс по
1 мкс, дальше каждая степень двойки делится на 32 корзины. Ошибка
перцентиля — не больше 1/32 (≈3%), память постоянная, гистограммы
складываются. Перцентиль — верхняя граница корзины, но не больше точного
максимума.

## Тесты

```sh
cd labs/loadgen && go test -race ./...
```

Сервер — `httptest`: открытая модель выполняет ровно расписание (100
сценариев за 250 мс при 400/с), задержка — от плана при «зависшем»
сервере, предохранитель генератора, закрытая модель не превышает N
одновременных запросов, 429 и проверка read-your-writes, разбор целиком
на фейковых «Заказах» (переключатели по шагам и возврат в исходное
состояние, пропуск ненастроенной реплики).
