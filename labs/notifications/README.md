# Сервис «Уведомления»

Третий сервис итогового проекта курса «Go для C#-разработчика» (модули 11–12).
Читает события заказов из Kafka, сохраняет уведомление покупателю и
«отправляет» его. Входящего API нет: работа приходит из топика, наружу
смотрит только служебный HTTP (`/healthz`, `/readyz`, `/metrics`).

Что делает:

- читает `orders.events` (его пишет relay outbox «Заказов») в consumer group
  `notifications`;
- на `OrderCreated` пишет «Заказ 42 оформлен на 5 980,00 ₽», на
  `OrderCancelled` — «Заказ 42 отменён»: сохраняет в SQLite и пишет в журнал
  запись `notification sent` (это и есть «отправка»);
- повторную доставку того же события (тот же `event_id`) распознаёт и
  пропускает;
- записи, которые не разбираются или не обрабатываются после нескольких
  попыток, кладёт в DLQ `notifications.dlq` и идёт дальше;
- продолжает трассу запроса создания заказа: в Jaeger видна цепочка
  HTTP → «Заказы» → «Склад» → Kafka → «Уведомления».

## Структура

```
labs/notifications/
├── cmd/notifications/main.go   тонкий main → run(ctx, args, getenv, stdout): конфигурация,
│                               трассировка, база, клиент Kafka, ops-сервер, graceful shutdown
├── internal/
│   ├── notify/                 предметная логика: разбор OrderEvent, текст уведомления,
│   │                           «сначала коммит, потом отправка»; интерфейс Store — здесь
│   ├── consumer/               цикл franz-go: опрос, порядок внутри партиции, повторы,
│   │                           DLQ, ручной коммит, спан на запись, метрики
│   └── store/sqlite/           database/sql + modernc.org/sqlite: дедупликация и запись
│                               уведомления в одной транзакции
├── migrations/                 миграции goose, встроенные в бинарник (embed)
└── Dockerfile                  multi-stage, контекст — labs/, финальный образ scratch, не root
```

Общий каркас — `labs/platform`: журнал (`logging`), трассировка
(`telemetry`), ops-сервер (`httpx.OpsHandler`, `health`), заголовки Kafka как
носитель трассы и создание топика (`kafkax`), повторы (`resilience.Retry`).
Контракт события — `labs/api/proto/events/v1/events.proto`.

## Ключевые решения

- **Ручной коммит после обработки.** `kgo.DisableAutoCommit()`: автокоммит
  franz-go коммитит уже выданное опросом — возможно, ещё не обработанное, и
  падение в этот момент теряет запись. Цикл: `PollRecords` → обработать
  записи каждой партиции по порядку → `CommitRecords` обработанных →
  `AllowRebalance()`. Офсет записи коммитится, только когда она обработана
  или подтверждённо лежит в DLQ.
- **`BlockRebalanceOnPoll`.** Пока пачка в работе, группа не отбирает
  партиции — нельзя закоммитить офсет партиции, которая уже у другого
  участника. Цена: пачка должна успевать за rebalance timeout, поэтому она
  ограничена (`MaxPollRecords` = 100).
- **At-least-once + идемпотентность.** Сбой между обработкой и коммитом
  приводит к повторной доставке. В одной транзакции SQLite:
  `INSERT INTO processed_events … ON CONFLICT DO NOTHING`; 0 строк — повтор,
  пропускаем; иначе — `INSERT INTO notifications` и коммит. Дедупликация
  лежит в той же базе, что и результат, именно ради одной локальной
  транзакции: отметка в Redis и уведомление в базе при сбое между ними
  дали бы потерю или дубль.
- **Сначала коммит, потом «отправка».** Таблица `notifications` — источник
  истины, запись в журнал — доставка. Откат транзакции ничего не отправляет,
  повтор после отката не шлёт дубль. Окно «закоммитили, упали до отправки»
  остаётся: в настоящей системе отправку делает отдельный воркер по таблице
  (outbox), а провайдер писем получает ключ идемпотентности — побочный
  эффект тоже at-least-once.
- **Ядовитые сообщения — сразу в DLQ.** Не разобралось значение (или нет
  `event_id`) — повтор бессмыслен, а застрявшая запись остановила бы всю
  партицию. `dlq-reason: decode`.
- **Ошибки обработки — повторы, затем DLQ.** `resilience.Retry` с
  экспоненциальной паузой и jitter, `NOTIFICATIONS_MAX_ATTEMPTS` попыток
  (по умолчанию 3), затем DLQ с `dlq-reason: processing`. Сон внедрён —
  тесты повторов идут без пауз.
- **DLQ не теряет записи.** В DLQ уходят ключ, значение и заголовки
  оригинала плюс `dlq-reason`, `dlq-error` (≤ 256 байт), `dlq-attempts`,
  `dlq-source-topic`, `dlq-source-partition`, `dlq-source-offset`,
  `dlq-consumer-group`. Отправка подтверждается (`ProduceSync`) до коммита
  офсета; пока DLQ недоступен, попытки идут до остановки — консьюмер стоит,
  но ничего не пропускает. Топик DLQ создаёт сам сервис (`kafkax.EnsureTopic`):
  одна партиция (поток мал, общий порядок сбоев удобен для разбора),
  фактор репликации — по умолчанию брокера.
- **Незнакомые события — пропуск.** Вариант oneof, которого нет в этой версии
  контракта (`GetEvent() == nil`), — не ошибка: офсет коммитится, метрика
  `result="skipped"`.
- **Трассировка.** Контекст — из заголовков записи (`kafkax.HeaderCarrier` +
  глобальный пропагатор W3C), спан `orders.events process` (SpanKind
  Consumer, атрибуты semconv v1.43.0: `messaging.system=kafka`, destination,
  partition, offset, consumer group, `messaging.message.id` = `event_id`).
  Журнал пишется с контекстом спана — у `notification sent` тот же `trace_id`,
  что у HTTP-запроса создания заказа.
- **SQLite и одно соединение.** WAL (читатели не блокируют писателя),
  `busy_timeout`, `foreign_keys`, `BEGIN IMMEDIATE`. `SetMaxOpenConns(1)`:
  писатель в SQLite один на всю базу, несколько соединений только
  соревновались бы за блокировку файла и ловили `SQLITE_BUSY` друг от друга;
  консьюмер пишет последовательно, а пинг готовности подождёт конца короткой
  транзакции.
- **Мягкая остановка.** Сигнал → готовность снята → `DRAIN_DELAY` → опрос
  прекращается, текущая пачка дообрабатывается (её контекст не отменяется
  сигналом: `context.WithoutCancel` + 10 с на завершение) и коммитится →
  `CloseAllowingRebalance()` (выход из группы, партиции сразу уходят другим
  репликам) → ops-сервер → база → сброс спанов.

## Конфигурация

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `NOTIFICATIONS_KAFKA_BROKERS` | — (обязательно) | брокеры `host:port` через запятую |
| `NOTIFICATIONS_KAFKA_TOPIC` | `orders.events` | топик событий заказов |
| `NOTIFICATIONS_KAFKA_GROUP` | `notifications` | consumer group |
| `NOTIFICATIONS_DLQ_TOPIC` | `notifications.dlq` | топик DLQ (создаётся при старте) |
| `NOTIFICATIONS_MAX_ATTEMPTS` | `3` | попыток обработки записи (1–100) |
| `NOTIFICATIONS_DB_PATH` | `/data/notifications.db` | файл SQLite |
| `NOTIFICATIONS_OPS_ADDR` | `:8081` | служебный HTTP: `/healthz`, `/readyz`, `/metrics` |
| `NOTIFICATIONS_OTLP_ENDPOINT` | пусто | `host:port` приёмника OTLP/gRPC (Jaeger); пусто — спаны не экспортируются |
| `NOTIFICATIONS_LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `NOTIFICATIONS_DRAIN_DELAY` | `0` | пауза между снятием готовности и остановкой (в k8s ~`5s`) |

Ошибки конфигурации сообщаются все сразу, при старте. `/readyz` проверяет
пинг базы и `kgo.Client.Ping` (брокер доступен).

## Запуск

В профиле `labs` сервис поднимается вместе с Kafka и Jaeger:

```sh
docker compose --profile labs up --build
```

Создайте заказ через «Заказы» — в журнале «Уведомлений» появится запись:

```sh
docker compose logs -f notifications | grep 'notification sent'
# {"level":"INFO","msg":"notification sent","order_id":1,"customer_id":42,
#  "kind":"order_created","text":"Заказ 1 оформлен на 5 980,00 ₽","trace_id":"…"}

curl -s localhost:8192/readyz
curl -s localhost:8192/metrics | grep ^notifications_
```

По `trace_id` трасса находится в Jaeger (http://localhost:16686): спан
`orders.events process` — потомок публикации события «Заказами».

Содержимое DLQ:

```sh
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic notifications.dlq --from-beginning \
  --property print.headers=true
```

Локально, без Docker (нужна Kafka на 127.0.0.1:59092):

```sh
cd labs/notifications
NOTIFICATIONS_KAFKA_BROKERS=127.0.0.1:59092 NOTIFICATIONS_DB_PATH=./notifications.db \
NOTIFICATIONS_OPS_ADDR=127.0.0.1:8081 go run ./cmd/notifications
```

## Тесты

```sh
cd labs/notifications
go vet ./...
go test -race -count=3 ./...
GOWORK=off go test -race -count=3 ./...   # модуль сам по себе, без go.work
```

Брокер не нужен: тесты консьюмера и `run()` идут против `kfake` — брокера
Kafka в памяти процесса из franz-go (настоящий протокол, группы, коммиты),
у каждого теста свой кластер и свои топики. База — временный файл SQLite в
`t.TempDir()`. Переменные окружения тесты не читают. Асинхронное ждут
циклом с проверкой условия под общим таймаутом, без `time.Sleep`; сон
повторов внедрён.

Что проверяется:

- `OrderCreated` → строка в `notifications`, офсет закоммичен (через
  `kadm.FetchOffsets` группы), метрики;
- две записи с одним `event_id` → одно уведомление, оба офсета закоммичены;
- незнакомый вариант oneof → пропуск и коммит;
- мусор в значении → DLQ с заголовками причины, офсет закоммичен, следующее
  событие той же партиции обработано;
- хранилище падает K раз при N попытках: K < N — обработано после повторов,
  K ≥ N — DLQ с `dlq-reason: processing`, `dlq-attempts: N`;
- брокер отверг коммит → после перезапуска консьюмера та же запись приходит
  снова и отсеивается как повтор (at-least-once);
- DLQ недоступен → офсет не коммитится, отправка повторяется и доходит,
  когда топик появляется; остановка в этот момент укладывается в таймаут и
  оставляет запись незакоммиченной;
- `traceparent` в заголовке → спан обработки — его потомок, атрибуты
  semconv, `trace_id` в журнале;
- контрактные тесты SQLite: дедупликация (в том числе конкурентная), откат
  отметки при сбое второй вставки, повторное открытие и миграции;
- `run()` целиком: поднимается на kfake, обрабатывает событие, отвечает на
  `/readyz` и `/metrics`, останавливается по отмене контекста.

## Метрики

| Метрика | Метки | Смысл |
|---|---|---|
| `notifications_events_total` | `type` = `order_created`\|`order_cancelled`\|`unknown`, `result` = `sent`\|`duplicate`\|`skipped`\|`dlq` | обработанные записи |
| `notifications_sent_total` | `kind` | отправленные уведомления |
| `notifications_dlq_total` | `reason` = `decode`\|`processing` | записи в DLQ — повод для алерта |
| `notifications_processing_retries_total` | — | повторы обработки |
| `notifications_event_processing_seconds` | — | время обработки записи (с повторами и DLQ) |

Плюс стандартные `go_*` и `process_*`. Лаг консьюмера (насколько группа
отстала от конца топика) в продакшне снимают снаружи — kafka-exporter или
Burrow по офсетам группы, а не сам сервис.

## Чего нет и как в продакшне

- **Своя база сервиса.** В labs SQLite лежит в tmpfs (`/data`), данные
  учебные и пропадают при перезапуске — как у всего профиля. В продакшне это
  была бы собственная база «Уведомлений», например PostgreSQL (не общая с
  «Заказами»: у каждого сервиса свои данные), и несколько реплик в одной
  группе. Дедупликация осталась бы в той же базе, что и уведомления, — ради
  одной транзакции; `processed_events` чистили бы по сроку старше окна
  повторной доставки.
- **Настоящей отправки.** «Отправка» — запись в журнал. В жизни — отдельный
  воркер по таблице `notifications` (outbox) к провайдеру писем/push с ключом
  идемпотентности, своими повторами и автоматическим выключателем
  (`resilience.Breaker`).
- **Переобработки DLQ.** Записи DLQ разбирают вручную или утилитой,
  которая после исправления возвращает их в `orders.events`; её здесь нет.
- **TLS и аутентификации к Kafka.** В labs брокер в docker-сети без
  шифрования. В продакшне — `kgo.DialTLSConfig` и SASL (SCRAM/OAUTHBEARER),
  ACL группы только на чтение своего топика и запись в свой DLQ.
- **Порядок при повторной обработке.** Внутри партиции записи обрабатываются
  строго по порядку, поэтому «отменён» не обгонит «оформлен» того же заказа.
  Но после DLQ событие заказа может «выпасть» из последовательности —
  для уведомлений это приемлемо, для состояния (например, проекции статуса
  заказа) потребовались бы версии событий.
