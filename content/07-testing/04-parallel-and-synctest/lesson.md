По умолчанию тесты пакета идут последовательно. `t.Parallel()` разрешает тесту идти одновременно с другими параллельными тестами: тест ставится на паузу (`=== PAUSE`) и продолжается (`=== CONT`), когда последовательная часть закончилась. Для подтестов это значит: параллельные подтесты стартуют, только когда функция родителя **вернулась**. Её `defer` к тому моменту уже выполнен, а `t.Cleanup` родителя ждёт завершения всех подтестов. Сколько тестов идут одновременно, задаёт флаг `-parallel` (по умолчанию `GOMAXPROCS`). Параллельные тесты, которые трогают общие данные, гоняют с `-race`.

Код со временем — таймауты, ретраи, TTL, debounce — тестировать сложно: настоящий `time.Sleep` делает тесты медленными, а пороги вроде «уложилось в 50 мс» — нестабильными. Классическое решение — интерфейс часов и фейк. С Go 1.25 есть `testing/synctest`: `synctest.Test(t, func(t *testing.T) {...})` запускает функцию в «пузыре», где у пакета `time` фейковые часы. Они стартуют с полуночи 2000-01-01 UTC и прыгают вперёд, только когда все горутины пузыря **прочно заблокированы** (durably blocked) — ждут то, что может дать только другая горутина пузыря. Минута «сна» занимает микросекунды, и результат всегда один и тот же. `synctest.Wait()` ждёт, пока все остальные горутины пузыря не заблокируются: после него можно проверять, что фоновая работа сделана.

## Как это в C#

- **Параллельность.** В xUnit параллельно идут тестовые коллекции (по умолчанию — классы), а тесты внутри класса — последовательно; управляют этим `[Collection]` и `xunit.runner.json`. В Go всё наоборот: последовательно по умолчанию, параллельность — явный вызов `t.Parallel()` в конкретном тесте. Разные пакеты `go test ./...` и так идут в отдельных процессах параллельно (`-p`).
- **Время.** В .NET 8 появился `TimeProvider` и `FakeTimeProvider` (Microsoft.Extensions.TimeProvider.Testing): код должен принимать `TimeProvider`, а тест двигает время `Advance(...)`. `synctest` не требует менять код — подменяются сами `time.Now`, `time.Sleep`, таймеры и тикеры, — и время двигается автоматически, когда всё ждёт.
- **«Дождаться фоновой работы».** В C# это `await` задачи или опрос с таймаутом. `synctest.Wait()` — детерминированная точка «все горутины встали», без опроса и `Task.Delay`.

## Ловушки

### `defer` в родителе параллельных подтестов

```go
func TestAPI(t *testing.T) {
	srv := startServer()
	defer srv.Close() // выполнится до того, как подтесты начнут работать
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			t.Parallel()
			call(srv, tt) // сервер уже закрыт
		})
	}
}
```

Параллельные подтесты ждут возврата из функции родителя, а `defer` срабатывает именно при возврате. Освобождайте общие ресурсы через `t.Cleanup` — он выполнится после всех подтестов. Либо оберните подтесты в `t.Run("group", ...)`: родительский `t.Run` вернётся, когда завершатся все вложенные.

### Не всякая блокировка «прочная»

```go
synctest.Test(t, func(t *testing.T) {
	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	go serve(ln)            // горутина ждёт сеть — это не прочная блокировка
	time.Sleep(time.Second) // зависнет: часы стоят, пока serve не заблокирован прочно
})
```

Сетевое ожидание может закончиться из-за события извне пузыря, поэтому часы не двигаются, а `synctest.Wait()` не возвращается. Прочно блокируют: отправка и приём по каналу, созданному в пузыре; `select`, где все каналы из пузыря; `time.Sleep`; `sync.Cond.Wait`; `sync.WaitGroup.Wait`, если `Add` вызывался в пузыре. Не прочно: `sync.Mutex`, сетевой и файловый ввод-вывод, системные вызовы, каналы, созданные вне пузыря. Поэтому внутри пузыря не используют настоящую сеть — берут `net.Pipe` или фейк. А к концу `synctest.Test` все горутины пузыря должны завершиться: зависшая навсегда горутина — это ошибка теста.

### Тест и код спят одинаково долго

```go
d := NewDebouncer(time.Second, 0, fire)
d.Trigger()
time.Sleep(time.Second) // таймер дебаунсера сработал в тот же момент
if count != 1 { ... }   // гонка: callback ещё мог не выполниться
```

Когда часы доходят до момента, на котором ждут несколько горутин, все они просыпаются одновременно, и порядок между ними не определён. После `time.Sleep` вызывайте `synctest.Wait()`: он дождётся, пока горутина таймера закончит работу.

## Задание

Напишите debounce: функция выполняется не на каждое событие, а после паузы в потоке событий — как автосохранение, которое ждёт, пока пользователь перестанет печатать.

```go
func NewDebouncer(wait, maxWait time.Duration, f func()) *Debouncer
func (d *Debouncer) Trigger()
func (d *Debouncer) Stop() bool
```

Требования:

- `Trigger` сообщает о событии. Серия начинается с первого `Trigger`, когда вызов `f` не ожидается. Пока серия идёт, `f` будет вызвана один раз — в момент `последний Trigger + wait`. Каждый новый `Trigger` в серии переносит этот момент;
- если `maxWait > 0`, вызов не откладывается дальше `первый Trigger серии + maxWait`: момент вызова — меньшее из двух. `maxWait == 0` — ограничения нет. `wait` всегда больше нуля;
- вызов `f` завершает серию: следующий `Trigger` начинает новую, и её момент считается заново. `f` может и сама вызвать `Trigger` — это тоже начало новой серии, без взаимоблокировки;
- `f` вызывается в отдельной горутине (например, той, что запускает `time.AfterFunc`), и строго в рассчитанный момент: тесты работают в `synctest` с фейковыми часами и сверяют время вызова точно;
- `Stop` отменяет ожидаемый вызов и возвращает `true`, если он был запланирован (`false`, если ждать было нечего — в том числе когда `f` уже начала выполняться: такой вызов не отменяется и не считается ожидаемым). После `Stop` дебаунсер выключен навсегда: `Trigger` ничего не делает, повторный `Stop` возвращает `false`;
- методы безопасны для одновременного вызова из разных горутин. Тесты вызывают `Stop` в конце, и после него у дебаунсера не должно оставаться работающих горутин — иначе `synctest.Test` не завершится.
