Инструменты модуля — `t.Run`, хелперы, `t.Parallel`, фейки, `httptest` — сами по себе не делают тесты хорошими. В настоящем проекте тесты гоняют сотни раз в день на разных машинах, и ценятся три свойства: тест падает **только** когда сломано поведение, падает **каждый раз**, когда оно сломано, и по сообщению сразу ясно, что именно. Ниже — практики, которые к этому ведут, и пример, где они собраны вместе.

**Что тестировать.** Поведение через публичный API — внешний пакет `x_test`, как в примере. Такой тест — документация («вот как этим пользоваться») и не ломается от рефакторинга внутренностей. Внутренний тест (`package x`) — для сложной приватной логики, которую неудобно достать снаружи. Один тест — одна причина упасть: подтест на каждый случай, а не десять проверок подряд, где после первого `Fatal` остальные не выполнятся. Сообщение — в формате `Place(" alice ", 25000) = <got>, want <want>`: вызов с входными данными и оба значения. Ассерт-библиотеки не обязательны: testify (`assert`, `require`) очень распространён, и это нормальное решение команды, но `if got != want { t.Errorf(...) }` плюс `slices.Equal`, `maps.Equal`, `reflect.DeepEqual` и `errors.Is` закрывают почти всё, а для больших структур есть `github.com/google/go-cmp` (`cmp.Diff`).

**Детерминизм.** Всё, что меняется от запуска к запуску, — внедряемая зависимость: время (`now func() time.Time`), идентификаторы и случайность (`newID func() string`, `*rand.Rand` с фиксированным seed). Порядок обхода map и результатов БД без `ORDER BY` не обещан — сортируйте с полным ключом. Никакого `time.Sleep` для синхронизации: ждите канал, `sync.WaitGroup` или используйте `testing/synctest`. Пакетные переменные, которые тесты меняют, создают зависимость от порядка тестов; её ловит `go test -shuffle=on` — он перемешивает тесты и печатает seed (`-test.shuffle 1731...`), с которым порядок можно повторить: `-shuffle=1731...`. Подозрение на флак проверяют `go test -run TestX -count=200 -race`. **Флак — это баг** в тесте или в коде, а не повод нажать «перезапустить»: его чинят или временно помечают `t.Skip("флак: issue #123")` с задачей, но не оставляют мигать.

**Изоляция ресурсов.** Каждый тест создаёт своё и убирает за собой: `t.TempDir()` вместо общего `/tmp/test`, `t.Cleanup` вместо ручной уборки, `t.Setenv` вместо `os.Setenv` (в параллельном тесте `t.Setenv` паникует: окружение общее на процесс), `t.Context()` для операций с контекстом, сервер на `127.0.0.1:0` (`httptest.NewServer`) вместо фиксированного порта `:8080`, который занят у соседа. Для БД — отдельная база, схема или транзакция с откатом на каждый тест, а не общие таблицы, которые тесты портят друг другу.

**Уровни тестов.** Unit-тесты быстрые и без внешних систем — их запускают на каждое сохранение. Интеграционные (настоящая БД, брокер, сеть) отделяют, чтобы `go test ./...` у разработчика не требовал Docker:

- build tag: файл начинается с `//go:build integration` и компилируется только с `go test -tags=integration ./...`;
- `testing.Short()`: тест пропускается при `go test -short`;
- переменная окружения с адресом зависимости, как в примере: нет переменной — `t.Skip` с понятной причиной.

Поднимать зависимости в тестах часто доверяют **testcontainers-go** — он запускает Postgres, Kafka и т.п. в Docker прямо из теста (в песочнице Docker нет). В CI интеграционные тесты идут отдельным job с сервисами.

**Данные.** Builder или фабрика с разумными значениями по умолчанию (`anOrder(func(o *Order){ o.Total = 0 })`) — тест показывает только то, что для него важно, а новое обязательное поле правится в одном месте. Входные файлы — в `testdata/` (его игнорирует `go build`), большие ожидаемые выводы — golden-файлы с флагом `-update`.

**Фейки против моков.** In-memory фейк проверяет результат: «после `Place` заказ лежит в хранилище». Мок с ожиданиями проверяет реализацию: «`Save` вызван ровно один раз с такими аргументами» — и ломается от любого рефакторинга. Шпион уместен, когда вызов и есть поведение: письмо отправлено, кеш не пошёл в источник, ретраев было три. Фейк стоит прогонять тем же набором проверок (контрактным тестом), что и настоящую реализацию в интеграционном тесте, — иначе он врёт.

**Организация.**

- `x_test.go` лежит рядом с `x.go`; хелперы, нужные нескольким пакетам (фабрики, фейки, запуск тестовой БД), — в `internal/testutil`.
- Если внешнему тесту нужен доступ к внутренностям, файл `export_test.go` в `package x` открывает их только для тестов: `var ParseHeader = parseHeader`. Он компилируется лишь при `go test`.
- `TestMain` — редко: для дорогой подготовки на весь пакет (контейнер, миграции); обычно хватает хелпера с `sync.Once`.

**CI-конвейер.** Типичный минимум:

```sh
test -z "$(gofmt -l .)"                   # форматирование
go vet ./...
golangci-lint run
go test -race -shuffle=on -count=1 ./...  # без кеша, с гонками, в случайном порядке
govulncheck ./...                          # уязвимые зависимости (модуль 9)
go test -race -tags=integration ./...      # отдельный job с БД
```

`-count=1` отключает кеш результатов: локально кеш экономит время, но в CI тест должен реально выполниться. Покрытие — сигнал: смотрите, какие важные ветки красные в отчёте, но не ставьте порог «90% обязательно» — он рождает тесты без проверок.

## Как это в C#

- **Где лежат тесты.** Отдельный проект `Orders.Tests` со ссылкой на основной и `InternalsVisibleTo` для доступа к внутренностям → `orders_test.go` рядом с кодом и `export_test.go`. Тестовый бинарник собирается из пакета, отдельного проекта нет.
- **`[Fact]`/`[Theory]` + `[InlineData]`** → обычные функции `TestXxx` и table-driven тесты с `t.Run`; категории `[Trait("Category", "Integration")]` и фильтр `dotnet test --filter` → build tag, `-short` или `-run`.
- **Moq/NSubstitute** → фейки и шпионы руками на маленький интерфейс. **`IClassFixture`/`WebApplicationFactory`** → хелпер с `t.Cleanup`, `TestMain` и `httptest`. Testcontainers есть в обоих мирах (`Testcontainers` для .NET, `testcontainers-go`).
- **`dotnet test`** каждый раз собирает и запускает всё. `go test` кеширует результат пакета: при неизменных исходниках, флагах и прочитанных файлах и переменных окружения он печатает `ok ... (cached)` без запуска. В CI — `-count=1`.

## Ловушки

### `time.Sleep` вместо синхронизации

```go
go s.Process(job)
time.Sleep(10 * time.Millisecond) // «должно успеть»
if !job.Done() {
	t.Fatal("не обработан") // на загруженном CI-агенте под -race — иногда падает
}
```

Планировщик не обещает, что горутина выполнится за 10 мс: под `-race`, на перегруженном агенте или при `-cpu=1` тест начинает мигать, а увеличение до секунды делает набор медленным и всё равно не гарантирует успеха. Дождитесь события явно: `Process` возвращает канал или принимает `done`, тест ждёт `<-done` (с щедрым таймаутом через `select`), а код с таймерами проверяйте в `synctest.Test`.

### Скрытое общее состояние

```go
var cache = map[string]User{} // пакетная переменная

func TestCreate(t *testing.T) { cache["bob"] = User{Name: "Bob"} /* ... */ }
func TestList(t *testing.T)   { if len(cache) != 0 { t.Fatal("ожидался пустой кеш") } }
```

`TestList` проходит, только если идёт раньше `TestCreate`; при `t.Parallel` это ещё и гонка. Так тесты «зелёные» по отдельности и красные вместе — или наоборот. `-shuffle=on` в CI вскрывает такие зависимости. Лечение — состояние в экземпляре (`NewService(...)` на каждый тест), а не в пакете; в крайнем случае — подмена с возвратом через `t.Cleanup`.

### Проверка реализации вместо поведения

```go
if repo.saveCalls != 1 || repo.lastSaved.Total != 25000 {
	t.Fatal("Save вызван не так")
}
```

Тест знает, как сервис устроен внутри: добавите пакетное сохранение `SaveAll` или кеш — тест упадёт, хотя поведение не изменилось. Проверяйте наблюдаемый результат: что вернул метод и что теперь отдаёт хранилище (`repo.ByCustomer`). Счётчик вызовов оставьте для случаев, где число вызовов — само требование («второй запрос — из кеша»).

## Задание

Сервис очереди тикетов написан «как получилось»: он берёт время из `time.Now`, нумерует тикеты пакетным счётчиком, хранит их в пакетной map и выдаёт очередь в порядке обхода map. Тесты для него недетерминированы, а экземпляры мешают друг другу. Перепишите `task.go` так, чтобы он был тестопригодным, и заодно напишите тестовых двойников — фейковые часы и генератор идентификаторов.

```go
type Ticket struct {
	ID       string
	Title    string
	Priority int
	Created  time.Time
}

var ErrInvalid = errors.New("desk: неверный тикет")

func NewDesk(now func() time.Time, newID func() string) *Desk
func (d *Desk) Open(title string, priority int) (Ticket, error)
func (d *Desk) Queue() []Ticket
func (d *Desk) Expire(maxAge time.Duration) int

func NewFakeClock(start time.Time) *FakeClock
func (c *FakeClock) Now() time.Time
func (c *FakeClock) Advance(d time.Duration)

func SeqIDs(prefix string) func() string
```

`Desk`:

- `NewDesk` сохраняет переданные функции. Если `now == nil`, используется `time.Now`; если `newID == nil` — `rand.Text` из `crypto/rand`;
- состояние (тикеты) хранится в экземпляре: два `Desk` никак не влияют друг на друга. Пакетных изменяемых переменных быть не должно;
- `Open` убирает пробелы по краям `title` (`strings.TrimSpace`). Если заголовок пустой или `priority` не в диапазоне 1..3, возвращает нулевой `Ticket` и ошибку, для которой `errors.Is(err, ErrInvalid)`, ничего не сохраняет и **не вызывает** ни `now`, ни `newID`;
- иначе ровно один раз вызывает `newID()` и ровно один раз `now()`, сохраняет и возвращает `Ticket{ID: newID(), Title: <без пробелов>, Priority: priority, Created: now()}`. Уникальность ID — забота генератора (тесты передают генераторы с уникальными ID);
- `Queue` возвращает новый срез со всеми тикетами (изменение среза не влияет на `Desk`; для пустого `Desk` — срез длины 0) в порядке: по `Priority` по убыванию (3 первым), при равном — по `Created` по возрастанию (раньше созданный первым), при равном — по `ID` по возрастанию как строки (`"T-10" < "T-2"`);
- `Expire` один раз вызывает `now()` (даже для пустого `Desk`) и удаляет тикеты, у которых `now().Sub(Created) >= maxAge` (ровно `maxAge` — уже удаляется), и возвращает число удалённых;
- все методы `Desk` безопасны для одновременного вызова из многих горутин (тесты идут с `-race` и `t.Parallel`).

`FakeClock`:

- `NewFakeClock(start)` — часы, которые показывают `start`; `Now` возвращает текущее показание, `Advance(d)` прибавляет к нему `d`. Время само не идёт;
- безопасен для одновременного использования; метод-значение `clock.Now` подходит как аргумент `now` для `NewDesk`.

`SeqIDs(prefix)` возвращает генератор, который при вызовах выдаёт `prefix + "-1"`, `prefix + "-2"`, `prefix + "-3"`, …. У каждого генератора свой счётчик (два генератора с одним префиксом оба начинают с `-1`). Генератор безопасен для одновременного вызова: при конкурентных вызовах ID не повторяются и вместе образуют `-1`…`-N` без пропусков.
