Табличный тест проверяет входы, которые придумал человек, — и пропускает те, что ему в голову не пришли. Фаззер (Go 1.18+) генерирует входы сам: берёт seed-корпус, мутирует его (меняет, вставляет, удаляет байты, склеивает входы) и с помощью инструментирования покрытия оставляет мутации, открывшие новые ветки кода. Всё встроено в `go test`, внешних инструментов не нужно.

Fuzz-тест — функция `func FuzzXxx(f *testing.F)`. `f.Add(...)` добавляет входы в seed-корпус, `f.Fuzz(func(t *testing.T, ...))` задаёт цель: после `t` идут аргументы, которые подбирает фаззер. Допустимые типы — `string`, `[]byte`, `bool`, все целые (`int`, `int8`…`int64`, `uint`…`uint64`, а значит и `byte`, `rune`) и `float32`/`float64`. Структуры, срезы чисел, map — нет: собирайте их из `[]byte` или нескольких аргументов.

Раз ответ для случайного входа заранее неизвестен, fuzz-тест проверяет **свойства** — то, что верно для любого входа:

- обратимость (round-trip): `Decode(Encode(x)) == x`, `Unmarshal(Marshal(v)) == v`;
- инварианты: результат — валидный UTF-8, длина не больше входа, сортировка упорядочена и сохраняет элементы, функция не паникует;
- сравнение с эталоном: быстрая реализация совпадает с медленной, но очевидно верной.

Режимов два. Обычный `go test` (без флага) прогоняет fuzz-тест как табличный: seed-корпус из `f.Add` и файлы из `testdata/fuzz/FuzzXxx/`. Это быстро и детерминированно — в CI fuzz-тест работает регрессионным. `go test -fuzz=FuzzRoundTrip` запускает собственно фаззинг: по воркеру на ядро, пока не найдётся ошибка или не истечёт `-fuzztime` (`-fuzztime=30s` или `-fuzztime=10000x`). Регулярное выражение в `-fuzz` должно совпасть ровно с одним fuzz-тестом. Интересные входы фаззер копит в кеше `$GOCACHE/fuzz` (очистка — `go clean -fuzzcache`), а упавший вход сначала минимизирует и сохраняет в `testdata/fuzz/FuzzRoundTrip/<хеш>`:

```
go test fuzz v1
string("00")
```

Первая строка — версия формата, дальше по строке на аргумент в синтаксисе Go-литералов (`[]byte("…")`, `int64(-1)`, `rune('ж')`). Файл добавляют в репозиторий: с этого момента обычный `go test` проверяет этот вход всегда. Запустить его отдельно — `go test -run=FuzzRoundTrip/<хеш>`.

Пример ниже содержит ошибку: `go test -v` проходит, потому что в таблице и seed-корпусе нет цифр. Нажмите «Fuzzing» — фаззер за доли секунды найдёт строку из цифр, на которой `Decode` не может прочитать результат `Encode`. Потом исправьте код: ограничьте серию девятью байтами (`aaaaaaaaaaaa` → `9a3a`), а в `Decode` читайте ровно одну цифру `1`–`9` и следующий за ней байт — каким бы он ни был. Запустите фаззинг ещё раз: теперь он отработает все 4 секунды без ошибок.

## Как это в C#

- Встроенного фаззинга в .NET нет. Есть SharpFuzz — обвязка над AFL/libFuzzer: отдельная сборка с инструментированием, отдельный запуск. В Go это `go test -fuzz`, а цель живёт рядом с тестами.
- Свойства в .NET проверяют property-based-библиотеками (FsCheck, CsCheck): `Prop.ForAll<string>(s => Decode(Encode(s)) == s)`. Они генерируют входы по типу, но не видят покрытие кода; фаззер Go генерирует вслепую, но направляется покрытием.
- Найденный FsCheck контрпример печатается с seed для повторения; фаззер Go сохраняет вход файлом в `testdata/fuzz`, и он становится обычным тестовым случаем.
- `[InlineData]`/`[MemberData]` у `[Theory]` ≈ seed-корпус `f.Add`: без `-fuzz` fuzz-тест — это и есть параметризованный тест.

## Ловушки

### Типы в `f.Add` не совпадают с аргументами цели

```go
f.Add("x", 5) // 5 — это int
f.Fuzz(func(t *testing.T, s string, n int64) { ... })
// mismatched type in call to (*testing.F).Add: int, fuzz target expects int64
```

Типы должны совпадать точно, без преобразований: пишите `f.Add("x", int64(5))`. Ошибку ловит `go vet`, который `go test` запускает перед тестами; с `-vet=off` тест упадёт при запуске с `mismatched types in corpus entry`.

### Недетерминированная или медленная цель

```go
f.Fuzz(func(t *testing.T, s string) {
	cache[s] = Parse(s)                // состояние между вызовами
	if time.Now().Second()%2 == 0 { … } // поведение зависит от времени
})
```

Фаззер повторяет упавший вход, минимизирует его и сохраняет в корпус — всё это бессмысленно, если результат зависит от времени, случайности или того, что осталось от прошлых вызовов. Цель должна быть чистой функцией входа и быстрой: миллионы вызовов по миллисекунде — это часы. Тяжёлую подготовку делайте один раз до `f.Fuzz`, а слишком большие входы отбрасывайте через `t.Skip()`.

### Найденный вход не попал в репозиторий

После `go test -fuzz` упавший вход лежит в `testdata/fuzz/FuzzXxx/`, а всё «интересное» — только в локальном `$GOCACHE/fuzz`. Если не закоммитить файл из `testdata`, после исправления ошибки регрессионной проверки не останется, и CI её не увидит. И наоборот: пока ошибка не исправлена, обычный `go test` с этим файлом будет падать — так и задумано.

## Задание

В `task.go` лежит кодек для полей, разделённых запятыми, написанный «в лоб» через `strings.ReplaceAll` и `strings.Split`. На простых строках он работает, но нарушает свойства ниже. Исправьте его (сигнатуры не меняйте):

```go
var ErrSyntax = errors.New("field: неверная escape-последовательность")

func Escape(s string) string
func Unescape(s string) (string, error)
func Join(fields []string) string
func Split(line string) ([]string, error)
```

Требования:

- `Escape` заменяет `\` на `\\`, `,` на `\,` и перевод строки на `\n` (два символа: обратная косая черта и `n`); все остальные байты, включая невалидный UTF-8, копируются как есть;
- `Unescape` выполняет обратную замену, читая строку слева направо: после `\` допустимы только `\`, `,` и `n`. Любой другой байт после `\` (в том числе настоящий перевод строки) или `\` в самом конце строки — ошибка: функция возвращает `""` и `ErrSyntax`. Байты вне последовательностей, включая неэкранированные запятые и переводы строк, копируются как есть;
- для любой строки `s`: `Unescape(Escape(s))` возвращает `s` без ошибки;
- `Join` экранирует каждое поле и склеивает их через `,`; для пустого или `nil` среза — `""`;
- `Split` делит строку по запятым, которые не экранированы (запятая в `\,` — часть поля, а в `\\,` — разделитель после поля, оканчивающегося на `\`), и раскодирует каждое поле `Unescape`. Пустая строка — одно пустое поле `[""]`, строка `","` — два пустых поля. Если хоть одно поле раскодировать нельзя, `Split` возвращает `nil` и `ErrSyntax`;
- для любого непустого среза `fields`: `Split(Join(fields))` возвращает `fields` без ошибки.

Скрытые тесты — это fuzz-тесты с seed-корпусом из каверзных входов, таблицы и проверка свойств на тысячах псевдослучайных строк.
