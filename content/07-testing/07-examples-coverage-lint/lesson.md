Example-функция — третий вид функций в `_test.go` после тестов и бенчмарков: `func ExampleXxx()` без параметров. Она живёт двумя жизнями. `go doc` и pkg.go.dev показывают её как пример использования рядом с описанием функции (на pkg.go.dev — с кнопкой Run). А `go test` запускает её, перехватывает stdout и сравнивает с комментарием `// Output:` в конце тела. Пример, который разошёлся с кодом, падает как тест — документация не устаревает молча.

Имя привязывает пример к идентификатору: `Example` — ко всему пакету, `ExampleSplit` — к функции `Split`, `ExampleAmount` — к типу, `ExampleAmount_String` — к методу. Несколько примеров к одному имени различают суффиксом со строчной буквы: `ExampleAmount_String_negative`. Опечатка в имени — ошибка `go vet`, а значит и `go test`: `ExampleAmount_Format refers to unknown field or method`.

Сравнение вывода:

- `// Output:` — точное совпадение после обрезки пробелов в начале и конце всего вывода;
- `// Unordered output:` — те же строки в любом порядке (вывод map, горутин);
- нет комментария — пример компилируется, но не запускается: так показывают код, которому нужны сеть, файлы или `os.Exit`.

**Покрытие** считает, какие операторы выполнились во время тестов. `go test -cover` печатает процент, `-coverprofile=c.out` сохраняет профиль, `go tool cover -func=c.out` выводит процент по функциям, а `go tool cover -html=c.out` открывает исходники с подсветкой: зелёное выполнялось, красное — нет. Режим задаёт `-covermode`: `set` (выполнялся ли оператор, по умолчанию), `count` (сколько раз) и `atomic` (`count`, безопасный для параллельных тестов; включается сам с `-race`). По умолчанию учитывается только тестируемый пакет; `-coverpkg=./...` засчитывает и вызовы в другие пакеты модуля. Нажмите в песочнице «Покрытие»: отчёт покажет, что ветка `n <= 0` в `Split` не выполнялась ни разу.

Покрытие отвечает на вопрос «какой код **не проверен** точно», но не «какой код проверен». Строка, выполненная в тесте без единой проверки результата, считается покрытой. 100% не гарантирует отсутствия ошибок, а погоня за процентом рождает тесты, которые ничего не проверяют. Полезнее смотреть на красные участки в HTML-отчёте и решать, нужен ли там тест.

**`go vet`** — статический анализатор из поставки Go: неверные форматы `Printf`, копирование `sync.Mutex`, недостижимый код, ошибки в тегах структур, неверные имена тестов и примеров, неиспользованный `cancel` у контекста и другое. Часть его проверок `go test` запускает сам перед тестами. Всё остальное — **golangci-lint**: один бинарник, который запускает десятки линтеров параллельно. В песочнице его нет; в проекте он настраивается файлом `.golangci.yml`:

```yaml
version: "2"
linters:
  enable:
    - errcheck     # необработанные ошибки: f.Close() без проверки
    - govet        # go vet
    - staticcheck  # большой набор проверок: ошибки, упрощения, устаревшие API
    - revive       # стиль: имена, doc-комментарии экспортируемых имён
    - gocritic     # подозрительные и неидиоматичные конструкции
    - gosec        # безопасность: SQL из строк, слабая криптография, права файлов
  settings:
    errcheck:
      exclude-functions:
        - fmt.Fprintf  # ошибки печати в отчёт осознанно не проверяем
```

Запуск — `golangci-lint run ./...`, в CI — готовый GitHub Action. Линтер стоит включить с первого дня: на старом коде он выдаст сотни замечаний, а новое замечание в маленьком диффе исправляют сразу.

## Как это в C#

- XML-документация с `<example><code>` — только текст: компилятор не проверяет, что код в примере собирается и печатает то, что написано. Example-функция в Go — компилируемый и исполняемый тест.
- coverlet (`dotnet test --collect:"XPlat Code Coverage"`) + ReportGenerator ≈ `-coverprofile` + `go tool cover -html`. В Go всё встроено: ни пакета, ни отдельного генератора отчётов.
- Roslyn-анализаторы (`Microsoft.CodeAnalysis.NetAnalyzers`, StyleCop) с настройкой в `.editorconfig` ≈ `go vet` + golangci-lint с `.golangci.yml`. Разница: анализаторы работают при каждой сборке (NetAnalyzers входят в SDK, StyleCop подключают NuGet-пакетом), а golangci-lint — отдельный инструмент, который обычно запускают в CI и в редакторе (gopls показывает часть проверок сам).
- Предупреждений в Go нет, `TreatWarningsAsErrors` не нужен: неиспользуемая переменная или импорт — ошибка компиляции, а находки `go vet` при `go test` останавливают тесты.

## Ловушки

### Пример без `// Output:` ничего не проверяет

```go
func ExampleAmount_String() {
	fmt.Println(money.Amount(1234))
	// Вывод: 12.34   ← не тот комментарий: пример только компилируется
}
```

Последний комментарий тела должен начинаться с `Output:` или `Unordered output:`. Опечатка или русское «Вывод:» превращают тест в документацию, которая только компилируется, и `go test -v` даже не покажет `=== RUN` для этого примера. Проверить просто: пример, который не запускается, отсутствует в выводе `go test -v`.

### Вывод с картой и `// Output:`

```go
for k, v := range totals {
	fmt.Println(k, v)
}
// Output:
// еда 470.50
// транспорт 62.00
```

Порядок обхода map случаен — пример будет то проходить, то падать. Либо `// Unordered output:`, либо сортировка ключей перед выводом (`slices.Sorted(maps.Keys(totals))`), что заодно лучше для читателя документации.

### 100% покрытия без проверок

```go
func TestSplit(t *testing.T) {
	money.Amount(1000).Split(3) // выполнено — значит «покрыто»
	money.Amount(1000).Split(0)
}
```

Тест поднимает покрытие `Split` до 100% и не находит ни одной ошибки — он ничего не сравнивает. Покрытие показывает, куда тесты не заглядывали, а качество проверок оценивают по ассертам, а не по процентам.

## Задание

Напишите печать чека в `io.Writer`. Скрытые тесты — в основном Example-функции с `// Output:`, поэтому формат важен до пробела.

```go
type Item struct {
	Name  string
	Qty   int
	Price int64 // цена за штуку в копейках
}

var ErrInvalidItem = errors.New("receipt: неверная позиция")

func FormatMoney(kop int64) string
func WriteReceipt(w io.Writer, items []Item) error
```

Требования:

- `FormatMoney` печатает сумму в копейках как рубли и ровно две цифры копеек: `0` → `0.00`, `5` → `0.05`, `1234` → `12.34`, `-150` → `-1.50`, `-5` → `-0.05`; работает для любого `int64`, включая `math.MinInt64`;
- `WriteReceipt` печатает по строке на позицию в исходном порядке и последней — строку итога. Каждая строка — `<название> + два пробела + <сумма>` и перевод строки `\n`;
- название позиции — `Name`, а если `Qty > 1` — `Name`, пробел, `×` и количество: `Milk ×2`. Название итоговой строки — `Итого`. Сумма позиции — `Qty * Price`, итог — сумма всех позиций, обе через `FormatMoney`;
- названия дополняются пробелами справа до длины самого длинного названия (включая `Итого`), суммы — пробелами слева до длины самой длинной суммы (включая итог). Длина считается в символах (рунах), а не в байтах. Пробелов в конце строк нет;
- без позиций (`nil` или пустой срез) печатается одна строка `Итого  0.00`;
- если у какой-либо позиции пустое `Name`, `Qty < 1` или `Price < 0`, функция возвращает ошибку, для которой `errors.Is(err, ErrInvalidItem)`, и ничего не пишет в `w`;
- при ошибке записи в `w` функция сразу возвращает эту ошибку (можно обёрнутую) и больше не пишет. Переполнение `int64` при умножении и сложении не проверяется.

Пример:

```
Молоко ×2   179.80
Хлеб         45.00
Сыр        1250.00
Итого      1474.80
```
