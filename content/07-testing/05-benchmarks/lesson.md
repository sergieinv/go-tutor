Бенчмарк в Go — такая же функция в `_test.go`, как тест, только с сигнатурой `func BenchmarkXxx(b *testing.B)`. Фреймворк не нужен: `go test -bench=.` находит бенчмарки, подбирает число итераций, чтобы замер длился около секунды (`-benchtime`), и печатает время на операцию. Без `-bench` бенчмарки не запускаются — обычный `go test` их только компилирует.

С Go 1.24 тело бенчмарка пишут циклом `for b.Loop() { ... }`. Раньше писали `for i := 0; i < b.N; i++`, и в старом коде вы встретите именно его. У `b.Loop` три преимущества: таймер включается при первом вызове и выключается при последнем, поэтому подготовка до цикла не попадает в замер без `b.ResetTimer()`; функция бенчмарка вызывается **один раз**, а не по разу на каждую пробу `b.N` (1, 100, 10 000…), так что дорогая подготовка выполняется однажды; результаты и аргументы вызовов внутри цикла компилятор считает используемыми и не выкидывает «бесполезный» код.

Строка результата читается так:

```
BenchmarkJoin/builder/n=100-12   419793   572.3 ns/op   704 B/op   1 allocs/op
```

Имя бенчмарка и под-бенчмарка, `-12` — значение `GOMAXPROCS`, затем число итераций, время на итерацию, байты и число аллокаций в куче на итерацию. Последние две колонки появляются с флагом `-benchmem` или после `b.ReportAllocs()` в коде. В песочнице кнопка «Бенчмарки» запускает `go test -bench=. -benchmem -benchtime=200ms` — нажмите её и сравните, как растут `naive` и `builder` с размером входа.

Одному замеру верить нельзя: шум от планировщика, турбобуста и фоновых процессов легко даёт ±10%. Сравнивают так: `go test -bench=Join -count=10 > old.txt`, правка, то же в `new.txt`, затем `benchstat old.txt new.txt` (ставится `go install golang.org/x/perf/cmd/benchstat@latest`; в песочнице его нет). benchstat печатает медианы, разброс и p-value — изменение со значком `~` статистически незначимо. Если нужно понять, **где** тратится время, добавьте `-cpuprofile=cpu.out` или `-memprofile=mem.out` и откройте профиль `go tool pprof`; профилированию посвящён модуль 13.

Число аллокаций удобно закрепить обычным тестом: `testing.AllocsPerRun(runs, f)` возвращает среднее число аллокаций за вызов `f`. Такой тест падает сразу, как только кто-то случайно добавит аллокацию в горячий путь, и не зависит от скорости машины.

## Как это в C#

- BenchmarkDotNet — отдельный NuGet-пакет и отдельное консольное приложение в Release; `[Benchmark]` ≈ `BenchmarkXxx`, `[Params(10, 100, 1000)]` ≈ цикл по размерам с `b.Run`. В Go всё встроено в `go test` и лежит рядом с тестами.
- `[MemoryDiagnoser]` ≈ `-benchmem`/`b.ReportAllocs()`: колонка `Allocated` — это `B/op`. Числа аллокаций BenchmarkDotNet не показывает, Go показывает `allocs/op`.
- `[GlobalSetup]` ≈ код до `for b.Loop()`. Защиту от выкидывания кода в BenchmarkDotNet даёт возврат значения из метода (`Consumer`), в Go — сам `b.Loop`.
- Аналога `testing.AllocsPerRun` в тестах .NET нет; ближе всего `GC.GetAllocatedBytesForCurrentThread()` до и после вызова.

## Ловушки

### Старый цикл по `b.N` и подготовка внутри замера

```go
func BenchmarkSort(b *testing.B) {
	data := makeData(1_000_000) // попадёт в замер, если не сбросить таймер
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		sorted := slices.Clone(data) // копия — тоже часть замера
		slices.Sort(sorted)
	}
}
```

С `b.N` вся функция вызывается несколько раз, и `makeData` выполнится столько же. Таймер надо сбрасывать вручную, а то, что нужно делать на каждой итерации, но не хочется мерить, — оборачивать в `b.StopTimer()`/`b.StartTimer()` (что само по себе дорого). С `for b.Loop()` подготовка выполняется один раз и не попадает в замер. Смешивать `b.Loop` и `b.N` в одном бенчмарке нельзя.

### Компилятор выкинул измеряемый код

```go
for i := 0; i < b.N; i++ {
	isPrime(97) // результат не используется — вызов могут встроить и удалить
}
```

В цикле по `b.N` результат приходилось сохранять в глобальную переменную-«сток» (`sink = isPrime(97)`), иначе бенчмарк мерил пустой цикл и показывал подозрительные `0.3 ns/op`. `for b.Loop()` держит аргументы и результаты вызовов живыми сам. Правило на будущее: если результат неправдоподобно хорош — сначала проверьте, что код вообще выполняется.

### Сравнение по одному запуску

```
naive/n=100    10093 ns/op
naive/n=100     9120 ns/op   // ничего не меняли
```

Разница в 10% между двумя запусками без изменений — норма. Решение «стало быстрее» принимают по `-count=10` и `benchstat`, на одной и той же машине без нагрузки. Для регрессий по памяти надёжнее `allocs/op` и тест с `AllocsPerRun`: число аллокаций от шума не зависит.

## Задание

Напишите две функции, которые превращают срез чисел в текст, не тратя лишней памяти:

```go
func AppendInts(dst []byte, nums []int, sep string) []byte
func JoinInts(nums []int, sep string) string
```

Требования:

- обе функции записывают числа `nums` в десятичном виде (как `strconv.Itoa`, отрицательные — со знаком `-`) в исходном порядке, разделяя соседние числа строкой `sep`; перед первым и после последнего числа разделителя нет; `sep` может быть пустым или многобайтовым;
- `AppendInts` дописывает текст в конец `dst` и возвращает расширенный срез, как `strconv.AppendInt`: содержимое `dst` сохраняется в начале результата, `dst == nil` допустим; если ёмкости `dst` хватает, функция пишет в тот же массив и **не делает ни одной аллокации**;
- `JoinInts` возвращает ту же строку и делает **не больше одной аллокации** на вызов при любом размере входа (тесты проверяют это через `testing.AllocsPerRun` на 100 и 1000 чисел, включая `math.MinInt` и `math.MaxInt`);
- для пустого или `nil` среза `JoinInts` возвращает `""` без аллокаций, `AppendInts` возвращает `dst` без изменений.
