В модуле 2 срез, строка и map были «встроенными типами». Здесь посмотрим, во что они превращаются в рантайме, потому что от этого зависит, сколько стоит код. Срез — структура `slice{array, len, cap}` из `runtime/slice.go`, три машинных слова. Строка — `stringStruct{str, len}` из `runtime/string.go`, два слова, а байты лежат отдельно и никогда не меняются. Map — один указатель на структуру `Map` из `internal/runtime/maps`: поэтому map передаётся «по ссылке», а срез и строка копируются заголовком.

Отсюда три вопроса, которые стоит задавать себе при чтении горячего кода. Сколько раз вырастет срез и сколько памяти при этом станет мусором? Где конвертация `string`↔`[]byte` копирует байты? И что станет с памятью map, когда из неё удалят элементы?

**Рост `append`.** Когда места нет, компилятор вызывает `runtime.growslice`. Новую ёмкость сначала считает `nextslicecap(newLen, oldCap)`: если нужно больше, чем вдвое, берётся ровно нужная длина; если старая ёмкость меньше 256 — удвоение; дальше в цикле `newcap += (newcap + 3*256) >> 2`, то есть плавный переход от ×2 к ×1,25. Затем байты округляются вверх функцией `roundupsize` до **класса размера** аллокатора (таблица в `internal/runtime/gc/sizeclasses.go`: 8, 16, 24, 32, 48, 64, 80… 32768 байт), и ёмкость пересчитывается из округлённого размера. Поэтому `append` пяти `int` к пустому срезу даёт `cap` 6 (40 байт → класс 48), а срез из 512 `int` вырастает до 848, а не до 832. Ещё одна деталь: объекту больше 512 байт с указателями внутри аллокатор добавляет 8-байтовый заголовок с типом, и он тоже съедает место из класса размера — `[]string` после 32 элементов получает `cap` 71.

**Строки неизменяемы**, поэтому `string(b)` и `[]byte(s)` в общем случае копируют байты: иначе запись в срез поменяла бы строку. Компилятор убирает копию там, где она гарантированно не нужна: ключ поиска в map `m[string(b)]`, сравнение `string(b) == "x"`, конкатенация `"<" + string(b) + ">"` (копируется только результат), обход `for i, c := range []byte(s)`, а также `[]byte(s)`, который никто не изменяет (`-gcflags=-m` пишет `zero-copy string->[]byte conversion`). Строку из одного байта рантайм берёт из статической таблицы, а результат до 32 байт, который не убегает, кладёт в буфер на стеке. `strings.Builder` копит байты в `[]byte` и в `String()` отдаёт их как строку **без копии** — через `unsafe.String(unsafe.SliceData(b.buf), len(b.buf))`. Это законно только потому, что Builder больше никогда не меняет уже записанные байты.

**Map — Swiss table** (с Go 1.24). Слоты хранятся в группах по 8, у каждой группы 8-байтовое контрольное слово — по байту на слот. Хеш делится на `h1` (старшие 57 бит, выбирают стартовую группу) и `h2` (младшие 7 бит, лежат в контрольном байте занятого слота; `0x80` — пусто, `0xFE` — надгробие). Поиск сравнивает `h2` сразу с восемью байтами одной операцией над словом и сравнивает ключи только в совпавших слотах; группа с пустым слотом обрывает поиск, иначе — следующая группа по квадратичной последовательности. Map до 8 элементов — одна группа без таблицы. Дальше таблица растёт вдвое при заполнении на 7/8, а таблица на 1024 слота при росте **делится на две**: нужную таблицу выбирает каталог по старшим битам хеша (extendible hashing). Поэтому один рост никогда не перестраивает всю большую map — только одну таблицу.

## Как это в C#

- **`List<T>` растёт ровно вдвое** (`Capacity` 4 → 8 → 16…), и ёмкость предсказуема. В Go удвоение только до 256 элементов, потом ×1,25, и всё округляется до классов размера аллокатора: на конкретный `cap` полагаться нельзя. Общее правило одно: известен размер — задайте его (`new List<T>(n)` / `make([]T, 0, n)`).
- **`string` в .NET — объект в куче** с длиной и UTF-16 символами внутри, переменная — ссылка на него. В Go строка — значение из двух слов, указывающее на UTF-8 байты; подстрока `s[i:j]` не копирует байты (в .NET `Substring` копирует, без копии — только `ReadOnlySpan<char>`/`AsSpan`).
- **`Encoding.UTF8.GetBytes(s)` и `new string(chars)` всегда копируют.** Компилятор Go в ряде случаев убирает копию сам (`m[string(b)]`, сравнение). Ручной обход копии — `unsafe.String`/`unsafe.StringData` — аналог `MemoryMarshal`/`Unsafe.As` в C#: ответственность за неизменность байтов на вас.
- **`Dictionary<TKey,TValue>`** — массив bucket-индексов плюс массив записей с цепочками через `next`; `Remove` освобождает запись в free-list, `Clear` обнуляет массивы, но не уменьшает их (`TrimExcess` уменьшает). В Go `clear` и `delete` тоже не возвращают память, а `TrimExcess` нет: уменьшить map можно только создав новую и переложив в неё элементы.

## Под капотом

Визуализатор проходит по серии `append` и показывает обе стадии расчёта ёмкости: формулу `nextslicecap` и округление байтов до класса размера. Видно, откуда берутся «странные» ёмкости 6, 848 и 71 и почему следующий `append` после округления может обойтись без нового массива.

Ёмкость зависит ещё и от компилятора. Если срез не убегает из функции, Go 1.25+ может выделить первые 32 байта массива на стеке: тогда после первого `append` к `[]int` будет `cap` 4, а не 1. А с Go 1.26, если срез убегает только в самом конце (например, возвращается из функции после цикла), компилятор растит его в стековом буфере по классам размера (1, 2, 3, 4) и переносит в кучу одним копированием. Поэтому пример и визуализатор уводят срез в глобальную переменную — чтобы показать чистый `growslice`.

## Ловушки

### Подстрока держит всю строку

```go
func firstLine(page string) string {
	i := strings.IndexByte(page, '\n')
	return page[:i] // указатель внутрь page: пока жива строка-результат, жива вся страница
}
return strings.Clone(page[:i]) // копия только нужных байтов
```

То же со срезами: `data[:64]` держит весь массив. Для строк — `strings.Clone`, для срезов — `slices.Clone` или `bytes.Clone`.

### `unsafe.String` над изменяемым буфером

```go
buf := []byte("hello")
s := unsafe.String(unsafe.SliceData(buf), len(buf)) // УЯЗВИМО: строка разделяет память с buf
m := map[string]int{s: 1}
buf[0] = 'j' // «неизменяемая» строка стала "jello", ключ map испорчен
fmt.Println(s, m["hello"], len(m)) // jello 0 1 — элемент есть, но его не найти
```

`unsafe.String` оправдан, только если байты гарантированно больше не меняются, пока жива строка (так делает `strings.Builder`). Во всех остальных случаях — обычный `string(buf)`: компилятор сам уберёт копию там, где может.

### `clear` и `delete` не возвращают память map

```go
cache := make(map[string][]byte)
// ...заполнили миллионом элементов, потом удалили почти все
clear(cache) // len 0, но таблицы того же размера остаются в куче
cache = make(map[string][]byte) // старую map соберёт GC
```

Map, которая однажды выросла, остаётся большой: удаление ставит в слот «пусто» или надгробие, но таблицы не уменьшаются. Долгоживущий кеш с пиками размера периодически пересоздают. Подробнее про память и кеши — в модуле 14.

## Задание

Напишите маленькую Swiss table: хеш-таблицу `string → int` с открытой адресацией, группами по 8 слотов и контрольными байтами. Таблица не растёт.

- `New(numGroups int, hash func(string) uint64) *Table` — таблица из `numGroups` групп. `numGroups` — степень двойки не меньше 1, иначе `panic`. Все контрольные байты новой таблицы — `Empty` (`0x80`).
- Хеш ключа делится так: `h1 = hash >> 7`, `h2 = hash & 0x7f`. Стартовая группа — `h1 & (numGroups-1)`. Последовательность групп (квадратичное пробирование): `g0` — стартовая, `g(i) = (g(i-1) + i) & (numGroups-1)`; ровно `numGroups` шагов обходят все группы по одному разу.
- Контрольный байт слота: `Empty` (`0x80`) — пусто, `Deleted` (`0xFE`) — надгробие, иначе слот занят и байт равен `h2` ключа.
- `Get(key) (int, bool)`: идёт по группам последовательности; в группе проверяет слоты 0…7 и сравнивает ключ только там, где контрольный байт равен `h2`. Если в группе есть хотя бы один `Empty`, а ключ не найден — ключа нет. Просмотрев все `numGroups` групп — ключа нет.
- `Put(key, val) error`: если ключ есть — обновляет значение. Иначе вставляет в первое надгробие, встреченное по пути (по порядку групп последовательности и слотов 0…7 внутри группы, включая все слоты группы, где поиск закончился), а если надгробий не было — в первый `Empty` слот этой группы. Если обойдены все `numGroups` групп и `Empty` не встретился, вставка идёт в первое надгробие, а если и его нет — возвращает `ErrFull` и ничего не меняет.
- `Delete(key) bool`: `false`, если ключа нет. Иначе удаляет: если среди остальных слотов группы ключа есть хотя бы один `Empty`, контрольный байт становится `Empty`, иначе — `Deleted`.
- `Len() int` — число ключей; `Ctrl(group int) [8]byte` — контрольные байты группы (для проверки устройства таблицы).
