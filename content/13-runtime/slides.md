# Механизмы рантайма

Обзор модуля для показа команде: что происходит под капотом Go-программы и сколько это стоит.

---

## Планировщик GMP

- G — горутина, M — поток ОС, P — право выполнять Go-код. У каждого P слот `runnext` и локальная очередь на 256 горутин.
- Пустой P крадёт половину чужой очереди; глобальную очередь проверяют раз в 61 запуск.
- Блокирующий syscall отдаёт P другому потоку, ожидание сети уходит в netpoller без потока.
- Бесконечный цикл не вешает программу: sysmon вытесняет горутину сигналом.

## Стек горутины растёт копированием

- Поток ОС получает стек фиксированного размера, горутина начинает с 2 КБ и растёт до 1 ГБ.
- Пролог функции проверяет границу; не хватает — `morestack` выделяет стек вдвое больше и копирует, исправляя указатели.
- Рекурсия глубиной в миллион вызовов работает. Переполнение — `fatal error`, его не перехватить `recover`.

## Стек или куча решает компилятор

```go
func sum(p *point) int { return p.x + p.y } // p does not escape

func newPoint() *point { return &point{1, 2} } // &point{...} escapes to heap
```

| C# | Go |
| --- | --- |
| `class` — куча, `struct` — на месте | место выбирает escape analysis |
| `stackalloc`, `Span<T>` | `var buf [64]byte` и `buf[:]` |
| boxing в `object` | упаковка в интерфейс, `...any` |

Решение видно при сборке: `go build -gcflags=-m`.

## Сборщик мусора

- Конкурентный mark-and-sweep без поколений и без уплотнения: объект не двигается, закреплять нечего.
- Трёхцветная маркировка и гибридный барьер записи, включённый только на время маркировки.
- Мир останавливается дважды за цикл на десятки микросекунд.

## Настройка: две ручки

- `GOGC` — сколько лишней памяти потратить ради реже идущих сборок.
- `GOMEMLIMIT` — мягкий лимит. Если живых данных больше лимита — «спираль смерти»; ограничитель держит долю CPU на GC не выше 50%.
- `GOGC=off` + `GOMEMLIMIT` — для пакетной обработки с известным бюджетом памяти.
- Остальное подбирает pacer; `runtime.GC()` «для порядка» не вызывают.

## Срезы, map, интерфейсы

- Срез — три слова, строка — два, map — указатель. `append` удваивает до 256, дальше плавно к ×1,25 и округляет до класса размера.
- Подстрока держит всю строку; `clear` и `delete` не возвращают память map.
- Интерфейс — пара указателей (`eface`, `iface` с itab). Вызов через интерфейс мешает inlining и escape analysis.

## Memory model, Pool, unsafe

- Чтение гарантированно видит запись, только если между ними есть happens-before: канал, мьютекс, `Once`, `WaitGroup`, атомик.
- Двойная проверка на обычной переменной и ожидание флага в цикле — гонки.
- `sync.Pool` ничего не обещает: `Reset` обязателен, кладут `*[]byte`, а не `[]byte`.
- `uintptr` не держит объект; `unsafe` — только по допустимым шаблонам и под `go vet`.

---

## Измерять, а не верить

- pprof: CPU, heap, allocs, goroutine, mutex, block; `net/http/pprof` — только на внутреннем адресе.
- `runtime/trace` и `go tool trace` показывают работу планировщика.
- Нет JIT: inlining (бюджет 80), BCE и PGO по `default.pgo` решаются при сборке.

---

## Что запомнить

- Горутина дешёвая: 2 КБ стека, а планировщик сам раздаёт их по потокам.
- `new` и `&` не значат «куча» — смотрите `-gcflags=-m`.
- В контейнере ставьте `GOMEMLIMIT` ниже лимита памяти.
- Оптимизацию подтверждает профиль или бенчмарк.
