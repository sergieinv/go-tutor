У сборщика мусора Go почти нет настроек — и это сознательно. Ручек две: `GOGC` говорит, сколько лишней памяти можно потратить ради реже идущих сборок, `GOMEMLIMIT` — сколько памяти нельзя превышать. Обе задаются переменными окружения при старте или из кода — `debug.SetGCPercent` и `debug.SetMemoryLimit` (новое значение действует сразу, функции возвращают прежнее). Всё остальное — когда начать цикл, сколько CPU отдать воркерам, кого заставить помогать — подбирает **pacer** (`runtime/mgcpacer.go`).

**GOGC и цель кучи.** После каждого цикла pacer считает цель — размер кучи, к которому должен закончиться следующий цикл (`gcControllerState.commit`):

```
цель = живая куча + (живая куча + стеки + глобальные) × GOGC / 100
```

«Живая куча» — то, что нашла последняя маркировка; стеки и глобальные с Go 1.18 тоже входят в базу, потому что их тоже надо сканировать. При `GOGC=100` (по умолчанию) куча может вырасти примерно вдвое от живой, при `GOGC=50` — в полтора раза, при `GOGC=200` — втрое. Снизу цель ограничена минимумом `4 МиБ × GOGC / 100` — поэтому маленькая программа первый раз собирает мусор на 4 МиБ (видно в `gctrace`: `4 MB goal`). Начинает цикл pacer заранее, когда куча прошла от 70 до 95% пути от живой к цели (`minTriggerRatioNum`/`maxTriggerRatioNum`), чтобы маркировка, идущая параллельно с выделениями, закончилась как раз у цели. `GOGC=off` (или отрицательное значение) выключает сборки по проценту совсем.

Смысл ручки — обмен памяти на CPU. Работа одного цикла пропорциональна живой куче, а число циклов — скорости выделений, делённой на «запас» `цель − живая`. Удвоили GOGC — циклов вдвое меньше, пиковая память выше. Задержки (паузы STW) от GOGC почти не зависят; зависят доля CPU на GC и mark assist на горячих путях.

**GOMEMLIMIT — мягкий лимит** (Go 1.19). Он считает не кучу, а всю память, которую рантайм получил у ОС и не вернул: `/memory/classes/total:bytes − /memory/classes/heap/released:bytes` — кучу, стеки горутин, метаданные, буферы. Не входят сам исполняемый файл, память C-кода (cgo) и `syscall.Mmap`. Формат — байты с суффиксами `B`, `KiB`, `MiB`, `GiB`, `TiB` (степени двойки): `GOMEMLIMIT=900MiB`. По умолчанию лимита нет (`math.MaxInt64`). Pacer вычисляет вторую цель (`memoryLimitHeapGoal`):

```
цель по лимиту = лимит − память вне кучи − превышение лимита
               − запас 3% (не меньше 1 МиБ)
```

и берёт меньшую из двух целей; цель никогда не опускается ниже живой кучи. У лимита есть и второй рычаг: фоновый scavenger энергичнее возвращает ОС свободные страницы.

**Почему «мягкий».** Если живых данных больше лимита, цель упирается в живую кучу, и сборщик запускается почти без перерыва — это «спираль смерти»: вся CPU уходит на GC, а память не освобождается. Чтобы программа продолжала работать, у сборщика есть **ограничитель CPU** (`mgclimit.go`): «дырявое ведро», которое наполняется временем GC и опустошается временем программы, держит долю GC не выше **50%**; ёмкость ведра — по процессорной секунде на каждый P, так что короткие всплески работы GC оно пропускает. Когда ограничитель срабатывает, mark assist отключается, и куча переходит лимит — лучше превысить мягкий лимит, чем встать. Последний цикл, когда он срабатывал, — метрика `/gc/limiter/last-enabled:gc-cycle`; если она растёт, лимит слишком мал для живых данных. Убить процесс за превышение может только ОС (OOM killer контейнера), рантайм — нет.

**Типовые конфигурации:**

- **По умолчанию** (`GOGC=100`, без лимита) — разумно для большинства сервисов.
- **Контейнер с лимитом памяти** — `GOMEMLIMIT` на 10–20% ниже лимита пода, то есть 80–90% от него (запас на память вне рантайма: cgo, исполняемый файл, буферы ядра) и обычный `GOGC`. Пока живых данных мало, работает GOGC; когда куча подходит к лимиту, сборки учащаются, а не случается OOM. Сам Go лимит памяти контейнера не читает (с Go 1.25 из cgroup берётся только лимит CPU для `GOMAXPROCS`) — его выставляют в манифесте или вычисляют при старте.
- **`GOGC=off` + `GOMEMLIMIT`** — для пакетной обработки с известным бюджетом памяти: сборок нет совсем, пока память не подошла к лимиту, — минимум работы GC. Опасно при росте живых данных: без запаса это прямой путь в спираль смерти.
- **Меньше памяти любой ценой** — снизить GOGC (50, 25) и смириться с ростом CPU. Обычно выгоднее сократить выделения (escape analysis, `sync.Pool`, переиспользование буферов).

**Наблюдение.** `runtime/metrics` читает значения без остановки мира: `/gc/heap/goal:bytes`, `/gc/heap/live:bytes`, `/gc/cycles/total:gc-cycles`, `/gc/gogc:percent`, `/gc/gomemlimit:bytes`, `/cpu/classes/gc/total:cpu-seconds`, `/memory/classes/...` — их и экспортируют в мониторинг. `runtime.ReadMemStats` останавливает мир (`stopTheWorld(stwReadMemStats)` в `mstats.go`) — в обработчике метрик раз в секунду это лишняя пауза. Фактические настройки при старте сервиса стоит залогировать по `/gc/gogc:percent` и `/gc/gomemlimit:bytes` — например, песочница курса запускает программы с заданным `GOMEMLIMIT`. Для разовой диагностики — `GODEBUG=gctrace=1`: по строке на цикл с целью (`MB goal`), живой кучей и долей CPU.

## Как это в C#

- **Ручки другие.** В CLR нет прямого аналога GOGC: бюджеты поколений сборщик подбирает сам. Выбирают режим — Workstation или Server GC, конкурентный (background) или нет — в `runtimeconfig.json`, а во время работы — `GCSettings.LatencyMode` (`Batch`, `Interactive`, `SustainedLowLatency`) и `GC.TryStartNoGCRegion`. Ближайшее к GOGC по смыслу — `GCConserveMemory` (0–9): сколько памяти готовы сэкономить ценой CPU.
- **Жёсткий лимит против мягкого.** `GCHeapHardLimit` (`System.GC.HeapHardLimit`, `DOTNET_GCHeapHardLimit`) — жёсткий: при нехватке после сборки будет `OutOfMemoryException`. `GOMEMLIMIT` мягкий: сборщик работает чаще, при необходимости переходит лимит, а исключения не бывает. Лимит в CLR считает кучу GC, в Go — всю память рантайма.
- **Контейнеры.** .NET сам видит лимит памяти контейнера и по умолчанию ограничивает кучу 75% от него. Go лимит памяти cgroup не читает — `GOMEMLIMIT` выставляют явно.
- **Метрики.** `GC.GetGCMemoryInfo()`, `dotnet-counters` и EventPipe ↔ `runtime/metrics` и `gctrace`.

## Ловушки

### GOMEMLIMIT меньше живых данных

```sh
GOMEMLIMIT=256MiB ./service   # а кеш в памяти — 300 МиБ
```

Цель кучи упирается в живые данные, GC запускается непрерывно и съедает до половины CPU (дальше не пускает ограничитель), задержки растут, а память всё равно выше лимита. Лимит — защита от всплесков, а не способ уменьшить рабочий набор. Следите за `/gc/limiter/last-enabled:gc-cycle` и долей `/cpu/classes/gc/total:cpu-seconds`.

### Опечатка в переменной окружения

```sh
GOGC=of ./service           # молча работает как GOGC=100
GOMEMLIMIT=1GB ./service    # fatal error: malformed GOMEMLIMIT
```

Нераспознанный `GOGC` рантайм молча заменяет на 100 (`readGOGC`), а нераспознанный `GOMEMLIMIT` роняет процесс при старте (`readGOMEMLIMIT`): суффикс `GB` не поддерживается, нужен `GiB`. Проверяйте фактические значения по `/gc/gogc:percent` и `/gc/gomemlimit:bytes` при старте сервиса.

### `ReadMemStats` в горячем пути метрик

```go
http.HandleFunc("/metrics", func(w http.ResponseWriter, r *http.Request) {
	var m runtime.MemStats
	runtime.ReadMemStats(&m) // остановка мира на каждый запрос
	fmt.Fprintln(w, m.HeapAlloc)
})
```

Каждый вызов останавливает все горутины. Используйте `runtime/metrics` (`metrics.Read` с заранее созданным срезом `[]metrics.Sample`) — он не останавливает мир. Эндпоинт метрик держите на внутреннем порту.

## Задание

Реализуйте расчёт цели кучи так, как это делает pacer, и вычисление `GOMEMLIMIT` по лимиту памяти контейнера. Константы `MiB`, `HeapMinimum` (4 МиБ), `NoLimit` (`math.MaxInt64`), `MaxContainerBytes` (1 ТиБ), тип `State` и ошибка `ErrBadInput` даны в шаблоне.

```go
func HeapGoal(s State) uint64
func MemoryLimit(memoryMax string, reservePercent int) (int64, error)
```

`HeapGoal` возвращает меньшую из двух целей; вся арифметика — в `uint64`, деление целочисленное, порядок операций — как в формулах:

- **Цель по GOGC.** Если `GOGC < 0` — `math.MaxUint64`. Иначе `HeapMarked + (HeapMarked+StackScan+GlobalsScan)*GOGC/100` (сначала умножение, потом деление), но не меньше `HeapMinimum*GOGC/100`.
- **Цель по лимиту.** Если `NonHeap >= MemoryLimit` — `HeapMarked`. Иначе `goal = MemoryLimit − NonHeap`, `headroom = goal/100*3` (сначала деление), но не меньше `MiB`. Если `goal < headroom` или `goal − headroom < headroom` — цель равна `headroom`, иначе `goal − headroom`. Итог не меньше `HeapMarked`.

`MemoryLimit` получает содержимое файла cgroup v2 `memory.max` и процент запаса:

- пробельные символы по краям строки игнорируются;
- `"max"` (ровно так, в нижнем регистре; лимита нет) — `NoLimit`, `nil`;
- иначе строка — десятичное целое `n` байт (как его понимает `strconv.ParseInt(s, 10, 64)`), `0 < n <= MaxContainerBytes`; результат — `n * (100 − reservePercent) / 100` (целочисленно, в `int64`);
- `reservePercent` должен быть в диапазоне `[0, 100)`, иначе ошибка — в том числе для `"max"`;
- при любой ошибке — `0` и ошибка, для которой `errors.Is(err, ErrBadInput)`.
