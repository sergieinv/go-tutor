В C# место значения задаёт тип: экземпляр `class` живёт в куче, `struct` — там, где его объявили. В Go такого правила нет. `new(T)`, `&T{}` и `make` только просят память, а **где** она окажется, решает компилятор. Он прослеживает каждый указатель (escape analysis): если ссылка на значение не может пережить кадр функции, значение кладётся на стек и исчезает вместе с кадром бесплатно. Если может — или компилятор не в силах это доказать, — значение «убегает» (escapes) в кучу, и за ним будет следить сборщик мусора.

Решение принимается при компиляции, один раз, и его можно посмотреть: `go build -gcflags=-m` печатает по сообщению на каждое интересное место, `-gcflags=-m=2` добавляет цепочку «почему». Этот урок собирается с `-m`, так что под выводом примера песочница показывает диагностику компилятора.

**Типичные причины побега:**

- **Возврат указателя на локальную переменную** — `return &p`: компилятор пишет `moved to heap: p`. Сам `&` ничего не решает: `p := &point{}` внутри функции, указатель на который никуда не уходит, — это `&point{...} does not escape`, стек.
- **Сохранение за пределами вызова** — в глобальную переменную, в поле объекта из кучи, в канал. Для параметра компилятор пишет `leaking param: p`: то, на что указывает `p`, у вызывающего тоже должно жить в куче. `leaking param: p to result ~r0` — параметр утекает только в результат: вызывающий может оставить объект на стеке, если сам результат никуда не денет.
- **Интерфейсы.** Значение, упакованное в `any` или другой интерфейс, копируется в кучу, если интерфейс убегает или компилятор не видит, куда он уходит: аргументы `fmt.Println` — классика (`x escapes to heap`). Исключения из `runtime/iface.go`: значения 0–255 однобайтовых и целых типов берутся из готовой таблицы `staticuint64s`, нулевые значения строк и срезов — из `zeroVal`, константы компилятор кладёт в статические данные, а указатель помещается в интерфейс как есть.
- **Вызов через интерфейс или значение-функцию.** Компилятор не знает, какой метод вызовется, поэтому считает, что аргумент может утечь. Так `sort.Sort(byLen(words))` копирует заголовок среза в кучу, а `slices.SortFunc` — нет.
- **Замыкания.** Литерал функции, который возвращают или сохраняют, уходит в кучу вместе с захваченными переменными (`func literal escapes to heap`, `moved to heap: n`). Замыкание, которое вызывают на месте или передают в функцию, не сохраняющую его, остаётся на стеке.
- **Размер.** Явная переменная (`var a [N]byte`) больше 128 КиБ и неявный объект (`new`, `&T{}`, `make`, `[]byte("…")`) больше 64 КиБ идут в кучу (`MaxStackVarSize` и `MaxImplicitStackVarSize` в `cmd/compile/internal/ir/cfg.go`). `make([]T, n)` с переменным `n`, который не убегает, с Go 1.25 получает на стеке буфер в 32 байта и обращается к куче, только если `n` в него не влез.

**Inlining меняет ответ.** Маленькие функции компилятор встраивает в место вызова и анализирует заново уже там: `newPoint` из живого визуализатора без `//go:noinline` встроилась бы в `main`, и решение о `p` принималось бы уже там. В куче он всё равно останется — `main` отдаёт указатель в `remember`, а та сохраняет его в глобальной `last`; на стек `p` вернётся, только если убрать и вызов `remember(a)`. Поэтому сообщения `-m` для одной функции могут повторяться на строках, где её вызвали.

**Сколько выделений на самом деле**, показывает `testing.AllocsPerRun(n, f)` — среднее число выделений в куче за вызов `f` (работает и вне тестов, как в примере). В бенчмарке то же даёт `b.ReportAllocs()` или флаг `-benchmem`: колонка `allocs/op`. Это и есть проверка оптимизации — «выделений: 0», а не «кажется, должно быть на стеке».

## Как это в C#

- **Тип против анализа.** В C# `class` — куча, `struct` — значение на месте объявления, и это часть контракта типа. В Go один и тот же `point` оказывается то на стеке, то в куче — в зависимости от того, как с ним обращаются. JIT .NET 9 и новее тоже умеет размещать на стеке объекты, которые не покидают метод, но только в простых случаях; в Go escape analysis — основной механизм, и его решение видно при сборке, а не в дизассемблере JIT.
- **`stackalloc` и `Span<T>`.** В C# стековый буфер просят явно: `Span<byte> buf = stackalloc byte[64]`, и компилятор следит, чтобы `Span` не утёк (ref struct). В Go пишут `var buf [64]byte` и работают с `buf[:]` — на стеке он останется, пока срез не убегает.
- **Boxing.** `object o = 42` упаковывает значение в кучу, `List<object>` с числами — тысячи маленьких объектов. Упаковка в интерфейс Go — то же самое, включая аргументы `string.Format` ↔ `...any` у `fmt.Sprintf`: с .NET 9 и C# 13 у него есть перегрузка `params ReadOnlySpan<object?>` — массива уже нет, но каждое число по-прежнему упаковывается. Ответ в обоих языках одинаковый: дженерики и специализированные API (`strconv.AppendInt` ↔ `int.TryFormat` в `Span<char>`).
- **Замыкания.** Лямбда C#, захватывающая локальную переменную, превращает её в поле объекта-замыкания в куче (display class). Замыкание Go, которое не убегает, держит захваченные переменные на стеке.

## Под капотом

Живой визуализатор собирает программу ниже с `-gcflags=-m` и раскладывает сообщения компилятора по колонкам «стек» и «куча» — по шагу на сообщение. В программе собраны все причины побега из урока. Уберите `//go:noinline` у `newPoint` (и вызов `remember(a)`, иначе `p` останется в куче), верните `point` по значению, замените `fmt.Println` на встроенный `println` или увеличьте `sumTo(4)` — и запустите снова: колонки перестроятся. Помните, что `make([]int, n) does not escape` для переменного `n` — это «стек, если влезет в 32 байта».

## Ловушки

### `does not escape` ещё не значит «ноль выделений»

```go
func sum(n int) int {
	buf := make([]int, n) // make([]int, n) does not escape
	// ...
}
```

Компилятор доказал, что буфер не переживёт функцию, но размер неизвестен. На стеке под него 32 байта (четыре `int`); при `n = 5` выделение пойдёт в куче во время работы. Если размер ограничен сверху, объявите массив: `var arr [64]int; buf := arr[:n]`.

### Логирование на горячем пути

```go
log.Printf("got %d bytes from %s", n, addr) // n и addr упаковываются в any
```

Каждый аргумент `...any` — кандидат в кучу, даже если уровень логирования отключён и строка не нужна: упаковка происходит до вызова. На горячем пути проверяйте уровень заранее (`if logger.Enabled(ctx, slog.LevelDebug)`) или вызывайте `logger.LogAttrs` с типизированными атрибутами `slog.Int`, `slog.String`: они хранят число и строку без упаковки в `any`.

### Возврат указателя «для скорости»

```go
func NewConfig() *Config { return &Config{...} } // куча, если не встроится
func NewConfig() Config  { return Config{...} }  // копия в кадр вызывающего
```

Привычка C#-разработчика «большие объекты — по ссылке» в Go часто оборачивается лишним выделением и работой для GC. Копия структуры в десятки байт дешевле выделения в куче. Возвращайте указатель, когда он нужен по смыслу (общее изменяемое состояние, `sync.Mutex` внутри), а не ради экономии копирования, — и проверяйте `-benchmem`.

## Задание

В `task.go` четыре функции работают правильно, но выделяют память в куче на каждый вызов. Перепишите их так, чтобы `testing.AllocsPerRun` для каждой был **0**, не меняя поведения:

```go
func AppendKey(dst []byte, user string, id int) []byte
func ParseKV(line string) (key, value string, ok bool)
func SortByLen(words []string)
func Mean(xs []float64) (float64, error)
```

- `AppendKey` дописывает к `dst` строку `user`, двоеточие и `id` в десятичной записи (`"alice:42"`, отрицательные — со знаком минус) и возвращает результат, как `append`: если ёмкости `dst` хватает, пишет в тот же массив. Ноль выделений требуется, когда ёмкости `dst` достаточно.
- `ParseKV` делит строку по **первому** `'='` на ключ и значение и обрезает пробельные символы (как `strings.TrimSpace`) у обоих: `"a=b=c"` → `"a"`, `"b=c"`, `true`; `"=x"` → `""`, `"x"`, `true`. Если `'='` нет — `""`, `""`, `false`.
- `SortByLen` сортирует срез на месте по длине в байтах, равные по длине — лексикографически (`<` для строк). `nil` и пустой срез допустимы.
- `Mean` возвращает среднее арифметическое и `nil`; для пустого или `nil` среза — `0` и ошибку, для которой `errors.Is(err, ErrEmpty)` истинно (текст ошибки может отличаться от шаблона).

Тесты проверяют поведение и число выделений: аргументы в них — переменные, а не константы.
