В уроке `03-types/04-interface-values` интерфейс был парой «тип, значение». Теперь — что это за пара в памяти и сколько она стоит. В `runtime/runtime2.go` пустой интерфейс `any` — это `eface{_type, data}`: указатель на дескриптор типа и указатель на данные. Непустой (`io.Writer`, `error`) — `iface{tab, data}`, где `tab` указывает на **itab** (`internal/abi.ITab`): интерфейс `Inter`, динамический тип `Type`, копия хеша типа `Hash` для type switch и таблица методов `Fun` — адреса реализаций в порядке методов интерфейса. Оба варианта — два машинных слова, 16 байт на 64-битной платформе.

**Откуда берётся itab.** Если конвертация видна компилятору (`var w io.Writer = &buf`), он сам генерирует itab для пары «`*bytes.Buffer`, `io.Writer`» в статических данных. Если пара известна только во время выполнения — type assertion `x.(io.Reader)` из `any` или из другого интерфейса — рантайм вызывает `getitab`: ищет в глобальной хеш-таблице `itabTable` (без блокировки), а не найдя, под мьютексом строит itab, сверяя списки методов, и навсегда кладёт его в таблицу (память из `persistentalloc` не освобождается). Отрицательный результат тоже кешируется: у такого itab `Fun[0] == 0`. Вдобавок каждое место type assertion к интерфейсу и каждый type switch с интерфейсными ветками держит свой маленький кеш (`abi.TypeAssertCache`, `abi.InterfaceSwitchCache` в `runtime/iface.go`), так что повторная проверка на том же месте почти бесплатна. Assertion к **конкретному** типу (`w.(*strings.Builder)`) ещё проще: сравнивается указатель на тип (или itab).

**Вызов метода** через интерфейс — косвенный: загрузить `tab`, взять адрес из `tab.Fun[i]`, вызвать, передав `data` как получателя. Сам по себе это пара лишних загрузок из памяти; дорого другое — компилятор не знает, кого вызывает, и не может встроить функцию (inlining) и провести escape analysis через вызов: аргументы, переданные в метод интерфейса, обычно убегают в кучу. Поэтому компилятор **девиртуализирует** вызов, когда видит динамический тип (`var s Shape = Square{}; s.Area()` — `-m` печатает `devirtualizing s.Area to Square`), а с PGO (Go 1.21+) — и когда тип известен только по профилю: горячий вызов превращается в `if sq, ok := s.(Square); ok { sq.Area() } else { s.Area() }` с встраиванием в быстрой ветке.

**Упаковка значения в интерфейс.** Указатель (а также map, канал, функция и структура/массив из одного такого поля) кладётся прямо в слово `data` — без копии и без аллокации. Остальные значения копируются, и `data` указывает на копию. Копия не обязательно в куче — `cmd/compile/internal/walk/convert.go` и `runtime/iface.go` перебирают случаи:

| Значение | Где копия |
| --- | --- |
| нулевой размер (`struct{}`) | общий `zerobase`, аллокации нет |
| `bool`, `uint8`/`int8` | статическая таблица `staticuint64s`, аллокации нет |
| целое 0–255 (`convT16`/`convT32`/`convT64`) | `staticuint64s`, аллокации нет |
| константа (`sink = 1000`) | статические данные, аллокации нет |
| `""`, nil-срез (`convTstring`, `convTslice`) | общие нулевые данные `zeroVal`, аллокации нет |
| интерфейс не убегает, значение ≤ 1024 байт | временная переменная на стеке |
| всё остальное | `mallocgc` — аллокация в куче |

Структура из одного поля упаковывается как само поле: `Square{3}` — как число 3. Отсюда практическое правило: `fmt.Println(x)`, `slog.Any`, `map[string]any`, `[]any` упаковывают каждое значение, и в горячем коде это заметная доля аллокаций.

**Сравнение интерфейсов.** `a == b` для интерфейсов — сначала сравниваются типы (`_type` или `itab`), затем, если типы совпали, значения функцией равенства типа (`efaceeq`/`ifaceeq` в `runtime/alg.go`). Разные динамические типы — просто `false`. Одинаковый **несравнимый** тип (срез, map, функция или структура с таким полем) — паника `runtime error: comparing uncomparable type []int`. Компилятор её не поймает: статический тип `any` сравним. Та же паника — при использовании такого интерфейса как ключа map.

## Как это в C#

- **Ссылка на объект vs пара слов.** В .NET указатель на таблицу методов (MethodTable) лежит в заголовке каждого объекта, а ссылка на интерфейс — обычная ссылка. В Go у значения заголовка нет: тип и таблица методов хранятся в самом интерфейсе, во втором слове рядом с данными. Поэтому интерфейс в Go занимает 16 байт, а `Square` сам по себе — 8.
- **Вызов интерфейсного метода.** CLR находит реализацию через virtual stub dispatch (кеш на месте вызова), а Tiered JIT с Dynamic PGO на лету девиртуализирует горячие вызовы с проверкой типа. В Go то же делает компилятор заранее: девиртуализация по статическому анализу и PGO-девиртуализация по профилю (`default.pgo`), JIT нет.
- **Boxing.** `object o = 42` в C# всегда выделяет объект в куче (если JIT не уберёт его escape-анализом — в .NET 9+ это бывает в простых случаях). В Go упаковка `int` в `any` выделяет память только для значений вне 0–255 и только если интерфейс убегает; маленькие числа, `bool`, пустые строки и указатели упаковываются бесплатно.
- **Сравнение.** `object.Equals` и `==` для `object` в C# не бросают исключений. В Go `any(x) == any(y)` паникует, если динамический тип несравним — например, срез внутри `any`.

## Ловушки

### Интерфейс как ключ map паникует на срезе

```go
seen := map[any]bool{}
seen["a"] = true
seen[[]int{1}] = true // panic: runtime error: hash of unhashable type []int
```

Компилятор пропускает код: тип ключа `any` допустим. Если в map с ключом `any` (или `==` между интерфейсами) могут попасть произвольные значения, проверьте сравнимость заранее: `reflect.TypeOf(v).Comparable()` — или ограничьте ключ дженериком `comparable`.

### `AllocsPerRun` показывает 0 из-за констант

```go
n := 1000
allocs := testing.AllocsPerRun(100, func() { sink = n }) // 0
```

`n` нигде не меняется, компилятор подставляет константу 1000 и упаковывает её в статические данные. Измеряя упаковку, берите значения, которые компилятор не может вычислить: параметры функций, глобальные изменяемые переменные, элементы среза.

### Метод с получателем-указателем и упаковка значения

```go
type Counter struct{ n int }
func (c *Counter) Inc() { c.n++ }

var c Counter
var i interface{ Inc() } = c // ошибка компиляции: Counter does not implement interface{Inc()} (method Inc has pointer receiver)
i = &c                        // так: в интерфейс кладётся указатель, копии нет
```

Значение в интерфейсе — копия, и менять её через интерфейс бессмысленно, поэтому методы с получателем-указателем в набор методов значения не входят. Указатель упаковывается без аллокации, а изменения видны через `c`.

## Задание

Сделайте типизированное значение `Value` в духе `slog.Value`: оно хранит число, флаг, строку или произвольное значение и **не выделяет память** для первых трёх видов — даже если `Value` уходит в кучу.

- `type Kind int` с константами `KindAny` (0), `KindInt64`, `KindBool`, `KindString` — именно в таком порядке. Нулевое `Value{}` — это `KindAny` с `Any() == nil`.
- Конструкторы `Int64Value(int64)`, `BoolValue(bool)`, `StringValue(string)`, `AnyValue(any)`. `AnyValue` всегда даёт `KindAny`, даже если внутри `int64`.
- Методы `Kind() Kind`, `Int64() int64`, `Bool() bool`, `Str() string`, `Any() any`. `Int64`, `Bool` и `Str` паникуют, если вид другой. `Any()` для любого вида возвращает значение как `any` (для `Int64Value(5)` — `int64(5)`), здесь аллокация допустима.
- `Equal(other Value) bool`: `false` при разных видах; для `KindAny` — сравнение `==` динамических значений, но если хотя бы одно из них несравнимо (срез, map, функция или структура/массив с таким полем — проверьте `reflect.TypeOf(v).Comparable()`), результат `false`, без паники. `Comparable()` смотрит только на статический тип: сравнимая структура с полем-интерфейсом, внутри которого срез, всё равно запаникует на `==` — этот случай тоже должен давать `false`. Два `KindAny` с `nil` равны.
- Конструкторы и методы `Kind`, `Int64`, `Bool`, `Str`, `Equal` для видов `KindInt64`, `KindBool`, `KindString` делают 0 аллокаций (`testing.AllocsPerRun`), в том числе когда результат конструктора сохраняют в глобальную переменную.
