Оптимизация без измерения — гадание. В Go инструменты измерения встроены в стандартную библиотеку и тулчейн: `runtime/pprof` собирает профили, `go tool pprof` их показывает, `runtime/trace` записывает трассу событий планировщика, а `go tool trace` её рисует. Ничего ставить не нужно, а накладные расходы профилей настолько малы, что их снимают прямо в продакшне.

**Профили** — это выборки стеков с весами. Все пишутся в одном формате (protobuf, сжатый gzip) и открываются одним инструментом:

| Профиль | Что в нём | Как включить |
| --- | --- | --- |
| CPU | где тратится процессорное время: 100 раз в секунду процессорного времени поток получает `SIGPROF`, обработчик записывает стек горутины | `pprof.StartCPUProfile(w)` … `StopCPUProfile()` |
| `heap` | откуда выделена память: живые объекты (`inuse_space`, `inuse_objects`) и всё выделенное с начала работы (`alloc_space`, `alloc_objects`). Выборка — в среднем раз на 512 КБ выделений (`runtime.MemProfileRate`), данные — на момент последней завершённой сборки мусора | всегда включён: `pprof.Lookup("heap").WriteTo(w, 0)` |
| `allocs` | те же данные, но по умолчанию показывается `alloc_space` — кто мусорит | `pprof.Lookup("allocs")` |
| `goroutine` | стеки всех горутин: где они стоят и сколько их | `pprof.Lookup("goroutine")`; `debug=1` — текст, сгруппированный по стекам, `debug=2` — каждая горутина, как при панике |
| `mutex` | кто держал мьютекс, пока другие ждали: стек — место `Unlock`, вес — суммарное ожидание | `runtime.SetMutexProfileFraction(n)` — записывать в среднем 1 из n событий |
| `block` | где горутины ждали: каналы, `select`, мьютексы, `WaitGroup`, `Cond` | `runtime.SetBlockProfileRate(rate)` — в среднем одно событие на `rate` наносекунд ожидания, 1 — все |

Профили `mutex` и `block` по умолчанию выключены: их включают в начале `main` на время расследования. Переключать индекс выборки heap-профиля можно при просмотре: `go tool pprof -sample_index=alloc_space heap.pprof`.

**`go tool pprof`** работает с файлом, бинарником и даже URL:

- `top` — функции по собственному времени (`flat`) и с вызываемыми (`cum`); `top -cum` — по второму;
- `list hashRounds` — исходник функции с весом каждой строки; `peek hashRounds` — кто её вызывает и кого вызывает она;
- `go tool pprof -http=localhost:8080 cpu.pprof` — веб-интерфейс с графом вызовов, flame graph (View → Flame Graph) и исходниками;
- `-diff_base=before.pprof after.pprof` — разница двух профилей: что стало дороже после изменения;
- метки: `-tags` — распределение по меткам, `-tagfocus=phase=sort` — только сэмплы с меткой.

**Профиль из бенчмарка** снимают без правки кода: `go test -bench=Format -cpuprofile cpu.out -memprofile mem.out` (а также `-blockprofile`, `-mutexprofile`), потом `go tool pprof cpu.out`. Так проверяют оптимизацию из урока про бенчмарки: сначала профиль показал горячую функцию, потом бенчмарк подтвердил выигрыш.

**`net/http/pprof`** отдаёт те же профили по HTTP: `/debug/pprof/heap`, `/debug/pprof/profile?seconds=30`, `/debug/pprof/trace?seconds=5`. Это удобно и опасно: профиль раскрывает имена функций, пути исходников, аргументы командной строки (`/debug/pprof/cmdline`), а запрос CPU-профиля нагружает процесс. Поэтому — **только на отдельном порту, привязанном к loopback или внутренней сети**, и никогда на публичном сервере:

```go
import "net/http/pprof"

func debugServer() *http.Server {
	mux := http.NewServeMux() // свой mux, не DefaultServeMux
	mux.HandleFunc("GET /debug/pprof/", pprof.Index)
	mux.HandleFunc("GET /debug/pprof/cmdline", pprof.Cmdline)
	mux.HandleFunc("GET /debug/pprof/profile", pprof.Profile)
	mux.HandleFunc("GET /debug/pprof/symbol", pprof.Symbol)
	mux.HandleFunc("GET /debug/pprof/trace", pprof.Trace)
	return &http.Server{
		Addr:              "127.0.0.1:6060", // только loopback
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
	}
}
```

`pprof.Index` сам отдаёт именованные профили (`/debug/pprof/heap`, `/goroutine`, `/mutex`…). С сервера профиль забирают через проброс порта (`kubectl port-forward pod/api 6060`) или SSH-туннель.

**Метки.** `pprof.Do(ctx, pprof.Labels("phase", "sort"), f)` вешает метки на горутину на время `f`; горутины, запущенные внутри `f`, их наследуют. Метки попадают в CPU-профиль и профиль горутин, и по ним можно разрезать профиль по эндпоинту, тенанту или фазе работы.

**Трасса** отвечает на другой вопрос: не «где тратится время», а «что происходило во времени». `trace.Start(w)` … `trace.Stop()` записывает события планировщика: запуск и остановку горутин, блокировки на каналах и мьютексах, системные вызовы, фазы GC, — с точностью до наносекунд. `go tool trace trace.out` открывает браузерный просмотр: временная шкала по P, задержки планировщика, профили блокировок, построенные по трассе. Разметка пользовательскими задачами и регионами (`trace.NewTask`, `trace.WithRegion`, `trace.Log`) — та, что показывает живой визуализатор `spans` в уроке про interceptors gRPC. Трасса тяжелее профиля, поэтому её пишут секунды, а не часы.

**`trace.FlightRecorder`** (Go 1.25) — «бортовой самописец»: трассировка идёт постоянно в кольцевой буфер в памяти, а на диск попадают только последние секунды и только когда случилось что-то интересное — медленный запрос, таймаут, всплеск ошибок:

```go
fr := trace.NewFlightRecorder(trace.FlightRecorderConfig{
	MinAge:   10 * time.Second, // хранить не меньше 10 с истории
	MaxBytes: 16 << 20,         // но не больше ~16 МБ
})
if err := fr.Start(); err != nil { /* ... */ }
defer fr.Stop()
// ...
if elapsed > time.Second { // медленный запрос — сохранить контекст
	f, _ := os.Create("slow.trace")
	fr.WriteTo(f)
	f.Close()
}
```

Активен может быть только один `FlightRecorder` на процесс, зато он работает одновременно с обычным `trace.Start`.

## Как это в C#

- **Инструменты.** CPU-профиль — `dotnet-trace collect` (EventPipe) или PerfView; счётчики в реальном времени — `dotnet-counters`; снимок кучи — `dotnet-gcdump`. В Go всё это — профили одного формата из стандартной библиотеки, а смотрит их один `go tool pprof`.
- **По HTTP.** Аналог `net/http/pprof` — `dotnet-monitor`: отдельный процесс-сайдкар с HTTP API для трасс и дампов. В Go обработчики живут прямо в процессе приложения, поэтому вопрос «на каком адресе слушать» решаете вы.
- **Метки.** Ближе всего к `pprof.Do` — `Activity` с тегами в `System.Diagnostics`: контекст текущей операции, который течёт через `async`-вызовы. Но теги `Activity` попадают в трассы OpenTelemetry, а не в CPU-сэмплы; в Go метка оказывается прямо в сэмпле профиля.
- **Трасса.** `go tool trace` ближе всего к ETW/EventPipe-трассе в PerfView: события потоков и GC во времени. Кольцевой буфер последних секунд, который сбрасывают по событию, в Go — `FlightRecorder` в самой программе. `dotnet-monitor` с триггерами на него похож лишь отчасти: трасса там начинается уже после срабатывания, а не захватывает то, что было до него.

## Ловушки

### `net/http/pprof` на публичном сервере

```go
import _ "net/http/pprof" // УЯЗВИМО: регистрирует /debug/pprof/ в DefaultServeMux

func main() {
	// публичный сервер с DefaultServeMux — профили видит весь интернет
	http.ListenAndServe(":8080", nil)
}
```

Пустой импорт регистрирует обработчики в `http.DefaultServeMux` неявно. Если публичный сервер использует тот же mux (`Handler: nil`), любой может скачать стеки горутин и аргументы запуска и нагрузить процесс CPU-профилем. Регистрируйте обработчики явно на отдельном `ServeMux` и слушайте `127.0.0.1` или внутренний адрес, как в примере выше.

### Профиль кучи без сборки мусора

```go
build() // выделили 100 МБ
pprof.Lookup("heap").WriteTo(f, 0) // inuse_space их ещё не видит
```

Heap-профиль показывает состояние на момент последней **завершённой** сборки: так в нём нет мусора, который ещё не собран. Объекты, выделенные после последнего цикла GC, в `inuse_*` не попадут. Перед записью снимка в коротких программах вызывайте `runtime.GC()` (по HTTP — параметр `?gc=1`).

### Короткий CPU-профиль

Сэмплы идут 100 раз в секунду процессорного времени: программа, которая работала 50 мс, даст пять сэмплов, и любой вывод по ним — шум. Профилируйте под нагрузкой хотя бы несколько секунд (с сервера — `?seconds=30`) и сравнивайте профили через `-diff_base`, а не по одному запуску.

## Задание

Напишите функцию, которая по тексту профиля горутин находит, где они застряли, — первый шаг расследования утечки горутин:

```go
type Site struct {
	Func  string
	Count int
}

var ErrFormat = errors.New("goroutine profile: bad format")

func Blocked(profile, pkg string) ([]Site, error)
```

`profile` — текст, который печатает `pprof.Lookup("goroutine").WriteTo(w, 1)`: первая строка `goroutine profile: total N`, дальше группы, разделённые пустыми строками. Группа начинается заголовком `<число горутин> @ <адреса>` и содержит строки кадров от вершины стека вниз; строка кадра начинается с `#` и табуляции, поля в ней разделены одной или несколькими табуляциями: `#`, адрес, функция со смещением (`main.waitLock+0x20`), файл и строка. В группе может быть строка меток `# labels: {...}` — её пропускают где угодно. Число `N` в первой строке не проверяется. Любая другая непустая строка, которая не начинается с `#` и табуляции, — заголовок новой группы (пустая строка перед ним не обязательна); число в заголовке разбирается `strconv.Atoi`.

Требования:

- для каждой группы найдите **верхний** кадр, функция которого принадлежит пакету `pkg`: её имя (без `+0x…`) начинается с `pkg + "."`. Так `main.(*server).handle` и `main.main.func1` принадлежат пакету `main`, а `mainx.Run` — нет; `example.com/app/worker.Loop` не принадлежит `example.com/app`. Число горутин группы прибавляется к этой функции; группы без функций пакета пропускаются;
- результат — по одному `Site` на функцию с суммой по всем группам, отсортированный по убыванию `Count`, при равенстве — по возрастанию `Func`. Если подходящих функций нет — срез длины 0 (`nil` допустим) и `nil`-ошибка;
- `ErrFormat` (для `errors.Is`), если: первая строка не начинается с `goroutine profile: total ` (в том числе пустой текст); строка кадра стоит не внутри группы (до первого заголовка или после пустой строки); в заголовке нет `" @"` или число до него не целое положительное; в строке кадра меньше трёх непустых полей.
