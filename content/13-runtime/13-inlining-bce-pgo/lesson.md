В Go нет JIT: всё, что программа получит от оптимизатора, компилятор решает один раз при сборке. Три механизма определяют, насколько дёшев горячий код: **встраивание** (inlining) убирает вызовы маленьких функций, **устранение проверок границ** (bounds check elimination, BCE) убирает проверки `0 <= i < len(s)`, которые Go обязан делать при каждой индексации, а **PGO** (profile-guided optimization) даёт компилятору профиль из продакшна, чтобы он знал, какой код горячий. Все три видны через `-gcflags`: пример ниже показывает решения компилятора прямо под выводом.

**Встраивание.** Компилятор оценивает тело функции в «узлах» дерева: операция, переменная, константа — примерно по единице. По `cmd/compile/internal/inline/inl.go` (Go 1.27):

- бюджет — **80** (`inlineMaxBudget`); функция дешевле встраивается в любом месте вызова;
- вызов функции, которую встроить нельзя, добавляет к стоимости **57** (`inlineExtraCallCost`) — поэтому функция с двумя такими вызовами уже не помещается. Вызов встраиваемой функции стоит столько же, сколько её тело: так работает встраивание в середине цепочки (mid-stack inlining), когда `a` вызывает `b`, `b` вызывает `c`, и в `a` оказываются обе;
- `panic` стоит 1 — проверки с паникой встраиванию не мешают;
- в очень большую функцию (больше 5000 узлов) встраиваются только функции стоимостью до 20; замыкания получают удвоенный бюджет;
- не встраиваются функции с `//go:noinline`, с `go` и `defer` («unhandled op DEFER»), с `recover`. Циклы, `switch`, обращения к map встраиванию не мешают.

`-gcflags=-m` печатает `can inline f` и `inlining call to f`, `-m=2` — ещё и стоимость (`can inline add with cost 4`) и причину отказа (`function too complex: cost 124 exceeds budget 80`), `-l` выключает встраивание. Встроенный вызов не стоит ничего: нет пролога с проверкой стека, нет передачи аргументов, и — главное — тело функции оптимизируется вместе с местом вызова: константы протягиваются внутрь, лишние проверки исчезают, а escape analysis видит, что указатель не убегает. Поэтому геттеры, конструкторы `NewX`, маленькие хелперы в Go не нужно «оптимизировать вручную».

**Проверки границ.** Каждое `s[i]` компилируется в сравнение `i` с `len(s)` и переход на `panicIndex`. Проверка дешёвая, но в горячем цикле мешает векторизации и занимает место. Проход `prove` компилятора удаляет проверки, которые можно доказать: `for i := 0; i < len(s); i++`, `for i := range s`, индекс после явного `if i < len(s)`, и все меньшие индексы после проверки большего. `-gcflags=-d=ssa/check_bce/debug=1` печатает `Found IsInBounds` (индекс) и `Found IsSliceInBounds` (срез `s[a:b]`) для каждой **оставшейся** проверки. Приёмы:

- подсказка `_ = b[3]` перед `b[0]..b[3]` — одна проверка вместо четырёх (так написан `binary.LittleEndian.Uint32`);
- `s = s[:n]` перед циклом до `n` — одна проверка среза вместо проверки на каждой итерации;
- обращаться к элементам от большего индекса к меньшему: после `s[2]` доказаны и `s[1]`, и `s[0]`;
- явная проверка длины с ошибкой (`if len(b) < 6 { return ErrShort }`) — и паники на коротком входе нет, и проверки дальше не нужны. Так написан эталон задачи: в `Parse` не остаётся ни одной проверки.

Флаг `-B` выключает проверки границ вообще. Не делайте этого: выход за границу станет порчей памяти, а не паникой.

**PGO.** С Go 1.21 `go build` по умолчанию работает с `-pgo=auto`: если в каталоге пакета `main` лежит файл `default.pgo`, это CPU-профиль в формате pprof, и компилятор оптимизирует по нему весь бинарник (пакет `main` и все его зависимости). Что меняется:

- **горячие вызовы встраиваются с бюджетом 2000** вместо 80 (`inlineHotMaxBudget`). Горячими считаются места вызова, которые вместе дают 99% веса рёбер графа вызовов в профиле;
- **девиртуализация**: если в профиле вызов через интерфейс или значение-функцию почти всегда приходится на один конкретный тип, компилятор вставляет проверку `if r, ok := x.(*bytes.Reader); ok { r.Read(p) /* прямой вызов, его можно встроить */ } else { x.Read(p) }`;

Документация Go оценивает выигрыш на типичных программах в единицы процентов CPU (2–14%). Профиль снимают с продакшна под настоящей нагрузкой — через `net/http/pprof` на внутреннем порту (урок 12): `curl -o cpu.pprof "http://127.0.0.1:6060/debug/pprof/profile?seconds=30"`, несколько профилей с разных реплик сливают командой `go tool pprof -proto a.pprof b.pprof > default.pgo`, файл коммитят рядом с `main.go`. Профиль не обязан быть свежим и снятым с той же версии кода: компилятор сопоставляет функции по именам и смещениям строк внутри функции, а устаревшие места просто не оптимизирует. Проверить, что сборка использовала профиль, — `go version -m ./app` покажет `-pgo=…/default.pgo` в настройках сборки. В песочнице PGO не показать (профиль — бинарный файл, а флаг `-pgo` runner не передаёт), поэтому здесь — только команды.

## Как это в C#

- **Когда оптимизирует.** CLR компилирует метод JIT-ом при первом вызове: Tiered Compilation сначала даёт быстрый неоптимизированный код (tier 0), а горячие методы перекомпилирует с полной оптимизацией (tier 1). Go оптимизирует один раз при сборке — без прогрева, но и без знания о реальной нагрузке, если не дать ему профиль.
- **Dynamic PGO против PGO по файлу.** С .NET 8 Dynamic PGO включён по умолчанию: tier 0 собирает статистику в самом процессе, а tier 1 по ней встраивает и делает guarded devirtualization — та же проверка типа с прямым вызовом, что и PGO-девиртуализация в Go. В Go профиль снимают отдельно и кладут в репозиторий как `default.pgo`; зато оптимизированный код есть с первой секунды, а сборка воспроизводима.
- **Подсказки.** `[MethodImpl(MethodImplOptions.AggressiveInlining)]` в C# поднимает бюджет для метода. В Go обратной директивы нет — только `//go:noinline`; повлиять на встраивание можно размером функции или профилем.
- **Проверки границ.** RyuJIT убирает их в цикле `for (int i = 0; i < arr.Length; i++)` и по `Span<T>`, а принудительно — через `Unsafe.Add` и `MemoryMarshal.GetReference`. В Go приёмы те же по духу (`range`, подсказка `_ = s[n]`, срез до `n`), а безопасного «выключателя» нет вовсе.

## Ловушки

### Подсказка не там, где проверки

```go
func sum4(s []int) int {
	t := s[0] + s[1] // две проверки
	_ = s[3]         // поздно: s[0] и s[1] уже проверены
	return t + s[2] + s[3]
}
```

Подсказка работает только для обращений **после** неё. Ставьте `_ = s[n]` в начало, до первого индекса, и проверяйте результат флагом `-d=ssa/check_bce/debug=1`, а не на глаз: компилятор доказывает меньше, чем кажется. Здесь он покажет три проверки — `s[0]`, `s[1]` и саму подсказку `s[3]`.

### `//go:noinline` в продакшн-коде

```go
//go:noinline // «чтобы было видно в профиле»
func (c *Cache) Get(k string) (V, bool) { ... }
```

Директива нужна в бенчмарках и тестах компилятора. В обычном коде она лишает горячую маленькую функцию встраивания и всего, что идёт следом: протягивания констант, удаления проверок, удержания значений на стеке. Встроенные функции и так видны в pprof: профиль хранит кадры встроенных вызовов (в `-top` они помечены `(inline)`).

### Бенчмарк без PGO, продакшн с PGO

`default.pgo` лежит в каталоге `main`, а `go test -bench` собирает тестовый бинарник пакета, где файла нет. Бенчмарк и прод оптимизированы по-разному, и выигрыш PGO в бенчмарке не виден. Чтобы сравнить, передайте профиль явно: `go test -bench=. -pgo=../cmd/api/default.pgo`.

## Задание

Напишите разбор кадров простого бинарного протокола — без паник на любом входе и без выделения памяти. Кадр: два байта `'G'`, `'T'`; байт версии (поддерживается только `1`); байт флагов; длина полезной нагрузки — `uint16` big-endian; затем столько байт нагрузки. Заголовок — 6 байт.

```go
var ErrShort, ErrMagic, ErrVersion error // уже объявлены в шаблоне

type Frame struct {
	Flags   byte
	Payload []byte
}

func Parse(b []byte) (Frame, int, error)
func Walk(b []byte, fn func(Frame)) (int, error)
```

Требования к `Parse` — разбирает один кадр в начале `b`:

- проверки по порядку: `len(b) < 6` — `ErrShort`; первые два байта не `'G'`, `'T'` — `ErrMagic`; версия не `1` — `ErrVersion`; в `b` меньше `6 + длина` байт — `ErrShort`. При любой ошибке — нулевой `Frame` и `0` прочитанных байт;
- на успехе — `Frame{Flags: b[3], Payload: …}` и число байт кадра `6 + длина`. `Payload` указывает в `b` (без копирования), и у него `cap == len`, чтобы `append` к нагрузке не перезаписал следующий кадр в том же буфере. Пустая нагрузка — срез длины и ёмкости 0 (`nil` или нет — не важно). Убирать все проверки границ не требуется — компилятор сам решит, какие оставить, урок проверяет поведение;
- не паникует ни на каком входе, включая `nil` и длину 65535 при коротком буфере, и не выделяет память (`testing.AllocsPerRun == 0`).

Требования к `Walk` — разбирает кадры подряд с начала `b`:

- для каждого успешно разобранного кадра по порядку вызывает `fn` (если `fn != nil`);
- возвращает число байт во всех успешно разобранных кадрах и ошибку `Parse` для первого неразобранного кадра — например, `ErrShort` для обрезанного хвоста; если весь вход разобран — `len(b)` и `nil`; пустой вход — `0, nil`;
- не паникует и не выделяет память сама (если не выделяет `fn`).
