В уроке про гонки данных модель памяти появилась одним абзацем. Здесь — подробно, по документу «The Go Memory Model» в ревизии от 6 июня 2022 года (Go 1.19). Ревизия формализовала модель по образцу C++ и Java и впервые описала атомики `sync/atomic` — до неё документ о них молчал.

Модель отвечает на один вопрос: когда чтение переменной в одной горутине **гарантированно** видит запись из другой. Ответ строится из трёх отношений:

- **sequenced before** — порядок операций внутри одной горутины, как его задают спецификация и порядок вычисления выражений;
- **synchronized before** — ребро между синхронизирующими операциями разных горутин: отправка в канал и получение, `Unlock` и следующий `Lock`, атомарная запись и атомарное чтение, увидевшее её;
- **happens before** — транзитивное замыкание первых двух. Обычное чтение `r` обязано увидеть запись `w`, если `w` happens before `r` и между ними нет другой записи в ту же переменную.

**Гонка данных** — запись и другое обращение к той же ячейке памяти, не упорядоченные happens-before, если хотя бы одно из них не атомарное. Главная гарантия модели — **DRF-SC**: программа без гонок данных ведёт себя так, будто все горутины по очереди выполняются на одном процессоре. Поэтому корректный конкурентный код можно рассуждать «последовательно»: перестановки компилятора и процессора в нём не видны.

Рёбра synchronized before, которые даёт язык и стандартная библиотека:

| Операция | Гарантия |
| --- | --- |
| `init` | завершение `init` импортируемого пакета — до начала `init` импортирующего; все `init` — до `main.main` |
| `go f()` | оператор `go` — до начала выполнения горутины. **Завершение** горутины ни с чем не синхронизировано |
| отправка в канал | до завершения соответствующего получения (для любой ёмкости) |
| `close(ch)` | до получения, которое вернуло нулевое значение из-за закрытия |
| получение из небуферизованного канала | до завершения соответствующей отправки |
| буферизованный канал ёмкости `C` | k-е получение — до завершения (k+C)-й отправки: так канал работает семафором |
| `sync.Mutex`, `RWMutex` | n-й `Unlock` — до возврата из m-го `Lock` при n < m; неудачный `TryLock` ничего не синхронизирует |
| `sync.Once` | завершение `f` в `once.Do(f)` — до возврата из **любого** `Do` |
| `sync.WaitGroup` | `Done` — до возврата из `Wait`, который он разблокировал |
| `sync/atomic` | если атомарная операция B увидела эффект A, то A — до B; все атомарные операции программы выполняются в одном последовательно согласованном порядке |
| `sync.Pool`, `sync.Cond`, `sync.Map` | `Put(x)` — до `Get`, вернувшего `x`; `Signal`/`Broadcast` — до возврата разбуженного `Wait`; запись в `Map` — до чтения, увидевшего её |

**Что бывает при гонке.** В C и C++ программа с гонкой не определена вовсе. Go строже: реализация может сообщить о гонке и остановить программу (так делает `-race`), а если не остановила — чтение значения не шире машинного слова обязано вернуть то, что действительно кто-то записал, и никаких значений «из воздуха». Но значения из нескольких слов — интерфейс (тип + данные), строка (указатель + длина), срез (указатель + длина + ёмкость) — читаются и пишутся пословно в произвольном порядке. Гонка на них даёт пару, которую никто не записывал, а это уже порча памяти, а не «устаревшее значение».

## Как это в C#

- **Атомики сильнее `volatile`.** `Volatile.Read`/`Volatile.Write` и поле `volatile` в C# дают acquire/release: запись может «обогнать» последующее чтение другой переменной, поэтому шаблон «записал свой флаг — прочитал чужой» (алгоритм Деккера) на `volatile` ломается, нужен `Interlocked` или `Thread.MemoryBarrier()`. Атомики Go последовательно согласованы, как `std::memory_order_seq_cst` в C++ и `volatile` в Java, — этот шаблон на них работает. Модификатора `volatile` в Go нет вовсе.
- **Двойная проверка.** В C# классическая double-checked locking корректна, если поле объявлено `volatile`. В Go аналога нет: быстрая проверка обязана быть атомарной (`atomic.Pointer`), а проще — `sync.Once`, `sync.OnceValue` (Go 1.21), которые и есть двойная проверка на атомике внутри. Это то же, что `Lazy<T>` и `LazyInitializer.EnsureInitialized`.
- **Рваные значения.** В .NET запись ссылки атомарна всегда, а рвутся только структуры шире слова (`decimal`, `Guid`, свои `struct`) — и в худшем случае получается неверное число, но не неверная ссылка. В Go интерфейс, строка и срез — многословные значения, и гонка на них способна построить указатель с чужой длиной или чужим типом.
- **Как искать.** В .NET встроенного детектора гонок нет. В Go `-race` проверяет ровно эту модель: отслеживает рёбра happens-before по векторным часам и сообщает о доступах, между которыми ребра нет.

## Под капотом

Процессоры переставляют операции с памятью: x86 держит записи в буфере и позволяет чтению обогнать более раннюю запись в другую ячейку, ARM64 переставляет почти всё. Компилятор тоже переставляет, объединяет и выносит из циклов обычные обращения. DRF-SC работает потому, что синхронизирующие операции запрещают такие перестановки через себя.

Атомики в Go — встроенные функции компилятора. По реализациям в `internal/runtime/atomic` (`atomic_amd64.go`, `atomic_amd64.s`, `atomic_arm64.s`) видно, во что они превращаются: на amd64 `Store` — инструкция `XCHG`, у которой неявный полный барьер, а `Load` — обычный `MOV` (на x86 этого достаточно, потому что `XCHG` уже не даёт записи обогнать чтение); на arm64 — пара `STLR`/`LDAR`, release-запись и acquire-чтение, которые на ARMv8 вместе дают последовательную согласованность. Мьютексы и каналы построены на тех же атомиках, поэтому дают те же гарантии.

Модель ограничивает и компилятор: он не вправе вводить записи, которых не было в программе (например, выносить запись из-под `if`), перечитывать локальную переменную из общей памяти и считать, что цикл завершится: чтение `*p`, стоящее **после** возможно бесконечного цикла, переносить **до** него можно, только если доказано, что оно не упадёт. По той же причине вынести **чтение** общей переменной из цикла (`n += *shared`) он вправе, если доказал, что чтение не упадёт, — документ приводит оба примера. Компилятор gc из Go 1.27 (проверено по ассемблеру `-gcflags=-S` на arm64) в цикле `for !done {}` перечитывает `done` на каждой итерации, но это свойство реализации, а не гарантия.

## Ловушки

### Буферизованный канал не заменяет небуферизованный

```go
var a string
c := make(chan int, 1) // с make(chan int) было бы корректно
go func() {
	a = "hello"
	<-c
}()
c <- 0
print(a) // гонка: может напечатать пустую строку
```

С небуферизованным каналом получение synchronized before завершения отправки, и `print` видит `a`. С буфером отправка завершается сразу, не дожидаясь получателя, и ребра нет. Правило k-го получения здесь не помогает: оно связывает получение с (k+C)-й отправкой, а не с первой.

### Двойная проверка на обычной переменной

```go
var cfg *Config
var mu sync.Mutex

func get() *Config {
	if cfg == nil { // гонка: чтение без синхронизации
		mu.Lock()
		if cfg == nil {
			cfg = load()
		}
		mu.Unlock()
	}
	return cfg // можно увидеть указатель, но не поля, записанные в load
}
```

Чтение `cfg` вне мьютекса не упорядочено с записью под ним. Горутина может увидеть ненулевой указатель и при этом незаполненные поля объекта: из того, что видна запись указателя, не следует, что видны более ранние записи. Правильно — `sync.OnceValue(load)` или `atomic.Pointer[Config]` на быстром пути.

### Публикация через ожидание в цикле

```go
var g *T
go func() {
	t := new(T)
	t.msg = "hello"
	g = t // обычная запись
}()
for g == nil { // гонка
}
print(g.msg) // может быть пустой строкой
```

Даже увидев `g != nil`, читатель не обязан увидеть `t.msg`, а выход из цикла вообще не гарантирован. Тот же код с `atomic.Pointer[T]` (`Store` у писателя, `Load` у читателя) корректен, а с каналом — ещё и не жжёт процессор в ожидании.

## Задание

В `task.go` — тип `Service`: текущая конфигурация с ленивой загрузкой и горячей заменой, флаг готовности и счётчик обращений. В одной горутине он работает, но методы вызывают одновременно из многих горутин, и в коде гонки данных: тесты запускаются с `-race`, и любой отчёт детектора их проваливает. Перепишите `Service` так, чтобы гонок не было, сохранив сигнатуры:

```go
func New(load func() *Config) *Service
func (s *Service) Config() *Config
func (s *Service) Reload(c *Config)
func (s *Service) MarkReady()
func (s *Service) Ready() bool
func (s *Service) Done() <-chan struct{}
func (s *Service) Hit()
func (s *Service) Hits() int64
```

Требования:

- все методы можно вызывать одновременно из любого числа горутин; сервис создаётся только через `New`;
- `New` не вызывает `load`. `load` вызывается не больше одного раза за жизнь сервиса — при первом вызове `Config` (в том числе когда первые вызовы идут одновременно), и только если к этому моменту не завершился ни один `Reload`; `load` всегда возвращает не `nil`;
- `Config` никогда не возвращает `nil`. После возврата из `Reload(c)` любой `Config`, начатый позже, возвращает `c` или конфигурацию из более позднего `Reload` — результат `load` её не затирает;
- `Reload` получает не `nil`. Опубликованные конфигурации не изменяются: горутина, получившая конфигурацию, может читать её поля сколько угодно, пока другие вызывают `Reload`;
- `Ready` возвращает `false` до первого `MarkReady` и `true` после. `MarkReady` можно вызывать повторно и одновременно; первый вызов закрывает канал `Done`, остальные ничего не делают. `Done` всегда возвращает один и тот же канал. Горутина, дождавшаяся закрытия `Done`, видит `Ready() == true`;
- `Hits` возвращает точное число завершившихся вызовов `Hit`.
