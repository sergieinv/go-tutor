В модуле 10 outbox публиковал в фейк. Теперь брокер настоящий, и relay становится конкретным: прочитать пачку неопубликованных событий **по порядку id**, отправить её в Kafka одним `ProduceSync`, отметить опубликованные. Ключ записи — id заказа (одна партиция на заказ, урок 8), в заголовке `event-id` — id строки outbox: по нему потребитель отсечёт дубли (урок 10).

**Что отмечать, если часть пачки не ушла.** `ProduceSync` возвращает результат по каждой записи, а партиции живут независимо: брокер может принять записи партиции 0 и отказать партиции 1. Отмечаем события **по порядку id до первой неудачной записи** и возвращаем ошибку. Удачные записи после неё не отмечены и уйдут в следующем проходе ещё раз — это и есть at-least-once: дубль в топике допустим, потеря — нет. Внутри партиции kgo старается не оставлять дыр: если запись провалилась из-за исчерпанных повторов или таймаута, все следующие записи этой партиции из буфера тоже завершаются ошибкой (документация `RecordRetries` и `RecordDeliveryTimeout`). Но опираться relay должен на своё правило «отмечаем до первой неудачи по id» — оно сохраняет порядок по ключу при любом исходе: в худшем случае событие уйдёт повторно, после уже опубликованного. Результаты `ProduceSync` идут в порядке подтверждений — ошибку конкретной записи ищите по указателю на `*kgo.Record`, а не по индексу.

Остальное — как в модуле 10: несколько экземпляров relay — `FOR UPDATE SKIP LOCKED` и порядок только по ключу или один экземпляр-лидер (advisory lock); пачку держат небольшой, а у публикации — таймаут через `ctx`; опубликованное чистят. Отмечать **после** подтверждения брокера, никогда до.

**Сага.** Заказ требует трёх сервисов: склад резервирует товар (MySQL), заказы создают заказ (PostgreSQL), оплата списывает деньги. Общей транзакции нет и не будет (2PC через сервисы — не вариант). Сага — последовательность **локальных** транзакций, где у каждого шага есть **компенсирующее действие**: если шаг N упал, выполняются компенсации шагов N−1, …, 1 **в обратном порядке**. Компенсация — не откат, а новое бизнес-действие: «отменить резерв», «перевести заказ в cancelled» (не `DELETE` — история нужна), «вернуть деньги». Пока сага идёт, промежуточное состояние видно снаружи (заказ в статусе `pending`) — изоляции, как у транзакции, нет.

**Хореография против оркестрации.**

- **Хореография** — центра нет: заказы публикуют `order.created`, склад слушает и публикует `stock.reserved` или `stock.rejected`, заказы слушают и подтверждают или отменяют. Слабая связность, каждый сервис знает только свои события. Минус — ход процесса размазан по сервисам: кто что ждёт, видно лишь по трассам (урок 3), а циклы событий легко создать случайно.
- **Оркестрация** — один компонент (оркестратор) вызывает шаги по очереди (gRPC или команды через Kafka), хранит состояние саги и запускает компенсации. Процесс читается в одном месте, состояние саги можно показать и мониторить. Минус — ещё один сервис и связность с ним.

В итоговом проекте курса резерв на складе — синхронный gRPC-вызов из сервиса заказов (оркестрация в малом), а уведомления — хореография через Kafka. Для длинных процессов (часы, ожидание людей) берут движки workflow — Temporal (у него есть Go SDK) или Camunda; в курсе их нет.

**Идемпотентность шагов.** Оркестратор сохраняет состояние **после** каждого шага. Упал между шагом и сохранением — после перезапуска повторит шаг. Значит, каждый шаг и каждая компенсация идемпотентны: ключ — id саги (`reserve(saga_id, ...)` второй раз возвращает тот же резерв), а компенсация несуществующего («отменить резерв, которого нет») — успех, а не ошибка. Шаг, упавший по таймауту, мог на самом деле выполниться — поэтому компенсацию часто делают безусловной и для упавшего шага; в задании упавший шаг считается не выполненным, и его `Do` обязан это обеспечить.

**Полууспех и наблюдаемость.** Хуже всего, когда не удалась сама компенсация: деньги списаны, заказ отменён, а резерв висит. Автоматически такое не чинится — сага переходит в состояние `failed`, и об этом должен узнать человек:

- состояние саги — в таблице (`saga_id`, статус, выполненные шаги, время обновления), а не в памяти процесса;
- метрика `sagas_total{status="failed"}` и алерт на неё; ещё один алерт — на саги, которые давно в `running`/`compensating` (процесс умер и никто не продолжил);
- фоновая задача перезапускает зависшие саги — `Run` должен уметь продолжить с любого сохранённого состояния;
- в логах и трассе — `saga_id` у каждого шага (урок 2–3).

## Как это в C#

- **MassTransit**: Transactional Outbox (`AddEntityFrameworkOutbox`, `UseBusOutbox`) публикует из таблицы после `SaveChanges`, а саги — **state machine** (`MassTransitStateMachine<TState>` с `Event`, `During`, `TransitionTo`) с состоянием в БД через `ISagaRepository`. В Go то и другое — свой код: relay на 50 строк и оркестратор, сохраняющий `State` после каждого шага.
- **NServiceBus Sagas** и **Durable Functions / Dapr Workflow** — оркестрация с сохранением состояния «из коробки»; ближайший аналог для Go — Temporal Go SDK.
- **`IHostedService` с relay** → горутина с тикером (модуль 10); **`ProduceAsync` в цикле с `await`** → один `ProduceSync` на пачку и разбор результатов по записям.

## Ловушки

### Отметка до подтверждения

```go
for _, e := range batch {
	cl.Produce(ctx, record(e), nil)   // асинхронно
	markPublished(ctx, db, e.ID)      // а записи ещё в буфере
}
```

Процесс упал — события отмечены, но не отправлены: потеряны навсегда. Отмечайте после того, как брокер подтвердил запись (`ProduceSync` или колбэк без ошибки).

### Компенсации в прямом порядке

```go
for _, s := range done { // reserve, order
	s.Compensate(ctx, id) // склад освобождает резерв, пока заказ ещё активен
}
```

Компенсации идут в обратном порядке: последний выполненный шаг откатывается первым. Иначе в промежутке система видит заказ без резерва — и, например, склад успевает продать товар, на который заказ ещё претендует.

### Состояние саги в памяти

```go
done := []Step{} // процесс упал — никто не знает, что компенсировать
```

После перезапуска оркестратор не знает, какие шаги уже выполнены: резерв висит вечно. Состояние сохраняется в хранилище после каждого шага и каждой компенсации, а `Run` продолжает с сохранённого места.

## Задание

Напишите оркестратор саги, который переживает перезапуск. Типы даны в шаблоне:

```go
type Status string

const (
	StatusRunning      Status = "running"
	StatusCompleted    Status = "completed"
	StatusCompensating Status = "compensating"
	StatusCompensated  Status = "compensated"
	StatusFailed       Status = "failed" // компенсация не удалась — нужен человек
)

type Step struct {
	Name       string
	Do         func(ctx context.Context, sagaID string) error
	Compensate func(ctx context.Context, sagaID string) error // nil — компенсировать нечего
}

type State struct {
	Status Status
	Done   []string // выполненные и ещё не компенсированные шаги, по порядку
}

type Store interface {
	Load(ctx context.Context, sagaID string) (State, error) // саги нет — State{} и nil
	Save(ctx context.Context, sagaID string, s State) error
}

var ErrUnknownStatus = errors.New("сага: неизвестный статус")

func Run(ctx context.Context, store Store, sagaID string, steps []Step) (Status, error)
```

Имена шагов уникальны; `Done` содержит только имена из `steps`. Каждый `Save` получает полное текущее состояние. `ctx` только передаётся в `Do`, `Compensate` и хранилище — между шагами `Run` его не проверяет.

1. `Run` загружает состояние (`Load`). Статус `completed` или `compensated` — возвращает его и `nil`, ничего не вызывая и не сохраняя.
2. Статус пустой или `running` — **вперёд**: шаги по порядку, пропуская те, что уже есть в `Done`. После каждого успешного `Do` — имя в конец `Done` и `Save` со статусом `running`. Все шаги выполнены — `Save` со статусом `completed`, результат `completed, nil`.
3. Упал `Do` — сам этот шаг выполненным не считается и не компенсируется; `Save` со статусом `compensating` и компенсации (п. 5). Если они прошли — результат `compensated` и ошибка, для которой `errors.Is(err, <ошибка Do>)`.
4. Статус `compensating` или `failed` — шаги вперёд не выполняются, только компенсации (п. 5); если они прошли — `compensated, nil`. Любой другой статус (испорченное или чужое состояние) — `""` и ошибка, для которой `errors.Is(err, ErrUnknownStatus)`; ни `Do`, ни `Compensate`, ни `Save` не вызываются.
5. **Компенсации**: шаги из `Done` с конца к началу. Для каждого вызывается `Compensate` (если не `nil`); при успехе (или `nil`) имя убирается из `Done` и следует `Save` со статусом `compensating`. `Done` опустел — `Save` со статусом `compensated`. Упал `Compensate` — `Save` со статусом `failed` (в `Done` остаются этот и все более ранние шаги) и результат `failed` и ошибка, для которой `errors.Is` находит ошибку `Compensate` (и ошибку `Do`, если она была в этом запуске).
6. Ошибка `Load` или любого `Save` — `Run` сразу останавливается (ни шагов, ни компенсаций дальше) и возвращает `""` и ошибку, для которой `errors.Is` находит ошибку хранилища, а также ошибку `Do`, если шаг упал в этом запуске, и ошибку `Compensate`, если не удалось сохранить статус `failed`. Следующий `Run` продолжит с последнего сохранённого состояния — шаг, после которого не удалось сохранить, будет выполнен повторно (поэтому шаги идемпотентны).
