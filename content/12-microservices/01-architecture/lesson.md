В модуле 10 «Заказы» были одним сервисом с одной базой: заказ, остаток на складе и событие `order.created` в outbox писались в одной транзакции. В этом модуле сервис делится на три, и почти всё, что дальше, — плата за это деление: логи, трассы и метрики нужны, чтобы видеть запрос, который прошёл через три процесса; повторы, circuit breaker и дедлайны — чтобы пережить падение соседа; Kafka и outbox — чтобы обмениваться событиями, не теряя их.

| Сервис | Владеет | Наружу | Ходит к соседям |
| --- | --- | --- | --- |
| «Заказы» | заказы, позиции, outbox (PostgreSQL) | gRPC `orders.v1` и REST через grpc-gateway | `Reserve`/`Release` «Склада» по gRPC; события в Kafka |
| «Склад» | остатки и резервы (MySQL) | gRPC `warehouse.v1` | никуда: зовут его |
| «Уведомления» | своё состояние (что уже отправлено) | ничего, кроме health и метрик | читает события заказов из Kafka |

**Владение данными.** У каждого сервиса своя база, и чужую он не читает — ни SQL-запросом, ни «только для отчёта». Остаток знает и меняет только «Склад»; «Заказы» спрашивают его через контракт. Цена — больше нет транзакции на заказ и резерв сразу: резерв на складе и запись заказа — два разных коммита в двух базах, и согласованность между ними держится на компенсациях и идемпотентности (урок `11-outbox-saga`). Выигрыш — схему склада можно менять, не спрашивая команду заказов, и падение MySQL не роняет приём заказов целиком.

**Синхронно или событием.** Вопрос один: нужен ли ответ, чтобы ответить клиенту. Без резерва заказа нет — поэтому `Reserve` синхронный gRPC-вызов с дедлайном, и «Заказы» ждут его результата. Письмо покупателю ответа не требует — поэтому «Заказы» публикуют `order.created` в Kafka и не знают, кто и когда его прочтёт. Синхронный вызов связывает доступность: если «Склад» лежит, заказ не создать. Событие развязывает: «Уведомления» могут лежать час, а потом дочитать всё, что накопилось в топике.

```
   клиент ──REST──▶ grpc-gateway ──▶ «Заказы» ──gRPC Reserve──▶ «Склад»
                                        │  PostgreSQL               MySQL
                                        │ outbox → relay
                                        ▼
                                Kafka: события заказов ──▶ «Уведомления»
```

**Контракты — в общем buf-модуле.** `orders.v1` и `warehouse.v1` лежат в одном месте, и сгенерированный Go-код берут все сервисы. `buf lint` и `buf breaking` гоняются в CI по всему модулю: несовместимую правку контракта «Склада» поймают до того, как она сломает «Заказы» (уроки `11-grpc/02-contract-evolution` и `11-grpc/03-buf`). События Kafka тоже описаны в `.proto`, а не «договорённостью в вики».

**Как это устроено в репозитории.** Система лежит в `labs/`, каждый сервис — отдельный Go-модуль со своими `cmd/`, `internal/`, миграциями и `Dockerfile` (раскладка из урока `10-services-db/02-project-layout`):

- `labs/api` — контракты (`buf.yaml`, `orders/v1`, `warehouse/v1`, события) и сгенерированный код, который импортируют остальные;
- `labs/orders` — «Заказы»: сервис из урока `10-services-db/15-orders-service`, теперь с gRPC, grpc-gateway и relay из outbox в Kafka;
- `labs/warehouse` — «Склад»: резервы с блокировками строк на MySQL (урок `10-services-db/14-mysql`);
- `labs/notifications` — «Уведомления»: потребитель событий заказов из Kafka.
- `labs/platform` — общий для сервисов «скучный» код: логирование, телеметрия, health, обёртки gRPC, HTTP и Kafka, повторы — то, что разбирают уроки этого модуля.

Запуск всего вместе — `docker compose --profile labs up --build`: compose поднимает PostgreSQL, MySQL, Kafka и сервисы. Порты, переменные окружения и как прогнать тесты каждого сервиса — в `README.md` рядом с его кодом. В итоговом уроке модуля система собирается целиком, а уроки между ними разбирают её части по одной.

Пример ниже — та же схема в миниатюре: три «сервиса» в одном процессе на loopback, у каждого своя map вместо базы. Outbox здесь нет — двойная запись помечена в коде.

## Как это в C#

- **Композиция.** В ASP.NET Core соседей собирает контейнер: `AddGrpcClient<T>`, `AddSingleton<IProducer<…>>`, конфигурация из `appsettings.json` через `IOptions<T>`, жизненный цикл — `IHostedService`. В Go ничего из `Microsoft.Extensions.*` нет: `main` сам создаёт клиентов (`grpc.NewClient`, `kgo.NewClient`), передаёт их в конструкторы и сам останавливает в обратном порядке. Граф зависимостей — обычный код, его видно целиком.
- **Генерация из контракта.** `Grpc.Tools` генерирует C#-код при каждой сборке из `<Protobuf Include="…">` в `.csproj`; в Go код генерирует `buf generate`, и его коммитят (или собирают в общем модуле вроде `labs/api`). Контракт один на оба языка — сервис на C# может звать «Склад» на Go без единой строчки общего кода.
- **Оркестрация локально.** .NET Aspire описывает систему кодом в AppHost и сам поднимает контейнеры; здесь ту же роль играет `docker compose --profile labs`.
- **Размер и старт.** Go-сервис — один статический бинарник: образ на `scratch` или distroless весит десятки мегабайт и стартует за миллисекунды. ASP.NET Core тянет рантайм (chiseled-образы его ужимают) и прогревает JIT; Native AOT даёт похожий результат, но с ограничениями на рефлексию. Для микросервисов, которые масштабируются десятками реплик, это заметно (урок `12-deploy-k8s`).

## Ловушки

### Общая база на два сервиса

```go
// «Заказы» «просто читают» остаток из базы склада
row := warehouseDB.QueryRowContext(ctx, `SELECT available FROM stock WHERE sku = ?`, sku)
```

Так получается распределённый монолит: два деплоя, но одна схема. Переименовал колонку на складе — упали заказы; сменил движок или разделил таблицу — надо согласовывать с чужой командой. Чужие данные — только через контракт (`Reserve`, `GetStock`) или через события, из которых сервис строит свою копию нужного ему среза.

### Цепочка синхронных вызовов

```go
// CreateOrder: Reserve на складе, Charge в оплате, Send в уведомлениях —
// и всё ждём, прежде чем ответить клиенту
```

Доступность цепочки — произведение: три соседа по 99,9 % дают 99,7 %, то есть около 26 часов простоя в год вместо девяти, а задержки складываются. Синхронно вызывают только то, без чего нельзя ответить. Остальное — событием: «письмо отправлено» клиенту знать не нужно.

### Клиент на каждый запрос

```go
func (o *orders) create(w http.ResponseWriter, r *http.Request) {
	conn, _ := grpc.NewClient(warehouseAddr, opts...) // новое HTTP/2-соединение
	defer conn.Close()
	// ...
}
```

`*grpc.ClientConn` — как `*sql.DB`: дорогой, потокобезопасный, один на сервис-соседа на весь процесс. Создаётся в `main` и передаётся зависимостям; иначе каждый запрос платит за TCP и TLS, а балансировка и keepalive не работают (урок `11-grpc/13-grpc-client`). Та же история с `*kgo.Client`.

## Задание

Монолитная `PlaceOrder` из модуля 10 сама проверяла остаток в общей map, списывала его и дописывала уведомление в общий срез. Перепишите её для системы из трёх сервисов: «Заказы» говорят со «Складом» и брокером только через интерфейсы `Stock` и `Publisher` (они, как и типы `Line`, `Order`, `Event` и ошибки `ErrInvalid`, `ErrOutOfStock`, даны в шаблоне). И напишите фейк «Склада» `MemStock` для тестов.

```go
func NewService(stock Stock, events Publisher, newID func() string) *Service
func (s *Service) PlaceOrder(ctx context.Context, customer string, lines []Line) (Order, error)
func (s *Service) Get(id string) (Order, bool)

func NewMemStock(stock map[string]int) *MemStock
func (m *MemStock) Reserve(ctx context.Context, orderID string, lines []Line) error
func (m *MemStock) Release(ctx context.Context, orderID string) error
func (m *MemStock) Available(sku string) int
```

`PlaceOrder`:

- пустой `customer`, пустой или `nil` список позиций, позиция с пустым `SKU` или `Qty <= 0` — ошибка, для которой `errors.Is(err, ErrInvalid)`; при этом ни `newID`, ни методы `Stock` и `Publisher` не вызываются;
- позиции нормализуются: одинаковые `SKU` складываются в одну позицию, результат сортируется по `SKU` по возрастанию. Именно этот список передаётся в `Reserve` и попадает в `Order.Lines`;
- для валидного заказа `newID` вызывается ровно один раз — до `Reserve`; этот id — `Order.ID`, он же передаётся в `Reserve`, `Publish` и `Release`;
- `Reserve(ctx, id, lines)` вызывается один раз с контекстом запроса. Ошибка — заказ не сохраняется, `Publish` и `Release` не вызываются, возвращается ошибка, оборачивающая ошибку `Reserve` (`errors.Is` находит её, например `ErrOutOfStock`);
- затем `Publish(ctx, Event{Type: "order.created", OrderID: id, Customer: customer})` с контекстом запроса. Ошибка — компенсация: `Release` с тем же id, заказ не сохраняется, возвращается ошибка, для которой `errors.Is` находит ошибку `Publish`, а если `Release` тоже вернул ошибку — и её. Компенсация должна выполниться, даже если контекст запроса к этому моменту отменён: в `Release` передаётся контекст, который не отменяется вместе с запросом, но хранит его значения;
- при успехе заказ сохраняется и возвращается; `Get(id)` возвращает его и `true`, неизвестный id — `Order{}` и `false`;
- при любой ошибке `PlaceOrder` возвращает нулевой `Order{}`;
- изменение среза `Lines` в заказе, возвращённом `PlaceOrder` или `Get`, или в переданном `lines` не меняет сохранённый заказ: каждый вызов `Get` отдаёт копию, включая свою копию `Lines`;
- `Service` безопасен для одновременных вызовов.

`MemStock`:

- `NewMemStock` копирует переданную map; дальнейшие изменения этой map складу не видны, и склад её не меняет;
- `Reserve` проверяет по порядку: отменённый контекст — ошибка контекста (`errors.Is(err, context.Canceled)`); позиция с `Qty <= 0` — `ErrInvalid` (даже если резерв с этим id уже есть); затем идемпотентность по id; затем остатки. При любой ошибке ничего не меняется. `SKU` склад не проверяет: пустой `SKU` — такой же неизвестный товар с остатком 0. Пустой или `nil` список позиций — успех без списаний (резерв по id фиксируется, `Release` по нему ничего не возвращает);
- `Reserve` — всё или ничего: позиции с одинаковым `SKU` складываются; если хоть какого-то `SKU` меньше нужного (неизвестный `SKU` — это остаток 0), возвращается ошибка с `errors.Is(err, ErrOutOfStock)` и ничего не списывается;
- `Reserve` идемпотентен по `orderID`: повторный вызов с id, у которого уже есть резерв, возвращает `nil` и ничего не списывает;
- `Release` с отменённым контекстом возвращает ошибку контекста; иначе возвращает зарезервированное по заказу и забывает резерв. Повторный `Release` и `Release` неизвестного id — `nil` без изменений. После `Release` тот же id можно зарезервировать заново;
- `Available(sku)` — текущий остаток (0 для неизвестного `SKU`);
- `MemStock` безопасен для одновременных вызовов: при 100 параллельных заказах на остаток 50 ровно 50 успешны.
