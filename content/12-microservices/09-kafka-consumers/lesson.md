Один экземпляр «Уведомлений» не успевает — запускаем три. Чтобы они не обработали каждое событие трижды, их объединяют в **группу потребителей** (`kgo.ConsumerGroup("notifications")`): брокер-координатор делит партиции топика между участниками так, что **каждую партицию читает ровно один участник группы**. Три партиции и три участника — по одной; четвёртый участник будет простаивать. Другая группа («Аналитика») читает тот же топик независимо и со своим прогрессом.

**Офсеты коммитов.** Прогресс группы — не «прочитанные сообщения», а **закоммиченный офсет** для каждой партиции: номер записи, с которой группа продолжит. Его хранит брокер (во внутреннем топике `__consumer_offsets`). Участник упал или перезапустился — новый владелец партиции начнёт с закоммиченного офсета. Отсюда вся семантика доставки:

- коммит **после** обработки — сбой между обработкой и коммитом даст повтор: **at-least-once**, потерь нет, дубли возможны;
- коммит **до** обработки — сбой после коммита потеряет запись: at-most-once;
- exactly-once между Kafka и внешним миром (БД, почта) не бывает — потребитель делает обработку **идемпотентной** (урок 10).

**Автокоммит в kgo.** По умолчанию клиент группы коммитит сам: раз в 5 секунд (`kgo.AutoCommitInterval`) и при отзыве партиций. Коммитятся записи **предыдущих** опросов: всё, что вернул `PollFetches`, считается обработанным, когда вы вызвали `PollFetches` снова. Пока обработка синхронная — «обработал пачку, опросил ещё» — это at-least-once. Ломается, если отдать записи в горутины и сразу опрашивать дальше: офсет закоммитится раньше, чем горутина закончит, и при сбое запись пропадёт. Ещё деталь: последний опрос перед `Close` «грязный» и при закрытии не коммитится (проверено на kfake и Kafka 4.3) — после перезапуска эта пачка придёт снова; закоммитить её можно явно — `cl.CommitUncommittedOffsets(ctx)` перед `Close`.

**Ручной коммит** — `kgo.DisableAutoCommit()` и `cl.CommitRecords(ctx, recs...)` после обработки: клиент для каждой партиции коммитит офсет последней переданной записи **плюс один** («следующую читать отсюда»). Коммитить каждую запись отдельно дорого — обычно коммитят пачку после опроса. Промежуточный вариант — `kgo.AutoCommitMarks()` и `cl.MarkCommitRecords(r)`: автокоммит, но только отмеченных записей.

**Ребалансировка.** Участник вошёл, вышел или пропал (нет heartbeat дольше `SessionTimeout`, по умолчанию 45 с) — координатор перераспределяет партиции. Колбэки `kgo.OnPartitionsAssigned` и `kgo.OnPartitionsRevoked` вызываются с картой `топик → партиции`; в `Revoked` успевают закоммитить сделанное, иначе новый владелец повторит его. `OnPartitionsLost` — партиции отобраны из-за ошибки группы, коммит уже не пройдёт. Балансировщик по умолчанию в kgo — **cooperative-sticky**: при ребалансировке отбирают только переезжающие партиции, остальные участники продолжают читать (в старом «eager»-протоколе все отдавали всё и ждали). В Kafka 4 есть и новый протокол групп (KIP-848, балансировка на брокере) — kgo 1.21 включает его только по явному согласию, курс его не использует.

**Порядок и параллельность.** Внутри партиции клиент отдаёт записи по возрастанию офсетов; обрабатывайте их последовательно — и порядок событий заказа сохранится. Параллельность — **по партициям**: горутина на партицию (`fetches.EachPartition` и `sync.WaitGroup`), внутри — по порядку. Раздать записи одной партиции пулу воркеров — значит потерять порядок и сломать коммит: офсет 7 обработан, а 5 ещё нет — что коммитить?

**Корректная остановка.** `signal.NotifyContext` отменяет `ctx` → `PollFetches(ctx)` возвращается с ошибкой `context.Canceled` (`fetches.Err0()`) → цикл заканчивает текущую запись → коммит обработанного (на контексте, который **не** отменён: `context.WithoutCancel(ctx)` с таймаутом) → `cl.Close()`: клиент выходит из группы, и координатор сразу отдаёт партиции другим, не дожидаясь `SessionTimeout`. `kgo.InstanceID` (static membership) — наоборот: перезапуск пода с тем же id не вызывает ребалансировку.

В отличие от Java-клиента и librdkafka, у kgo нет `max.poll.interval.ms`: heartbeat и ребалансировки идут в фоне, а участника не выгонят из группы за долгую обработку между опросами. Обратная сторона — ребалансировка может случиться посреди обработки пачки, и коммит уйдёт за партицию, которой вы уже не владеете (дубль у нового владельца). Если это важно — `kgo.BlockRebalanceOnPoll()` и `cl.AllowRebalance()` после обработки.

## Как это в C#

- **`ConsumerBuilder` с `GroupId` → `kgo.ConsumerGroup`**, `consumer.Subscribe(topic)` → `kgo.ConsumeTopics`, `consumer.Consume(ct)` возвращает одну запись; `cl.PollFetches(ctx)` — всё, что накопилось, по партициям.
- **`EnableAutoCommit = false` + `consumer.Commit(result)` → `DisableAutoCommit()` + `CommitRecords`.** Автокоммит librdkafka коммитит «сохранённые» офсеты (`EnableAutoOffsetStore`), и типичный приём — `EnableAutoOffsetStore = false` + `StoreOffset(result)` после обработки; в kgo аналог — `AutoCommitMarks` + `MarkCommitRecords`.
- **`SetPartitionsAssignedHandler`/`SetPartitionsRevokedHandler` → `OnPartitionsAssigned`/`OnPartitionsRevoked`**; `PartitionAssignmentStrategy.CooperativeSticky` в librdkafka включают явно (по умолчанию range/roundrobin), в kgo cooperative-sticky — по умолчанию.
- **`BackgroundService` с циклом `Consume` и `consumer.Close()` в `StopAsync`** → горутина с циклом `PollFetches(ctx)`, `signal.NotifyContext` и `cl.Close()`. В Confluent.Kafka долгая обработка без `Consume` дольше `MaxPollIntervalMs` выкидывает участника из группы; в kgo такого лимита нет.

## Ловушки

### Коммит до обработки

```go
fetches := cl.PollFetches(ctx)
cl.CommitUncommittedOffsets(ctx) // «потом обработаем»
fetches.EachRecord(func(r *kgo.Record) {
	send(r) // упали здесь — записи уже закоммичены и потеряны
})
```

Коммит означает «обработано». Сначала обработка, потом коммит — тогда сбой даёт повтор, а не потерю.

### Обработка в горутинах при автокоммите

```go
for {
	fetches := cl.PollFetches(ctx)
	fetches.EachRecord(func(r *kgo.Record) {
		go handle(r) // следующий PollFetches «закоммитит» и эту запись
	})
}
```

Автокоммит считает обработанным всё из прошлого опроса. Горутины ещё работают, а офсеты уже закоммичены — сбой потеряет записи. Да и порядок внутри партиции пропал. Распараллеливайте по партициям и дожидайтесь обработки перед следующим опросом.

### Коммит на отменённом контексте

```go
<-ctx.Done() // SIGTERM
cl.CommitRecords(ctx, done...) // context canceled — коммит не ушёл
cl.Close()
```

После остановки обработанное не закоммичено, и после перезапуска всё придёт снова. Финальный коммит — на `context.WithoutCancel(ctx)` (лучше с таймаутом), а не на контексте, который уже отменён.

## Задание

Напишите цикл потребителя с ручным коммитом:

```go
type Handler func(ctx context.Context, r *kgo.Record) error

func Run(ctx context.Context, cl *kgo.Client, h Handler) error
```

Клиент создают тесты: группа, топик, `kgo.DisableAutoCommit()`. `Run` его не закрывает.

- `Run` в цикле опрашивает клиент (`PollFetches(ctx)`) и передаёт записи в `h` по одной в том порядке, в каком их вернул опрос (внутри партиции — по возрастанию офсетов).
- Когда все записи опроса обработаны без ошибок, `Run` коммитит их (`CommitRecords`) **до** следующего опроса. Ошибка коммита — `Run` возвращает её.
- Если `h` вернул ошибку — запись не считается обработанной: `Run` больше не вызывает `h` ни для одной записи (в отличие от примера, где пропускается только партиция упавшей записи, здесь останавливается весь цикл), коммитит записи, успешно обработанные до неё, и возвращает ошибку, для которой `errors.Is(err, <ошибка h>)`. Новый клиент той же группы получит упавшую запись снова — и все необработанные после неё, но ни одной успешно обработанной.
- Отмена `ctx` — штатная остановка: `Run` не вызывает `h` для следующих записей (проверка `ctx.Err()` перед каждой записью), коммитит обработанное и возвращает `nil`. Истечение дедлайна `ctx` — такая же отмена. Опрос, вернувшийся из-за отмены `ctx` или закрытия клиента, — тоже `nil`; любая другая ошибка опроса — возвращается, и записи этого опроса не обрабатываются.
- Коммит выполняется и тогда, когда `ctx` уже отменён: используйте контекст без отмены (`context.WithoutCancel(ctx)`). Например, обработчик отменил `ctx` после успешной обработки записи — эта запись должна быть закоммичена.
