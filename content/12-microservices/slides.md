# Микросервисы

Обзор модуля для показа команде: сервис заказов становится системой из трёх — наблюдаемость, устойчивость к сбоям соседей, Kafka и Kubernetes.

---

## Три сервиса и плата за деление

- «Заказы» (gRPC + REST, PostgreSQL), «Склад» (MySQL), «Уведомления» (консьюмер Kafka).
- Каждый сервис владеет своими данными: общая база на два сервиса — ловушка.
- Логи, трассы и метрики — чтобы видеть запрос в трёх процессах; повторы, breaker и дедлайны — чтобы пережить соседа; Kafka и outbox — чтобы не терять события.
- Запуск всей системы: `docker compose --profile labs up --build`.

---

## Наблюдаемость: логи, трассы, метрики

- `slog` пишет JSON в stdout; `request_id` и `trace_id` берутся из `ctx` обёрткой над `slog.Handler` — логируйте через `InfoContext`.
- OpenTelemetry: спан от `ctx` становится ребёнком спана в `ctx`. Потерянный `ctx` рвёт дерево трассы.
- Prometheus: RED — counter с кодом и histogram длительности, в одном interceptor на весь сервер.
- В метку — шаблон пути, а не путь с id: иначе кардинальность взорвётся.

## Повторы: что и как

| Код | Повторять? |
| --- | --- |
| `Unavailable` | да |
| `ResourceExhausted`, `Aborted` | да, с паузой / всю операцию |
| `InvalidArgument`, `NotFound`, `PermissionDenied` | нет |

Пауза — экспонента с потолком и полным джиттером; подсказка `RetryInfo` от сервера важнее своей экспоненты. `CreateOrder` повторяют только с ключом идемпотентности.

## Дедлайн важнее числа попыток

```go
limit := min(p.base<<(attempt-1), p.max)
d = time.Duration(p.rand() * float64(limit)) // полный джиттер
// Пауза переживёт дедлайн — ждать бессмысленно.
if dl, ok := ctx.Deadline(); ok && p.clk.now().Add(d).After(dl) {
	return err
}
```

Повторы на каждом слое перемножаются: три слоя по три попытки — 27 вызовов к упавшему соседу.

## Бюджет времени едет с запросом

- grpc-go пересчитывает дедлайн `ctx` в заголовок `grpc-timeout`, сервер превращает его обратно в `ctx.Deadline()`.
- Каждый сервис видит реальный остаток, а не «свои» 5 секунд из конфигурации, и отказывает раньше начала, если не успеет.
- Фоновая работа после ответа — на `context.WithoutCancel`, а не на контексте запроса.

## Kafka: лог, а не очередь

- Топик — партиции, партиция — лог с офсетами. Запись не удаляется после чтения.
- Ключ выбирает партицию, порядок гарантирован только внутри партиции: ключ — id сущности.
- В группе потребителей каждую партицию читает один участник. Коммит после обработки — at-least-once, дубли возможны.
- franz-go: продюсер идемпотентен по умолчанию; ядовитое сообщение — ограниченные повторы и DLQ.

## Outbox и саги

- Relay публикует пачку одним `ProduceSync` и отмечает события по порядку id до первой неудачи.
- Отмечать — после подтверждения брокера, никогда до.
- Сага: хореография или оркестрация; компенсации — в обратном порядке, шаги идемпотентны, состояние саги — не в памяти.

---

## Docker и Kubernetes

- Статический бинарник: multi-stage, `CGO_ENABLED=0`, distroless, не root — образ в десятки мегабайт.
- Пробы: readiness и liveness разные; база в liveness — ловушка.
- SIGTERM: сначала readiness 503 и пауза, потом `Shutdown` с таймаутом — балансировщик узнаёт об удалении пода позже.
- `GOMAXPROCS` с Go 1.25 сам учитывает лимит CPU cgroup, а память — нет: `GOMEMLIMIT` ставят примерно в 80–90% от `limits.memory`.

---

## Что запомнить

- `ctx` — по всей цепочке: в нём трасса, `request_id` и дедлайн.
- Повторять — только идемпотентное, с джиттером, в пределах дедлайна и на одном слое.
- Порядок Kafka — только по ключу, доставка — at-least-once, потребитель — идемпотентный.
- Дубль допустим, потеря — нет.
