Кеш процессора хранит память кеш-линиями (урок 15): 64 байта на x86-64 и большинстве arm64, 128 — на Apple M (`sysctl hw.cachelinesize`). Когерентность кешей тоже работает на уровне линий: прежде чем ядро запишет хоть байт, оно должно получить линию в единоличное владение, а копии в кешах остальных ядер становятся недействительными. Это упрощённый протокол MESI: у каждой копии линии одно из состояний M (изменена), E (исключительная), S (общая), I (недействительна).

Отсюда **false sharing**. Две горутины на двух ядрах пишут в **разные** переменные — данных они не делят, гонки нет, синхронизация не нужна. Но если переменные лежат в одной линии, каждая запись забирает линию у соседнего ядра, и она бесконечно ездит между кешами. Код корректен и даже выглядит параллельным, а с ростом числа ядер работает медленнее, чем на одном. Типичные жертвы — массивы счётчиков «по одному на воркера», поля статистики рядом в одной структуре, голова и хвост очереди, мьютексы, сложенные в срез.

Лекарство — разнести горячие переменные по разным линиям:

```go
type paddedSlot struct {
	n atomic.Int64
	_ [CacheLine - 8]byte // безымянное поле: только занимает место
}
```

- **Заполнитель `_ [N]byte`.** Безымянное поле нельзя прочитать или записать, оно только сдвигает следующее. Важен **шаг**: если соседние горячие поля отстоят друг от друга не меньше чем на размер линии, в одну линию они не попадут, где бы ни начиналась структура. Язык не обещает выравнивания начала структуры по линии — опирайтесь на шаг.
- **Какой размер.** В примере и задаче `CacheLine = 128`. Так делает и рантайм: `internal/cpu.CacheLinePadSize` равен 64 на x86 и 128 на arm64 («Apple Silicon has 128-byte cache line size»), а `sync.Pool` добивает свой `poolLocal` до кратного 128 на любой платформе. На x86-64 128 байт заодно защищают от предвыборки парной линии. Готовый тип — `cpu.CacheLinePad` из `golang.org/x/sys/cpu` (он есть в песочнице как косвенная зависимость), но тянуть модуль ради одного массива байт не обязательно.
- **Плата — память.** Шестнадцать выровненных счётчиков занимают 2 КБ вместо 128 байт. Заполнитель ставят только туда, где профиль показал конкуренцию: в структуре, которую создают миллионами, он вреден.

**Шардированные счётчики и striped locks.** Один атомарный счётчик, в который пишут все ядра, — уже не false, а true sharing: линия одна по смыслу. Его разбивают на N шардов, каждый в своей линии; писатель прибавляет к «своему» шарду, читатель складывает все. Запись становится дешёвой, а чтение — дороже и не мгновенным снимком: шарды читаются по очереди. Для метрик и лимитов это нормально. Номера горутины в Go нет, поэтому шард выбирают по подсказке (номер воркера, хеш ключа) или случайно — `math/rand/v2` держит состояние генератора на каждом потоке ОС и не берёт общей блокировки. Ещё лучше, если можно копить локально и прибавлять один раз в конце. Тот же приём для блокировок — striped locks: N мьютексов (каждый с заполнителем), ключ выбирает мьютекс по хешу; так устроен шардированный кеш из урока о кеше в процессе.

**RWMutex не спасает от общей линии.** Читатели `RWMutex` не ждут друг друга, но `RLock` — это `readerCount.Add(1)`, а `RUnlock` — `Add(-1)` (`sync/rwmutex.go`): каждый читатель пишет в одно и то же поле. На коротких секциях время операции растёт с числом ядер, как и у мьютекса (issue 17973), а на одном ядре `RWMutex` чуть дороже `Mutex`. Он выигрывает, когда чтение долгое по сравнению с самой блокировкой. Для «почти только чтения» с короткими секциями лучше подходят copy-on-write на `atomic.Pointer` (урок 19) или шардирование.

**Как увидеть.** Бенчмарк с `b.RunParallel` и флаг `-cpu 1,4,8`: при `-cpu 1` варианты с заполнителем и без почти равны, при нескольких ядрах плотный вариант отстаёт, и время на операцию растёт вместе с числом ядер. Сравнивайте прогоны `-count 10` через `benchstat`. Числа зависят от процессора — в песочнице мало ядер, и разница может быть скромнее, чем на рабочей машине. В профиле CPU false sharing выглядит как «дорогой» `atomic.Add` или простое присваивание без видимой причины; на Linux его ищет `perf c2c`.

## Как это в C#

- **`[StructLayout]` вместо заполнителя.** В C# размер задают атрибутом: `[StructLayout(LayoutKind.Explicit, Size = 128)]` с `[FieldOffset(0)]`, проверяют через `Unsafe.SizeOf<T>()`. В Go — поле `_ [N]byte` и `unsafe.Sizeof`; атрибутов нет, всё видно в объявлении.
- **В BCL это уже сделано.** `ConcurrentQueue<T>` разносит голову и хвост внутренней структурой `PaddedHeadAndTail` (на arm64 она занимает 384 байта: по 128 на линию). В Go стандартная библиотека так же прячет заполнители внутри `sync.Pool` и рантайма, а в своём коде их ставят руками.
- **`Interlocked.Increment` на общем поле** — та же true sharing, что `atomic.Int64.Add` из всех горутин. Шардированного счётчика в BCL нет ни там, ни там: его пишут сами (или берут готовый из библиотек вроде `xsync` в Go).
- **`ReaderWriterLockSlim`** при каждом входе читателя тоже обновляет общее состояние блокировки, так что совет тот же: на коротких чтениях не ждите от него линейного роста с числом ядер — меряйте против обычного `lock`.

## Под капотом

Сценарий показывает два ядра и их кеши L1 с упрощённым MESI. Сначала счётчики `a` и `b` лежат в одной 64-байтной линии: каждая запись забирает линию у соседнего ядра, и счётчик передач растёт. Потом заполнитель сдвигает `b` в соседнюю линию, и ядра пишут каждое в свою копию без обмена.

## Ловушки

### Массив мьютексов или счётчиков подряд

```go
type Striped struct {
	mu [16]sync.Mutex // 8 байт каждый: 8–16 мьютексов в одной линии
}
```

Разбили один мьютекс на 16 — а горутины, взявшие разные мьютексы, всё равно гоняют общую линию. Каждому элементу нужен заполнитель: `struct { sync.Mutex; _ [CacheLine - 8]byte }`. То же с `[]atomic.Int64` «по счётчику на воркера».

### Заполнитель на 64 байта на Apple M и arm64-серверах

```go
type slot struct {
	n atomic.Int64
	_ [56]byte // на линии 128 байт два слота делят линию
}
```

Бенчмарк на ноутбуке разработчика с Apple M покажет false sharing даже после «исправления». Размер — константа под самую большую линию, на которой код будет работать (128), а не магическое 64.

### Заполнитель там, где конкуренции нет

```go
type Order struct {
	ID    int64
	_     [120]byte // «на всякий случай»
	Total int64
}
```

Объект, который читает и пишет одна горутина, от заполнителя только растёт: меньше объектов помещается в кеш, больше работы GC и памяти. Выравнивают горячие поля, которые **одновременно пишут разные ядра**, — и только после замера.

## Задание

Напишите шардированный счётчик, у которого каждый шард занимает свою кеш-линию.

```go
const CacheLine = 128

type shard struct {
	n atomic.Int64
	// заполнитель
}

type Counter struct {
	shards []shard
}

func New(n int) *Counter
func (c *Counter) Shards() int
func (c *Counter) AddAt(hint int, delta int64)
func (c *Counter) Add(delta int64)
func (c *Counter) Load() int64
```

Требования:

- `unsafe.Sizeof(shard{})` равен ровно `CacheLine`; поле `n` остаётся первым (смещение 0); шарды хранятся в срезе `shards` типа `[]shard`, и `len(shards) == Shards()`;
- `New(n)` создаёт счётчик с числом шардов, равным `n`, округлённому вверх до степени двойки (1 → 1, 3 → 4, 8 → 8, 1000 → 1024). При `n <= 0` вместо `n` берётся `runtime.GOMAXPROCS(0)` и тоже округляется вверх;
- `AddAt(hint, delta)` прибавляет `delta` к шарду с индексом `hint & (Shards()-1)` — для любого `hint`, в том числе отрицательного;
- `Add(delta)` прибавляет `delta` к любому шарду — какому именно, решаете вы;
- `Load` возвращает сумму всех шардов. Когда одновременных записей нет, она точна; во время записей `Load` не обязан быть снимком, но если все приращения положительны, более поздний `Load` не меньше более раннего;
- все методы безопасны для одновременного вызова из любого числа горутин; тесты запускаются с `-race`. Нулевое значение `Counter` использовать не нужно — счётчик создаётся только через `New`.
