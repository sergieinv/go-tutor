Процессор считает быстрее, чем память успевает отдавать данные, и между ними стоит иерархия кешей. Порядки величин стоит помнить как ориентир, а не как числа для расчёта: регистр — доли наносекунды; **L1** (десятки КиБ на ядро) — около наносекунды, несколько тактов; **L2** (от сотен КиБ до нескольких МиБ) — единицы наносекунд; **L3** (мегабайты, общий для группы ядер) — десяток-другой наносекунд; **оперативная память** — порядка сотни наносекунд. Промах мимо всех кешей стоит сотни тактов, за которые ядро могло бы выполнить сотни инструкций. Поэтому для горячего кода часто важнее не «сколько операций», а «сколько раз ждали память».

**Кеш-линия.** Память переезжает в кеш не байтами, а линиями: 64 байта на x86-64 и на большинстве серверных arm64, **128 байт** на Apple M (`sysctl hw.cachelinesize` на M-серии показывает 128; поэтому и `internal/cpu.CacheLinePadSize` в Go для arm64 — 128 с пометкой про Apple Silicon). Прочитали одно `int64` — в кеш приехали ещё 7 (или 15) соседних. Код, который использует соседей, получает их бесплатно; код, который прыгает по памяти, платит за каждую линию ради одного значения.

**Предвыборка.** Процессор следит за адресами промахов, и когда видит последовательный обход или постоянный шаг, начинает загружать следующие линии заранее — к моменту обращения данные уже в кеше. Отсюда два правила локальности: **пространственная** (рядом лежит то, что понадобится следом) и **временная** (то, что нужно снова, ещё не вытеснено).

**Срез против связного списка.** Срез — значения подряд: последовательный обход идеален и для линий, и для предвыборки. Связный список — цепочка зависимых загрузок: адрес следующего узла становится известен, только когда прочитан текущий, и процессор не может забежать вперёд (pointer chasing). Пока узлы лежат подряд — например, только что выделены один за другим, — разница невелика; когда список пожил, порос вставками и удалениями, узлы разбросаны, и каждый шаг — промах. В примере тот же список, связанный в случайном порядке, обходится в сотни раз медленнее. Поэтому в Go почти всегда берут срез: очередь — кольцевой буфер, «список с удалением из середины» — срез с перестановкой последнего элемента на место удалённого, дерево — узлы в срезе с индексами вместо указателей (`14-highload/17-gc-friendly-data`).

**Матрица по строкам и по столбцам.** Двумерные данные в Go удобнее всего держать в одном срезе: элемент `(i, j)` — по индексу `i*n+j` (row-major). Обход по строкам идёт по памяти подряд. Обход по столбцам прыгает на `n*8` байт: для матрицы 2048×2048 `int64` — 16 КиБ между соседними шагами, каждая загруженная линия даёт одно нужное значение. Ещё один повод для одного среза вместо `[][]int64`: у среза срезов каждая строка — отдельное выделение где-то в куче и лишний переход по указателю.

**TLB.** Адреса виртуальные, и перевод страниц в физические адреса тоже кешируется — в TLB, где сотни-тысячи записей. Страница — 4 КиБ на типичном Linux x86-64, 16 КиБ на macOS с Apple M. Случайный доступ к сотням мегабайт промахивается и мимо TLB, поэтому разброс по памяти бьёт дважды.

**Как мерить.** Только бенчмарком и только на своих данных: `go test -bench . -benchmem`, несколько прогонов (`-count 10`) и сравнение версий через `benchstat` из `golang.org/x/perf`. Размер данных решает всё: пока всё помещается в L1/L2, раскладка почти не важна, а на десятках мегабайт меняет время в разы. Числа зависят от процессора — бенчмарк, который на ноутбуке с огромным L2 «не показывает разницы», на сервере с меньшим кешем на ядро покажет. В песочнице кнопка «Бенчмарки» запустит пример с `-benchtime=200ms -benchmem`: сравните `ListSequential` и `ListShuffled`, `MatrixRows` и `MatrixCols`.

## Как это в C#

- **`Queue<T>` в .NET — кольцевой буфер на массиве, `LinkedList<T>` — объект на каждый узел.** В Go `container/list` — тот же `LinkedList<T>`, а встроенной очереди-кольца нет: её пишут на срезе (задание урока) или берут канал, если нужна синхронизация.
- **`List<T>` ↔ срез, `T[]` из структур ↔ `[]T`.** Локальность в обоих языках одинаковая: массив структур лежит подряд, массив классов (как `[]*T`) — массив ссылок на объекты, разбросанные по куче. Отличие в том, что в Go значения — по умолчанию, а в C# объект класса — привычка.
- **`long[,]` и jagged `long[][]`.** Многомерный массив .NET хранится одним блоком по строкам — как срез с `i*n+j`; jagged — как `[][]int64`, строка на отдельное выделение.
- **Измерение:** BenchmarkDotNet ↔ `go test -bench` + `benchstat`; у BenchmarkDotNet есть аппаратные счётчики промахов кеша (на Windows), в Go их смотрят внешним профилировщиком (`perf stat` на Linux).

## Ловушки

### Бенчмарк, в котором всё помещается в кеш

```go
func BenchmarkList(b *testing.B) {
	l := buildList(1000) // 16 КБ — целиком в L1/L2
	for b.Loop() {
		sink = sumList(l)
	}
}
```

Тысяча узлов, выделенных подряд, — это 16 КБ в кеше: список «не медленнее среза», вывод неверный. Данные бенчмарка должны быть сопоставимы с рабочими по объёму и по разбросу в памяти, а сравнения — на нескольких размерах.

### `[][]T` вместо одного среза

```go
grid := make([][]float64, rows)
for i := range grid {
	grid[i] = make([]float64, cols) // rows отдельных выделений
}
```

Каждая строка — отдельный объект: `rows + 1` выделений, строки не обязаны лежать рядом, и каждый доступ — лишний переход по указателю. `make([]float64, rows*cols)` с индексом `i*cols+j` — одно выделение и непрерывная память; если нужен синтаксис `grid[i][j]`, нарежьте строки из одного общего среза.

### Удаление из середины среза «как в списке»

```go
items = append(items[:i], items[i+1:]...) // сдвиг хвоста — O(n) на удаление
```

Если порядок не важен, переставьте последний элемент на место удалённого и укоротите срез — O(1), и срез остаётся плотным. Если порядок важен и удалений много, помечайте удалённые и уплотняйте пачкой. Связный список «ради дешёвого удаления» почти всегда проигрывает на обходе больше, чем выигрывает на удалении.

## Задание

В `task.go` очередь задач `Queue` написана на `container/list`: каждый `Push` выделяет узел в куче, обход прыгает по указателям. Перепишите её на срезе, сохранив поведение.

```go
func (q *Queue) Push(v int64)
func (q *Queue) Pop() (int64, bool)
func (q *Queue) Peek() (int64, bool)
func (q *Queue) Len() int
func (q *Queue) All() iter.Seq[int64]
```

- Нулевое значение `Queue` — пустая очередь, готовая к работе.
- FIFO: `Pop` убирает и возвращает самый ранний из оставшихся элементов, `Peek` возвращает его же, не убирая. На пустой очереди оба возвращают `0, false`. `Len` — число элементов.
- `All` обходит элементы от первого к последнему, не меняя очередь; поддерживает досрочный выход из `for range`.
- **Без выделений в рабочем режиме:** когда очередь однажды дорастала до размера `N`, любые последовательности `Push`/`Pop`, при которых в ней не больше `N` элементов, не выделяют память. Обход `All` тоже не выделяет память: замыкание, которое возвращает `All`, остаётся на стеке, только пока компилятор встраивает `All` в цикл `for range` вызывающего, — держите `All` коротким, без лишних обёрток и захвата чего-то кроме `q`.
- Рост — с запасом (например, удвоением): 100 000 `Push` в новую очередь — не больше 64 выделений.
- `Push` и `Pop` — амортизированно O(1): никаких сдвигов всего содержимого на каждом `Pop`.
