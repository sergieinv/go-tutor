Таблица заказов растёт на миллионы строк в месяц, а читают почти всегда последние недели. Индексы пухнут и перестают помещаться в память, VACUUM ходит по всей таблице, а удаление заказов старше двух лет — это `DELETE` миллионов строк, который час грузит диск и оставляет мёртвые версии строк. **Партиционирование** делит одну логическую таблицу на несколько физических — партиций — по значению **ключа партиционирования**. Приложение по-прежнему пишет и читает `orders`, а PostgreSQL сам кладёт строку в нужную партицию и читает только те партиции, которые могут содержать ответ.

**Три способа разбиения** (`CREATE TABLE … PARTITION BY`):

- **RANGE** — по диапазонам: `FOR VALUES FROM ('2026-01-01 00:00:00+00') TO ('2026-02-01 00:00:00+00')`. Нижняя граница включается, верхняя — нет, поэтому месяцы стыкуются без зазоров. Главный случай — время: заказы, события, журналы.
- **LIST** — по списку значений: `FOR VALUES IN ('eu', 'uk')` — регионы, арендаторы, статусы.
- **HASH** — по остатку от хеша: `FOR VALUES WITH (MODULUS 4, REMAINDER 0)`. Ровно раскладывает ключ без естественных диапазонов (покупатель), но запрос «за период» прочтёт все партиции.

Родительская таблица данных не хранит — только схему. Строка, которой не нашлось партиции, даёт ошибку `no partition of relation … found for row`, если нет партиции `DEFAULT`. Партиции бывают и сами партиционированными (по месяцу, внутри — по hash покупателя), но каждый уровень усложняет обслуживание.

**Partition pruning** — главный выигрыш. Если условие запроса сравнивает ключ партиционирования с константой или параметром, планировщик выбрасывает партиции, которые не могут подойти: в примере запрос за 10–20 февраля читает одну партицию из пяти. Отсечение бывает двух видов. При **планировании** — когда значение известно сразу (константа или параметр, под который строится конкретный план). При **выполнении** — для обобщённого плана подготовленного выражения или значения из подзапроса: план содержит все партиции, но лишние не запускаются, а `EXPLAIN` пишет `Subplans Removed: 4`. Условие без ключа (`WHERE customer_id = $1`) читает все партиции, и функция над ключом (`date_trunc('month', created_at) = $1`) тоже прячет его от планировщика — пишите диапазон.

**Индексы.** `CREATE INDEX` на родителе создаёт индекс на каждой партиции, а у будущих — автоматически при создании. Индексы получаются маленькими — по одному на партицию, — и горячий месяц со своим индексом помещается в память. `CREATE INDEX CONCURRENTLY` на родителе нельзя: создают индексы на партициях по одному конкурентно, потом индекс на родителе `ON ONLY` и `ALTER INDEX … ATTACH PARTITION`.

**Уникальность.** Уникальный индекс проверяется внутри одной партиции, поэтому PostgreSQL требует, чтобы `PRIMARY KEY` и `UNIQUE` включали все колонки ключа партиционирования: `PRIMARY KEY (id)` на таблице, разбитой по `created_at`, — ошибка `0A000`, а `PRIMARY KEY (id, created_at)` — можно. Глобальной уникальности одного `id` база больше не гарантирует; её обеспечивают последовательностью или UUID, а внешние ключи на такую таблицу ссылаются парой колонок.

**Обслуживание по времени.** Партиции создают заранее — задание по расписанию держит готовыми два-три месяца вперёд (вручную, как в задании урока, или расширением `pg_partman`). Старые данные удаляют не `DELETE`, а **отсоединением**: `ALTER TABLE orders DETACH PARTITION orders_2024_01`, затем `DROP TABLE` или перенос в архив. Это операция над метаданными: мгновенно, без мёртвых строк и без нагрузки на диск. `DETACH … CONCURRENTLY` не держит сильную блокировку на родителе, но не работает внутри транзакции и при наличии DEFAULT-партиции.

**DEFAULT-партиция** спасает от ошибок вставки, но у неё есть цена: при создании новой партиции PostgreSQL проверяет, что в DEFAULT нет строк нового диапазона (сканирует её под блокировкой), а если есть — отказывает (`updated partition constraint for default partition would be violated`). Заказы «из будущего» в DEFAULT ломают завтрашнее создание партиции. Лучше вовремя создавать партиции и мониторить, что DEFAULT пуста.

**Партиционирование или шардирование.** Партиции живут на **одном сервере**: они ускоряют запросы по ключу, упрощают удаление старых данных и делают индексы компактными, но не добавляют ни ядер, ни дисков, ни соединений. Если упёрлись в запись или объём одного сервера — нужно шардирование: данные на разных серверах, ключ шарда и роутинг в приложении (урок `12-sharding`) или Citus. Частая схема — обе вещи вместе: шард по покупателю, внутри шарда — партиции по месяцу.

## Как это в C#

- **ORM не помогает.** EF Core не моделирует партиции: таблица в модели одна, DDL партиций пишут руками в миграции (`migrationBuilder.Sql(...)`) или в отдельном задании. В Go то же самое, только миграции — goose или SQL-файлы (урок `10-services-db/08`).
- **SQL Server.** Там партиционирование устроено через partition function и partition scheme, а старые данные отрезают `ALTER TABLE … SWITCH PARTITION` в архивную таблицу — аналог `DETACH`. Уникальный индекс, выровненный по партициям, тоже должен включать колонку партиционирования.
- **Время.** Npgsql с версии 6 строг к `timestamptz`: принимает только `DateTime` с `Kind = Utc`. В Go `time.Time` несёт свой пояс, и pgx передаёт момент времени корректно, но **литералы** в DDL (`'2026-02-01'`) PostgreSQL читает в часовом поясе сессии — пишите смещение явно и в Go, и в C#.

## Ловушки

### Граница без смещения

```go
// ОШИБКА: граница зависит от TimeZone сессии
conn.Exec(ctx, `CREATE TABLE orders_2026_02 PARTITION OF orders
	FOR VALUES FROM ('2026-02-01') TO ('2026-03-01')`)
```

Для `timestamptz` литерал без смещения читается в часовом поясе текущей сессии. Задание, запущенное с `TimeZone = 'Asia/Tokyo'`, создаст партицию `[2026-01-31 15:00 UTC, 2026-02-28 15:00 UTC)`. Если все соседние партиции созданы в той же сессии, сдвинуты все границы, и последние девять часов февраля по UTC молча уезжают в мартовскую партицию; если соседа создали с `+00` (или не создали вовсе) — между партициями дыра, и вставка в неё падает. `pg_get_expr(relpartbound, oid)` печатает границы в поясе текущей сессии: в сессии UTC — `'2026-01-31 15:00:00+00'`, так что сдвиг виден, только если знать, что ждёшь полночь. Пишите `'2026-02-01 00:00:00+00'`.

### Ключ партиционирования спрятан в функцию

```go
pool.Query(ctx, `SELECT … FROM orders WHERE created_at::date = $1`, day) // читает все партиции
```

Отсечение работает, только когда условие сравнивает саму колонку ключа. Приведение типа, `date_trunc`, `extract` превращают запрос «за день» в проход по всем партициям. Пишите полуинтервал: `created_at >= $1 AND created_at < $1 + interval '1 day'`.

### Очистка через DELETE

```go
pool.Exec(ctx, `DELETE FROM orders WHERE created_at < now() - interval '2 years'`)
```

На партиционированной таблице это работает, но теряет главный выигрыш: миллионы удалённых строк, WAL на гигабайты (и на реплики тоже), мёртвые версии строк до VACUUM. Если граница хранения совпадает с границей партиций, отсоединяйте и удаляйте партиции целиком — это и есть причина разбивать по времени.

## Задание

Напишите генератор месячных партиций для таблицы, разбитой `PARTITION BY RANGE (created_at)`, и функции обслуживания — всё без базы, DDL строками.

```go
var ErrBadName = errors.New("bad name")
var ErrBadRange = errors.New("bad range")

type Partition struct {
	Parent string
	Name   string
	From   time.Time
	To     time.Time
}

func Monthly(parent string, from, to time.Time) ([]Partition, error)
func (p Partition) CreateSQL() (string, error)
func (p Partition) DetachSQL() (string, error)
func Locate(parts []Partition, t time.Time) (Partition, bool)
func Expired(parts []Partition, now time.Time, keep int) []Partition
```

Месяцы считаются в UTC; моменты времени сравниваются как моменты (пояс входных значений не важен).

- **Имена.** Допустимое имя — от 1 символа, только строчные латинские буквы `a-z`, цифры и `_`, первый символ — не цифра. Для `Monthly` имя родителя не длиннее 55 символов (имя партиции на 8 длиннее), в `CreateSQL`/`DetachSQL` имена `Parent` и `Name` — не длиннее 63 (предел PostgreSQL). Недопустимое имя — ошибка, для которой `errors.Is(err, ErrBadName)`; результат при этом `nil` или `""`.
- **`Monthly`** возвращает по партиции на каждый месяц UTC, пересекающийся с полуинтервалом `[from, to)`, по возрастанию: `Name` — `"<parent>_YYYY_MM"` (год четырьмя цифрами, месяц двумя), `From` — 1-е число месяца 00:00 UTC, `To` — 1-е число следующего месяца, оба в `time.UTC`. Если `from` не раньше `to` или год какого-нибудь из месяцев вне 1000–9999 — `nil` и ошибка `ErrBadRange`. Имя проверяется первым.
- **`CreateSQL`** возвращает ровно `CREATE TABLE IF NOT EXISTS <Name> PARTITION OF <Parent> FOR VALUES FROM ('<From>') TO ('<To>')`, где время — в UTC в формате `2006-01-02 15:04:05` и сразу за ним `+00`. **`DetachSQL`** — ровно `ALTER TABLE <Parent> DETACH PARTITION <Name>`. Оба сначала проверяют имена (`ErrBadName`), затем — что `From` раньше `To` (иначе `ErrBadRange`); при любой ошибке результат `""`. Год границ здесь не проверяется: тесты дают только годы 1000–9999.
- **`Locate`** возвращает первую по порядку партицию из `parts`, для которой `From <= t < To`, и `true`; нет такой — нулевую `Partition` и `false`.
- **`Expired`**: граница — 1-е число месяца UTC, в котором лежит `now`, минус `keep` месяцев (`keep < 0` считается за 0). Возвращает партиции из `parts`, у которых `To` не позже границы, в исходном порядке; нет таких — срез длины 0 (`nil` допустим).

С профилем labs скрытый тест выполняет ваш DDL на PostgreSQL в сессии с часовым поясом `Asia/Tokyo` и проверяет, что строки ложатся в те партиции, которые называет `Locate`.
