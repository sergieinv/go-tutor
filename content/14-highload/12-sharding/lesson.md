Партиционирование из прошлого урока делит таблицу внутри одного сервера: запись, CPU и диск всё равно одни. Когда упираешься в них, данные раскладывают по нескольким независимым базам — **шардам**. В PostgreSQL и MySQL нет встроенного «распредели таблицу по десяти серверам», поэтому чаще всего шардирует само приложение: роутер по ключу решает, в какой пул соединений идти. В Go это обычный код — map имён шардов на `*pgxpool.Pool` и функция выбора.

**Ключ шарда** — главное решение, его почти невозможно поменять потом. Для «Заказов» естественный ключ — покупатель: все заказы одного покупателя лежат на одном шарде, «мои заказы» и транзакция «создать заказ» не выходят за его пределы. Хороший ключ есть почти в каждом запросе, у него много разных значений и нет гигантов. Плохой — дата создания: вся запись идёт в «сегодняшний» шард.

**Как ключ превращается в шард:**

- **Диапазонное** — таблица «покупатели A–F → шард 1». Удобно для запросов по диапазону и ручного переноса, но таблицу надо хранить, а соседние ключи, которые приходят вместе (новые id по порядку), бьют в один шард.
- **Хеш по модулю** — `hash(key) % N`. Равномерно и без состояния, но номер шарда зависит от `N`: при переходе с 4 на 5 шардов меняется 4/5 ответов, и почти все данные надо переносить.
- **Consistent hashing** (Karger и др., 1997) — шарды и ключи лежат на одном кольце хешей, ключ достаётся первому шарду по часовой стрелке. Новый шард забирает только дугу перед собой — в среднем `K/(N+1)` ключей, ровно столько, сколько ему и положено. С одной точкой на шард дуги случайной длины, поэтому каждый шард ставит на кольцо 100–200 **виртуальных узлов**: доли выравниваются, а при добавлении и удалении нагрузка перетекает между всеми шардами, а не к одному соседу. Поиск — бинарный по отсортированному срезу точек.
- **Rendezvous hashing, HRW** (Thaler, Ravishankar, 1996) — для ключа считают вес `hash(key, shard)` каждого шарда и берут максимальный. То же свойство «переезжает только своё», ни кольца, ни виртуальных узлов, равномерность из коробки; цена — `O(N)` хешей на ключ, что для десятков шардов ничего не стоит.
- **Jump consistent hash** (Lamping, Veach, 2014) — десять строк, без памяти, идеальная равномерность, но шарды — это номера `0…N-1`: добавлять и убирать можно только последний. Подходит, когда шарды — реплицированные «корзины», а не конкретные серверы.

Пример считает всё это на 10 000 покупателях: сколько ключей у каждого из четырёх шардов и сколько сменят шард при добавлении пятого. Хеш — FNV-1a из стандартной библиотеки с финализатором `fmix64`: он должен давать одно и то же в каждом процессе, на каждой машине и в каждой версии программы.

**Решардинг** — перенос данных при смене схемы. Даже с consistent hashing данные надо физически скопировать, и делают это без остановки записи: (1) новый шард добавляется в роутер «на запись» — двойная запись в старое и новое место; (2) фоновый перенос (backfill) копирует старые строки, идемпотентно, батчами; (3) сверка; (4) чтение переключается на новую схему; (5) двойная запись выключается, старые данные удаляются. Каждый шаг обратим, пока не сделан последний. Частый приём — сразу завести много **логических шардов** (скажем, 1024 корзины по хешу) и отображение «корзина → сервер»: решардинг тогда — перенос целых корзин и правка таблицы, хеш ключей не меняется никогда.

**Запросы через все шарды** (scatter-gather): «последние 20 заказов магазина» спрашивают у каждого шарда его 20 последних — параллельно, `errgroup` с общим контекстом, — сливают и сортируют. Каждый шард обязан вернуть полный `limit`: все 20 лучших могут оказаться на одном. Задержка такого запроса — задержка самого медленного шарда, а глубокая пагинация (`OFFSET 10000`) превращается в 10 000 строк с каждого шарда — её заменяют курсором («старше, чем последний показанный»). Агрегаты (`COUNT`, `SUM`) сливаются легко, `AVG` — только как сумма и количество, медиана — никак. Частые кросс-шардовые запросы — признак неудачного ключа или повод держать отдельную модель чтения.

**Транзакции через шарды** — то же, что транзакции через сервисы: двухфазный коммит дорог и хрупок, поэтому либо ключ выбирают так, чтобы транзакция жила в одном шарде, либо используют сагу с компенсациями и outbox (`12-microservices/11-outbox-saga`).

**Горячие ключи.** Хеш выравнивает число ключей, но не нагрузку: маркетплейс-гигант с миллионом заказов — один ключ на одном шарде. Помогают отдельный шард для известных гигантов (таблица исключений перед хешем), составной ключ `customer#bucket` для записи с чтением по всем корзинам и кеш для чтения.

**Готовые решения.** Citus — расширение PostgreSQL: `create_distributed_table('orders', 'customer_id')` раскладывает таблицу по рабочим узлам, координатор маршрутизирует запросы, таблицы с одинаковым ключом (colocation) соединяются локально, а запросы без ключа идут на все узлы. Vitess — то же для MySQL: прокси VTGate, «vindex» как функция «значение колонки → keyspace ID», а диапазоны keyspace ID распределены по шардам, решардинг встроенным перекачиванием данных. Оба снимают роутинг с приложения, но ключ шарда всё равно выбираете вы. В итоговом проекте `labs/` «Заказы» шардируются по покупателю — там видно, как роутер живёт рядом с пулами соединений настоящего сервиса.

## Как это в C#

- **Нет `GetHashCode` для шардирования.** В .NET Core `string.GetHashCode()` рандомизирован на каждый процесс — роутер на нём отправит одного и того же покупателя в разные шарды из разных экземпляров. В Go та же ловушка у `hash/maphash` и хеша встроенной map: сид случайный. В обоих языках нужен явный стабильный хеш (FNV, xxHash, MurmurHash).
- **Шардирование в EF Core не встроено.** Обычно делают фабрику `DbContext` по ключу шарда (строка подключения выбирается роутером) — в Go это map «шард → пул» и функция выбора, без контекста и без DI.
- **Scatter-gather:** `Task.WhenAll` по шардам и `CancellationTokenSource` для отмены остальных ↔ `errgroup.WithContext` в Go: первая ошибка отменяет общий контекст, `Wait` возвращает её после завершения всех горутин.
- **Готовые варианты** те же, они живут на стороне базы: Citus для PostgreSQL (работает и с Npgsql, и с pgx), Vitess для MySQL — приложению на любом языке они видны как обычный PostgreSQL или MySQL.

## Под капотом

Сценарий ниже раскладывает двенадцать ключей сначала остатком от деления, затем по кольцу с одной и с тремя точками на шард, и добавляет четвёртый шард. Позиция — CRC-32 по модулю 360, чтобы её можно было нарисовать градусами; в настоящем роутере кольцо — все 2⁶⁴ значений хеша. Двенадцать ключей — маленькая выборка, поэтому числа скачут; на 10 000 ключей их выравнивает пример урока.

## Ловушки

### Хеш, который меняется между процессами

```go
var seed = maphash.MakeSeed() // ОШИБКА: новый сид при каждом запуске
func shard(key string, n int) int { return int(maphash.String(seed, key) % uint64(n)) }
```

После перезапуска сервиса покупатель «переезжает» на другой шард, его заказы перестают находиться, новые пишутся рядом со старыми в чужой шард. То же с хешем от `fmt.Sprintf("%p")`, порядком обхода map и `string.GetHashCode()` в C#. Хеш шардирования фиксируется навсегда, как формат данных: FNV-1a, CRC-32, xxHash — с тестом, который сверяет пару известных значений.

### Плохо перемешанный хеш

```go
h := fnv.New64a()
h.Write([]byte("shard-0#" + strconv.Itoa(v))) // точки одного шарда слипаются
```

FNV-1a обрабатывает строку побайтно и последний байт лишь умножает на простое число около 2⁴⁰: строки, различающиеся последним символом, получают хеши, отличающиеся меньше чем на 255·2⁴⁰ — одну 65-тысячную кольца. Виртуальные узлы шарда слипаются в кучки, и кольцо даже с 200 точками на шард делит ключи почти так же неровно, как с одной: на 10 000 ключей у четырёх шардов вышло 1510/1620/3980/2890 против 2413/2406/2568/2613 с финализатором. Помогает финализатор вроде `fmix64` из примера или хеш с хорошим лавинным эффектом.

### `LIMIT` на каждом шарде меньше общего

```go
perShard := limit / len(shards) // 20 заказов на 4 шарда — по 5 с каждого?
```

Если все самые новые заказы — у одного шарда, ответ получится неверным: с него взяли 5, а должны были 20. Каждый шард отдаёт полный `limit`, лишнее отрезается после слияния. С пагинацией то же: продолжение — курсор «старше `(created_at, id)`», а не `OFFSET`.

## Задание

Напишите роутер запросов «Заказов» по шардам (ключ — покупатель) и запрос «последние заказы» по всем шардам.

```go
func NewRouter(shards ...string) (*Router, error)
func (r *Router) Shard(customerID string) string
func (r *Router) Add(name string) error
func (r *Router) Remove(name string) error
func (r *Router) Shards() []string

func RecentOrders(ctx context.Context, stores map[string]Store, limit int) ([]Order, error)
```

Роутер:

- Алгоритм — consistent hashing с виртуальными узлами или rendezvous hashing, на ваш выбор; `hash % N` требования ниже не выполнит. Хеш должен быть одинаковым в любом процессе (не `maphash` и не хеш map).
- `Shard` возвращает имя одного из шардов роутера; один и тот же покупатель — всегда тот же шард при том же наборе шардов, независимо от порядка, в котором шарды передали в `NewRouter` и добавляли через `Add`. Если шардов нет — `""`.
- **Равномерность:** на 10 000 покупателей `customer-0` … `customer-9999` у каждого из N шардов (N от 1 до 10) от 60% до 140% средней доли.
- **Стабильность:** при `Add` шарда меняют шард только покупатели, которые переходят на **новый** шард, и их не больше 1,5·K/(N+1) из K. При `Remove` меняют шард только покупатели удалённого шарда. `Remove`, а затем `Add` того же шарда возвращают исходное распределение.
- Ошибки: пустое имя — `ErrEmptyName`, повтор имени (в `NewRouter` или `Add`) — `ErrDuplicateShard`, `Remove` несуществующего — `ErrUnknownShard` (обёртки допустимы, проверка через `errors.Is`). `NewRouter` при ошибке возвращает `nil`; неудачные `Add`/`Remove` роутер не меняют.
- `Shards` возвращает имена по возрастанию — копию, изменение которой не влияет на роутер.
- Все методы безопасны для одновременного вызова из разных горутин.

`RecentOrders` (scatter-gather):

- `limit <= 0` — пустой результат (срез длины 0, `nil` допустим) и ошибка `nil`, шарды не вызываются. Нет шардов — тоже пустой результат и `nil`.
- Каждый шард вызывается ровно один раз с тем же `limit`, все шарды — **параллельно**.
- Ответы объединяются и сортируются: новые первыми (`CreatedAt` по убыванию), при равном времени — по возрастанию `ID`; возвращаются первые `limit`. Шард может вернуть заказы в любом порядке и даже больше `limit`.
- Если какой-то шард вернул ошибку, функция возвращает `nil` и ошибку, которая оборачивает ошибку шарда (`errors.Is`) и содержит его имя; контекст, переданный остальным шардам, при этом отменяется. Функция возвращается только после того, как завершились все вызовы шардов.
- Контекст шардов — производный от `ctx`: если `ctx` отменён, шарды это видят.
