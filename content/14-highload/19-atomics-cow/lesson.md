В модуле 5 атомики были счётчиками и флагами, а в уроке о модели памяти — способом синхронизации. Здесь — два приёма, на которых держится почти весь код без блокировок: **CAS-цикл** и **публикация неизменяемого снимка** через `atomic.Pointer`.

**Гарантии.** Типы `atomic.Int32/Int64/Uint32/Uint64/Uintptr/Bool/Pointer[T]` (с Go 1.19) и функции пакета дают две вещи (`go doc sync/atomic`). Первая: если атомарная операция B увидела результат атомарной операции A, то A «synchronizes before» B — всё, что горутина записала до A, видно после B. Вторая: все атомарные операции программы выглядят выполненными в некотором едином порядке — последовательная согласованность, как `seq_cst` в C++ и `volatile` в Java. Ослабленных режимов (`acquire`/`release`/`relaxed`) в Go нет: выбирать нечего и ошибиться в выборе нельзя. `atomic.Int64` выровнен на 8 байт даже на 32-битных платформах, а копировать атомики нельзя — `go vet` (copylocks) это поймает.

**CAS-цикл.** `CompareAndSwap(old, new)` записывает `new`, только если в переменной всё ещё `old`, и сообщает, удалось ли. Любая операция «прочитать — вычислить — записать» превращается в цикл:

```go
for {
	cur := x.Load()
	next := f(cur)              // вычисление без побочных эффектов
	if x.CompareAndSwap(cur, next) {
		break                   // никто не вмешался — опубликовали
	}
	// значение изменили между Load и CAS — пробуем заново
}
```

Так пишут счётчик с потолком (лимитер из примера), атомарный максимум, переходы состояний (`closed → open` у circuit breaker). Для простого сложения есть `Add`, для битовых масок — `And`/`Or` (Go 1.23) — они делают то же без вашего цикла: на arm64 с LSE это одна инструкция, на amd64 — `LOCK AND`/`LOCK OR`, если старое значение не нужно, а если результат используется, компилятор сам подставляет цикл с `LOCK CMPXCHG`. `f` может вызываться несколько раз, поэтому она должна быть чистой: никаких логов, отправок в канал и выделения ресурсов внутри цикла.

**Copy-on-write через `atomic.Pointer`.** Конфигурацию, таблицу маршрутов, список фич-флагов читают на каждом запросе, а меняют раз в минуты. Мьютекс на каждое чтение — общая линия и очередь (урок 18). Вместо этого:

- данные лежат в **неизменяемом снимке** — структуре, которую после публикации никто не трогает, включая map и срезы внутри;
- читатель делает один `p.Load()` и дальше работает со своим снимком без блокировок, сколько угодно долго;
- писатель **копирует** текущий снимок, меняет копию и публикует её: `Store` — если писатель один, CAS-цикл — если их несколько, иначе одновременные обновления затрут друг друга.

Это идея RCU (read-copy-update) из ядра Linux. Самая трудная часть RCU — понять, когда старую версию можно освободить, ведь её ещё могут читать. В Go это делает сборщик мусора: старый снимок живёт, пока на него ссылается хоть один читатель.

**Когда CAS-цикл хуже мьютекса.** При высокой конкуренции писателей большинство попыток проваливается, и работа `f` выбрасывается: с copy-on-write это копирование целой map на каждую неудачную попытку плюс мусор для GC. Мьютекс ставит ожидающих в очередь, и каждый делает работу один раз. Прикидка: CAS-цикл хорош, когда `f` дешёвая (несколько инструкций) или писатели редки; copy-on-write — когда чтений на порядки больше, чем записей, и снимок небольшой. Частые записи в большую структуру — мьютекс или шардирование (урок 14-highload/06). Lock-free не значит быстрее: меряйте бенчмарком с `-cpu`.

## Как это в C#

- **`Interlocked` ↔ `sync/atomic`.** `Interlocked.CompareExchange(ref x, next, cur) == cur` — тот же CAS, только возвращает старое значение, а не `bool`. `Interlocked.Add`/`Increment` ↔ `Add`, `Interlocked.Exchange` ↔ `Swap`.
- **`Volatile.Read`/`Write` против последовательной согласованности.** В .NET `Volatile.Read` — чтение с семантикой acquire, `Volatile.Write` — release, а полный барьер даёт только `Interlocked` и `Thread.MemoryBarrier`. В Go режим один — последовательно согласованный, и все атомики в нём одинаковы.
- **`ImmutableInterlocked` ↔ CAS-цикл с copy-on-write.** `ImmutableInterlocked.Update(ref dict, f)` и `AddOrUpdate` над `ImmutableDictionary` — готовый цикл из этого урока. В Go неизменяемых коллекций нет: неизменяемость — договорённость, которую не проверит компилятор (но нарушение поймает `-race`).
- **`record` с `with`** удобно делает копию снимка. В Go копию структуры даёт присваивание, но map и срезы внутри копируются по ссылке — их клонируют явно: `maps.Clone`, `slices.Clone`.

## Ловушки

### Неглубокая копия снимка

```go
func (h *Holder) Set(key string, v int) {
	old := h.cur.Load()
	next := *old              // копия структуры...
	next.Limits[key] = v      // ...но map та же: читатели видят запись
	h.cur.Store(&next)
}
```

Копирование структуры не копирует map, срезы и то, на что указывают указатели. Запись идёт в опубликованную map, которую в этот момент читают другие горутины, — гонка данных, а при одновременной записи в map ещё и `fatal error: concurrent map writes`. Клонируйте всё, что меняете: `next.Limits = maps.Clone(old.Limits)`.

### Load + Store вместо CAS

```go
old := h.cur.Load()
next := bump(old)
h.cur.Store(next) // другой писатель мог опубликовать своё между Load и Store
```

Каждая операция атомарна, а их сочетание — нет: два писателя прочитают один и тот же `old`, и обновление первого пропадёт. С несколькими писателями нужен `CompareAndSwap` в цикле — или мьютекс только для писателей (читатели по-прежнему делают `Load` без блокировок).

### Побочные эффекты внутри CAS-цикла

```go
for {
	old := p.Load()
	next := clone(old)
	next.Items = append(next.Items, item)
	log.Printf("добавлен %v", item) // при повторе напечатается дважды
	if p.CompareAndSwap(old, next) {
		break
	}
}
```

Тело цикла выполняется столько раз, сколько попыток понадобилось. Всё, что должно случиться ровно один раз, — после успешного CAS.

## Задание

Напишите хранилище конфигурации copy-on-write на `atomic.Pointer`.

```go
var ErrNilConfig = errors.New("update returned nil config")

type Config struct {
	Version int
	Limits  map[string]int
}

func (c *Config) Clone() *Config

type Holder struct {
	cur atomic.Pointer[Config]
}

func NewHolder(initial *Config) *Holder
func (h *Holder) Load() *Config
func (h *Holder) Update(f func(old *Config) (*Config, error)) (*Config, error)
func (h *Holder) Set(key string, value int) *Config
```

Требования:

- `Clone` возвращает глубокую копию: новую структуру с тем же `Version` и новой map с теми же парами. Если у исходной конфигурации map нет (`nil`), у копии — пустая map, не `nil`. Вызов `Clone` у `nil`-указателя тесты не проверяют;
- `NewHolder` публикует **копию** `initial` (изменения исходного объекта и его map после вызова не видны через `Load`); `nil` — пустая конфигурация: `Version` 0, пустые `Limits`. Holder создаётся только через `NewHolder`;
- `Load` никогда не возвращает `nil` и не блокируется. Опубликованный снимок никто не изменяет — ни `Holder`, ни пользователи; `f` тоже не меняет `old`;
- `Update(f)` вызывает `f` с текущим снимком (не `nil`) и публикует то, что она вернула:
  - если `f` вернула ошибку — ничего не публикуется, `Update` возвращает `nil` и эту ошибку как есть;
  - если `f` вернула `nil` без ошибки — ничего не публикуется, возвращаются `nil, ErrNilConfig`;
  - если `f` вернула сам `old` — ничего не публикуется, возвращаются `old, nil`;
  - иначе (в том числе если у нового снимка `Limits == nil` — он публикуется как есть, читать из `nil` map можно) `Version` нового снимка устанавливается в `old.Version + 1` (что бы ни записала туда `f`), снимок публикуется, только если текущим всё ещё остаётся `old`, и возвращается `next, nil`. Если за это время опубликовали другой снимок, `f` вызывается снова со свежим снимком — столько раз, сколько нужно; ни одно обновление не теряется;
- `f` возвращает новый, ещё нигде не опубликованный объект (или `old`); она может быть вызвана несколько раз;
- `Set(key, value)` публикует новый снимок — копию текущего с `Limits[key] = value` и версией на 1 больше — и возвращает его, даже если значение не изменилось;
- все методы безопасны для одновременного вызова; тесты запускаются с `-race` и проверяют, что читатели не видят частично обновлённых снимков.
