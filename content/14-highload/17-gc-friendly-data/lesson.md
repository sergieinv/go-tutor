Сборщик мусора Go без поколений: каждый цикл он заново размечает всю живую кучу (урок `13-runtime/04-gc`). Стоимость цикла растёт не столько с объёмом памяти, сколько с числом **указателей**, по которым надо пройти. И здесь у Go есть сильный рычаг: объект, в типе которого нет указателей, аллокатор кладёт в отдельные **noscan**-спаны, а маркировка такой объект не читает вовсе — помечает живым и идёт дальше (`greyobject` в `runtime/mgcmark.go`: «fast-track it to black instead of greying it»; в Green Tea GC — то же в `mgcmark_greenteagc.go`). Гигабайтный `[]int64` стоит GC столько же, сколько один маленький объект; `[]*Order` на миллион элементов — миллион указателей и миллион объектов на каждом цикле.

Увидеть это можно метрикой `/gc/scan/heap:bytes` из `runtime/metrics` — сколько байт кучи придётся сканировать. Пример урока сравнивает её рост для `[]int64` и `[]*int64` (числа зависят от машины, поэтому печатаются сравнения): у первого почти ноль, у второго — все 8 МБ массива указателей. Где указатели прячутся: указатели и интерфейсы, `string` (указатель на байты), срезы, map, каналы, функции, `time.Time` (поле `loc`). Где их нет: числа, `bool`, массивы и структуры из них.

**Приёмы:**

- **Значения вместо указателей.** `map[int64]Item` вместо `map[int64]*Item`, `[]Item` вместо `[]*Item` (урок `14-highload/16-struct-layout`). Если ключи и значения map без указателей, её группы тоже noscan: в примере map на 256 Ки записей значений-структур сканируется в сотни раз меньше, чем такая же map указателей.
- **Индексы вместо указателей.** Дерево, граф, список — узлы в одном срезе, связи — `int32`-индексы. Бонус: вдвое меньше места на связь, локальность (урок `14-highload/15-cpu-caches`) и простое копирование/сериализация. Цена — ручное управление «свободными» слотами при удалении (список свободных индексов).
- **Арена `[]byte` со смещениями** — для больших кешей строк и blob'ов: все значения подряд в одном большом `[]byte`, индекс «хеш ключа → смещение» — тоже без указателей. В bigcache каждый шард — очередь байтов и `map[uint64]uint64` (map без указателей GC не сканирует). freecache обходится вовсе без Go-map: 256 сегментов, в каждом кольцевой буфер `RingBuf` и срез `slotsData []entryPtr`, упорядоченный по 16-битному хешу ключа, — запись ищут бинарным поиском. Ни одного указателя на запись. Цена — своя сериализация, обработка коллизий хеша (ключ хранят в арене рядом со значением и сравнивают) и вытеснение (кольцевая арена с перезаписью старого).
- **Интернирование строк** — пакет `unique` (Go 1.23): `unique.Make(s)` возвращает `unique.Handle[string]`, равный для равных строк. Миллион записей с городом «Москва» хранят один указатель на одну копию вместо миллиона копий, а сравнение двух `Handle` — сравнение указателей. Канонические копии держатся слабо (`weak.Pointer` в `unique/canonmap.go`) и собираются, когда на них нет `Handle`. `Handle` всё же указатель; если нужно совсем без указателей — свой словарь «строка → `uint32`».

**Структура под нагрузку.** Выбор контейнера — это и скорость, и память, и работа GC:

- **map** на Swiss tables (с Go 1.24): группы по 8 слотов с контрольными байтами, таблицы до 1024 слотов и каталог (урок `13-runtime/06-slice-map-string`). Заранее задайте размер — `make(map[K]V, n)` избавляет от серии ростов с перекладыванием. Удаление не возвращает память: слоты становятся пустыми или «надгробиями», `clear` тоже не уменьшает таблицы. Map, из которой ушло почти всё, пересоздают — перекладывают живые записи в новую.
- **Отсортированный срез + `slices.BinarySearch`** — для данных «собрали один раз, читаем часто» (справочник, таблица тарифов): плотно, без указателей при числовых ключах, `O(log n)` с хорошей локальностью, диапазонные запросы бесплатно. Вставка — `O(n)`, поэтому для частых изменений не годится.
- **Кольцевой буфер** — последние N событий, окно метрик, очередь фиксированного размера: один срез, ноль выделений в работе (задание урока `14-highload/15-cpu-caches`).
- **Bitset** — `[]uint64` и операции `|=`, `&^=`, `math/bits.OnesCount64`: множество небольших целых (id флагов, занятые слоты) в 64 раза плотнее `[]bool` и на два порядка плотнее `map[int]bool`.
- **`container/heap`** — очередь с приоритетом поверх вашего среза (таймеры, top-K, планировщик). Элементы-значения в срезе, а не указатели, — и куча тоже не нагружает GC.
- **Фильтр Блума** — «точно нет / возможно да» для множества, которое не помещается в память целиком: m бит и k хешей, ~9,6 бита на ключ при 1% ложных срабатываний независимо от длины ключа. Перед походом в БД или Valkey за ключом, которого, скорее всего, нет (отрицательное кеширование, проверка «логин занят»), фильтр отсекает большинство пустых запросов. Ложных отказов не бывает, удалять нельзя (для этого есть counting Bloom и cuckoo filter).

Всё это — инструменты для горячих структур, которые держат миллионы элементов. Для сотни объектов указатели не стоят ничего; сначала профиль (`13-runtime/12-pprof-trace`) и метрики GC, потом раскладка.

## Как это в C#

- **Тот же принцип, другой GC.** Массив структур без ссылок CLR тоже не просматривает, а массив классов — миллион ссылок. Но поколения CLR прячут цену: старые объекты живут во втором поколении и редко сканируются целиком. В Go поколений нет — каждый цикл проходит всю кучу с указателями, поэтому раскладка без указателей окупается сильнее.
- **`string.Intern` ↔ `unique.Make`.** Пул `string.Intern` живёт до конца процесса, интернированные строки не собираются; канонические копии `unique` слабые и уходят вместе с последним `Handle`. И `unique.Make` работает с любым сравнимым типом, не только со строками.
- **Готовые контейнеры:** `BitArray` ↔ bitset на `[]uint64`, `PriorityQueue<TElement, TPriority>` ↔ `container/heap` (в Go — интерфейс над вашим срезом, а не готовая коллекция), `Array.BinarySearch` ↔ `slices.BinarySearch`, `Queue<T>` ↔ кольцо на срезе. Фильтра Блума нет ни там, ни там — его пишут или берут библиотекой.
- **`ArrayPool<T>` и `MemoryCache`.** Большие кеши в .NET часто держат объектами в `MemoryCache`, и GC второго поколения это терпит; в Go кеш на миллионы объектов с указателями заметно увеличивает работу каждого цикла GC — отсюда арены и библиотеки вроде bigcache.

## Ловушки

### `map[string]*T` на миллионы записей

```go
cache := map[string]*Session{} // ключ-строка и значение-указатель: два указателя на запись
```

Каждая запись — указатель на байты ключа и указатель на объект, и GC проходит по обоим на каждом цикле, плюс миллион отдельных объектов `Session`. Варианты: ключ — `uint64`-хеш или числовой id, значение — структура без указателей прямо в map, строки — в арене со смещениями. Проверяйте метрикой `/gc/scan/heap:bytes` и профилем CPU GC (`runtime.gcBgMarkWorker` в `pprof`), а не на глаз.

### Срез, который держит большой массив

```go
func header(b []byte) []byte { return b[:16] } // держит весь 10-МБ буфер
```

Подсрез ссылается на исходный массив, и GC не освободит 10 МБ, пока жив 16-байтный кусок. То же со строкой-подстрокой большого ответа. Если кусок живёт долго, скопируйте: `bytes.Clone(b[:16])`, `strings.Clone(s[:n])`.

### Map, которая только растёт

```go
for id := range expired {
	delete(sessions, id) // память таблиц останется
}
```

После пика нагрузки map хранит таблицы под пиковый размер — и всё это сканируется, если в записях есть указатели. Периодически пересоздавайте: `fresh := make(map[K]V, len(old)); maps.Copy(fresh, old)`, или храните данные в структурах, которые отдают память (срез, который можно укоротить и пересоздать).

## Задание

Напишите фильтр Блума на `[]uint64`, без выделений памяти на `Add` и `MayContain`.

```go
func NewBloom(n int, p float64) *Bloom
func (b *Bloom) Bits() int
func (b *Bloom) K() int
func (b *Bloom) Add(key string)
func (b *Bloom) MayContain(key string) bool
```

- `NewBloom(n, p)`: если `n < 1` — считать `n = 1`; если `p` не в интервале (0, 1) (в том числе NaN) — считать `p = 0.01`. Число бит `m = ⌈−n·ln p / (ln 2)²⌉` (в Go: `math.Ceil(-float64(n) * math.Log(p) / (math.Ln2 * math.Ln2))`), число хешей `k = round(m/n · ln 2)` (`math.Round`), но не меньше 1. `Bits()` возвращает `m`, `K()` — `k`. Поведение при огромных `n`, когда `m` бит не помещаются в память, тесты не проверяют.
- Хеш ключа: FNV-1a 64 по байтам строки (начальное значение `14695981039346656037`, для каждого байта `h ^= byte; h *= 1099511628211`), затем финализатор: `h ^= h >> 33; h *= 0xff51afd7ed558ccd; h ^= h >> 33; h *= 0xc4ceb9fe1a85ec53; h ^= h >> 33`. Из результата `h1` — младшие 32 бита, `h2` — старшие 32 бита (оба как `uint64`).
- Ключу соответствуют биты с номерами `(h1 + i·h2) mod m` для `i = 0 … k−1` (вычисления в `uint64`). `Add` выставляет их все. `MayContain` возвращает `true`, если выставлены все, иначе `false`. Бит номер `j` — бит `j % 64` слова `j / 64`.
- Ложных отказов нет: после `Add(key)` `MayContain(key)` всегда `true`, в том числе для пустой строки и при переполнении фильтра. Ответы `MayContain` должны в точности совпадать с этим описанием.
- `Add` и `MayContain` не выделяют память (`testing.AllocsPerRun` = 0).
