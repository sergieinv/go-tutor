Инструменты профилирования мы разобрали в модуле про рантайм: `runtime/pprof`, `go tool pprof`, трасса и метки. Здесь вопрос другой: **как найти узкое место сервиса, который тормозит под нагрузкой**. Профиль программы в тишине почти бесполезен — в тишине нет очередей, конкуренции за блокировки и пауз GC. Поэтому профиль снимают *во время* нагрузочного теста из прошлого урока, на той же ступени нагрузки, где p99 начал расти, или прямо с продакшна.

**Откуда брать профили.** С живого сервиса — через `net/http/pprof` на **служебном** порту: отдельный `http.Server` со своим `ServeMux`, слушающий `127.0.0.1` или внутреннюю сеть, а снаружи — только через проброс порта (`kubectl port-forward`). Публичный сервер обработчиков `/debug/pprof/` иметь не должен: профили раскрывают устройство кода, а запрос CPU-профиля нагружает процесс (урок о DoS). Пример поднимает оба сервера и проверяет, что публичный отвечает на `/debug/pprof/` кодом 404. Дальше:

- `go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30` — CPU за 30 секунд нагрузки;
- `.../debug/pprof/heap` (с `?gc=1` — после сборки), `.../allocs`, `.../goroutine?debug=1`, `.../mutex`, `.../block`;
- `.../debug/pprof/trace?seconds=5` — трасса для `go tool trace`.

Для постоянного наблюдения есть continuous profiling (Pyroscope, Parca, облачные профилировщики): агент снимает профиль раз в минуту, и можно сравнить «до релиза» и «после». Профиль с продакшна заодно годится для PGO (урок про inlining и PGO).

**Какой профиль на какой симптом.** Узкие места сервиса бывают трёх видов, и у каждого свой след:

| Симптом | Что смотреть | Типичная находка |
| --- | --- | --- |
| CPU под 100%, задержки растут вместе с нагрузкой | CPU-профиль: `top`, flame graph | сериализация JSON, регулярные выражения, хеширование, логирование, GC (`runtime.gcBgMarkWorker`, `mallocgc`) |
| CPU свободен, а запросы стоят в очереди | **mutex** и **block**-профили | работа под общим мьютексом, канал без буфера как узкое горлышко, `WaitGroup` на медленной горутине |
| CPU свободен, блокировок нет, а задержки большие | профиль **горутин**, трасса | синхронный вызов медленного соседа или базы: тысячи горутин стоят в `net/http.(*persistConn).roundTrip` или в ожидании соединения пула |
| GC в CPU-профиле заметен, p99 скачет | `allocs` (`-sample_index=alloc_space`), `runtime/metrics` | лишние аллокации в горячем обработчике (следующий урок) |

Главная ловушка — **CPU-профиль показывает только работу на CPU**. Горутина, которая ждёт мьютекс, канал или ответ сети, в нём не видна вообще. Сервис, который тормозит из-за блокировки, даёт «чистый» CPU-профиль, и это само по себе подсказка: ищите ожидание.

**Mutex и block.** Оба профиля по умолчанию выключены: `runtime.SetMutexProfileFraction(n)` записывает в среднем одно из `n` событий конкуренции, `runtime.SetBlockProfileRate(rate)` — одно событие на `rate` наносекунд ожидания. В продакшне берут выборку (например, `SetMutexProfileFraction(100)`), накладные расходы при этом малы. Mutex-профиль приписывает ожидание **тому, кто держал** блокировку: стек — место `Unlock`, вес — сколько из-за этого ждали другие. Поэтому в примере сверху оказывается `sync.(*Mutex).Unlock` из `(*service).handle`: команда `list handle` покажет строку критической секции. Block-профиль, наоборот, показывает **ждущих**: где горутины стояли на `Lock`, каналах, `select`, `Cond`, `WaitGroup`. Сетевое ожидание и системные вызовы в block-профиль не попадают — для них профиль горутин и трасса.

**Метки по эндпоинтам.** Под нагрузкой через сервис идёт смесь запросов. Middleware с `pprof.Do(r.Context(), pprof.Labels("handler", name), ...)` помечает сэмплы обработчика, и `go tool pprof -tagfocus=handler=orders` оставляет только его. В примере так помечен обработчик заказов.

**Трасса под нагрузкой.** `go tool trace` показывает то, чего нет в профилях: задержки планировщика (горутина готова, но ждёт P), паузы и mark assist GC, блокировки во времени, системные вызовы. Пишут её секунды, а не минуты: файл растёт быстро. Самое ценное — трасса **того самого** медленного запроса, и для этого есть `trace.FlightRecorder` (Go 1.25): трасса пишется постоянно в кольцевой буфер в памяти, а `WriteTo` сохраняет последние секунды, когда сервис заметил проблему — медленный запрос, всплеск ошибок, таймаут. Ограничения: активен один `FlightRecorder` на процесс, а `WriteTo` одновременно может выполняться только один — второй вызов сразу получает ошибку. Поэтому триггер снимка должен быть «не чаще чем раз в N секунд и не больше одного одновременно» — это задание урока.

**Порядок расследования.** Нагрузка на ступени, где растёт p99 → метрики рантайма (`/sched/latencies:seconds` — ожидание планировщика, `/sync/mutex/wait/total:seconds` — суммарное ожидание мьютексов, `/gc/...`) → CPU-профиль; если CPU не загружен — mutex/block и горутины → гипотеза → исправление → тот же прогон нагрузки и `-diff_base` профилей «до» и «после». Пример делает упрощённую версию: гоняет нагрузку, исправляет работу под блокировкой (тяжёлое — вне мьютекса, под ним — только обновление общего состояния) и гоняет ту же нагрузку снова; оба прогона попадают в один CPU-профиль, а mutex-профиль показывает, кто держал блокировку.

## Как это в C#

- **Инструменты.** `dotnet-counters` ≈ `runtime/metrics` и Prometheus-метрики рантайма; `dotnet-trace collect` ≈ CPU-профиль и трасса; `dotnet-gcdump` ≈ heap-профиль. В Go всё это — один формат профилей и один `go tool pprof`, а снимать можно прямо из процесса по HTTP.
- **Сайдкар против обработчиков в процессе.** `dotnet-monitor` — отдельный процесс с HTTP API и триггерами (собрать трассу, когда CPU выше порога). В Go обработчики `net/http/pprof` живут в самом сервисе, поэтому вопрос безопасности — какой адрес он слушает — решаете вы. Триггер «сохранить трассу при медленном запросе» пишется в коде вокруг `FlightRecorder`, и, в отличие от триггера `dotnet-monitor`, он сохраняет то, что было **до** события.
- **Конкуренция за блокировки.** В .NET её видно по счётчику `monitor-lock-contention-count` (в метриках `System.Runtime` .NET 9+ — `dotnet.monitor.lock_contentions`) и событиям contention в трассе; в Go — mutex-профиль со стеком того, кто держал блокировку, и вес в наносекундах ожидания.
- **Ожидание вместо CPU.** В .NET поток пула, заблокированный синхронным вызовом, — это ещё и голодание пула потоков (`threadpool-queue-length`, в .NET 9+ — `dotnet.thread_pool.queue.length`, растёт). В Go заблокированная горутина почти ничего не стоит, голодания нет, но запросы всё равно ждут: искать их надо в профиле горутин, а не по загрузке пула.

## Ловушки

### Профиль без нагрузки

```go
// локально, один запрос curl'ом
go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30
```

Тридцать секунд простоя — пустой профиль, и вывод «узких мест нет». Узкие места проявляются только под нагрузкой: блокировки не конкурируют, очереди пусты, GC не торопится. Снимайте профиль, пока идёт нагрузочный тест на интересующей ступени.

### Искать ожидание в CPU-профиле

```go
mu.Lock()
resp, err := inventory.Reserve(ctx, req) // сетевой вызов под мьютексом
mu.Unlock()
```

Задержки огромные, а в CPU-профиле — тишина: горутины ждут сеть и мьютекс, не тратя CPU. Включите `SetMutexProfileFraction` и `SetBlockProfileRate` и посмотрите профиль горутин: сотни горутин в `sync.(*Mutex).Lock` и одна в `roundTrip` сразу покажут ошибку. Сетевые вызовы под общей блокировкой — один из самых частых источников «необъяснимых» задержек.

### Снимок трассы на каждый медленный запрос

```go
if elapsed > time.Second {
	f, _ := os.Create(fmt.Sprintf("slow-%d.trace", time.Now().UnixNano()))
	fr.WriteTo(f) // при деградации — сотни снимков в секунду
	f.Close()
}
```

Когда сервис деградирует, медленным становится каждый запрос: снимки забьют диск и добавят нагрузки, а одновременные `WriteTo` получат ошибку. Ограничивайте частоту (не чаще раза в минуту) и число одновременных снимков (один), считайте снимки метрикой.

## Задание

Напишите middleware, которое сохраняет снимок трассы (например, `FlightRecorder.WriteTo` в файл), когда запрос оказался медленным, — с ограничением частоты и без одновременных снимков.

```go
type Capture struct {
	Threshold time.Duration
	Cooldown  time.Duration
	Now       func() time.Time
	Snapshot  func(reason string) error
	// неэкспортируемые поля — на ваше усмотрение
}

func (c *Capture) Middleware(next http.Handler) http.Handler
func (c *Capture) Captured() int64
```

- `Middleware` вызывает `next.ServeHTTP(w, r)` с теми же `w` и `r` и ответ не меняет. Время запроса — разница двух вызовов `Now()`: перед `next.ServeHTTP` и после него (`Now == nil` — `time.Now`). Других вызовов `Now` нет, и эти два делаются всегда — в том числе при `Threshold <= 0` и `Snapshot == nil`.
- Запрос медленный, если `Threshold > 0` и его время не меньше `Threshold`. При `Threshold <= 0` снимков не бывает.
- После медленного запроса, в той же горутине, до возврата из обработчика, делается **попытка** снимка — вызов `Snapshot(reason)`, где `reason` — `fmt.Sprintf("%s %s %v", r.Method, r.URL.Path, elapsed)`, например `"GET /orders/7 2s"`. Попытка разрешена, только если одновременно не выполняется другой вызов `Snapshot` (иначе снимок пропускается сразу, без ожидания) и если это первая попытка или с момента предыдущей прошло не меньше `Cooldown` (`Cooldown <= 0` — без ограничения частоты). Момент попытки — второе показание `Now()` запроса, который её сделал. Пропущенный снимок (занят другим вызовом или не прошёл `Cooldown`) попыткой не считается и отсчёт `Cooldown` не сдвигает.
- Попытка считается и для `Cooldown`, и для запрета одновременных снимков, даже если `Snapshot` вернул ошибку. `Captured()` возвращает число вызовов `Snapshot`, вернувших `nil`. `Snapshot == nil` — снимков нет, `Captured() == 0`.
- Методы безопасны для одновременного вызова из многих горутин; `Capture` используется по указателю и после первого запроса не меняется снаружи. `Snapshot` не вызывает методы `Capture`.
