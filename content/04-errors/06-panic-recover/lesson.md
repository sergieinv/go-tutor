`panic` останавливает обычное выполнение функции и начинает раскрутку стека: рантайм по очереди выполняет отложенные вызовы каждого кадра, от вершины к `main`. Если ни один из них не вызвал `recover`, программа печатает значение паники со стектрейсом и завершается с кодом 2.

Паника похожа на исключение, но роль у неё другая. Ожидаемые сбои — сеть, файлы, ввод пользователя — возвращают как `error`. `panic` — для программных ошибок: выход за границы среза, `nil`-map, нарушенный инвариант, невозможное значение. А `recover` нужен на границах — там, где одна упавшая задача не должна уронить весь процесс.

## Как это в C#

- `throw` в C# — обычный способ сообщить о любой ошибке. `panic` в Go — только для багов; использовать его как `throw` для управления потоком — плохой стиль, и библиотека не должна выпускать панику наружу.
- `catch` можно поставить где угодно. `recover` работает только внутри отложенной функции: «блок catch» в Go — это `defer func() { if r := recover(); r != nil { ... } }()`.
- После `catch` выполнение продолжается за блоком `try`. После `recover` функция, где он сработал, не продолжает с места паники, а завершается — и возвращает то, что лежит в именованных результатах.
- Необработанное исключение внутри `Task` остаётся в задаче, пока её не дождутся. Паника в горутине, которую никто не перехватил, роняет весь процесс — как исключение в `Thread` или `async void` в .NET — и перехватить её можно только в той же горутине.

## Под капотом

У каждой горутины свой стек кадров, у каждого кадра — свой список отложенных вызовов. При панике рантайм идёт по кадрам сверху вниз и выполняет их отложенные вызовы в порядке LIFO. Если один из них напрямую вызывает `recover`, паника останавливается: оставшиеся отложенные вызовы этого кадра выполняются как при обычном `return`, а функция возвращает значения своих именованных результатов. Кадры выше неё уже сняты со стека и никогда не продолжатся.

## Ловушки

### Паника в другой горутине

```go
func handler() (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("panic: %v", r)
		}
	}()
	go func() {
		panic("boom") // этот recover её не увидит — процесс упадёт
	}()
	return nil
}
```

`recover` перехватывает только панику своей горутины. Каждая горутина, которая может запаниковать, должна сама ставить `defer` с `recover` и передавать ошибку наружу — через канал или `errgroup`.

### `recover` не в той функции

```go
func logPanic() {
	if r := recover(); r != nil { // вернёт nil: вызван не прямо из defer
		log.Println(r)
	}
}

defer func() { logPanic() }() // не сработает
defer logPanic()              // сработает: logPanic — сама отложенная функция
```

`recover` останавливает панику, только если его вызвала непосредственно отложенная функция. Вызов «через помощника» или вне паники возвращает `nil`.

### Проглоченная паника

```go
defer func() {
	recover() // любая паника молча превращается в «всё хорошо»
}()
```

Без именованного результата функция после `recover` вернёт нулевые значения, и вызывающий не узнает, что был сбой. Превращайте панику в ошибку, логируйте её со стеком (`debug.Stack()`), а неизвестные паники пробрасывайте дальше: `panic(r)`.

## Задание

Напишите функцию `SafeCall(f func() int) (result int, err error)`, которая вызывает `f` и превращает панику в ошибку.

Требования:

- `f` завершилась нормально — вернуть её результат и `nil`;
- `f` запаниковала значением-ошибкой `v` — вернуть `0` и ошибку с текстом `panic: <v.Error()>`, для которой `errors.Is(err, v)` истинно;
- `f` запаниковала значением другого типа — вернуть `0` и ошибку с текстом `panic: <v>` (формат `%v`);
- `panic(nil)` — тоже паника: с Go 1.21 `recover` возвращает для неё `*runtime.PanicNilError`, это значение-ошибка, и обрабатывать его нужно так же;
- если значение паники — ошибка, для которой `errors.Is(v, ErrFatal)`, `SafeCall` её не обрабатывает, а паникует снова тем же значением.
