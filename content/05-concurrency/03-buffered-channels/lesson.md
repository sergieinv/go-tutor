`make(chan T, n)` создаёт канал с буфером на `n` значений. Отправка кладёт значение в буфер и блокируется, только когда он полон. Получение забирает из буфера и блокируется, только когда он пуст. Отправителю и получателю больше не нужно встречаться: производитель может уйти вперёд на `n` значений.

Буфер решает две практические задачи. Это очередь, которая сглаживает разницу в скорости производителя и потребителя. И это семафор: канал на `n` пустых структур пропускает не больше `n` горутин одновременно.

## Как это в C#

- `Channel.CreateBounded<T>(n)` с режимом `BoundedChannelFullMode.Wait` — прямой аналог `make(chan T, n)`: запись ждёт, пока появится место. Других режимов переполнения (выбросить старое, новое) у каналов Go нет — их пишут через `select` с `default`.
- `Channel.CreateUnbounded<T>()` в Go аналога не имеет: буфер всегда конечен и задаётся при создании. Это сознательно — бесконечная очередь лишь откладывает проблему медленного потребителя до нехватки памяти.
- `SemaphoreSlim(n)` → `make(chan struct{}, n)`: `WaitAsync()` — отправка, `Release()` — получение. Отдельного типа семафора в стандартной библиотеке нет, есть `golang.org/x/sync/semaphore` с весами.
- `reader.Count` → `len(ch)`, ёмкость → `cap(ch)`. Как и в C#, это моментальный снимок: к следующей строке он может устареть.

## Ловушки

### «Добавлю буфер — и deadlock уйдёт»

```go
results := make(chan int, 10) // было make(chan int) и висло
for _, x := range input {
	results <- process(x) // а теперь виснет на 11-м элементе
}
for range input {
	fmt.Println(<-results)
}
```

Если отправитель и получатель — одна горутина, буфер лишь откладывает блокировку до момента, когда он заполнится. На тестовых данных из пяти элементов всё работает, в продакшене на тысяче — висит. Буфер не меняет логику синхронизации: если без него программа зависает, исправляйте структуру (отдельная горутина-производитель), а не ёмкость. Подбирать размер буфера стоит только для производительности, а не для корректности.

### Буферизованная отправка не значит «получено»

На небуферизованном канале завершившаяся отправка гарантирует, что получатель забрал значение. На буферизованном — только что значение легло в буфер. Если отправитель после этого завершится (а с ним и `main`), значение может так и не дойти до получателя. Для подтверждения нужен отдельный ответный сигнал или `sync.WaitGroup`.

### Решение по `len(ch)`

```go
if len(ch) < cap(ch) {
	ch <- v // может заблокироваться: место успел занять другой
}
```

Между проверкой и отправкой другая горутина может заполнить буфер. `len` годится для метрик и отладки, а не для логики. Неблокирующая отправка делается через `select` с `default`.

## Задание

Напишите функцию `RunLimited(tasks []func(), limit int)`, которая выполняет все задачи конкурентно, но так, чтобы одновременно работало не больше `limit` штук.

Требования:

- каждая задача вызывается ровно один раз;
- в любой момент выполняется не больше `limit` задач;
- если задач не меньше `limit`, ограничение должно использоваться полностью: задача может ждать, пока одновременно не запустятся `limit` задач, — и не должна ждать вечно; если задач меньше `limit`, все они выполняются одновременно;
- `limit < 1` считается равным 1;
- функция возвращается только после завершения всех задач; для пустого или `nil` списка — сразу;
- код без гонок данных: тесты запускаются с `-race`.
