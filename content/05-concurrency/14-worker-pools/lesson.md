Горутина дешёвая, но ресурс за ней — нет: соединения с базой, файловые дескрипторы, лимиты чужого API. Поэтому «горутина на задачу» без ограничений годится только для небольших объёмов. Пул воркеров — это N горутин, которые читают задачи из общего канала и пишут ответы в канал результатов. Параллелизм равен N, сколько бы задач ни пришло.

В схеме три правила закрытия: канал задач закрывает отправитель, когда задачи кончились; воркеры выходят из `range`, когда канал задач закрыт и пуст; канал результатов закрывает отдельная горутина после `wg.Wait()` — только она знает, что писателей больше нет. Второй способ ограничить параллелизм — семафор: буферизованный канал `chan struct{}` на N мест, который горутина занимает перед работой и освобождает после.

## Как это в C#

- `Parallel.ForEachAsync(items, new ParallelOptions { MaxDegreeOfParallelism = 3 }, ...)` — готовый пул с лимитом. В Go такой функции в стандартной библиотеке нет: пул собирают из канала, горутин и `WaitGroup` (или берут `errgroup` с `SetLimit` — об этом урок 19).
- `SemaphoreSlim(3)` с `WaitAsync`/`Release` — это `sem <- struct{}{}` и `<-sem` у буферизованного канала ёмкостью 3.
- `Task.WhenAll` возвращает результаты в порядке входа, а `Parallel.ForEach` результатов не возвращает вовсе — их пишут в массив по индексу. Канал результатов порядка не хранит — воркеры заканчивают когда угодно, поэтому результат несёт индекс задачи.
- Пул потоков .NET сам решает, сколько потоков держать. В Go планировщик раздаёт горутины по `GOMAXPROCS` потокам, а сколько горутин запустить — решаете вы.

## Ловушки

### Закрыть `results` из воркера

```go
for range workers {
	go func() {
		for j := range jobs {
			results <- work(j)
		}
		close(results) // первый закончивший воркер закроет канал под остальными
	}()
}
```

Остальные воркеры запаникуют на `send on closed channel`. Закрывать канал должен единственный владелец — горутина, которая дождалась `wg.Wait()`.

### `wg.Wait()` в той же горутине, что читает результаты

```go
wg.Wait()      // воркеры ждут, пока кто-нибудь прочтёт results,
close(results) // а читатель ещё не дошёл до цикла — deadlock
for r := range results { ... }
```

Небуферизованный `results` блокирует воркеров, пока его не читают. Ожидание и закрытие выносят в отдельную горутину, а читают в основной.

### Запись в общий срез через `append`

```go
var out []string
for r := range results { out = append(out, r) } // в одной горутине — нормально
// а вот append из нескольких воркеров сразу — гонка данных
```

Писать из воркеров в общий срез можно только в разные, заранее выделенные элементы: `out := make([]R, n)` и `out[i] = ...`. `append` из нескольких горутин меняет общий заголовок среза — `-race` это поймает.

## Задание

Напишите обобщённую функцию `Map[T, R any](in []T, workers int, f func(T) R) []R`, которая применяет `f` к каждому элементу `in` с помощью пула воркеров.

Требования:

- результат — срез длины `len(in)`, где `out[i] == f(in[i])`: порядок совпадает с входом, как бы ни завершались воркеры;
- `f` вызывается ровно один раз для каждого элемента;
- одновременно выполняется не больше `workers` вызовов `f`; при `workers < 1` используйте одного воркера;
- вызовы действительно идут параллельно: если `workers >= 2` и элементов хватает, `workers` вызовов `f` выполняются одновременно;
- для пустого или `nil` среза `in` возвращается пустой срез, не `nil`, а `f` не вызывается;
- к моменту возврата `Map` все запущенные ею горутины завершились.
