Вместо того чтобы защищать общие данные мьютексом, можно отдать их одной горутине. Только она читает и меняет состояние, а все остальные отправляют ей запросы через каналы. Если нужен ответ, запрос несёт свой канал: владелец кладёт результат туда. Запросы обрабатываются строго по одному, поэтому гонок нет без единой блокировки — это и есть девиз Go «Don't communicate by sharing memory; share memory by communicating».

Подход не заменяет мьютекс везде. Для счётчика или кеша `sync.Mutex` короче и быстрее: каждый запрос к владельцу — две операции с каналом и переключение горутин. Владелец выигрывает, когда операция над состоянием — это цельная транзакция (перевод между счетами, проверка и изменение), когда состояние живёт вместе с другими событиями (таймеры, сеть в том же `select`) или когда владелец сам по себе — долгоживущий процесс с жизненным циклом.

## Как это в C#

- Ближайший аналог — модель акторов (Akka.NET, Orleans) или «почтовый ящик» на `Channel<T>`: одна задача читает сообщения в цикле `await foreach (var msg in reader.ReadAllAsync())` и владеет состоянием.
- Канал ответа в запросе — это `TaskCompletionSource<T>` внутри сообщения: отправитель делает `await tcs.Task`, актор вызывает `tcs.SetResult(...)`.
- `lock` в C# и `sync.Mutex` в Go решают ту же задачу проще. Правило из Go Wiki: мьютекс — для защиты состояния, каналы — для передачи владения данными и координации.
- В .NET актор обычно живёт на пуле потоков и не занимает поток, пока ждёт. Горутина-владелец тоже почти ничего не стоит: пара килобайт стека и спит, пока нет запросов.

## Ловушки

### Владелец отдаёт наружу ссылку на состояние

```go
case r := <-snapshots:
	r.resp <- state // map — ссылочный тип: снаружи читают её, пока владелец пишет
```

Карта, срез или указатель, отправленные из горутины-владельца, остаются общими. Отдавайте копию: `maps.Clone(state)`.

### Ответ некому принять

```go
resp := make(chan int)
c.reads <- readOp{key, resp}
select {
case v := <-resp:
	return v
case <-time.After(time.Second):
	return 0 // ушли — а владелец навсегда застрянет на r.resp <- v
}
```

Если отправитель может не дождаться ответа, канал ответа делают буферизованным на одно значение: `make(chan int, 1)`. Тогда владелец отдаст ответ и пойдёт дальше.

### Медленная работа внутри владельца

Пока владелец обрабатывает один запрос, все остальные ждут. Сетевой вызов или тяжёлое вычисление внутри цикла владельца превращает его в узкое место. Внутри — только быстрые операции над состоянием, а медленную работу делайте до или после запроса.

## Задание

Напишите банк, состоянием которого владеет одна горутина:

```go
var ErrInsufficientFunds = errors.New("insufficient funds")

func NewBank() *Bank
func (b *Bank) Deposit(account string, amount int)
func (b *Bank) Withdraw(account string, amount int) error
func (b *Bank) Transfer(from, to string, amount int) error
func (b *Bank) Balance(account string) int
func (b *Bank) Close()
```

Требования:

- `NewBank` запускает горутину-владельца, которая хранит балансы; методы общаются с ней через каналы;
- счёт, которого ещё не было, имеет баланс 0; `amount` всегда больше нуля;
- `Withdraw` списывает `amount`, если на счёте достаточно денег, иначе возвращает `ErrInsufficientFunds` и ничего не меняет;
- `Transfer` переводит деньги атомарно: либо списание с `from` и зачисление на `to` происходят вместе, либо (если денег не хватает) — `ErrInsufficientFunds` и ничего не меняется; ни один другой вызов не видит промежуточного состояния;
- каждый метод возвращается, когда операция уже применена: `Balance` после `Deposit` из той же горутины видит новые деньги;
- все методы безопасно вызывать из многих горутин одновременно;
- `Close` вызывается один раз, после всех остальных вызовов; он останавливает горутину-владельца и возвращается, когда она завершилась.
