`close(ch)` помечает канал как закрытый: новых значений не будет. Получение из закрытого канала не блокируется — сначала отдаются значения, оставшиеся в буфере, а затем бесконечно нулевое значение. Отличить одно от другого помогает форма `v, ok := <-ch`: `ok == false` значит «закрыт и пуст». Цикл `for v := range ch` читает до закрытия и сам выходит.

Закрывать канал не обязательно — его, как и любой объект, соберёт сборщик мусора. Закрывают, когда получателю нужно знать о конце потока: чтобы завершился `range`, или чтобы разом разбудить всех ждущих. Правило одно: **закрывает отправитель**, и ровно один раз.

## Как это в C#

- `writer.Complete()` → `close(ch)`. `await foreach (var v in reader.ReadAllAsync())` → `for v := range ch`. Состояние «закрыт и пуст» в C# — это `false` из `WaitToReadAsync()` (или завершённый `reader.Completion`), в Go — `ok == false`.
- Запись в завершённый `Channel<T>` бросает `ChannelClosedException`, которое можно поймать. В Go отправка в закрытый канал — паника, то есть ошибка программиста, а не штатная ситуация.
- `TryComplete()` в C# можно вызывать повторно. В Go повторный `close` паникует, проверить «закрыт ли канал» без получения из него нельзя. Значит, у закрытия должен быть один ясный владелец.
- Широковещательного сигнала на `Channel<T>` нет — для него берут `CancellationTokenSource.Cancel()` или `TaskCompletionSource`. В Go это просто закрытый канал: все `<-done` возвращаются разом.

## Ловушки

### Закрывать канал с несколькими отправителями

```go
for _, u := range urls {
	go func() {
		results <- fetch(u)
		close(results) // первый закрывший уронит остальных: send on closed channel
	}()
}
```

Когда отправителей несколько, ни один из них не знает, что он последний. Закрытие поручают отдельной горутине, которая дожидается всех: `go func() { wg.Wait(); close(results) }()`.

### `range` по каналу, который никто не закроет

```go
ch := make(chan int)
go func() {
	for i := range 3 {
		ch <- i
	}
	// забыли close(ch)
}()
for v := range ch { // после трёх значений ждёт вечно
	fmt.Println(v)
}
```

Цикл `range` заканчивается только закрытием. Если отправитель забыл `close`, получатель повиснет: в `main` — с ошибкой deadlock, в сервере — тихой утечкой горутины. Надёжнее всего закрывать через `defer close(ch)` первой строкой горутины-отправителя.

### Повторный `close` и `close(nil)`

```go
close(ch)
close(ch) // panic: close of closed channel

var nilCh chan int
close(nilCh) // panic: close of nil channel
```

Обе ошибки — паники, их не ловят, а исключают устройством кода. Если закрыть канал могут из нескольких мест, оберните `close` в `sync.Once`.

## Задание

Напишите функцию `Batch(in chan int, size int) chan []int`, которая группирует поток чисел в пачки.

Требования:

- `Batch` сразу возвращает выходной канал, а обработку ведёт в отдельной горутине — не дожидаясь закрытия `in`;
- значения из `in` идут в пачки подряд, в исходном порядке, по `size` штук; последняя пачка может быть короче; пустые пачки не отправляются;
- полная пачка отправляется, как только в ней набралось `size` значений, — не дожидаясь следующего значения или закрытия `in`;
- после того как `in` закрыт и все пачки отправлены, выходной канал закрывается;
- каждая пачка — отдельный срез, не разделяющий память с другими пачками: получатель вправе изменять полученный срез;
- `size < 1` считается равным 1;
- если `in` закрыт без единого значения, выходной канал закрывается без пачек;
- после закрытия выходного канала горутина `Batch` завершается.
