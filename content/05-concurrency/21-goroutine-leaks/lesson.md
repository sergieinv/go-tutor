Горутина живёт, пока не вернётся её функция. Остановить её снаружи нельзя, а сборщик мусора заблокированные горутины не трогает: горутина, которая ждёт канал без второй стороны, висит до конца процесса вместе со своим стеком и всем, на что ссылается. В утилите это незаметно, в сервере — медленный рост памяти и числа горутин, пока процесс не упадёт.

Почти все утечки — одна из четырёх ситуаций: **отправка, которую никто не прочтёт** (вызывающий ушёл по таймауту), **получение, которое никогда не случится** (`range` по каналу, который забыли закрыть), **цикл без условия выхода** (горутина-тикер, воркер без `ctx.Done()`) и **ожидание мьютекса или `WaitGroup`, которые никто не отпустит**. Правило против всех сразу: запуская горутину, сразу решите, *как и когда она закончится*.

## Как это в C#

- В .NET задача, которую никто не ждёт, обычно всё равно доработает и будет собрана. Даже задача, навсегда застрявшая на `await` канала, соберётся GC, когда на канал не останется ссылок. Горутина, заблокированная на канале, не доработает никогда — её не собирает GC и не снимает таймаут.
- `CancellationToken` передают в `await`-вызовы, и отмена прерывает ожидание. В Go отмену видно, только если горутина сама ждёт `<-ctx.Done()` в том же `select`, где ждёт канал.
- `Task.WhenAny` с `Task.Delay` не оставляет проигравшую задачу в подвешенном состоянии. Аналог в Go с небуферизованным каналом результата — утечка.
- Аналог `goleak` в .NET — разве что ручные проверки; в Go утечки горутин принято ловить в тестах.

## Под капотом

Утечку видно по числу горутин. В коде — `runtime.NumGoroutine()`: в тестах сравнивают с базой до операции, дав завершающимся горутинам немного времени. В работающем сервисе — профиль `goroutine` из `net/http/pprof` (`/debug/pprof/goroutine?debug=1`): он группирует горутины по стеку, и тысяча одинаковых стеков на `chan send` сразу показывает строку утечки. В тестах — библиотека `go.uber.org/goleak`: `defer goleak.VerifyNone(t)` или `goleak.VerifyTestMain(m)` проверяют, что после теста не осталось лишних горутин (в песочнице она недоступна).

Ниже — «сервер» с тремя утечками: `fetch` ждёт медленный бэкенд с таймаутом через небуферизованный канал, `logger` читает `range` по каналу, который никто не закрывает, `heartbeat` крутится в цикле без выхода. Визуализатор запускает программу с трассировкой и группирует горутины по стадиям — функции и строке `go`. На последнем шаге он перечисляет горутины, которые не завершились к выходу из `main`, и строки, где они ждут: три горутины `fetch` ждут отправки, `logger` и `heartbeat` — получения. Мини-график сверху показывает, что живых горутин к концу больше, чем в начале.

Почините утечки по комментариям в коде и запустите снова:

1. `make(chan string, 1)` в `fetch` — отправка пройдёт без получателя;
2. `close(lines)` после `wg.Wait()` — `range` в `logger` закончится;
3. `case <-done: return` в `heartbeat`, `defer t.Stop()` и `close(done)` в `main`.

После каждого исправления из итога пропадает одна стадия, после всех трёх он скажет «утечек нет». `time.Sleep` в конце `main` здесь изображает сервер, который продолжает работать: без него `main` вышла бы раньше, чем исправленные горутины успели завершиться.

## Ловушки

### Буфер на одно значение при нескольких отправителях

```go
ch := make(chan string, 1)
for _, url := range mirrors {
	go func() { ch <- get(url) }()
}
return <-ch // первый ответ забрали, второй лёг в буфер, остальные висят
```

Буфер спасает, только если его хватает на все отправки, которые никто не прочтёт: `make(chan string, len(mirrors))`. Или отправка через `select` с `<-ctx.Done()` и отмена при возврате.

### Детектор дедлока молчит

```go
go func() {
	for v := range ch { // ch никто не закроет
		process(v)
	}
}()
```

`fatal error: all goroutines are asleep - deadlock!` бывает, только когда заблокированы *все* горутины. Пока `main` или HTTP-сервер работают, застрявшая горутина ничем себя не выдаёт.

### Тикер без `Stop` и цикл без выхода

```go
go func() {
	t := time.NewTicker(time.Second)
	for range t.C { // ни Stop, ни выхода
		refresh()
	}
}()
```

С Go 1.23 тикер, на который больше нет ссылок, собирает сборщик мусора и без `Stop`. Но здесь ссылка есть — у самой горутины, а горутина не завершится никогда. Нужен `select` с `<-ctx.Done()` и `defer t.Stop()`.

## Задание

В шаблоне — готовый код трёх функций. Он проходит функциональные тесты, но оставляет висящие горутины: в каждой функции по одной утечке из разобранных выше. Найдите и почините их, не меняя сигнатуры и описанное поведение:

```go
func Lookup(ctx context.Context, keys []string, get func(string) string) (map[string]string, error)
func Total(nums []int, weight func(int) int) int
func Every(interval time.Duration, f func()) (stop func())
```

Поведение, которое должно сохраниться:

- `Lookup` вызывает `get` ровно один раз для каждого ключа, каждый вызов — в своей горутине, все одновременно, и возвращает map «ключ → ответ» и `nil`. Ключи не повторяются. Без ключей — пустая не-`nil` map и `nil`, `get` не вызывается. Если `ctx` отменён раньше, чем пришли все ответы, `Lookup` сразу возвращает `nil` и `ctx.Err()`, не дожидаясь `get` (`get` контекст не слушает);
- `Total` вызывает `weight` ровно один раз для каждого числа, все вызовы одновременно, и возвращает сумму результатов; для `nil` или пустого `nums` — `0`;
- `Every` возвращается сразу и вызывает `f` в отдельной горутине раз в `interval` (первый вызов — не раньше, чем через `interval`), пока не вызовут `stop`. После возврата `stop` функция `f` больше не вызывается и не выполняется. `stop` можно вызывать повторно — это безопасно; из `f` его не вызывают. `interval > 0`.

Что нужно добиться:

- горутины `Lookup` завершаются, как только вернулся их `get`, даже если `Lookup` к этому времени уже вернулась по отмене;
- после возврата `Total` её горутин не остаётся — в том числе для пустого `nums`;
- после возврата `stop` горутина `Every` завершена, а её тикер остановлен.

Тесты проверяют утечки по `runtime.NumGoroutine()`: после операции число горутин должно вернуться к исходному.
