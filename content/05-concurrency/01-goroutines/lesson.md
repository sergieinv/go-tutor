`go f(x)` запускает вызов `f(x)` в новой горутине и сразу возвращает управление. Горутина — это функция, которая выполняется конкурентно с остальной программой. Её планирует рантайм Go, а не ОС: тысячи горутин работают поверх нескольких потоков.

В Go нет `async`/`await` и «окрашенных» функций. Код пишется синхронно: чтение файла или ответ по сети блокирует горутину, а не поток, — рантайм в это время выполняет на потоке другие горутины. Решение, выполнять ли работу конкурентно, принимает вызывающий код оператором `go`, а не автор функции.

## Как это в C#

- `Task.Run(f)` ставит делегат в очередь пула потоков и возвращает `Task`, у которого можно ждать результат и исключение. `go f()` не возвращает ничего: ни результата, ни дескриптора, ни способа отменить. Результат передают через канал или общую память, отмену — через `context`.
- Поток в C# (`new Thread`) — это поток ОС со стеком порядка мегабайта. Горутина начинается с 2 КБ стека, который растёт и сжимается. Поэтому горутину не берегут, как поток: десятки тысяч одновременно — норма, отдельный пул для них не нужен.
- `async`-метод «заражает» вызывающих: им тоже приходится становиться `async`. В Go любая функция может блокироваться, а вызывающий сам решает, запускать её в горутине или нет.
- Исключение в `Task`, которую никто не ждёт, процесс не роняет (а вот необработанное исключение в `new Thread` или `async void` — роняет). Паника в горутине без `recover` роняет весь процесс, и перехватить её снаружи, из другой горутины, нельзя.

## Под капотом

Планировщик Go устроен по схеме GMP. **G** — горутина: стек, указатель команд, состояние. **M** — поток ОС. **P** — «процессор», право выполнять Go-код; P ровно `GOMAXPROCS` штук. Поток выполняет горутины, только пока держит P. У каждого P своя локальная очередь готовых горутин (до 256) и слот `runnext` — для той, что выполнится следующей. Ещё есть общая глобальная очередь.

`go f()` кладёт новую G в `runnext` своего P, а прежнюю оттуда — в хвост локальной очереди. Поток, у которого кончилась работа, проверяет свою очередь, затем глобальную, а затем крадёт половину очереди у другого P (work stealing). Если горутина ушла в блокирующий системный вызов, фоновый поток `sysmon` отбирает у её потока P и отдаёт другому потоку (handoff), — поэтому потоков ОС бывает больше, чем `GOMAXPROCS`. Горутину, которая занимает P дольше 10 мс, `sysmon` вытесняет сигналом — даже из цикла без вызовов функций (асинхронное вытеснение, Go 1.14+).

`GOMAXPROCS` по умолчанию равен числу доступных ядер. С Go 1.25 в Linux учитывается и лимит CPU контейнера (cgroup), а значение пересматривается, если лимит меняется. Явный вызов `runtime.GOMAXPROCS(n)` или переменная окружения `GOMAXPROCS` это отключают.

## Ловушки

### `main` не ждёт горутины

```go
func main() {
	go fmt.Println("из горутины") // скорее всего, не успеет
	fmt.Println("main")
}
```

Возврат из `main` завершает процесс, недоработавшие горутины просто обрываются: без `defer`, без сообщений. Ждать надо явно — `sync.WaitGroup`, каналом или `errgroup`. `time.Sleep` «чтобы горутины успели» — не синхронизация, а гадание.

### `append` в общий срез из горутин

```go
var res []int
for i := range 10 {
	wg.Add(1)
	go func() {
		defer wg.Done()
		res = append(res, i) // гонка данных: часть значений потеряется
	}()
}
```

`append` читает и пишет заголовок среза — две горутины затрут друг друга. Под `-race` такая программа падает с отчётом `DATA RACE`. Выделите срез заранее и пишите каждая в свою ячейку `res[i]` — разные элементы массива гонки не образуют.

### Порядок выполнения не определён

Горутины, запущенные в цикле, могут выполняться в любом порядке и параллельно. Если вывод должен быть упорядочен — собирайте результаты по индексу и печатайте после ожидания, а не из самих горутин.

## Задание

Напишите функцию `ParallelMap(in []int, f func(int) int) []int`, которая применяет `f` к каждому элементу `in` конкурентно.

Требования:

- результат — новый срез той же длины, где `out[i] == f(in[i])`: порядок соответствует входу, а не порядку завершения горутин;
- каждый вызов `f` выполняется в своей горутине, все вызовы идут одновременно — `f` может ждать, пока не запустятся остальные;
- `f` вызывается ровно один раз для каждого элемента;
- функция возвращается только после того, как все вызовы `f` завершились;
- для пустого или `nil` входа возвращается пустой срез (длины 0), `f` не вызывается;
- код без гонок данных: тесты запускаются с `-race`.
