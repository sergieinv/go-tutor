**Гонка данных** (data race) — два доступа к одной переменной из разных горутин, хотя бы один из них — запись, и между ними нет отношения **happens-before**. **Race condition** — более широкое понятие: результат зависит от порядка выполнения. Они пересекаются, но не совпадают: `Load` и `Store` атомика по отдельности гонки данных не образуют, а связка «прочитал — посчитал — записал» всё равно теряет обновления.

Модель памяти Go говорит, какие операции создают happens-before: отправка в канал — до завершения соответствующего получения (`close` — до получения, увидевшего закрытие); `Unlock` мьютекса — до следующего `Lock`; `wg.Done()` — до возврата из `wg.Wait()`; завершение функции в `once.Do` — до возврата из любого `Do`; атомарные операции последовательно согласованы. Программа без гонок данных ведёт себя так, будто горутины выполняются по очереди в каком-то порядке. Программа с гонкой — нет: компилятор и процессор вправе переставлять операции, а запись из нескольких машинных слов может быть видна наполовину.

## Как это в C#

- `lock`, `Interlocked`, `Lazy<T>` и `ConcurrentDictionary` — это `sync.Mutex`, `sync/atomic`, `sync.Once` и map под мьютексом (или `sync.Map`). Идея та же, а вот средства поиска разные.
- В .NET нет встроенного детектора гонок. В Go он в тулчейне: `go test -race`, `go run -race`, `go build -race` — и его принято включать в CI.
- `Dictionary` при одновременной записи может испортиться: потерять записи, зациклиться, иногда — бросить `InvalidOperationException` (ловится лишь часть случаев). Map в Go в таком случае аварийно завершает процесс: `fatal error: concurrent map writes`.
- Модель памяти .NET даёт больше гарантий на практике (запись ссылки атомарна, `volatile`), но и там рвутся структуры шире машинного слова (`decimal`, `Guid`). В Go таковы `interface`, срез и строка — несколько машинных слов, и гонка на них может породить значение, которого никто не записывал.

## Под капотом

Детектор гонок (ThreadSanitizer) инструментирует каждое обращение к памяти и операции синхронизации. Для каждой горутины он ведёт векторные часы и помнит последние доступы к каждому участку памяти. Если два доступа не упорядочены happens-before, он печатает `WARNING: DATA RACE` с двумя стеками и местами создания горутин. Важно, что ему не нужно, чтобы гонка «сработала» — достаточно, чтобы оба доступа выполнились в этом запуске без синхронизации. Но код, который не выполнялся, он не проверит. Цена — память в 5–10 раз и время в 2–20 раз больше, поэтому `-race` включают в тестах и на стендах, а не в продакшен-сборке. Найдя гонку, программа продолжает работу и в конце завершается с кодом 66.

Ниже — программа с двумя гонками: горутины без синхронизации увеличивают `total` и дописывают в общий срез `log`. Визуализатор запускает её с `-race`, разбирает отчёт и для каждой уникальной пары строк показывает три шага: где созданы горутины, предыдущий доступ и текущий доступ к тому же адресу. Отчётов обычно больше, чем гонок: детектор повторяет одну и ту же пару строк для разных горутин.

Исправьте гонки: оберните обе строки, помеченные «гонка», в `mu.Lock()` и `mu.Unlock()` и запустите снова — детектор ничего не найдёт. Попробуйте исправить только одну строку: останется одна гонка. И попробуйте `GOMAXPROCS = 1`: горутины выполняются по очереди, но гонка никуда не девается — детектор её всё равно видит.

## Ловушки

### map не потокобезопасна

```go
m := map[int]int{}
for i := range 100 {
	go func() { m[i] = i }() // fatal error: concurrent map writes
}
```

Рантайм замечает одновременную запись (а также запись во время чтения или обхода) и завершает процесс фатальной ошибкой. Это не паника: `recover` её не перехватит. Нужна map под `sync.Mutex`/`RWMutex` или `sync.Map`.

### Гонка рвёт составные значения

```go
var v any = small{}
go func() {
	for { v = small{} }
}()
for { v = big{} } // читатель может увидеть тип big с данными small
```

Интерфейс — два слова (тип и указатель на данные), срез — три, строка — два. Без синхронизации читатель может увидеть слова из разных записей: `len` от одного среза и указатель от другого. Итог — выход за границы памяти и падение в неожиданном месте, а не просто «старое значение».

### «Безобидная» гонка на флаге

```go
var ready bool
go func() {
	data = load()
	ready = true
}()
for !ready { // компилятор вправе вынести чтение из цикла
}
use(data) // и даже увидев ready, можно не увидеть data
```

Без happens-before нет гарантий ни что цикл закончится, ни что `data` будет видна. Флаги делают на `atomic.Bool`, а ещё лучше — закрытием канала.

## Задание

Напишите потокобезопасный счётчик по ключам `Counter` с методами:

- `Inc(key string)` — увеличивает счётчик `key` на 1;
- `Value(key string) int` — текущее значение, 0 для ключа, который не встречался;
- `Snapshot() map[string]int` — копия всех счётчиков.

Требования:

- все методы можно вызывать одновременно из многих горутин; тесты запускаются с `-race`, и любой отчёт детектора их проваливает;
- нулевое значение `Counter` готово к работе (`var c Counter`), в том числе когда первые `Inc` идут одновременно;
- `Snapshot` возвращает новую map: её изменения не влияют на счётчик, а последующие `Inc` не меняют выданный снимок; у пустого счётчика — пустая map, не `nil`;
- методы объявлены на указателе `*Counter`; поля структуры (`mu sync.Mutex`, `m map[string]int`) уже есть в шаблоне.
