Таймаут в Go — это `select` из двух веток: результат работы и `<-time.After(d)`. Какая ветка готова первой, та и выполняется. Отдельного типа «задача с таймаутом» нет: работа идёт в горутине и сообщает о результате через канал.

Главное, что нужно усвоить: таймаут прекращает **ожидание**, а не работу. Горутину нельзя остановить снаружи — она доработает сама или по сигналу отмены. Поэтому исполнитель должен уметь завершиться и тогда, когда результат уже никому не нужен: для этого канал результата делают буферизованным на одно значение.

Для настоящей отмены — чтобы долгая операция узнала о таймауте и прекратила работу — в Go есть `context.WithTimeout`. Ему посвящён отдельный урок; внутри он устроен на том же `select`.

## Как это в C#

- `await Task.WhenAny(work, Task.Delay(t))` — прямой аналог `select` с `time.After`. В .NET 6+ есть ещё `work.WaitAsync(timeout)`, который бросает `TimeoutException`; в Go таймаут — обычное значение ошибки.
- `CancellationTokenSource.CancelAfter(t)` отменяет работу, а не только ожидание. В Go это `context.WithTimeout`; голый `time.After` ничего не отменяет.
- Брошенная `Task` в .NET доработает и будет собрана сборщиком. Брошенная горутина, заблокированная на отправке в канал, не собирается никогда — это утечка, и её нужно предотвращать кодом.
- После Go 1.23 неиспользованный таймер из `time.After` собирается сборщиком мусора, даже если ещё не сработал. Раньше в горячих циклах советовали `time.NewTimer` + `Stop` — теперь это не нужно. В .NET неотменённый `Task.Delay` держится в очереди таймеров до срабатывания, поэтому в циклах с `WhenAny` его отменяют токеном.

## Ловушки

### Небуферизованный канал результата

```go
ch := make(chan string) // без буфера
go func() { ch <- slowCall() }()
select {
case v := <-ch:
	return v, nil
case <-time.After(time.Second):
	return "", ErrTimeout // исполнитель застрянет на ch <- навсегда
}
```

После таймаута из `ch` больше никто не читает, и отправка блокируется навсегда. Каждый такой вызов оставляет висящую горутину со всем, что она держит. Лечится буфером на одно значение: `make(chan string, 1)`.

### Таймаут не останавливает работу

```go
go func() {
	for _, item := range items {
		process(item) // продолжит работать после таймаута вызывающего
	}
	ch <- done
}()
```

Вызывающий получил `ErrTimeout`, а горутина продолжает тратить CPU, держать соединения и писать в базу. Если работа долгая, передайте ей сигнал отмены — канал `done` или `context.Context` — и проверяйте его между шагами.

### Таймаут на каждую итерацию вместо общего

`time.After` внутри цикла с `select` создаёт новый таймер на каждой итерации — это лимит «тишины» между событиями, а не на весь цикл. Для общего лимита создайте канал таймера один раз до цикла: `deadline := time.After(d)`.

## Задание

Напишите обобщённую функцию `Call[T any](timeout time.Duration, f func() (T, error)) (T, error)`, которая выполняет `f` в отдельной горутине и ждёт результат не дольше `timeout`.

Требования:

- если `f` вернулась вовремя, `Call` возвращает её значение и ошибку как есть;
- если за `timeout` результата нет, `Call` возвращает нулевое значение `T` и ошибку `ErrTimeout`, не дожидаясь `f`;
- если `timeout <= 0`, `f` не вызывается вовсе, а `Call` сразу возвращает нулевое значение и `ErrTimeout`;
- `f` вызывается не больше одного раза;
- горутина с `f` не должна утечь: когда `f` всё-таки вернётся после таймаута, горутина обязана завершиться.
