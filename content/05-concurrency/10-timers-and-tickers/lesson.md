`time.After(d)` из прошлого урока — это обёртка над `time.NewTimer(d).C`. Сам `*time.Timer` нужен, когда таймером надо управлять: отменить через `Stop`, перезапустить через `Reset`. `time.Ticker` присылает время в канал `C` каждые `d`, пока его не остановят, — это периодическая работа: опрос, сброс буферов, heartbeat.

В Go 1.23 таймеры заметно упростились. Канал таймера стал синхронным: после возврата из `Stop` или `Reset` из `C` уже не придёт значение, относящееся к старой настройке, — раньше его приходилось вычитывать вручную. И неостановленные таймеры и тикеры, на которые больше нет ссылок, теперь собирает сборщик мусора. Новое поведение включается по версии `go` в `go.mod` (1.23 и выше), поэтому в старых проектах и старых статьях встречается «ритуал» `if !t.Stop() { <-t.C }` — сегодня он не нужен.

## Как это в C#

- `System.Threading.Timer` вызывает callback в пуле потоков — это `time.AfterFunc`. Канальных таймеров в .NET нет; ближе всего `await Task.Delay(d, token)`, где отмена — через токен, а не `Stop`.
- `PeriodicTimer` (.NET 6+) с `await timer.WaitForNextTickAsync()` — прямой аналог `time.Ticker`. И он тоже не копит пропущенные тики: если обработка затянулась, следующий `WaitForNextTickAsync` завершится сразу, но только один раз.
- `timer.Change(dueTime, period)` — это `Reset`. В Go у таймера и тикера разные типы, и `Timer.Reset` не делает таймер периодическим.
- В .NET таймер останавливают `Dispose` — он `IDisposable`, и его принято освобождать; а `System.Threading.Timer`, на который не осталось ссылок, GC может собрать прямо на ходу. В Go `Stop` нужен, чтобы таймер не сработал, а не ради освобождения ресурсов: с Go 1.23 забытый таймер соберёт GC.

## Ловушки

### `range` по тикеру после `Stop`

```go
ticker := time.NewTicker(time.Second)
go func() {
	time.Sleep(5 * time.Second)
	ticker.Stop()
}()
for t := range ticker.C { // после Stop цикл не закончится
	fmt.Println(t)
}
```

`Stop` не закрывает канал — иначе читатель принял бы закрытие за тик. Цикл просто зависнет. Для остановки заведите отдельный канал `done` и слушайте оба в `select`.

### `AfterFunc` и `Stop`, вернувший `false`

```go
t := time.AfterFunc(d, cleanup)
if !t.Stop() {
	// cleanup уже запущена в своей горутине — и, возможно, ещё работает
}
```

`Stop` не ждёт завершения функции. Если важно, что `cleanup` закончилась, синхронизируйтесь с ней явно — каналом или `WaitGroup`.

### Тики теряются, а не копятся

Если обработка тика дольше периода, пропущенные тики не встают в очередь: в канале ждёт не больше одного, а следующий придёт по расписанию. Это защищает от лавины после паузы, но считать тики как «сколько прошло периодов» нельзя — для этого сравнивайте время.

## Задание

Напишите функцию `Debounce(in <-chan string, d time.Duration) <-chan string` — «гашение дребезга»: из серии значений, идущих чаще чем раз в `d`, наружу проходит только последнее.

Требования:

- `Debounce` сразу возвращает канал `out` (не `nil`) и обрабатывает `in` в отдельной горутине;
- каждое значение из `in` запоминается как ожидающее (заменяя предыдущее) и перезапускает отсчёт; если после него `d` не приходило новых значений, ожидающее значение отправляется в `out`;
- промежуточные значения серии отбрасываются; одно и то же значение не выдаётся дважды;
- когда `in` закрыт: если есть ожидающее значение, оно отправляется в `out` сразу, не дожидаясь `d`; затем `out` закрывается и горутина завершается;
- `d > 0`; читатель вычитывает `out` до закрытия.
