Часто по каналу не нужно передавать данные — достаточно сообщить, что что-то произошло: работа закончена, можно начинать, твой ход. Для таких сигналов берут `chan struct{}`. Пустая структура не занимает памяти, а тип канала сразу говорит читателю кода: здесь важен момент, а не значение.

Сигнал через канал — это ещё и барьер памяти. Модель памяти Go гарантирует: всё, что горутина записала до отправки, видно получателю после получения. Поэтому `done <- struct{}{}` в конце работы и `<-done` у ждущего — корректная синхронизация без мьютексов и `volatile`.

## Как это в C#

- `TaskCompletionSource` + `await tcs.Task` — одноразовый сигнал «готово». В Go это `done := make(chan struct{})`: отправитель делает `done <- struct{}{}` (или `close(done)`), ожидающий — `<-done`.
- `ManualResetEventSlim` / `AutoResetEvent` блокируют поток ОС. Ожидание на канале блокирует только горутину.
- Как и в C#, где барьеры памяти ставят `lock`, `Interlocked` и сами примитивы синхронизации (`TaskCompletionSource`, `Channel<T>`), отдельный барьер не нужен: по модели памяти Go отправка в канал happens-before соответствующего получения.
- Типа нулевого размера вроде `struct{}` в C# нет (пустая `struct` занимает 1 байт). Для сигнала без значения есть необобщённый `TaskCompletionSource` (.NET 5+), в остальных случаях обходятся `bool` или `Unit` из функциональных библиотек.

## Ловушки

### Сигнал раньше записи

```go
go func() {
	done <- struct{}{} // сигнал отправлен…
	result = compute() // …а запись — уже после
}()
<-done
fmt.Println(result) // гонка данных: может быть и старое значение
```

Гарантия видимости распространяется только на записи, сделанные **до** отправки. Сигнал «готово» отправляйте последним действием — удобно через `defer`.

### Отправку получает только один

```go
for range 3 {
	go func() {
		<-start // ждут сигнала старта
		run()
	}()
}
start <- struct{}{} // проснётся только одна горутина из трёх
```

Каждая отправка будит ровно одного получателя. Чтобы разбудить всех ждущих разом, канал закрывают: `close(start)` — получение из закрытого канала мгновенно завершается у всех.

### Флаг вместо канала

```go
var finished bool
go func() { work(); finished = true }()
for !finished { // гонка данных; компилятор вправе поднять чтение из цикла
}
```

Без синхронизации нет гарантии, что одна горутина вообще увидит запись другой, — цикл может крутиться вечно. А пустой цикл ещё и занимает ядро на 100%. Ждите на канале: горутина заснёт и проснётся ровно тогда, когда нужно.

## Задание

Напишите функцию `Alternate(n int, a, b func(i int))`, которая запускает две горутины-игрока и заставляет их ходить по очереди.

Требования:

- вызовы идут строго в порядке `a(0)`, `b(0)`, `a(1)`, `b(1)`, …, `a(n-1)`, `b(n-1)`; следующий вызов начинается только после возврата предыдущего;
- все вызовы `a` выполняются в одной горутине, все вызовы `b` — в другой, и обе отличаются от горутины, вызвавшей `Alternate`;
- общих переменных и мьютексов нет — очерёдность передаётся только через каналы (тесты запускаются с `-race` и пишут журнал вызовов без блокировок);
- `Alternate` возвращается после возврата `b(n-1)`, и к этому моменту обе горутины завершены или вот-вот завершатся — ни одна не остаётся ждать вечно;
- при `n <= 0` ни `a`, ни `b` не вызываются, и функция сразу возвращается.
