`count++` из нескольких горутин — гонка данных: это чтение, сложение и запись, и между ними может вклиниться другая горутина. Мьютекс решает проблему, но для одного числа или флага есть способ дешевле — атомарные операции из `sync/atomic`. Процессор выполняет их неделимо, и никто не увидит значение «наполовину записанным».

С Go 1.19 в пакете есть типы `atomic.Int32`, `atomic.Int64`, `atomic.Uint64`, `atomic.Bool`, `atomic.Pointer[T]` и `atomic.Value`. Их методы: `Load`, `Store`, `Swap`, `CompareAndSwap`, у чисел — `Add`, а с Go 1.23 — ещё `And` и `Or`. Старые функции вроде `atomic.AddInt64(&x, 1)` работают, но с типами нельзя случайно обратиться к значению без atomic, а `atomic.Int64` выровнен правильно даже на 32-битных платформах.

Атомарность охватывает **одно** значение. Как только правило связывает несколько полей — «сумма на счетах постоянна», «`count` и `sum` обновляются вместе, чтобы считать среднее» — атомарные поля по отдельности его не удержат: читатель увидит одно поле уже обновлённым, другое ещё нет. Тогда нужен мьютекс или неизменяемая структура, которую целиком подменяют через `atomic.Pointer[T]`.

## Как это в C#

- `Interlocked.Increment(ref x)` и `Interlocked.Add` — это `x.Add(1)` у `atomic.Int64`. В Go значение завёрнуто в тип, и обычное `x++` к нему просто не скомпилируется.
- `Interlocked.CompareExchange(ref x, new, old)` — это `x.CompareAndSwap(old, new)`. Порядок аргументов обратный, и Go возвращает `bool` (удалось ли), а не прежнее значение.
- `Volatile.Read` / `Volatile.Write` и поля `volatile` — это `Load` / `Store`. Ключевого слова `volatile` в Go нет; все операции `sync/atomic` последовательно согласованы — сильнее, чем acquire/release у `Volatile`.
- `Interlocked.Exchange(ref obj, newObj)` для ссылки — это `atomic.Pointer[T].Swap`. Приём «неизменяемый объект + атомарная подмена ссылки» одинаково работает в обоих языках.

## Ловушки

### Atomic-поля не дают атомарности их сочетания

```go
type Stats struct {
	count atomic.Int64
	sum   atomic.Int64
}

func (s *Stats) Add(v int64) { s.count.Add(1); s.sum.Add(v) }
func (s *Stats) Avg() int64  { return s.sum.Load() / s.count.Load() } // count уже +1, sum ещё нет
```

Каждое поле по отдельности корректно, а пара — нет: `Avg` может прочитать между двумя `Add`. Для инварианта из нескольких полей берите мьютекс.

### Проверка и запись — две операции

```go
if !started.Load() {
	started.Store(true) // две горутины могут обе пройти проверку
	start()
}
```

Между `Load` и `Store` успевает вклиниться другая горутина. «Проверить и установить» делают одной операцией: `if started.CompareAndSwap(false, true) { start() }`. А для «выполнить один раз» есть `sync.Once`.

### Смешанный доступ

```go
var n int64
go func() { atomic.AddInt64(&n, 1) }()
fmt.Println(n) // обычное чтение — гонка, -race её найдёт
```

Если к переменной хоть раз обращаются атомарно, то и все остальные обращения во время конкурентной работы должны быть атомарными. Типы `atomic.Int64` и другие защищают от этой ошибки: у них нет «обычного» доступа к значению.

## Задание

Напишите тип `Gauge`, который собирает статистику наблюдений без мьютекса — на `sync/atomic`.

```go
func (g *Gauge) Observe(v int64)
func (g *Gauge) Count() int64
func (g *Gauge) Max() (int64, bool)
```

Требования:

- нулевое значение `Gauge` готово к работе, конструктора нет;
- `Observe` учитывает наблюдение `v` (любое `int64`, в том числе 0 и отрицательные);
- `Count` возвращает число наблюдений;
- `Max` возвращает наибольшее наблюдение и `true`; если наблюдений не было — `0, false`;
- все методы безопасны для одновременного вызова; максимум, который видят читатели, никогда не уменьшается, и ни одно наблюдение не теряется;
- `Count` и `Max` — независимые величины: в момент одновременных `Observe` они не обязаны быть согласованы между собой (например, `Count` уже учёл наблюдение, а `Max` ещё нет).
