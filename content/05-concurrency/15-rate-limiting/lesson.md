Ограничитель частоты пропускает не больше N операций за интервал. Самая короткая реализация в Go — ждать тик `time.Ticker` перед каждой операцией: операции идут равномерно, не чаще раза в интервал.

Равномерность часто слишком строга: после паузы хочется сразу пропустить несколько запросов. Это модель **token bucket**: в ведре до `burst` токенов, новый токен появляется каждые `interval`, запрос забирает токен или ждёт его. На каналах ведро — буферизованный канал ёмкостью `burst`, который горутина с тикером пополняет неблокирующей отправкой. Без горутины токены можно досчитывать по прошедшему времени — так устроен `golang.org/x/time/rate`, стандартный выбор в продакшне (`rate.NewLimiter(rate.Every(d), burst)`, методы `Allow`, `Wait(ctx)`, `Reserve`). В песочнице курса этого модуля нет, поэтому здесь ограничитель собираем сами.

## Как это в C#

- В .NET 7+ есть пакет `System.Threading.RateLimiting` (в консольном приложении — из NuGet, в ASP.NET Core уже подключён): `TokenBucketRateLimiter`, `FixedWindowRateLimiter`, `SlidingWindowRateLimiter`, а в ASP.NET Core — middleware `AddRateLimiter`. В стандартной библиотеке Go готового ограничителя нет, есть `golang.org/x/time/rate`.
- `TokenBucketRateLimiter` выдаёт `RateLimitLease` через `AcquireAsync`. Аналог в Go — `<-tokens` (ждать) или `select` с `default` (попробовать без ожидания, как `AttemptAcquire`).
- `PeriodicTimer.WaitForNextTickAsync()` — это `<-ticker.C`.

## Ловушки

### `time.Tick` в долгоживущем коде

```go
for req := range requests {
	<-time.Tick(100 * time.Millisecond) // новый тикер на каждый запрос
	handle(req)
}
```

Каждый вызов `time.Tick` создаёт новый тикер, и ждём мы его первый тик — получается задержка, а не ограничение частоты. Создайте тикер один раз до цикла. Для тикеров, которые должны остановиться, используйте `time.NewTicker` и `Stop`.

### Блокирующее пополнение ведра

```go
for range t.C {
	tokens <- struct{}{} // ведро полное — горутина висит здесь
}
```

Пока ведро полное, пополняющая горутина блокируется и не видит сигнала остановки — утечка. Пополняйте через `select` с `default`: лишний токен выбрасывается.

### Ограничитель на каждый запрос

```go
func handle(w http.ResponseWriter, r *http.Request) {
	lim := NewLimiter(time.Second, 10) // новое полное ведро на каждый запрос
	lim.Wait()
}
```

Ограничитель должен быть общим для всех запросов, которые он ограничивает: одно ведро на клиента, на ключ API или на весь сервис.

## Задание

Напишите ограничитель на канале токенов:

```go
func NewLimiter(interval time.Duration, burst int) *Limiter
func (l *Limiter) Allow() bool
func (l *Limiter) Wait() bool
func (l *Limiter) Stop()
```

Требования:

- ведро вмещает `burst` токенов и создаётся полным; при `burst < 1` ёмкость — 1 токен; `interval` всегда больше нуля;
- каждые `interval` после создания в ведро добавляется один токен; если ведро полное, токен выбрасывается — запас не копится сверх `burst`;
- `Allow` забирает токен, если он есть, и возвращает `true`; иначе сразу возвращает `false`, не дожидаясь;
- `Wait` блокируется, пока не получит токен, и возвращает `true`;
- все методы можно вызывать из нескольких горутин одновременно; каждый токен достаётся только одному вызову;
- `Stop` вызывается один раз: новые токены больше не появляются, а горутина пополнения (если она есть) завершается;
- после `Stop` ни `Allow`, ни `Wait` не блокируются: оставшиеся в ведре токены по-прежнему можно забрать (`true`), а когда ведро пусто, оба сразу возвращают `false`; `Wait`, который ждал в момент `Stop`, тоже просыпается.
