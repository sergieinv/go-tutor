Девиз Go — «не общайтесь через общую память, а делите память через общение», но каналы подходят не для всего. Счётчик, кэш, набор балансов, который читают и меняют многие горутины, проще всего защитить мьютексом: `mu.Lock()` перед работой с данными, `mu.Unlock()` после. Между ними с данными работает только одна горутина.

В Go мьютекс — обычное поле структуры, его нулевое значение — открытый замок. Принято класть его прямо над полями, которые он охраняет, а в методах сразу после `Lock` писать `defer mu.Unlock()`. Мьютекс защищает не поля сами по себе, а **инвариант**: если правило связывает несколько полей («сумма на счетах постоянна»), все они меняются и читаются под одним замком.

`sync.RWMutex` пускает много читателей (`RLock`) одновременно, а писателя (`Lock`) — только одного и без читателей. Он выигрывает, когда чтений гораздо больше записей и они долгие; на коротких критических секциях обычный `Mutex` часто быстрее. Для map, в которую в основном пишут один раз и потом много читают, есть ещё `sync.Map` — но это специализированный инструмент, по умолчанию берите map с мьютексом.

## Как это в C#

- `lock (obj) { ... }` — это `mu.Lock()` + `defer mu.Unlock()`. Только в Go замок — отдельное поле-значение `sync.Mutex`, а не любой объект; «лочиться на `this`» нельзя и не нужно.
- `Monitor` в .NET реентерабелен: поток, уже держащий `lock`, может войти в него снова. Мьютекс Go — нет: повторный `Lock` из той же горутины заблокирует её навсегда. Владельца у мьютекса нет вовсе — `Unlock` может вызвать даже другая горутина.
- `ReaderWriterLockSlim` — это `sync.RWMutex`, но без режима upgradeable read: перейти от `RLock` к `Lock`, не отпустив замок, нельзя. Кстати, `ReaderWriterLockSlim` по умолчанию тоже нереентерабелен (`LockRecursionPolicy.NoRecursion`).
- `ConcurrentDictionary` — универсальный выбор в .NET. Его аналог `sync.Map` в Go рассчитан на узкие сценарии (ключи пишутся однажды, читаются часто; горутины работают с непересекающимися ключами). Обычно пишут `map` + `Mutex`.

## Под капотом

`Mutex` — это два числа: слово состояния (флаги `locked`, `woken`, `starving` и счётчик ждущих) и семафор. Захват свободного замка — одна атомарная операция CompareAndSwap, без планировщика. Если замок занят, горутина немного крутится в цикле, а потом засыпает в очереди семафора, не тратя процессор. `Unlock` снимает флаг и будит первую из очереди.

У мьютекса два режима. В нормальном разбуженная горутина не получает замок автоматически, а соревнуется с новыми — у тех преимущество, они уже на процессоре. Это быстро, но несправедливо. Если ждущая горутина не может получить замок дольше 1 мс, мьютекс переходит в режим голодания: `Unlock` передаёт замок первой в очереди напрямую, а новые горутины не пытаются его схватить и встают в хвост. Как только очередь опустела или ожидание стало коротким, мьютекс возвращается в нормальный режим.

`WaitGroup` устроен похоже: атомарный счётчик задач, число ждущих и семафор. `Wait` при ненулевом счётчике засыпает, а `Done`, обнуливший счётчик, будит всех ждущих разом.

## Ловушки

### Копия мьютекса

```go
type Counter struct {
	mu sync.Mutex
	n  int
}

func (c Counter) Inc() { // получатель-значение: копия вместе с мьютексом
	c.mu.Lock()
	c.n++ // меняется копия, и замок у каждого вызова свой
	c.mu.Unlock()
}
```

Методы типа с мьютексом объявляйте только с указателем-получателем. `go vet` ловит копии: `Inc passes lock by value: Counter contains sync.Mutex`.

### Повторный `Lock` в той же горутине

```go
func (s *Store) Put(k, v string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.data[k] = v
	s.size = s.Len() // Len тоже берёт s.mu — горутина висит навсегда
}
```

Привычный по C# приём «публичный метод с `lock` вызывает другой публичный метод с `lock`» в Go даёт дедлок. Выносите общий код в неэкспортируемые методы с суффиксом `Locked`, которые ожидают, что замок уже взят.

### Проверка и действие под разными замками

```go
if b.Balance("alice") >= 100 { // замок взят и отпущен
	b.Withdraw("alice", 100)     // за это время деньги могли потратить
}
```

Каждый метод по отдельности потокобезопасен, а их сочетание — нет. Проверка и изменение, связанные одним инвариантом, должны идти под одним `Lock`, поэтому операцию «перевести, если хватает» делают одним методом.

## Задание

Напишите тип `Bank` — банк со счетами, безопасный для одновременного использования из многих горутин.

```go
func NewBank(balances map[string]int) *Bank
func (b *Bank) Balance(name string) (int, bool)
func (b *Bank) Transfer(from, to string, amount int) error
func (b *Bank) Total() int
```

Требования:

- `NewBank` копирует переданные балансы: последующие изменения исходной map не влияют на банк, а банк не меняет её; `nil` — банк без счетов;
- `Balance` возвращает баланс и `true`; для несуществующего счёта — `0, false`;
- `Transfer` проверяет в таком порядке: `amount <= 0` — `ErrInvalidAmount`; нет счёта `from` или `to` — `ErrUnknownAccount`; на `from` меньше `amount` — `ErrInsufficientFunds`. При любой ошибке балансы не меняются. Перевести весь остаток можно;
- перевод на тот же счёт (`from == to`) проходит те же проверки и при успехе баланс не меняет;
- `Total` возвращает сумму всех балансов и даже во время одновременных переводов всегда видит согласованное состояние — сумму, равную начальной;
- все методы безопасны для одновременного вызова.
