Pipeline — цепочка стадий, связанных каналами. Стадия — функция, которая получает входной канал, запускает горутину и сразу возвращает выходной канал. Горутина читает вход, обрабатывает значения и пишет в выход. Главное правило: **стадия владеет своим выходом** — создаёт его, пишет в него и закрывает, когда вход исчерпан. Тогда `range` следующей стадии заканчивается, и закрытие проходит по цепочке до потребителя.

Из стадий собирают две формы параллелизма. **Fan-out** — несколько копий медленной стадии читают один канал: канал — очередь, каждое значение достаётся ровно одной копии. **Fan-in** — слияние нескольких каналов в один: по горутине на вход и `WaitGroup`, после которого единственный владелец закрывает выход. Третья обязательная деталь — **отмена**: если потребитель уходит раньше, стадии без `ctx` навсегда повиснут на отправке.

## Как это в C#

- Ближайший аналог — TPL Dataflow (`TransformBlock`, `LinkTo`) или пара задач с `System.Threading.Channels`. В Go это не библиотека, а приём: функция, канал и горутина.
- `PropagateCompletion = true` и `Writer.Complete()` — то же, что `defer close(out)` и `range` по входу: завершение течёт по цепочке.
- `MaxDegreeOfParallelism` у блока — это fan-out: несколько горутин читают один канал. Порядок при этом теряется так же, как у блока с `EnsureOrdered = false`.
- `BoundedCapacity` — буфер между стадиями: `make(chan T, n)`. Отмена — `context.Context` вместо `CancellationToken`, только проверять её нужно явно в каждом `select` с отправкой.

## Под капотом

Небуферизованный канал между стадиями — точка встречи: отправитель ждёт получателя и наоборот. Поэтому pipeline сам выравнивается по самой медленной стадии: быстрые стадии до неё простаивают в «ждут отправки» (это и есть backpressure — давление в обратную сторону), стадии после неё — в «ждут получения». Буфер на `n` значений позволяет быстрой стадии уйти вперёд на `n` шагов и сглаживает рывки, но пропускную способность не меняет: когда буфер заполнится, стадия снова ждёт.

Ниже — программа из пяти стадий: `gen`, три копии `square` (fan-out — одна стадия на схеме, потому что горутины созданы одним оператором `go`), пересылающие горутины `merge` и горутина, которая закрывает выход `merge`. Визуализатор запускает её с трассировкой (`runtime/trace`) и по кадрам показывает, сколько горутин каждой стадии работает, спит или ждёт, и стрелками — кто кого разбудил передачей значения. Что попробовать:

- `buffer = 4` — генератор перестанет ждать воркеров: «ждут отправки» у `gen` почти исчезнет;
- `workers = 1` — fan-out пропадёт, программа станет втрое дольше;
- `break` в цикле `main` — итоговый шаг покажет стадии, которые не завершились, и строки, где они застряли: так выглядит утечка, от которой спасает отмена через `ctx`.

## Ловушки

### Потребитель ушёл — стадии остались

```go
for v := range square(gen(1000)) {
	if v > 100 {
		break // gen и square навсегда повисли на отправке
	}
}
```

Заблокированная горутина не собирается сборщиком мусора. Каждая отправка в стадии должна быть `select` с веткой `<-ctx.Done()`, а потребитель — вызывать `cancel()` при уходе (обычно `defer cancel()`).

### Закрыть выход fan-in в каждой горутине

```go
for _, c := range chans {
	go func() {
		for v := range c {
			out <- v
		}
		close(out) // первая закончившая закроет канал под остальными
	}()
}
```

Остальные получат `panic: send on closed channel`, а второй `close` — `panic: close of closed channel`. Закрывает выход одна горутина после `wg.Wait()`.

### Отмена, которая не доходит

```go
for v := range in {
	select {
	case <-ctx.Done():
		return
	default:
	}
	out <- v * v // проверили ctx и всё равно повисли здесь
}
```

Проверка «до отправки» не помогает: отмена может прийти, пока горутина ждёт на `out <- v`. Ждать отправку и отмену нужно в одном `select`. Если вход может никогда не закрыться, `range in` тоже заменяют на `select` с `<-ctx.Done()`.

## Задание

Напишите функцию `Merge[T any](ctx context.Context, chans ...<-chan T) <-chan T` — fan-in с отменой.

Требования:

- `Merge` сразу возвращает канал, а пересылку ведёт в горутинах; выходной канал небуферизованный;
- в выход попадают все значения из всех входов; значения из одного входа идут в том же порядке, в каком пришли, между входами порядок любой;
- выход закрывается, когда закрыты все входы и все их значения отданы;
- `nil`-каналы в `chans` пропускаются; если входов нет или все они `nil`, возвращается уже закрытый (или вот-вот закрывающийся) канал без значений;
- после отмены `ctx` выход закрывается, даже если входы никогда не закроются и выход никто не читает; все горутины `Merge` завершаются. Значения, которые не успели отдать до отмены, теряются.
