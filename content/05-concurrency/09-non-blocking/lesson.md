Если в `select` есть ветка `default`, он не ждёт: когда ни одна операция с каналом не готова прямо сейчас, выполняется `default`. Так из блокирующих `ch <- v` и `<-ch` получаются попытки — `TrySend` и `TryRecv`, которых в стандартной библиотеке нет как отдельных функций.

Типичные применения: «отбросить, если занято» для метрик и логов, где потеря значения лучше, чем торможение горячего пути; забрать из канала всё, что накопилось, не дожидаясь новых значений; проверить сигнал остановки между шагами работы; try-lock на канале-семафоре.

## Как это в C#

- `ChannelWriter.TryWrite` и `ChannelReader.TryRead` — это `select` с одной веткой и `default`. В Go нет отдельных методов: любой канал можно попробовать без ожидания.
- `BoundedChannelFullMode.DropWrite` у `Channel.CreateBounded` отбрасывает новые элементы при полном буфере. В Go такую политику пишут руками — неблокирующей отправкой. `DropOldest` тоже выражается: при неудаче забрать одно значение и попробовать снова.
- `Monitor.TryEnter` и `SemaphoreSlim.Wait(0)` — попытка захвата без ожидания. В Go есть `sync.Mutex.TryLock`, но документация прямо предупреждает, что нужен он редко; для «занято — пропускаем» чаще берут канал с буфером 1.
- `select` с `default` проверяет готовность один раз и не уступает процессор. Крутить его в цикле — то же, что `while (!reader.TryRead(out _)) {}` без `await`: занятое ядро и никакой пользы.

## Ловушки

### Busy loop

```go
for {
	select {
	case v := <-jobs:
		handle(v)
	default:
		// ничего не готово — и сразу на следующий круг
	}
}
```

Пока `jobs` пуст, цикл вращается миллионы раз в секунду и занимает ядро целиком. Если ждать больше нечего, уберите `default` — горутина заснёт до прихода значения. Если `default` нужен для другой работы, она должна быть настоящей, а не пустым кругом.

### `len(ch)` вместо попытки

```go
if len(ch) > 0 {
	v := <-ch // может заблокироваться
	handle(v)
}
```

Между проверкой `len` и получением значение может забрать другая горутина — классическая гонка «проверил, потом сделал». `len` и `cap` канала годятся для метрик, но не для решений. Неблокирующий `select` проверяет и забирает атомарно.

### `default` молча теряет данные

Неблокирующая отправка, которая ничего не считает, превращает переполнение в тихую потерю. Отбрасывая значения, хотя бы считайте их — счётчиком `atomic.Int64` или метрикой, — иначе о проблеме никто не узнает.

## Задание

Напишите тип `Sampler` — буфер значений для метрик, который никогда не блокирует ни производителей, ни потребителей.

```go
func NewSampler(size int) *Sampler
func (s *Sampler) Offer(v int) bool
func (s *Sampler) TryTake() (int, bool)
func (s *Sampler) Drain() []int
```

Требования:

- `NewSampler(size)` создаёт буфер на `size` значений; `size < 1` трактуется как 1;
- `Offer` кладёт значение в буфер и возвращает `true`; если буфер полон, новое значение отбрасывается, а `Offer` сразу возвращает `false` (уже лежащие значения не трогаем);
- `TryTake` забирает самое старое значение и возвращает `true`; если буфер пуст, сразу возвращает `0, false`;
- `Drain` забирает значения от старых к новым, но не больше, чем лежало в буфере в момент вызова: значения, добавленные `Offer` во время `Drain`, могут остаться в буфере. Если буфер опустел раньше (значения забрал другой потребитель), `Drain` сразу возвращает то, что успел забрать. Так `Drain` завершается даже при непрерывном потоке `Offer`;
- для пустого буфера `Drain` возвращает срез нулевой длины (`nil` допустим); если других вызовов нет, после `Drain` буфер пуст и снова принимает `size` значений;
- ни один метод не блокируется, даже если другие горутины одновременно вызывают `TryTake` и `Drain`;
- все методы безопасны для одновременного вызова из многих горутин: каждое принятое значение забирается ровно один раз.
