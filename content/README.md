# Формат контента

Каждый модуль — папка `NN-slug/` с файлом `module.yaml`, каждый урок — папка `NN-slug/` внутри модуля. Числовой префикс задаёт порядок, slug идёт в URL. Всё, что описано ниже, проверяет `tools/lessonlint`.

```
content/
  05-concurrency/
    module.yaml
    slides.md              # слайды модуля (необязательно)
    07-select/
      lesson.md            # frontmatter + текст урока
      example/main.go      # аннотированный пример
      example/output.txt   # ожидаемый вывод примера
      csharp/Example.cs    # блок «Как это в C#»
      quiz.yaml            # вопросы квиза
      viz.ts               # сценарий визуализатора (необязательно)
      live/main.go         # программа для живого визуализатора (необязательно)
      task/
        task.go            # шаблон для ученика
        task_test.go       # открытые тесты
        hidden_test.go     # скрытые тесты
        solution.go        # эталон
        hints.md           # подсказки
```

## module.yaml

```yaml
title: Конкурентность
summary: Одна строка о модуле.
goals:
  - Что ученик умеет после модуля.
```

## lesson.md

Frontmatter:

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `title` | да | Название урока |
| `summary` | да | Одна строка для оглавления |
| `difficulty` | да | 1–5 |
| `minutes` | да | Оценка времени |
| `prerequisites` | нет | Список `модуль/урок`, например `02-basics/04-arrays` |
| `docs` | нет | Ссылки: `{title, url}` |
| `runner` | нет | Флаги запуска: `race`, `gomaxprocs`, `godebug` |
| `taskKind` | нет | `fix` — задача «найди и почини» (см. ниже) |
| `govulncheck` | нет | Кнопка govulncheck в песочнице, `expect` — id уязвимостей (см. ниже) |

Тело урока делится заголовками второго уровня. Текст до первого `##` — введение. Распознаются разделы:

- `## Как это в C#` — обязателен; 2–4 пункта различий, код берётся из `csharp/`.
- `## Под капотом` — необязателен; рядом лежит `viz.ts`.
- `## Ловушки` — обязателен; каждая ловушка — заголовок `###` с коротким примером.
- `## Задание` — обязателен, если есть папка `task/`; условие задачи.

## example/main.go

Аннотированный пример в стиле gobyexample. Файл режется на сегменты: блок комментариев `//` и код под ним до следующего блока комментариев. Комментарии становятся левой колонкой, код — правой. Комментарии пишем по-русски, идентификаторы — по-английски. В комментариях можно использовать `код` в обратных кавычках.

Рядом с `main.go` могут лежать файлы данных (`.txt`, `.json` и т.п. — например, для `//go:embed`). Их получает runner вместе с примером, а песочница показывает их под редактором только для чтения.

Сторонние модули: программа без своего `go.mod` получает `runner/sandbox/deps.mod` — там перечислено всё, что доступно урокам (сейчас `golang.org/x/sync`, `golang.org/x/crypto` и SQLite на чистом Go `modernc.org/sqlite`). У песочницы нет сети, другие модули не загрузятся.

Свой `go.mod` (и `go.sum`) в `example/` — для уроков о зависимостях. Образ runner скачивает всё, что перечислено в `go.sum` примера, так что туда кладут и уязвимую версию модуля, и исправленную, на которую ученик обновит `go.mod`. `go.mod` показывается в аннотированном примере и редактируется в песочнице, `go.sum` — только для чтения.

### govulncheck

Поле frontmatter `govulncheck` включает в песочнице кнопку «govulncheck»: runner проверяет модуль примера по снимку базы уязвимостей из образа и показывает дату снимка. `lessonlint` требует, чтобы перечисленные уязвимости нашлись в вызовах примера (нужен `govulncheck` в `PATH` или флаг `-govulncheck`):

```yaml
govulncheck:
  expect: [GO-2022-1059]
```

### Пример с тестами

Если рядом с `main.go` лежит хотя бы один `*_test.go`, пример запускается через `go test`, а не `go run`:

```
example/
  main.go          # код, который тестируем (package main, func main может быть пустой)
  main_test.go     # тесты, бенчмарки, fuzz-тесты, Example-функции
  output.txt       # вывод go test -v; время тестов «(0.12s)» записано как «(0.00s)»
```

- Аннотированный пример показывает `main.go`, затем каждый `*_test.go` под заголовком с именем файла; комментарии в тестах режутся на сегменты так же.
- В песочнице редактируются все `.go`-файлы. Кнопки: «Запустить тесты» (`go test -v`), «Покрытие» (`-cover` и отчёт `go tool cover -func`), «Бенчмарки» — если в тестах есть `func BenchmarkXxx(b *testing.B)`, «Fuzzing» — по кнопке на каждую `func FuzzXxx(f *testing.F)`.
- Бенчмарки идут с `-benchtime=200ms -benchmem`, fuzzing — 4 секунды одним воркером; найденный вход песочница показывает рядом с выводом.
- `lessonlint` требует, чтобы `go test -v` проходил и совпадал с `output.txt`, покрытие считалось, бенчмарки не падали, а fuzzing укладывался в лимиты (найденная ошибка допустима — пример может её демонстрировать). Порядок вывода должен быть детерминированным: параллельные подтесты и время в выводе проверку не пройдут.

`example/output.txt` — точный stdout примера. Сгенерировать: `go run ./tools/lessonlint -update content`, затем проверить diff глазами.

## quiz.yaml

```yaml
questions:
  - id: closed-channel        # уникален в пределах урока
    kind: output              # output | compile | single | multiple
    prompt: Что выведет программа?
    code: |                   # для output и compile — полная программа
      package main
      ...
    options:                  # для output, single, multiple
      - text: "0 false"
        correct: true
        explain: Почему этот вариант верен.
      - text: timeout
        explain: Почему неверен.
  - id: non-channel-case
    kind: compile
    prompt: Скомпилируется ли программа?
    code: |
      ...
    compiles: false           # варианты «да/нет» строит сайт
    explain: Почему.
```

`lessonlint` запускает код вопросов `output` и сверяет stdout с текстом правильного варианта, а для `compile` — сверяет результат `go build` с полем `compiles`.

## viz.ts

Визуализатор показывается в разделе «Под капотом», поэтому урок с `viz.ts` должен этот раздел иметь. Файл импортирует движок из `viz/src/index.ts` и по умолчанию экспортирует одно из двух.

**Сценарий** — шаги описаны заранее и считаются при сборке сайта:

```ts
import { arrow, defineScenario, memory, scene, struct } from "../../../viz/src/index.ts";

export default defineScenario({
  title: "Заголовок среза и append",
  code: "s := make([]int, 3, 4)\n...", // код, по строкам которого идут шаги
  width: 640,                         // размеры схемы в единицах SVG
  height: 352,
  steps: [
    {
      lines: [1],                     // подсвеченные строки code, с 1
      note: "`make` выделяет массив…", // текст шага, обязателен
      scene: scene(/* примитивы */),
    },
  ],
});
```

Сцена — список фигур со стабильными `id`. Одна и та же сущность на разных шагах должна сохранять `id`: тогда плеер плавно её переместит и шаги листаются в обе стороны. Примитивы из `viz/src/primitives.ts`:

- `memory` — участок памяти (массив, буфер);
- `struct` — структура с полями (заголовок среза, `hchan`);
- `arrow` — указатель; стороны выхода и входа задают `exit` и `enter`;
- `goroutine`, `channel`, `box`, `label`.

Каждый примитив возвращает фигуры и точки привязки для стрелок: `at(...)`.

**Живой** — код ученика запускается в runner (`POST /api/trace`), шаги строятся из трассы `runtime/trace`:

```ts
import { defineLive } from "../../../viz/src/index.ts";

export default defineLive({
  title: "select по реальному запуску",
  builder: "select",       // построитель шагов из viz/src/live
  file: "live/main.go",    // стартовый код, его можно менять в браузере
  gomaxprocs: [1, 2, 4],   // варианты GOMAXPROCS в интерфейсе
});
```

`lessonlint` запускает `live/main.go` так же, как runner, и требует, чтобы трасса содержала события `select`. Формат `viz.ts`, номера строк, уникальность `id` и размеры сцен проверяет `npm test` в `site/`.

## slides.md

Слайды модуля открываются на странице `/slides/<модуль>/`. Экраны разделяются строкой `---`. Строка `@viz 02-basics/05-slices` вставляет визуализатор урока, на одном экране — не больше одного. Клавиша → сначала листает шаги визуализатора, затем экраны.

## task/

Все файлы — `package task`. Шаблон и эталон объявляют одни и те же функции, поэтому никогда не лежат в одной сборке: `lessonlint` копирует нужные файлы во временный каталог.

- `solution.go` + `task_test.go` + `hidden_test.go` — тесты проходят.
- `task.go` + те же тесты — компилируется, но тесты падают.

`hints.md` — ровно три подсказки, каждая под заголовком `## Подсказка N`.

### Задачи по безопасности

Эксплойт — тест в `hidden_test.go` с именем `TestExploitXxx(t *testing.T)`: он атакует код ученика (SQL-инъекция, XSS-нагрузка, path traversal, SSRF на loopback…) и падает, если атака удалась. `lessonlint` требует, чтобы каждый эксплойт падал на шаблоне и проходил на эталоне. Сайт помечает такие тесты как «эксплойт».

`taskKind: fix` — задача «найди и почини»: `task.go` — рабочий, но уязвимый код. На шаблоне все тесты, кроме эксплойтов, проходят (`lessonlint` это проверяет), так что починить надо, не сломав функциональность. Без `taskKind` задача — «напиши безопасно»: шаблон — заготовка.
