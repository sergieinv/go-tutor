# Формат контента

Каждый модуль — папка `NN-slug/` с файлом `module.yaml`, каждый урок — папка `NN-slug/` внутри модуля. Числовой префикс задаёт порядок, slug идёт в URL. Всё, что описано ниже, проверяет `tools/lessonlint`.

```
content/
  05-concurrency/
    module.yaml
    slides.md              # слайды модуля (необязательно)
    07-select/
      lesson.md            # frontmatter + текст урока
      example/main.go      # аннотированный пример
      example/output.txt   # ожидаемый вывод примера
      csharp/Example.cs    # блок «Как это в C#»
      quiz.yaml            # вопросы квиза
      viz.ts               # сценарий визуализатора (необязательно)
      live/main.go         # программа для живого визуализатора (необязательно)
      task/
        task.go            # шаблон для ученика
        task_test.go       # открытые тесты
        hidden_test.go     # скрытые тесты
        solution.go        # эталон
        hints.md           # подсказки
```

## module.yaml

```yaml
title: Конкурентность
summary: Одна строка о модуле.
goals:
  - Что ученик умеет после модуля.
```

## lesson.md

Frontmatter:

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `title` | да | Название урока |
| `summary` | да | Одна строка для оглавления |
| `difficulty` | да | 1–5 |
| `minutes` | да | Оценка времени |
| `prerequisites` | нет | Список `модуль/урок`, например `02-basics/04-arrays` |
| `docs` | нет | Ссылки: `{title, url}` |
| `runner` | нет | Флаги запуска: `race`, `gomaxprocs`, `godebug`, `gcflags`, `gotraceback`, `labs` (см. «Флаги рантайма и компилятора», «Базы данных профиля labs») |
| `taskKind` | нет | `fix` — задача «найди и почини», `review` — «приведи к виду для ревью» (см. ниже) |
| `govulncheck` | нет | Кнопка govulncheck в песочнице, `expect` — id уязвимостей (см. ниже) |
| `buf` | нет | `expectLint` — правила `buf lint`, которые контракт примера нарушает намеренно (см. «Контракты .proto») |

Тело урока делится заголовками второго уровня. Текст до первого `##` — введение. Распознаются разделы:

- `## Как это в C#` — обязателен; 2–4 пункта различий, код берётся из `csharp/`.
- `## Под капотом` — необязателен; рядом лежит `viz.ts`.
- `## Ловушки` — обязателен; каждая ловушка — заголовок `###` с коротким примером.
- `## Задание` — обязателен, если есть папка `task/`; условие задачи.

## example/main.go

Аннотированный пример в стиле gobyexample. Файл режется на сегменты: блок комментариев `//` и код под ним до следующего блока комментариев. Комментарии становятся левой колонкой, код — правой. Комментарии пишем по-русски, идентификаторы — по-английски. В комментариях можно использовать `код` в обратных кавычках.

Рядом с `main.go` могут лежать файлы данных (`.txt`, `.json`, `.sql`, `.yaml` — например, миграции для `//go:embed`). Подкаталогов нет: все файлы примера лежат рядом. Их получает runner вместе с примером, а песочница показывает их под редактором только для чтения.

Сторонние модули: программа без своего `go.mod` получает `runner/sandbox/deps.mod` — там перечислено всё, что доступно урокам (сейчас `golang.org/x/sync`, `golang.org/x/crypto`, SQLite на чистом Go `modernc.org/sqlite`, `github.com/jackc/pgx/v5`, `github.com/go-sql-driver/mysql` и миграции `github.com/pressly/goose/v3`). У песочницы нет сети, другие модули не загрузятся.

Свой `go.mod` (и `go.sum`) в `example/` — для уроков о зависимостях. Образ runner скачивает всё, что перечислено в `go.sum` примера, так что туда кладут и уязвимую версию модуля, и исправленную, на которую ученик обновит `go.mod`. `go.mod` показывается в аннотированном примере и редактируется в песочнице, `go.sum` — только для чтения.

### govulncheck

Поле frontmatter `govulncheck` включает в песочнице кнопку «govulncheck»: runner проверяет модуль примера по снимку базы уязвимостей из образа и показывает дату снимка. `lessonlint` требует, чтобы перечисленные уязвимости нашлись в вызовах примера (нужен `govulncheck` в `PATH` или флаг `-govulncheck`):

```yaml
govulncheck:
  expect: [GO-2022-1059]
```

### Контракты .proto

Пример (и задача) может содержать `*.proto`. При каждом запуске runner удаляет присланный сгенерированный код и заново выполняет `buf generate`: рядом с `orders.proto` появляются `orders.pb.go`, `orders_grpc.pb.go` и, если в контракте есть `google.api.http`, `orders.pb.gw.go`. Всё — в пакете `main`, поэтому каждый `.proto` объявляет `option go_package = "lesson/proto;main";`.

- Конфигурацию buf задаёт runner (`runner/sandbox/proto/`): зависимости — только `buf.build/googleapis/googleapis` и `buf.build/bufbuild/protovalidate` по коммитам из `buf.lock` (они в кеше образа, сети нет), плагины — `protoc-gen-go`, `protoc-gen-go-grpc`, `protoc-gen-grpc-gateway`. Свои `buf.gen.yaml` и `buf.lock` примера игнорируются: плагины — это программы, которые buf запускает от имени runner. Свой `buf.yaml` допустим, но только с `version: v2`, `deps` из списка выше и `lint`/`breaking` (`use`, `except`).
- Сгенерированный код лежит в `example/` рядом с `.proto` (песочница показывает его только для чтения), и `lessonlint` требует, чтобы он совпадал с `buf generate`; `-update` перегенерирует его сам. Нужен `buf` в `PATH` или флаг `-buf` (плагины — рядом с buf), кеш зависимостей — `BUF_CACHE_DIR`.
- В песочнице `.proto` редактируется, кнопки «buf lint» и «buf breaking» (против исходного контракта урока) появляются у каждого примера с `.proto`. Вывод — `файл:строка:столбец ПРАВИЛО сообщение`. Поле `buf.expectLint` во frontmatter заставляет `lessonlint` проверить, что пример нарушает эти правила; без него контракт примера обязан проходить lint.
- Задача с контрактом: `task/orders.proto` (с `option go_package = "lesson/proto;task";` — пакет задачи `task`) и сгенерированный по нему код лежат рядом с тестами — как и тесты, их задаёт урок, ученик присылает только `task.go`. Сайт показывает контракт задачи над открытыми тестами.

### Флаги рантайма и компилятора

- `runner.godebug: gctrace=1` (и `schedtrace=…`, `inittrace=1`…) — переменная `GODEBUG` программы. Трассы рантайма идут в stderr, а `output.txt` — только stdout, поэтому `gctrace` не ломает проверку вывода. Сам stdout примера должен быть детерминированным: никаких адресов, времени, числа сборок мусора и размеров кучи — печатайте сравнения («куча выросла: true») или то, что не зависит от машины.
- `runner.gotraceback: all` — `GOTRACEBACK`: при панике печатаются стеки всех горутин. Допустимы `none`, `single`, `all`, `system`.
- `runner.gcflags: "-m"` — флаги компилятора для пакета примера (без `all=`, то есть не для fmt и рантайма). Песочница показывает под выводом программы, что сообщил компилятор: escape analysis и inlining при `-m` (подробнее — `-m=2`), оставшиеся проверки границ при `-d=ssa/check_bce/debug=1`; `-l` выключает inlining, `-N` — оптимизации. Допустимы только эти слова. `lessonlint` требует, чтобы компилятор что-то вывел. Работает для примеров без тестов (`go run`).
- Пример, который импортирует `runtime/pprof`, получает в песочнице кнопку «pprof»: программа запускается, а по каждому файлу `*.pprof`, который она записала в рабочий каталог (не больше четырёх, по алфавиту), runner показывает `go tool pprof -top`. `lessonlint` требует хотя бы один читаемый профиль. Числа в профиле от запуска к запуску разные — текст урока на них не опирается.

### Базы данных профиля labs

`runner: {labs: [postgres]}` (или `[mysql]`, `[kafka]`, `[valkey]`, в любом сочетании) — пример работает на настоящей базе из профиля `docker compose --profile labs up`. На каждый запуск — пример, тесты, задача — runner создаёт пустую базу со своим пользователем, передаёт программе DSN в `POSTGRES_DSN` / `MYSQL_DSN` и удаляет базу после запуска. DSN MySQL — без параметров (`user:pass@tcp(mysql:3306)/db`): `parseTime` и прочее урок выставляет сам через `mysql.ParseDSN`.

`labs: [kafka]` — общий брокер Kafka профиля labs. **По умолчанию выключен** (`RUNNER_LAB_KAFKA` в `docker-compose.yml` закомментирован, брокер не в сети песочницы): у Kafka нет аутентификации и ACL, и программа ученика могла бы трогать чужие топики, в том числе топики сервисов, и настройки брокера. Уроки пишутся на `kfake` (ниже); с включённым брокером программа получает `KAFKA_BROKERS` и `KAFKA_TOPIC_PREFIX` и называет этим префиксом все свои топики и группы потребителей, а после запуска runner удаляет всё с префиксом. Автосоздание топиков выключено — урок создаёт их через `kadm`. Без labs у Kafka есть замена прямо в песочнице: `github.com/twmb/franz-go/pkg/kfake` поднимает кластер в процессе, и тот же клиент `kgo` работает с ним без изменений.

`labs: [postgres]` при запущенной реплике (`postgres-replica`) получает и `POSTGRES_REPLICA_DSN` — ту же базу на потоковой реплике, только для чтения. Реплика labs применяет транзакции с задержкой 200 мс, поэтому только что записанное на ней видно не сразу: урок о задержке репликации на это опирается, но вывод примера не должен зависеть от точного времени (ждите появления строки циклом с пределом, а не `time.Sleep`). Без реплики переменной нет.

`labs: [valkey]` — Valkey песочницы (`valkey-sandbox`, не тот, что у сервисов): программа получает `VALKEY_ADDR`, `VALKEY_USERNAME`, `VALKEY_PASSWORD` и `VALKEY_PREFIX` и называет этим префиксом все ключи и каналы — к остальным у пользователя запуска нет доступа, опасные команды (`FLUSHALL`, `KEYS`, `CONFIG`…) закрыты. После запуска ключи и пользователь удаляются. Без labs у Valkey есть замена прямо в песочнице — `github.com/alicebob/miniredis/v2` (сервер в процессе, `miniredis.Run()`, время двигается `FastForward`), клиент `github.com/valkey-io/valkey-go` работает с ним без изменений (`DisableCache: true` — miniredis не поддерживает клиентский кеш).

Без профиля переменная пуста, а runner дописывает в stderr подсказку, как его включить. Программа должна это пережить: проверить переменную и напечатать понятное сообщение, а не паниковать. Тесты задач, которым нужна база, вызывают `t.Skip`, если переменной нет: задача решается и проверяется и без labs (на SQLite или фейке), а с labs — дополнительно на настоящей базе.

`lessonlint` запускает такие примеры, только если ему переданы DSN администраторов (для модуля 14 — ещё `-postgres-replica 127.0.0.1:55433` и `-valkey valkey://default:labs-valkey@127.0.0.1:56380`): `-postgres 'postgres://runner:labs-runner@127.0.0.1:55432/postgres?sslmode=disable'` и `-mysql 'runner:labs-runner@tcp(127.0.0.1:53306)/'` (порты профиля labs на localhost). Без них пример только собирается. Вывод такого примера должен быть детерминированным на настоящей базе: никаких OID, времени, стоимостей из `EXPLAIN`, номеров транзакций.

### Пример с тестами

Если рядом с `main.go` лежит хотя бы один `*_test.go`, пример запускается через `go test`, а не `go run`:

```
example/
  main.go          # код, который тестируем (package main, func main может быть пустой)
  main_test.go     # тесты, бенчмарки, fuzz-тесты, Example-функции
  output.txt       # вывод go test -v; время тестов «(0.12s)» записано как «(0.00s)»
```

- Аннотированный пример показывает `main.go`, затем каждый `*_test.go` под заголовком с именем файла; комментарии в тестах режутся на сегменты так же.
- В песочнице редактируются все `.go`-файлы. Кнопки: «Запустить тесты» (`go test -v`), «Покрытие» (`-cover` и отчёт `go tool cover -func`), «Бенчмарки» — если в тестах есть `func BenchmarkXxx(b *testing.B)`, «Fuzzing» — по кнопке на каждую `func FuzzXxx(f *testing.F)`.
- Бенчмарки идут с `-benchtime=200ms -benchmem`, fuzzing — 4 секунды одним воркером; найденный вход песочница показывает рядом с выводом.
- `lessonlint` требует, чтобы `go test -v` проходил и совпадал с `output.txt`, покрытие считалось, бенчмарки не падали, а fuzzing укладывался в лимиты (найденная ошибка допустима — пример может её демонстрировать). Порядок вывода должен быть детерминированным: параллельные подтесты и время в выводе проверку не пройдут.

`example/output.txt` — точный stdout примера. Сгенерировать: `go run ./tools/lessonlint -update content`, затем проверить diff глазами.

## quiz.yaml

```yaml
questions:
  - id: closed-channel        # уникален в пределах урока
    kind: output              # output | compile | single | multiple
    prompt: Что выведет программа?
    code: |                   # для output и compile — полная программа
      package main
      ...
    options:                  # для output, single, multiple
      - text: "0 false"
        correct: true
        explain: Почему этот вариант верен.
      - text: timeout
        explain: Почему неверен.
  - id: non-channel-case
    kind: compile
    prompt: Скомпилируется ли программа?
    code: |
      ...
    compiles: false           # варианты «да/нет» строит сайт
    explain: Почему.
```

`lessonlint` запускает код вопросов `output` и сверяет stdout с текстом правильного варианта, а для `compile` — сверяет результат `go build` с полем `compiles`.

## viz.ts

Визуализатор показывается в разделе «Под капотом», поэтому урок с `viz.ts` должен этот раздел иметь. Файл импортирует движок из `viz/src/index.ts` и по умолчанию экспортирует одно из двух.

**Сценарий** — шаги описаны заранее и считаются при сборке сайта:

```ts
import { arrow, defineScenario, memory, scene, struct } from "../../../viz/src/index.ts";

export default defineScenario({
  title: "Заголовок среза и append",
  code: "s := make([]int, 3, 4)\n...", // код, по строкам которого идут шаги
  width: 640,                         // размеры схемы в единицах SVG
  height: 352,
  steps: [
    {
      lines: [1],                     // подсвеченные строки code, с 1
      note: "`make` выделяет массив…", // текст шага, обязателен
      scene: scene(/* примитивы */),
    },
  ],
});
```

Сцена — список фигур со стабильными `id`. Одна и та же сущность на разных шагах должна сохранять `id`: тогда плеер плавно её переместит и шаги листаются в обе стороны. Примитивы из `viz/src/primitives.ts`:

- `memory` — участок памяти (массив, буфер);
- `struct` — структура с полями (заголовок среза, `hchan`);
- `arrow` — указатель; стороны выхода и входа задают `exit` и `enter`;
- `goroutine`, `channel`, `box`, `label`.

Каждый примитив возвращает фигуры и точки привязки для стрелок: `at(...)`.

**Живой** — код ученика запускается в runner (`POST /api/trace`), шаги строятся из трассы `runtime/trace`:

```ts
import { defineLive } from "../../../viz/src/index.ts";

export default defineLive({
  title: "select по реальному запуску",
  builder: "select",       // построитель шагов из viz/src/live
  file: "live/main.go",    // стартовый код, его можно менять в браузере
  gomaxprocs: [1, 2, 4],   // варианты GOMAXPROCS в интерфейсе
});
```

`lessonlint` запускает `live/main.go` так же, как runner, и требует, чтобы трасса содержала события `select`. Формат `viz.ts`, номера строк, уникальность `id` и размеры сцен проверяет `npm test` в `site/`.

### Построитель spans

`builder: "spans"` — живой визуализатор запросов и их участков по разметке `runtime/trace`: `trace.NewTask(ctx, "orders.CreateOrder")` — строка (дочерняя задача — строкой ниже с отступом), `trace.WithRegion(ctx, "auth", f)` / `trace.StartRegion` — полоса под ней, `trace.Log(ctx, "deadline", "осталось 30 мс")` — точка и шаг с текстом. Подходит для interceptors, проброса дедлайна, повторов. `lessonlint` требует, чтобы в трассе были задачи или регионы.

### Построитель escape

`builder: "escape"` — живой визуализатор escape analysis: runner собирает `live/main.go` с `-gcflags=-m`, и каждая диагностика `main.go` («moved to heap», «escapes to heap», «does not escape», «leaking param») становится шагом — значение попадает в колонку «стек» или «куча» с объяснением почему. Inlining только считается. `lessonlint` требует хотя бы одну переменную или выражение main.go в куче.

### viz-live.ts

Урок может показать два визуализатора: сценарный `viz.ts` и рядом живой `viz-live.ts` (только `defineLive`, программа — в `live/main.go`). Сайт выводит оба в разделе «Под капотом», `lessonlint` прогоняет `live/main.go` по построителю из `viz-live.ts`. Если визуализатор у урока один, он лежит в `viz.ts`.

## slides.md

Слайды модуля открываются на странице `/slides/<модуль>/`. Экраны разделяются строкой `---`. Строка `@viz 02-basics/05-slices` вставляет визуализатор урока, на одном экране — не больше одного. Клавиша → сначала листает шаги визуализатора, затем экраны.

## task/

Все файлы — `package task`. Шаблон и эталон объявляют одни и те же функции, поэтому никогда не лежат в одной сборке: `lessonlint` копирует нужные файлы во временный каталог.

- `solution.go` + `task_test.go` + `hidden_test.go` — тесты проходят.
- `task.go` + те же тесты — компилируется, но тесты падают.

`hints.md` — ровно три подсказки, каждая под заголовком `## Подсказка N`.

### Задачи по безопасности

Эксплойт — тест в `hidden_test.go` с именем `TestExploitXxx(t *testing.T)`: он атакует код ученика (SQL-инъекция, XSS-нагрузка, path traversal, SSRF на loopback…) и падает, если атака удалась. `lessonlint` требует, чтобы каждый эксплойт падал на шаблоне и проходил на эталоне. Сайт помечает такие тесты как «эксплойт».

`taskKind: fix` — задача «найди и почини»: `task.go` — рабочий, но уязвимый код. На шаблоне все тесты, кроме эксплойтов, проходят (`lessonlint` это проверяет; пропущенные через `t.Skip` тоже допустимы), так что починить надо, не сломав функциональность. Без `taskKind` задача — «напиши безопасно»: шаблон — заготовка.

### Задачи «приведи к виду для ревью»

`taskKind: review` — `task.go` работает и проходит функциональные тесты, но ревью бы не прошёл: ошибки без контекста или проглоченные, `context` не первым параметром или не прокинут, незакрытые `Rows`, интерфейс на стороне реализации и т.п. Проверки — тесты `TestReviewXxx(t *testing.T)` в `hidden_test.go`; каждая падает на шаблоне и проходит на эталоне, остальные тесты проходят на шаблоне — так же, как эксплойты в fix-задачах. Проверка смотрит на поведение (ошибка оборачивается и находится через `errors.Is`, отмена контекста доходит до запроса, соединения возвращаются в пул), а где без этого не обойтись — на исходник через `go/parser` (`os.ReadFile("task.go")` из теста: тесты запускаются в каталоге пакета). Сайт ставит значок «приведи к виду для ревью» и ссылку на чек-лист `content/review-checklist.md` (страница `/review/`), а такие тесты помечает «ревью».
