В ASP.NET Core пароли хеширует `PasswordHasher` из Identity, cookie шифрует Data Protection, а JWT проверяет `JwtBearer` с разумными настройками по умолчанию. В Go ничего этого в стандартной библиотеке нет. Есть примитивы: `golang.org/x/crypto/bcrypt` и `argon2`, `crypto/rand`, `crypto/hmac`, `crypto/subtle`. Собирать из них приходится самому, поэтому важно знать, какой примитив для чего.

**Пароль** хранят медленным хешем с солью: даже после утечки базы перебор по словарю должен стоить дорого. `bcrypt.GenerateFromPassword(pw, cost)` возвращает строку вида `$2a$10$<соль><хеш>`, в ней уже есть соль и стоимость (`cost` — логарифм числа раундов, по умолчанию 10). Проверяет `bcrypt.CompareHashAndPassword`. У bcrypt есть жёсткий предел: учитываются только первые **72 байта** пароля. `GenerateFromPassword` более длинный пароль отвергает ошибкой, а `CompareHashAndPassword` молча обрезает. Современный выбор — **argon2id** (`argon2.IDKey`). Он требует не только времени, но и памяти, и это мешает перебору на GPU. Готового формата у пакета нет, поэтому параметры, соль и ключ записывают в PHC-строку `$argon2id$v=19$m=19456,t=2,p=1$<соль>$<ключ>`. Параметры лежат в самой строке, и их можно поднять, не ломая старые хеши.

**Токен сессии** не хешируют медленно: его генерирует сервер, и энтропии у него и так достаточно. Нужны 128+ бит из `crypto/rand`. Удобнее всего `rand.Text()` (Go 1.24): 26 символов base32, 130 бит. `math/rand` и `math/rand/v2` для секретов не годятся. В базе держат SHA-256 токена, а не сам токен: утечка таблицы не должна давать готовые сессии. Сессию при входе создают заново (новый токен — защита от фиксации сессии), при выходе и смене пароля удаляют.

**Подписанный токен** (JWT и его родственники) — данные плюс HMAC от них. Без ключа подпись не подделать, а проверять её нужно за постоянное время: `hmac.Equal` или `subtle.ConstantTimeCompare`. Обычное `==` на байтах выходит на первом несовпадении, и по времени ответа подпись можно подбирать побайтно. И главное правило: алгоритм и параметры проверки задаёт сервер, а не пришедший токен.

## Как это в C#

- `PasswordHasher<TUser>` из Identity — PBKDF2-HMAC-SHA512 со 100 000 итераций, соль и версия внутри строки. `VerifyHashedPassword` умеет вернуть `SuccessRehashNeeded`, когда параметры устарели. В Go то же самое делают вручную: `bcrypt.Cost(hash)` или разбор PHC-строки, затем перехеширование при входе.
- `RandomNumberGenerator.GetBytes` ≈ `crypto/rand.Read`, `System.Random` ≈ `math/rand`. `CryptographicOperations.FixedTimeEquals` ≈ `subtle.ConstantTimeCompare` и `hmac.Equal`.
- `JwtBearer` по умолчанию проверяет срок (`ValidateLifetime`), получателя (`ValidateAudience`) и требует подпись (`RequireSignedTokens`). В Go нет ни стандартного JWT, ни конвейера аутентификации: эти проверки — ваш код в middleware или настройки сторонней библиотеки, и ничего не включено само.
- Cookie-сессию в ASP.NET шифрует и подписывает Data Protection. В Go cookie — просто строка: кладите в неё случайный токен (а данные храните на сервере) или подписывайте HMAC сами.

## Ловушки

### `CompareHashAndPassword` обрезает пароль до 72 байт

```go
hash, _ := bcrypt.GenerateFromPassword([]byte(strings.Repeat("a", 72)), bcrypt.DefaultCost)
err := bcrypt.CompareHashAndPassword(hash, []byte(strings.Repeat("a", 72)+"что угодно"))
// err == nil: всё после 72-го байта не учитывается
```

Длину ограничивают при регистрации, а не при входе: не больше 72 **байт** (`len(pw)`, а не число рун — 37 кириллических букв уже 74 байта). Опасно и «удлинение» пароля перед bcrypt: склейка с перцем или именем пользователя в начале съедает часть лимита. Если пароли бывают длинными, берите argon2id.

### Токен из `math/rand`

```go
// УЯЗВИМО: генератор детерминирован — по выданным токенам
// восстанавливают состояние и предсказывают следующие.
token := strconv.FormatUint(mathrand.Uint64(), 36)

// Правильно: криптостойкий генератор ОС, 130 бит.
token = rand.Text() // crypto/rand
```

Даже `math/rand/v2` со случайным сидом не годится: его контракт — статистическое качество, а не непредсказуемость. Для всего, что работает как пароль (сессии, ссылки сброса, API-ключи, CSRF-токены), — только `crypto/rand`.

### Алгоритм из заголовка токена

```go
// УЯЗВИМО: сервер верит полю alg из токена.
switch h.Alg {
case "HS256":
	checkHMAC(...)
case "none": // «для отладки» — и токен без подписи принят
}
```

Атакующий пишет `{"alg":"none"}`, ставит в данные `"sub":"admin"` и отправляет токен без подписи. Родственная атака на библиотеки с RSA — путаница алгоритмов: токен с `alg: HS256` проверяется HMAC-ом, где в роли секрета выступает *публичный* RSA-ключ сервера, а его знают все. Правильно: алгоритм фиксирован в конфигурации проверки, а заголовок только сверяется с ним. Затем всегда проверяются `exp` (поле обязательно), `aud` (токен выпущен для нас, а не для соседнего сервиса с тем же ключом) и при необходимости `iss`. Секрет HMAC — 32+ случайных байта из хранилища секретов. Строку `"secret"` из README подберут по словарю офлайн по любому выданному токену.

## Задание

В сервисе есть самописный выпуск и проверка JWT с подписью HMAC-SHA256. Код рабочий — функциональные тесты проходят, — но **уязвим**. Найдите и закройте уязвимости, не меняя API и формат токена.

```go
type Claims struct {
	Sub string `json:"sub"`
	Aud string `json:"aud"`
	Exp int64  `json:"exp"` // Unix-время в секундах
}

type Issuer struct {
	Key      []byte           // секрет HMAC
	Audience string           // для какого сервиса токены
	Now      func() time.Time // часы; nil — time.Now
}

var ErrInvalid, ErrWeakKey error

func (iss *Issuer) Sign(c Claims) (string, error)
func (iss *Issuer) Verify(token string) (Claims, error)
```

Требования:

- **Формат.** Токен — три части через точку, каждая в `base64.RawURLEncoding`: заголовок `{"alg":"HS256","typ":"JWT"}`, данные — `json.Marshal(c)`, подпись — HMAC-SHA256 ключом `Key` от строки «заголовок.данные» (первые две части как есть, в base64).
- **Ключ.** Если `Key` короче 32 байт, `Sign` возвращает `""` и `ErrWeakKey`, а `Verify` — пустые `Claims` и `ErrWeakKey`, не глядя на токен.
- **`Verify`** возвращает данные и `nil` только если: частей ровно три, заголовок — JSON-объект с `alg` равным `"HS256"` (точно, с учётом регистра; другие поля заголовка не важны), подпись верна, данные — JSON-объект (неизвестные поля игнорируются), `aud` в точности равен `Audience`, и текущее время строго меньше `exp`: `Now().Unix() < Exp`. Токен без `exp` (или с `exp` ≤ 0) недействителен. Во всех остальных случаях — пустые `Claims` и ошибка, для которой `errors.Is(err, ErrInvalid)`.
- Подпись сравнивается за постоянное время.
