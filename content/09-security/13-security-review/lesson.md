В ASP.NET часть ревью безопасности сделана за вас: Razor экранирует вывод, Kestrel ограничивает тело, `[Authorize]` и антифорджери-токены подключаются атрибутами, а `UseExceptionHandler` прячет исключения. В Go каждая из этих защит — строка в вашем коде, поэтому ревью Go-сервиса — это проход по чек-листу, где у каждого пункта есть «что искать» и «как проверить атакой»:

| Что проверить | Что искать в коде | Атака-проверка |
| --- | --- | --- |
| Права на объект (IDOR) | запрос по `id` без условия на владельца — в **каждом** хендлере, который его использует | чужой `id` с токеном другого пользователя |
| SQL | `+` и `fmt.Sprintf` рядом с SQL; имена столбцов и `ORDER BY` из ввода | `' OR 1=1 --`, подзапрос в `sort` |
| HTML | `text/template` для HTML, `template.HTML(...)`, `template.JS`, `template.URL` от данных пользователя | `<script>`, `<img onerror>`, `javascript:` |
| Файлы и процессы | `filepath.Join(dir, ввод)`, `os.Open` с вводом, `exec.Command("sh", "-c", ...)` | `../`, абсолютный путь, символическая ссылка наружу |
| Лимиты | `json.NewDecoder(r.Body)` без `MaxBytesReader`, `&http.Server{}` без таймаутов, `io.ReadAll` ответа | мегабайтное тело, медленный клиент |
| Ошибки и логи | `err.Error()` в ответе, паника без recover, секреты в `%v` и в логах | закрытая база, каталог вместо файла |
| Остальное | `InsecureSkipVerify`, `math/rand` для токенов, `==` для секретов, CORS с отражением `Origin`, исходящие запросы по URL из ввода | уроки 06–09 модуля |

Хорошая привычка — превращать каждую найденную уязвимость в тест-эксплойт: он падает, пока дыра открыта, и не даст ей вернуться при рефакторинге. Пример урока — такой чек-лист в миниатюре: набор атак прогоняется по уязвимой и исправленной версиям хендлеров, результат — таблица. Скрытые тесты задачи устроены так же.

## Как это в C#

- Razor экранирует `@value` всегда, а `@Html.Raw(...)` — явный и заметный выход из защиты. В Go таким выходом служат `template.HTML(...)` и… выбор `text/template` вместо `html/template` — его на ревью легко пропустить, ищите оба.
- `[Authorize]` проверяет, что пользователь вошёл, но не что объект его: для этого в ASP.NET есть resource-based authorization (`IAuthorizationService.AuthorizeAsync(user, resource, policy)`). В Go и то и другое — явные проверки в коде хендлера или в запросе к базе (`WHERE id = ? AND owner = ?`).
- `PhysicalFileProvider` и `UseStaticFiles` отвергают `..` и абсолютные пути, но файл по симлинку наружу отдадут. В Go `os.Root` (Go 1.24) закрывает и `..`, и симлинки, а `filepath.Join` — ничего из этого.
- EF Core параметризует LINQ-запросы сам; `FromSqlRaw` с конкатенацией — та же дыра, что `db.Query("..." + s)` в Go. Сортировку по имени столбца из запроса в обоих мирах делают через allowlist.

## Ловушки

### Починили один хендлер — забыли второй

```go
mux.HandleFunc("GET /notes/{id}", s.getNote)       // проверка владельца добавлена
mux.HandleFunc("GET /notes/{id}/html", s.noteHTML) // УЯЗВИМО: та же выборка без проверки
```

Права на объект проверяйте там, где объект загружается, — в одной функции доступа к данным (`WHERE id = ? AND owner = ?`), а не в каждом хендлере. Тогда новый маршрут не сможет забыть проверку.

### `403` для чужого объекта

```go
if n.Owner != user {
	http.Error(w, "forbidden", http.StatusForbidden) // подтверждает, что id существует
	return
}
```

Ответ `403` против `404` — оракул: перебором `id` атакующий узнаёт, какие объекты существуют и сколько их. Для чужого объекта отвечайте так же, как для несуществующего.

### Экранирование вместо allowlist для идентификаторов

```go
// УЯЗВИМО: «экранирование» кавычек не спасает — в ORDER BY
// годится любое выражение без кавычек: (CASE WHEN ... END)
sort = strings.ReplaceAll(sort, "'", "''")
query := "SELECT ... ORDER BY " + sort
```

Имя столбца и направление сортировки плейсхолдером не передать. Единственная надёжная защита — сопоставить ввод с заранее известным списком: `map[string]string{"title": "title", "id": "id"}`, а неизвестное значение отвергнуть.

## Задание

В `task.go` — сервис заметок. Он работает, и открытые тесты проходят, но код **уязвим**: в нём несколько уязвимостей из уроков модуля. Найдите их и закройте, не меняя сигнатур и не ломая поведение, описанное ниже. Каждую уязвимость атакует свой скрытый тест-эксплойт.

```go
type Note struct {
	ID    int64  `json:"id"`
	Owner string `json:"owner"`
	Title string `json:"title"`
	Body  string `json:"body"`
}

func New(db *sql.DB, files string, tokens map[string]string) (*Service, error)
func (s *Service) Handler() http.Handler
```

`New` создаёт таблицу `notes` в `db` (тесты передают SQLite в памяти с одним соединением) и запоминает каталог вложений `files` и карту «токен → имя пользователя». Каждый запрос аутентифицируется заголовком `Authorization: Bearer <токен>`; нет заголовка или токен неизвестен — `401`.

- `POST /notes` с JSON `{"title": …, "body": …}` (неизвестные поля игнорируются) создаёт заметку текущего пользователя и отвечает `201` и JSON созданной `Note`. Невалидный JSON — `400`. `title` от 1 до 200 символов, `body` не длиннее 10 000 символов (символы — руны), иначе `400`. Тело запроса больше 64 КиБ — `413`, заметка не создаётся.
- `GET /notes?sort=…` — JSON-массив заметок текущего пользователя (пустой — `[]`). `sort` — `id` (по умолчанию, если параметр пуст или отсутствует) или `title`, по возрастанию; другое значение — `400`.
- `GET /notes/{id}` — JSON заметки. Заметка, которой нет или которая принадлежит другому пользователю, или нечисловой `id` — `404`.
- `GET /notes/{id}/html` — HTML-страница заметки (`Content-Type: text/html; charset=utf-8`): заголовок и тело выводятся как текст — любые символы показываются буквально, — а перевод строки `\n` в теле отображается как `<br>`. Для недоступной заметки — `404`, как выше.
- `GET /files?name=…` — содержимое файла вложения как `application/octet-stream`. Отдаются только обычные файлы, лежащие внутри каталога `files`; символическая ссылка отдаётся, только если её цель тоже внутри каталога. Всё, что отдать нельзя (нет файла, каталог, путь за пределами `files`), — `404`.
- Любая непредвиденная ошибка (например, сбой базы) — `500` с телом `internal error`; подробности ошибки клиенту не показываются (в лог — можно).
