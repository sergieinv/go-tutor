SQL-инъекция появляется, когда ввод становится частью **текста** запроса. `"... WHERE name = '" + name + "'"` или `fmt.Sprintf` с `%s` дают одну строку, и СУБД не может узнать, где кончился ваш SQL и начались данные пользователя. Кавычка во вводе закрывает литерал, и всё, что после неё, разбирается как код: `' OR 1=1 --` превращает условие в тавтологию, `'; DROP TABLE ...` — в новую команду, `' UNION SELECT ...` — в чтение чужой таблицы.

Плейсхолдер разделяет текст и данные на уровне протокола: `db.QueryContext(ctx, "... WHERE name = ?", name)` отправляет текст с `?` и значения **отдельно**. СУБД разбирает текст и фиксирует структуру запроса до того, как увидит значение, а значение потом занимает готовый слот и сравнивается как данные — с кавычками, `--` и чем угодно ещё. Так работают и `QueryContext` с аргументами, и явный `PrepareContext`; некоторые драйверы (MySQL с `interpolateParams=true`, режим simple protocol в `pgx`) подставляют значения на стороне клиента, но делают это по правилам литералов своей СУБД, а не вашей склейкой. Это экранирование — код драйвера, и в нём тоже находят ошибки (CVE-2024-27289 в simple protocol `pgx`, исправлена в v4.18.2), поэтому драйвер держат обновлённым. Правило одно: **в текст запроса попадают только константы из кода**, всё от клиента — в аргументы.

Плейсхолдер передаёт только значения. Имя таблицы или колонки, `ASC`/`DESC` — это структура, и `ORDER BY ?` не ошибка, а сортировка по константе (см. квиз). Для них — allowlist: карта «что прислал клиент → готовый фрагмент SQL, написанный вами», а всё, чего в карте нет, — отказ. Списки для `IN (...)` собирают из стольких `?`, сколько значений, — пустой список обрабатывают отдельно, `IN ()` — синтаксическая ошибка. А у `LIKE` свои метасимволы внутри значения: `%` — любая строка, `_` — любой символ. Это не инъекция — значение пришло плейсхолдером, — но ввод `%` превращает «поиск по подстроке» в «выдать всё», а `%a%b%c%...` на большой таблице — в долгий запрос. Экранируйте `\`, `%`, `_` и указывайте `ESCAPE '\'`.

## Как это в C#

- `cmd.Parameters.AddWithValue("@name", name)` или `DbParameter` → аргументы после текста: `db.QueryContext(ctx, q, name)`. Отличие только в синтаксисе плейсхолдеров: `?` в SQLite и MySQL, `$1` в PostgreSQL, именованных `@name` в `database/sql` по умолчанию нет (есть `sql.Named`, если драйвер поддерживает).
- EF Core `FromSqlInterpolated($"... {name}")` превращает интерполяцию в параметры, а `FromSqlRaw` с конкатенацией — нет. В Go такой «умной» строки нет: `fmt.Sprintf` всегда склейка, без исключений.
- Dapper разворачивает `WHERE id IN @ids` в список параметров сам. В `database/sql` `?` для каждого элемента собирают руками; в `sqlx` для этого есть `sqlx.In`.
- `ORDER BY` с колонкой от клиента одинаково опасен в обоих языках; LINQ в EF Core (`OrderBy(x => x.Price)`) решает это типами, в Go — allowlist.

## Под капотом

`db.QueryContext(ctx, query, args...)` сам по себе SQL не разбирает. `database/sql` берёт соединение из пула, приводит каждый аргумент к одному из типов драйвера (`int64`, `float64`, `bool`, `[]byte`, `string`, `time.Time` или `nil`; свои типы — через `driver.Valuer`) и передаёт драйверу пару «текст + `[]driver.NamedValue`». Если драйвер не умеет выполнять запрос сразу, `database/sql` сначала вызывает у него `Prepare`, а потом `Query` у подготовленного выражения — но текст и значения и тогда идут раздельно. Драйвер `modernc.org/sqlite` компилирует текст функцией SQLite `sqlite3_prepare_v2` в байт-код с пронумерованными слотами `?1`, `?2`…, а значения кладёт в слоты через `sqlite3_bind_*`. К моменту привязки разбор уже закончен — значению некуда «вылезти». С PostgreSQL то же происходит по сети: сообщения `Parse` (текст с `$1`) и `Bind` (значения) в расширенном протоколе — разные пакеты.

При склейке аргументов нет, и драйвер отдаёт парсеру всё. Причём `modernc.org/sqlite` выполняет в одном `QueryContext` **все** команды текста, разделённые `;`: нагрузка `x'; DELETE FROM users; --` в «поиске пользователя» действительно очищает таблицу (проверено на версии из песочницы). Не все драйверы так делают — MySQL без `multiStatements=true` откажет, — но полагаться на это нельзя: тавтология и `UNION SELECT` работают и в одной команде.

Ниже одна и та же строка ввода проходит оба пути: склейку, где она становится частью текста SQL и меняет структуру запроса, и плейсхолдер, где структура зафиксирована при подготовке, а ввод — значение в отдельном слоте.

## Ловушки

### `Sprintf` для «безопасных» типов

```go
// УЯЗВИМО: сегодня id — int, завтра поле станет string.
q := fmt.Sprintf("SELECT * FROM orders WHERE id = %v", id)
```

Целое число инъекцию не пропустит, но правило «в текст — только константы» удобно тем, что не требует думать о типах: рефакторинг поменяет `int64` на строковый UUID, а `Sprintf` останется. Проверка в ревью — одна: нет ли в аргументе `QueryContext`/`ExecContext` склейки или `Sprintf` с данными. Пишите `db.QueryContext(ctx, "... WHERE id = ?", id)` всегда.

### Самодельное экранирование

```go
// УЯЗВИМО: защищает только внутри кавычек.
safe := strings.ReplaceAll(input, "'", "''")
q := "SELECT * FROM users WHERE id = " + safe // input = "0 OR 1=1"
```

Удвоение кавычек работает только в строковом литерале; в числовом контексте, в `LIKE`, в идентификаторах и в СУБД с обратной косой (`\'` в MySQL) правила другие. Экранирование — задача драйвера, а ваша — передать значение плейсхолдером.

### `LIKE` без экранирования

```go
db.QueryContext(ctx, `SELECT * FROM products WHERE name LIKE ?`, "%"+q+"%")
// q = "%"  → все товары; q = "_" → все с непустым именем
```

Инъекции нет, но поиск делает не то, что обещан. Экранируйте метасимволы и объявляйте escape-символ:

```go
var likeEscaper = strings.NewReplacer(`\`, `\\`, `%`, `\%`, `_`, `\_`)
db.QueryContext(ctx, `SELECT * FROM products WHERE name LIKE ? ESCAPE '\'`, "%"+likeEscaper.Replace(q)+"%")
```

## Задание

Напишите поиск товаров, все параметры которого приходят от клиента как есть.

```go
const Schema = `CREATE TABLE products (
	id       INTEGER PRIMARY KEY,
	name     TEXT NOT NULL,
	category TEXT NOT NULL,
	price    INTEGER NOT NULL
)`

type Product struct {
	ID       int64
	Name     string
	Category string
	Price    int64
}

type Filter struct {
	NameContains string   // подстрока имени; "" — без фильтра
	Categories   []string // категория — одна из списка; пусто — без фильтра
	Sort         string   // "", "id", "-id", "name", "-name", "price", "-price"
}

var ErrBadSort = errors.New("bad sort")

func Search(ctx context.Context, db *sql.DB, f Filter) ([]Product, error)
```

Таблицу создают и заполняют тесты; драйвер `modernc.org/sqlite` импортируют тоже тесты — `task.go` использует только стандартную библиотеку. Требования:

- `Sort` — одно из значений `""`, `"id"`, `"-id"`, `"name"`, `"-name"`, `"price"`, `"-price"` (точно, с учётом регистра). Иначе — `nil` и ошибка, для которой `errors.Is(err, ErrBadSort)`, без обращения к базе. Минус — по убыванию; `""` — то же, что `"id"`. Строки с одинаковым значением ключа сортировки — по возрастанию `id`. Порядок строк — средствами SQLite (`ORDER BY`, по умолчанию побайтовое сравнение).
- `NameContains` — имя содержит эту подстроку **буквально**: символы `%`, `_` и `\` во вводе — обычные символы. Сравнение — как у оператора `LIKE` в SQLite: латинские буквы без учёта регистра, остальные символы точно.
- `Categories` — категория товара в точности равна одному из элементов (с учётом регистра); повторы в списке допустимы. `nil` или пустой срез — без фильтра.
- Фильтры объединяются через «и». На **любые** значения `NameContains`, `Categories` и `Sort` функция возвращает только строки, подходящие под описание выше, и никогда не меняет данные; ошибка — только при неверном `Sort` или сбое базы.
- Результат — срез длины 0 (`nil` допустим), если ничего не нашлось. Ошибки базы, в том числе отменённого `ctx`, возвращаются как есть или обёрнутыми; соединение возвращается в пул (`rows.Close`).
