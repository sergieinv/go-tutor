Контракт живёт дольше любой версии кода. Мобильное приложение двухлетней давности, соседний сервис, который выкатывают раз в месяц, сообщения в очереди Kafka, записанные вчера, — всё это говорит со свежим сервером на старой версии `.proto`. Обновить всех одновременно нельзя, поэтому каждое изменение контракта должно быть **совместимым в обе стороны**: новый код читает старые байты, старый — новые.

Protobuf для этого и придуман: по проводу идут номера полей и wire type, а не имена и не порядок. Получатель пропускает незнакомые номера, а для отсутствующих полей подставляет нули. Отсюда правила.

**Можно:**

- **Добавить поле** с новым номером. Старый код его не знает и сохранит как неизвестное, новый код, читая старые байты, получит ноль. Значит, ноль должен быть безопасным значением по умолчанию, либо поле — `optional`, чтобы «не пришло» отличалось от нуля.
- **Удалить поле**, зарезервировав номер и имя: `reserved 4; reserved "promo_code";`. Без `reserved` через год кто-нибудь займёт номер 4 под `discount_percent`, и старые клиенты станут присылать промокод там, где новый сервер ждёт скидку. Имя резервируют ради JSON: в нём поле идёт по имени. Для провода удаление с `reserved` безопасно, но сгенерированный код клиентов, обращавшихся к полю, перестанет собираться — поэтому поле сначала помечают `[deprecated = true]` и удаляют, когда им никто не пользуется.
- **Переименовать поле** — в бинарном виде незаметно, но это ломающее изменение для JSON (`protojson`, grpc-gateway) и для исходного кода: клиент на `GetCustomer()` перестанет собираться после обновления контракта. Нужно сохранить JSON — укажите старое имя явно: `string customer_email = 2 [json_name = "customer"];`.
- **Добавить значение enum.** Enum в proto3 открытый: старый клиент сохранит незнакомое число (в Go — `LegacyStatus(3)`, печатается как `3`). Код клиента должен быть к этому готов: `switch` по статусу — с веткой `default`.
- **Добавить сообщение, метод или сервис.**

**Нельзя:**

- **Менять номер** поля — для получателя это удаление старого поля и появление нового.
- **Менять тип.** Получатель видит не тот wire type, кладёт поле в неизвестные и подставляет ноль — ошибки нет, данные тихо пропадают. Совместимы по проводу только группы: `int32`, `uint32`, `int64`, `uint64`, `bool` (все — varint, но 32-битный получатель отбросит старшие биты), `sint32`↔`sint64`, `fixed32`↔`sfixed32`, `fixed64`↔`sfixed64`, `string`↔`bytes` (если байты — UTF-8). В JSON и `int32`↔`int64` уже различаются: строка против числа.
- **Менять `repeated` на одиночное и обратно.** Одиночное поле при повторах берёт последнее значение — остальные элементы списка теряются.
- **Переносить существующее поле в `oneof` или из него.** Старый код может прислать два поля, которые теперь в одном `oneof`, — останется одно. Добавить в `oneof` *новое* поле можно.
- **Менять смысл нулевого значения enum** и удалять значения без `reserved`.

Неизвестные поля Go хранит в сообщении и пишет обратно при `Marshal`, поэтому прокси на старом контракте пересылает новые данные целыми — пример это показывает. Но только пока байты идут через сообщение protobuf: `protojson` неизвестные поля не выводит, а перекладка в доменную структуру и обратно их теряет.

Ломающее изменение всё-таки нужно — делают **новую версию пакета**: `shop.orders.v1` → `shop.orders.v2`, новый каталог, новые сгенерированные типы. Сервер какое-то время обслуживает обе версии (две регистрации сервиса), клиенты переходят по одному, и только потом v1 удаляют. Нестабильные API помечают `v1alpha1`, `v1beta1`: от них совместимости не ждут. Порядок выкатки совместимого изменения — сначала те, кто читает новое поле (обычно сервер), потом те, кто его пишет.

Проверять правила глазами не нужно: `buf breaking` сравнивает контракт с прежней версией (веткой `main`, тегом релиза) и называет каждое нарушение. В песочнице кнопка «buf breaking» сравнивает ваш контракт с исходным контрактом урока. Попробуйте в `order_current.proto` сменить тип `total_cents` на `string`, убрать `reserved 4;` или удалить `paid_at` — и нажмите кнопку. Собственный `buf.yaml` примера включает категорию `FILE`, самую строгую: она считает ломающим даже удаление поля с `reserved` (код клиентов не соберётся). Поменяйте её на `WIRE_JSON` — удаление с `reserved` пройдёт, а на `WIRE` перестанет считаться нарушением и переименование. Подробно о категориях — в уроке 03.

## Как это в C#

- Правила те же: `Google.Protobuf` в C# так же хранит неизвестные поля (`UnknownFieldSet`) и пишет их обратно, а незнакомое значение enum — просто число в enum-типе C#. Совместимость задаёт формат, а не язык.
- Ближайшая аналогия в .NET — версионирование REST API (`Asp.Versioning`, `/api/v2/...`) и контракты DTO с `System.Text.Json`. Но JSON-сериализатор по умолчанию сопоставляет поля по именам, и переименование свойства ломает клиентов сразу; в protobuf опора — номера, а имена важны только для JSON.
- `[Obsolete]` на свойстве DTO ↔ `[deprecated = true]` на поле: генератор C# ставит на свойство `[Obsolete]`, а Go-генератор пишет комментарий `Deprecated:`, и его подсвечивают `staticcheck` и редакторы. Удалять поле всё равно приходится через `reserved`.
- Проверка в CI: в .NET-мире совместимость контрактов обычно ловят ревью или контрактными тестами (Pact); `buf breaking` делает это механически, по дескрипторам — и одинаково для всех языков, сгенерированных из контракта.

## Ловушки

### Номер переиспользован после удаления

```proto
message Order {
  // было: string promo_code = 4;  — удалено без reserved
  uint32 discount_percent = 4; // старые клиенты шлют промокод сюда
}
```

Старый клиент присылает поле 4 как строку, новый сервер ждёт varint: поле уйдёт в неизвестные, и скидка будет 0. Хуже, если типы совпадут по wire type (было `int64 bonus_points = 4`, стало `uint32 discount_percent = 4`): сервер без ошибки прочитает бонусы как процент скидки. Удаляя поле, всегда пишите `reserved` с номером и именем — `buf breaking` в категориях `WIRE` и `WIRE_JSON` поймает удаление без него (`FIELD_NO_DELETE_UNLESS_NUMBER_RESERVED`), а компилятор `.proto` не даст занять зарезервированный номер.

### Переименование «безопасно», пока нет JSON

```proto
string customer_email = 2; // было: string customer = 2;
```

Бинарные клиенты ничего не заметят, а REST-клиенты через grpc-gateway начнут получать `customerEmail` вместо `customer`, и их запросы с `"customer"` сервер отвергнет как незнакомое поле. С `DiscardUnknown: true` — молча потеряет значение. Если контракт отдаётся и в JSON, переименование — ломающее изменение; сохраняйте старое имя через `json_name`.

### Неизвестные поля теряются при перекладке

```go
func forward(in *pb.Order) *pb.Order {
	o := toDomain(in)  // доменная структура знает только старые поля
	return fromDomain(o) // tags и paid_at из новой версии пропали
}
```

Сохранение неизвестных полей работает, только пока байты живут в сообщении protobuf. Промежуточный сервис, который перекладывает сообщение в свою структуру, `protojson` с `DiscardUnknown`, кеш, хранящий JSON, — и новые поля исчезают на полпути. Узлы, которые лишь пересылают данные, должны передавать сообщение (или его байты) целиком.

## Задание

Напишите проверку совместимости двух версий сообщения по дескрипторам — упрощённый `buf breaking`. Дескриптор сообщения даёт любой сгенерированный тип: `(&OrderV1{}).ProtoReflect().Descriptor()`. Контракт с тремя версиями заказа (`contract.proto`) лежит рядом с тестами.

```go
const (
	RuleNoDelete        = "FIELD_NO_DELETE_UNLESS_NUMBER_RESERVED"
	RuleSameCardinality = "FIELD_SAME_CARDINALITY"
	RuleSameType        = "FIELD_SAME_TYPE"
	RuleSameOneof       = "FIELD_SAME_ONEOF"
	RuleSameJSONName    = "FIELD_SAME_JSON_NAME"
	RuleReservedReused  = "RESERVED_REUSED"
)

type Violation struct {
	Rule   string
	Number protoreflect.FieldNumber
}

func Check(prev, next protoreflect.MessageDescriptor) []Violation
```

Поля сопоставляются **по номеру** (имена сообщений `prev` и `next` могут различаться). Проверяются только поля самого сообщения, во вложенные сообщения заходить не нужно. Для каждого поля `prev`:

- **`FIELD_NO_DELETE_UNLESS_NUMBER_RESERVED`** — номера нет в `next`, и он не входит в зарезервированные номера `next` (`ReservedRanges()`).
- **`FIELD_SAME_CARDINALITY`** — у поля сменился вид: одиночное, список (`repeated`, не map) или map. В этом случае остальные правила для этого номера не проверяются.
- **`FIELD_SAME_TYPE`** — сменился `Kind()` (любой, даже совместимый по проводу `int32` → `int64`); для `MessageKind` и `GroupKind` — сменилось полное имя типа сообщения, для `EnumKind` — полное имя enum. У map сравниваются по этим правилам тип ключа и тип значения, а имя служебного сообщения записи (`OrderV1.LabelsEntry`) не важно; сменились и ключ, и значение — всё равно одно нарушение.
- **`FIELD_SAME_ONEOF`** — сменилось короткое имя (`Name()`) `oneof`, в котором лежит поле, или поле вошло в `oneof` либо вышло из него. Синтетический `oneof`, который компилятор создаёт для `optional` (`IsSynthetic()`), за `oneof` не считается: добавить или убрать `optional` — не нарушение.
- **`FIELD_SAME_JSON_NAME`** — сменился `JSONName()`.

Для каждого поля `next`:

- **`RESERVED_REUSED`** — его номер входит в зарезервированные номера `prev` или его имя — в зарезервированные имена `prev` (`ReservedNames()`). Одно нарушение на поле, даже если совпали и номер, и имя. (У buf такого правила нет: внутри одной версии занять зарезервированный номер не даст компилятор, а между версиями buf следит, чтобы `reserved` не исчезали.)

Каждое правило даёт для одного номера не больше одного нарушения. Результат отсортирован по `Number`, при равенстве — по `Rule` (строки по возрастанию). Совместимые версии — пустой результат (длины 0).
