Слово `stream` в контракте превращает вызов в поток сообщений поверх одного HTTP/2-стрима. Вариантов три: `returns (stream X)` — server streaming (подписка, выгрузка), `rpc M(stream X)` — client streaming (загрузка пачки), и поток с обеих сторон — bidi (чат, синхронизация, трекинг). Генератор `protoc-gen-go-grpc` v1.6 выражает их дженериками из пакета `grpc`: обработчик server streaming получает `grpc.ServerStreamingServer[Resp]` с методом `Send`, client streaming — `grpc.ClientStreamingServer[Req, Resp]` с `Recv` и `SendAndClose`, bidi — `grpc.BidiStreamingServer[Req, Resp]` с `Recv` и `Send`. У клиента — зеркальные `ServerStreamingClient`, `ClientStreamingClient` (`Send`, `CloseAndRecv`) и `BidiStreamingClient` (`Send`, `Recv`, `CloseSend`).

Главные правила одинаковы для всех трёх:

- **Конец потока — `io.EOF` из `Recv`.** Клиент видит его, когда обработчик сервера вернул `nil` (статус OK пришёл в трейлерах). Сервер — когда клиент вызвал `CloseSend` (или `CloseAndRecv`). Любая другая ошибка `Recv` — это статус вызова: `status.Code(err)`.
- **Вызов заканчивается возвратом из обработчика.** Возвращённая ошибка становится статусом в трейлерах; уже отправленные сообщения остаются у клиента — стрим, в отличие от unary, может закончиться ошибкой после половины данных.
- **Отмена — через контекст.** Клиент отменяет `ctx`, переданный при открытии стрима; у сервера отменяется `stream.Context()`, а `Send` и `Recv` начинают возвращать ошибки. Обработчик, который ждёт чего-то своего (канала, таймера, внешнего вызова), обязан слушать `stream.Context().Done()`, иначе он переживёт клиента, а `GracefulStop` будет ждать его вечно.
- **Один писатель и один читатель.** `Send` из двух горутин одновременно — гонка, как и `CloseSend` параллельно с `Send`. Разрешено ровно одно: одна горутина пишет, другая читает.

У стрима есть встроенная обратная связь — flow control HTTP/2. У каждого стрима и у соединения есть окно: сколько байт отправитель может послать, пока получатель их не прочитал. Начальное окно — 64 КиБ; grpc-go по умолчанию подстраивает его под пропускную способность канала (BDP-оценка), а `grpc.InitialWindowSize` фиксирует размер. Когда окно исчерпано, `Send` **блокируется**, пока приложение на той стороне не вызовет `Recv`. Поэтому медленный читатель тормозит только свой стрим, а сервер не накапливает в памяти гигабайты непрочитанных ответов. Обратная сторона: обработчик, застрявший в `Send` к медленному клиенту, не должен держать мьютекс или блокировать других — это и есть задача урока.

Когда что выбирать. Стрим хорош, если данные действительно идут потоком (события, логи, телеметрия), если нужно отправить много сообщений без задержки на каждый запрос-ответ или если клиенту нужен сервер-пуш. Unary с пагинацией (`page_size` + `page_token`) лучше для списков: каждый запрос независим, его легко повторить, кешировать и отдать через REST (grpc-gateway отдаёт server streaming потоком JSON-объектов, а client streaming и bidi — лишь ограниченно: сообщения клиента идут подряд в теле одного HTTP-запроса; JSON transcoding в ASP.NET Core умеет только server streaming). Долгий стрим привязан к одному соединению, а значит — к одной реплике за L4-балансировщиком; переподключение и продолжение «с места» — ваша забота (номер последнего полученного события, как `from_seq` в задании).

## Как это в C#

- `IServerStreamWriter<T>.WriteAsync` и `IAsyncStreamReader<T>` с `ReadAllAsync()` ↔ `Send` и цикл `Recv` до `io.EOF`. В .NET конец потока — завершение `await foreach`, в Go — значение-сигнал `io.EOF`, которое легко спутать с ошибкой.
- `call.RequestStream.CompleteAsync()` ↔ `CloseSend`; ответ client streaming — `await call` (или `call.ResponseAsync`) ↔ `CloseAndRecv`. Забыть `CompleteAsync` так же опасно, как `CloseSend`: сервер будет ждать продолжения.
- `ServerCallContext.CancellationToken` ↔ `stream.Context().Done()`. Отмена у клиента — `CancellationToken` при открытии вызова, ошибка — `RpcException` со `StatusCode.Cancelled` ↔ `codes.Canceled`.
- Обратная связь та же — она в HTTP/2, а не в языке: `WriteAsync` в .NET не завершается, пока окно не позволит, ровно как блокирующий `Send` в Go. Разница в стиле: в .NET ждут `await`, в Go блокируется горутина — поэтому в Go медленного подписчика обслуживает своя горутина, и это дёшево.

## Ловушки

### Подписка, которая не слышит отмену

```go
// ЛОВУШКА: после отмены клиента обработчик ждёт события вечно.
func (s *server) Subscribe(req *SubscribeRequest, stream grpc.ServerStreamingServer[Event]) error {
	for ev := range s.events { // канал из pub/sub, отмену не видит
		if err := stream.Send(ev); err != nil {
			return err
		}
	}
	return nil
}
```

`Send` вернёт ошибку только при следующей попытке отправить, а если событий нет, обработчик висит на канале: горутина и память на каждого ушедшего клиента, а `GracefulStop` не дождётся завершения. Ждите и событие, и отмену одним `select`:

```go
select {
case <-stream.Context().Done():
	return stream.Context().Err()
case ev := <-sub:
	if err := stream.Send(ev); err != nil {
		return err
	}
}
```

С `sync.Cond` так не получится: `Wait` не умеет ждать контекст. Для «разбудить всех» в Go используют закрытие канала.

### Рассылка, которая ждёт самого медленного

```go
// ЛОВУШКА: Publish пишет в канал каждого подписчика под мьютексом.
s.mu.Lock()
for _, ch := range s.subscribers {
	ch <- ev // подписчик застрял в Send → канал полон → встали все
}
s.mu.Unlock()
```

Клиент на мобильной сети перестал читать — его `Send` заблокирован flow control, канал заполнился, и вместе с ним встали издатель и все остальные подписчики. Варианты: журнал, из которого каждый подписчик читает со своей позиции (задание), буферизованный канал с политикой «отключить отстающего», или неблокирующая отправка со сбросом — но тогда потерю нужно явно обрабатывать.

### `Recv` после отмены возвращает данные

```go
cancel()
msg, err := stream.Recv() // может вернуть уже полученное сообщение, err == nil
```

Отмена не стирает сообщения, уже лежащие в буфере клиента: следующий `Recv` может вернуть одно из них, и только потом — `codes.Canceled`. Не рассчитывайте, что первый `Recv` после `cancel()` вернёт ошибку; читайте до ошибки или просто прекратите читать.

## Задание

Реализуйте ленту событий заказов по контракту `task/feed.proto` (код сгенерирован, пакет `task`):

```go
type FeedServer struct {
	UnimplementedOrderFeedServiceServer
	// состояние — ваше
}

func NewFeedServer() *FeedServer
func (s *FeedServer) Publish(stream grpc.ClientStreamingServer[PublishRequest, PublishResponse]) error
func (s *FeedServer) Subscribe(req *SubscribeRequest, stream grpc.ServerStreamingServer[SubscribeResponse]) error
```

Тесты регистрируют `NewFeedServer()` на `grpc.NewServer()` и работают через клиента по `bufconn`.

- `NewFeedServer()` возвращает пустую ленту. События нумеруются `seq` = 1, 2, 3, … в порядке приёма — общая нумерация для всех вызовов `Publish`.
- `Publish` читает события, пока клиент не закроет поток. Событие с пустым `order_id` или пустым `status` → вызов сразу завершается с `codes.InvalidArgument` (текст сообщения не проверяется); события, принятые до него в этом же вызове, остаются опубликованными, а следующие уже не читаются. Каждое валидное событие публикуется **сразу при получении** — подписчики видят его, не дожидаясь конца потока издателя. Когда клиент закрыл поток, ответ — `accepted` (сколько событий этого вызова принято) и `last_seq` (`seq` последнего из них, 0 — если ни одного).
- `Subscribe` отправляет события с `seq >= from_seq` (`from_seq <= 0` — с первого) по возрастанию `seq`, без пропусков и повторов: сначала уже опубликованные, затем новые по мере публикации. Если `from_seq` больше последнего `seq`, подписка ждёт, пока событие с таким номером появится. Сам по себе стрим не заканчивается.
- Когда клиент отменяет подписку, обработчик `Subscribe` завершается (тесты проверяют это через `GracefulStop`, который ждёт все обработчики). Что именно он вернёт при отмене, не проверяется — клиент в любом случае видит `Canceled`; естественный вариант — `status.FromContextError(ctx.Err()).Err()`.
- `Publish` никогда не ждёт подписчиков: подписчик, который не читает свой стрим, не замедляет издателей и других подписчиков и при этом ничего не теряет, когда начнёт читать.
- Методы вызываются конкурентно: несколько издателей и подписчиков одновременно. Все подписчики видят одну и ту же последовательность, события одного вызова `Publish` идут в ней в порядке отправки.
