Учебный протокол уроков 01–02 — упрощённая копия настоящего. Здесь — сам настоящий протокол Minecraft Java Edition **1.21.1, номер протокола 767**: что клиент и сервер говорят друг другу от первого байта до появления игрока в мире. Именно его реализует сервер в `labs/gameserver`, к которому подключается настоящий клиент. Описание протокола сообщество ведёт на Minecraft Wiki (раньше — wiki.vg); id пакетов ниже сверены со страницей для 767 и с таблицей `data/packetid` библиотеки `go-mc`. Сервер в курсе — учебная совместимая реализация, не официальный сервер, и ресурсы Mojang (данные реестров, ассеты) мы не цитируем и не распространяем.

**Общее.** Кадр — как в уроке 01: `VarInt длина`, `VarInt id`, данные; длина не больше 2097151 (3 байта VarInt). VarInt и VarLong — не длиннее 5 и 10 байт. Числа фиксированной ширины — big-endian, `Double`/`Float` — IEEE 754. Строка — VarInt длины в байтах и UTF-8, а лимит строки (`String (16)` для ника, `String (32767)` для JSON) считается в **UTF-16 code units** — наследие Java; сервер проверяет и то, и другое. Id пакета значим только вместе с состоянием и направлением: `0x03` от сервера в login — Set Compression, в configuration — Finish Configuration.

**Handshake и status.** Handshake (`0x00`): `Protocol Version` VarInt, `Server Address` String(255), `Server Port` Unsigned Short, `Next State` VarInt (1 — status, 2 — login, 3 — transfer). Status Request (`0x00`) → Status Response (`0x00`) с JSON; Ping Request (`0x01`, Long) → Pong Response (`0x01`, тот же Long), после чего сервер закрывает соединение (урок 02).

**Login.** Login Start (`0x00`): ник String(16) и UUID профиля (с 1.20.2). Дальше ветвление:

- *online-режим* — Encryption Request (`0x01`): идентификатор сервера (пустая строка), публичный ключ RSA в DER, verify token, флаг «проверять сессию». Клиент генерирует 16-байтный общий секрет, шифрует его и verify token ключом сервера (RSA PKCS#1 v1.5), сообщает сессионному серверу Mojang, что входит на этот сервер, и шлёт Encryption Response (`0x01`). Сервер расшифровывает секрет, сверяет verify token, считает SHA-1 от идентификатора, секрета и ключа (в странной знаковой hex-записи) и спрашивает у `sessionserver.mojang.com` (`hasJoined`), входил ли такой игрок. С этого момента весь поток в обе стороны шифруется **AES/CFB8** с ключом и IV, равными секрету. CFB8 в стандартной библиотеке Go нет: там только CFB с сегментом в целый блок, и тот помечен `Deprecated`; `go-mc` держит свою реализацию `net/CFB8`;
- *offline-режим* — ничего этого нет: сервер верит нику и вычисляет UUID v3 от `"OfflinePlayer:"+ник` (урок 02). Нет шифрования, нет проверки — подходит для `127.0.0.1`, тестов и серверов за прокси, который сам проверил игрока.

Затем, если сервер хочет, Set Compression (`0x03`, порог VarInt), и Login Success (`0x02`): UUID, ник, свойства профиля (скин; у offline — ноль) и в 767 ещё булев **Strict Error Handling** — поле, которое было только в 1.20.5–1.21.1. Клиент отвечает Login Acknowledged (`0x03`), и соединение переходит в configuration.

**Configuration** (с 1.20.2) — фаза, где сервер настраивает клиента до входа в мир, и куда может вернуть его посреди игры (Start Configuration в play). Основное:

- Clientbound Known Packs (`0x0E`) — наборы данных сервера (`minecraft:core` версии `1.21.1`); клиент отвечает Serverbound Known Packs (`0x07`) со списком тех, что знает сам;
- Registry Data (`0x07`) — по пакету на реестр: типы измерений, биомы, типы урона, типы чата, варианты картин и волков, узоры брони и баннеров, зачарования и другие. Каждая запись — id и, если клиент не знает набор, данные в NBT. Без обязательных реестров клиент не войдёт в мир;
- Update Tags, Plugin Message (`minecraft:brand`), Feature Flags — по необходимости;
- Finish Configuration (`0x03`) → Acknowledge Finish Configuration (`0x03`) → play.

С 1.20.3 текстовые компоненты (сообщения чата, Disconnect) в configuration и play передаются в **NBT**, а не JSON; в login и status — по-прежнему JSON. Ещё одна причина, почему NBT-библиотека нужна серверу с первого дня.

**Play.** Первые пакеты: Login (`0x2B`) — id сущности игрока, список измерений, максимум игроков, дальность видимости и симуляции (в чанках), тип и имя измерения, режим игры, `Enforces Secure Chat` и ещё полтора десятка полей; Game Event (`0x22`) с событием 13 «ждать чанки»; Set Center Chunk (`0x54`); чанки; Synchronize Player Position (`0x40`). Дальше — постоянный обмен:

- **Чанки** — Chunk Data and Update Light (`0x27`): координаты чанка (Int, Int), карты высот (NBT), данные секций, блочные сущности и свет. Колонна 16×16 по `x, z` делится по высоте на **секции 16×16×16** (в обычном мире их 24: от `y = −64` до `319`). Секция — число непустых блоков и два **контейнера с палитрой**: блоки (4096 записей) и биомы (64 записи). Контейнер хранит «бит на запись» и палитру: 0 бит — вся секция из одного значения; для блоков 4–8 бит — локальная палитра из нескольких состояний, а записи — индексы в ней; больше — прямые id из глобальной палитры. Записи упакованы в массив `long` и с 1.16 не переходят через границу `long`. Отправлять чанки только в зоне видимости и не отправлять заново то, что у клиента уже есть, — урок 07.
- **Позиция.** Сервер ставит игрока пакетом Synchronize Player Position (`0x40`: x, y, z, yaw, pitch, флаги «относительно», teleport id), клиент подтверждает Confirm Teleportation (`0x00`) и дальше шлёт Set Player Position (`0x1A`: x, y ног, z, on ground) или Set Player Position and Rotation (`0x1B`). Сервер обязан проверять перемещения — урок 09.
- **Keep-alive**: `0x26` от сервера, `0x18` от клиента, поле — Long (урок 02).
- **Чат.** Клиент шлёт Chat Message (`0x06`: текст до 256 символов, время, соль, необязательная подпись 256 байт, подтверждения увиденных сообщений) или Chat Command (`0x04`). Сервер рассылает Player Chat (`0x39`) с подписью отправителя или System Chat (`0x6C`) — без подписи. **Подписи сообщений** (с 1.19) — ключ сессии игрока, выданный Mojang (Player Session, `0x07`): кто угодно может проверить, что сообщение написал именно этот игрок. На offline-сервере ключей нет: сервер объявляет `Enforces Secure Chat = false` и рассылает чат без подписей — Player Chat с пустой подписью или, как делают многие серверы, System Chat.
- **Disconnect** (`0x1D`) — причина текстом, затем закрытие.

**Сжатие.** После Set Compression с неотрицательным порогом формат кадра меняется: `VarInt длина кадра` → `VarInt длина данных` → данные. Длина данных — размер `id + данных` до сжатия; `0` значит «не сжато», и дальше пакет как есть. Пакеты от порога и больше сжимаются zlib (RFC 1950 — `compress/zlib`, а не `compress/flate` и не gzip). Ванильный сервер отвергает сжатые пакеты меньше порога, а размер распакованного пакета от клиента ограничен 2²³ = 8388608 байт. Порог по умолчанию в `server.properties` — 256 (`network-compression-threshold`). Распаковка — классическое место для **zlib-бомбы**: deflate сжимает нули примерно в 1000 раз, так что мегабайт сжатых данных разворачивается в гигабайт. Защита — та же, что для gzip в уроке 09-security/10: сравнить объявленный размер с лимитом до распаковки и не распаковывать больше объявленного (`io.LimitReader(zr, n+1)` — лишний байт выдаёт обман).

**Открытые реализации на Go.**

- **`go-mc`** (MIT) — набор библиотек: протокол, NBT, форматы чанков и регионов, данные реестров, бот, заготовка сервера, RCON. В `labs/gameserver` из него берут то, что писать самим долго и неинтересно: NBT, данные реестров, форматы чанков. А кадрирование, VarInt и состояния соединения пишут сами, и не только ради учебы. В разобранной версии (master конца 2024 года) декодер VarInt дочитывает шестой байт, строка читается через `make([]byte, l)` по присланной длине — отрицательная длина вызывает панику `makeslice`, а огромная выделяет память без лимита; длина сжатого кадра не сравнивается с пределом до копирования. А паника в горутине соединения роняет весь процесс, если её не перехватить. Кроме того, пакет `server` библиотеки описывает протокол 764 (1.20.2), а `bot` — 767: версии внутри одной библиотеки расходятся. Протокол меняется каждые несколько месяцев, и границу «наш код — их данные» проще держать, когда сетевой слой свой.
- **Dragonfly** (MIT) — сервер на Go для **Bedrock Edition**: другой протокол (RakNet поверх UDP), другой клиент; полезен как пример архитектуры игрового сервера на Go, но не как источник для Java-протокола.
- На .NET тоже есть открытые реализации серверов Java-протокола (например, Obsidian), построенные на `async`/`await`; сравнивать производительность «вообще» бессмысленно, сравнивайте модель: задачи и пул потоков против горутин и netpoller.

Пример урока — настоящие байты: Handshake и Status Request в том виде, в каком их шлёт клиент 1.21.1, разбор своим кодом, Status Response с JSON, Ping/Pong, Login Success для offline-Steve с полем Strict Error Handling, Known Packs, схема configuration и два кадра после Set Compression: маленький — с длиной данных 0, большой — сжатый zlib и распакованный с лимитом.

## Как это в C#

- **Тот же zlib.** `ZLibStream` (.NET 6+) пишет и читает формат RFC 1950, совместимый с `compress/zlib`; `DeflateStream` — «голый» deflate без заголовка и Adler-32, `GZipStream` — gzip. Перепутать их — частая ошибка при переносе протоколов в обе стороны. Защита от бомбы одинакова: читать не больше объявленного + 1 байт; `CopyTo` и `ReadToEnd` без лимита распакуют всё.
- **Шифрование.** В .NET есть `Aes.EncryptCfb(data, iv, PaddingMode.None, feedbackSizeInBits: 8)` (.NET 6+), но это разовая операция над буфером, а не поток: для соединения IV между вызовами приходится протягивать вручную, поэтому серверы на .NET обычно пишут свой CFB8 поверх AES или берут BouncyCastle. В Go CFB8 тоже пишут сами поверх `cipher.Block` (два десятка строк) или берут у `go-mc`. RSA PKCS#1 v1.5 есть в обоих (`RSA.Decrypt(..., RSAEncryptionPadding.Pkcs1)` ↔ `rsa.DecryptPKCS1v15`), но в Go `DecryptPKCS1v15` с 1.26 помечен `Deprecated`: сам факт ошибки расшифровки раскрывает секрет (атака Блейхенбахера). Протокол Minecraft требует именно PKCS#1 v1.5, поэтому сервер обязан не раскрывать причину неудачи: на любой сбой расшифровки или несовпадение verify token — одно и то же отключение.
- **Протокол как данные.** В .NET пакеты часто описывают классами с атрибутами и генерируют сериализацию (source generators). В Go обычно пишут явный код чтения полей — по строке на поле, как в примере: длинно, зато каждая проверка лимита видна при ревью.

## Ловушки

### Распаковка без лимита

```go
// УЯЗВИМО: 20 КБ сжатых данных разворачиваются в 20 МБ нулей, 20 МБ — в 20 ГБ.
zr, _ := zlib.NewReader(br)
packet, _ := io.ReadAll(zr)
```

Объявленная «длина данных» — тоже число от клиента. Сначала сравнить её с лимитом (`> maxData` — разрыв), потом читать через `io.LimitReader(zr, int64(n)+1)` и проверить, что получилось ровно `n`. Тогда бомба остановится на `n + 1` байте.

### Перепутанные форматы до и после Set Compression

```go
conn.send(setCompression(256))
conn.send(loginSuccess(...)) // УЖЕ в новом формате: длина, длина данных, данные
```

Set Compression действует на **все следующие** пакеты в обе стороны, включая Login Success, а сам он ещё отправлен в старом формате. Сервер переключает и запись, и чтение сразу после отправки Set Compression, клиент — сразу после её получения: следующий пакет клиента, Login Acknowledged, приходит уже в новом формате. Ошибка на один пакет выглядит как «клиент отключился с `Badly compressed packet`» и ищется долго.

### Чужая библиотека как сетевой слой

```go
var name pk.String
name.ReadFrom(conn) // go-mc: длина -1 → panic: makeslice: len out of range
```

Паника в горутине соединения без `recover` роняет весь процесс вместе с миром и всеми игроками — один пакет от любого клиента. Сетевой слой, который читает недоверенные байты, должен проверять каждую длину сам (урок 01) и быть протестирован фаззером. Чужие библиотеки берите для данных (NBT, реестры, чанки), а границу с сетью держите своей — или хотя бы прогоните фаззер по их декодерам.

## Задание

Напишите кодек кадров со сжатием по порогу — формат после Set Compression.

```go
const MaxPacketLength = 2097151

func AppendCompressed(dst, packet []byte, threshold int) ([]byte, error)
func ReadCompressed(r Reader, threshold, maxData int) ([]byte, error) // Reader = io.Reader + io.ByteReader
```

`packet` — пакет без префикса длины: VarInt id и данные (`len(packet) >= 1`), `threshold >= 0`. Кадр: `VarInt длина тела`, затем тело — `VarInt длина данных` и данные. VarInt — как в уроке 01, но проверять неканоническую форму и лишние биты не нужно: больше 5 байт — `ErrVarInt`; поток кончился на первом байте VarInt длины — `io.EOF`, на следующем — `io.ErrUnexpectedEOF`. Ошибки проверяются через `errors.Is`.

**`AppendCompressed`** дописывает кадр к `dst`:

- `len(packet) < threshold` — длина данных `0`, за ней `packet` как есть;
- иначе — длина данных `len(packet)`, за ней `packet`, сжатый `compress/zlib` (уровень любой);
- тело длиннее `MaxPacketLength` — вернуть `dst` без изменений (ни байта не дописано) и `ErrTooLarge`; при успехе — `dst` с дописанным кадром и `nil`.

**`ReadCompressed`** читает из `r` ровно один кадр и возвращает пакет; при ошибке — `nil` и ошибку. По порядку:

1. Длина тела: ошибки VarInt — как выше; меньше 1 — `ErrBadLength`; больше `MaxPacketLength` — `ErrTooLarge` (до чтения тела). Поток кончился внутри тела — `io.ErrUnexpectedEOF`.
2. Длина данных — VarInt в начале тела: тело кончилось внутри неё — `ErrBadLength`, больше 5 байт — `ErrVarInt`.
3. Длина данных `0` — пакет — остаток тела как есть (порог и `maxData` не проверяются); пустой остаток — `ErrBadLength`.
4. Иначе: отрицательная — `ErrBadLength`; меньше `threshold` — `ErrBelowThreshold`; больше `maxData` — `ErrTooLarge`. Эти проверки — до распаковки.
5. Остаток тела — zlib-поток. Распаковывайте до конца потока, но не больше «длина данных + 1» байт (zlib-бомба). Если поток кончился раньше этого предела, его надо дочитать до `io.EOF` — только тогда zlib проверит Adler-32. Ошибка zlib при этом чтении (заголовок, обрыв, контрольная сумма) — `ErrBadCompression`. Если ошибки нет, но распаковано не столько, сколько объявлено (в том числе набран предел «+1»), — `ErrSizeMismatch`. Байты тела после конца zlib-потока игнорируются.

Скрытые тесты проверяют границу порога, предельные размеры, битые и обманные кадры, бомбу из 16 МиБ нулей с объявленными 1000 байт (память не должна расти на мегабайты) и чтение многих кадров подряд из потока по байту.
