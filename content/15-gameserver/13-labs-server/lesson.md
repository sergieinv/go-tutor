Уроки 01–12 разбирали приёмы по одному, каждый на своём упрощённом протоколе. В `labs/gameserver` они собраны в один сервер. Он совместим с подмножеством протокола **Minecraft Java Edition 1.21 / 1.21.1 (протокол 767)**, и рядом с ним работает WebSocket-шлюз для браузерного клиента. Оба вида клиентов живут на одном игровом цикле: игрок в Minecraft и игрок в браузере стоят в одном мире, видят друг друга и пишут в общий чат. Этот урок — путеводитель: как запустить сервер и подключиться, как проходит один тик, где в коде лежит каждая идея модуля, как читать метрики и отчёт нагрузочных ботов и чего сервер честно не умеет.

Сервер учебный и неофициальный, с Mojang не связан. Ресурсов Mojang в репозитории нет: ни jar, ни ассетов, ни дампов данных игры. Подключаться нужно своим лицензионным клиентом. Полное описание (протокол браузерного клиента, переменные окружения, чек-лист ручной проверки) — в `labs/gameserver/README.md`, общая картина — в `labs/README.md`, раздел «Модуль 15».

### Запуск

Серверу не нужны ни базы, ни Kafka, поэтому поднимать его можно отдельно от остального профиля labs. Из корня репозитория:

```sh
docker compose --profile labs up -d --build gameserver   # или docker-compose, если плагина нет
curl -s 127.0.0.1:25590/metrics | grep '^gameserver_tps'  # около 20
```

| Адрес (только 127.0.0.1) | Что |
| --- | --- |
| `127.0.0.1:25565` | Minecraft (TCP) |
| `ws://127.0.0.1:25580/ws` | WebSocket-шлюз браузерного клиента |
| `http://127.0.0.1:25590` | служебный порт: `/metrics`, `/healthz`, `/readyz`, `/debug/pprof/` |

Без Docker: `cd labs/gameserver && GAME_SAVE_PATH=/tmp/world.json go run ./cmd/gameserver`. В Docker мир сохраняется в том `gameserver-data` и переживает пересоздание контейнера; без Docker — в файл из `GAME_SAVE_PATH`.

### Подключиться из Minecraft

Нужен клиент **Java Edition 1.21.1** (или 1.21): «Мультиплеер» → «Добавить сервер» → адрес `localhost`. В списке серверов видно описание «go-tutor labs — учебный сервер (неофициальный)», онлайн и пинг — это фаза status из урока 02. После входа — креатив, вечный полдень и плоский мир из травы с линиями камня по границам чанков. Летайте (двойной пробел), и чанки будут догружаться впереди и выгружаться позади. Граница мира — ±512 блоков. Клиент другой версии получает отказ с текстом: номера пакетов меняются от версии к версии, и сервер не притворяется, что понимает их.

**Почему offline-режим и только локально.** У сервера нет шифрования и проверки сессии у Mojang (урок 03). Поэтому он верит имени, которое прислал клиент: любой может войти под любым ником, а сохранения привязаны к нику. UUID игрока — v3 от `"OfflinePlayer:"+имя`, как у ванильного сервера в offline-режиме (урок 02). На своей машине это нормально, в сети — нет. Поэтому порты опубликованы только на `127.0.0.1`, а в сеть песочницы контейнер не входит.

### Подключиться из браузера

Браузерный клиент — страница сайта учебника [/game/](/game/). Это вид мира сверху с чатом и живым визуализатором: номер тика, MSPT, TPS, зона видимости, события за тик. Откройте её, пока вы в игре в Minecraft: браузерный игрок появится перед вами как обычный игрок со скином по умолчанию и ником в списке Tab, а вы — точкой на его карте. Сообщения чата видны в обе стороны. Сломанный в Minecraft блок меняет цвет клетки на карте. Уйдите дальше 6 чанков — игроки пропадут друг у друга, вернитесь — появятся снова.

Шлюз пускает только страницы из списка `GAME_WS_ORIGINS`: сайт в Docker (`http://localhost:8080`) и dev-сервер Astro (`:4321`). Чужая страница в вашем браузере получит 403 на рукопожатии. Протокол — JSON, чтобы его было видно в DevTools (Network → WS). Сервер шлёт одно сообщение за тик — массив событий, и последним в нём всегда идёт `tick`:

```json
[{"t":"move","id":5,"x":12.345,"y":-60,"z":-3.2,"yaw":90,"pitch":0},
 {"t":"tick","n":10234,"mspt":0.84,"tps":20,"msgs":1,"bytes":67}]
```

По этим `tick` визуализатор и рисует график: `mspt` — длительность прошлого тика, `tps` — фактическая частота, `msgs` — сколько событий ушло **этому** клиенту в этом тике, `bytes` — их размер: байты событий без открывающей `[` и без самого `tick` (в примере выше — 67 байт события `move` с запятой). Браузерный игрок проходит ту же проверку ввода и те же лимиты мира, что игрок Minecraft: для мира это просто игрок с другим кодировщиком.

### Путь одного тика

```
соединение Minecraft ×N                         соединение WebSocket ×M
  горутина чтения: кадры → команды                горутина чтения: JSON → команды
  лимит частоты, дедлайн чтения                   лимит сообщений и кадров, дедлайн
            │ Submit — ждёт, если канал полон (обратное давление)
            ▼
   inbox: chan Command (8192)
            │ не больше 20000 команд за тик
            ▼
   горутина мира (одна, владеет состоянием, мьютексов нет)
     1 ввод: проверка и применение команд → события в w.out
     2 обновление: смена чанков, сетка, видимость, план чанков
     3 рассылка: событие кодируется один раз на протокол,
       пачка на клиента, trySend — не ждёт; полна → slow_consumer
            │                                │ каждые 30 с, если диск свободен: Offer(копия)
            ▼                                ▼
   очередь Peer: chan *Buffer (64 тика)   горутина сохранения: JSON → tmp → fsync → rename
            ▼
   горутина записи: пачки тиков + keep-alive / ping
```

Два направления ведут себя по-разному, и это сделано нарочно. Входящий канал ограничен, и `Submit` ждёт места: горутина чтения перестаёт читать сокет, клиент упирается в TCP-окно, команды не теряются, память не растёт. Исходящая очередь тоже ограничена, но тик не ждёт никогда: если клиент не вычитал 64 пачки (около 3 секунд), он «медленный», и его отключают. Один медленный клиент не тормозит мир для остальных — это урок 05 в действии.

**Игровой цикл (урок 04).** `World.Run` — фиксированный шаг на `time.Timer`, а не `time.Ticker`: расписание `next` растёт ровно на 50 мс за тик, а отставание решает `schedule`:

```go
func schedule(next, now time.Time) (time.Time, int) {
	lag := now.Sub(next)
	if lag <= maxCatchUp { // 5 тиков
		return next, 0 // вовремя или небольшое отставание: догоним подряд
	}
	return now, int(lag / TickInterval)
}
```

Небольшое отставание (пауза GC, подвисание машины) цикл догоняет тиками подряд. Если отставание больше пяти тиков, расписание переезжает на «сейчас», а долг списывается в `gameserver_ticks_skipped_total` и пишется в журнал «can't keep up». Мир замедляется, а не крутит десятки тиков подряд, — тот же выбор, что у ванильного «Can't keep up!». Тик дольше 50 мс пишет предупреждение `tick overran` не чаще раза в 5 секунд: перегрузка не должна превращаться ещё и в шторм журнала. TPS считается по времени начала последних 20 тиков и ограничен сверху двадцатью. Мир читает часы только для этих замеров: время мира — номер тика.

**Соединения и медленный клиент (урок 05).** На соединение — две горутины. Чтение (`readLoop` в `mc/play.go`) ставит дедлайн 30 секунд на каждый кадр, разбирает пакет в `world.Command` и отдаёт его `Submit`. `Command` — значение, а не интерфейс, поэтому отправка в канал не аллоцирует. Запись (`writeLoop`) — единственная горутина, которая пишет в сокет, поэтому мьютекс ей не нужен. Она шлёт пачки из очереди `Peer` и раз в 10 секунд keep-alive. Если ответа нет дольше трёх периодов (30 с), она закрывает `Peer` с причиной `timeout`. Мир кладёт пачки неблокирующей отправкой:

```go
if !p.peer.trySend(b) { // select { case p.out <- b: … default: }
	PutBuffer(b)
	// Очередь полна: клиент не успевает читать. Тик не ждёт —
	// отключаем, убираем из мира в начале следующего тика.
	p.peer.Close(ReasonSlowConsumer)
	w.kicks = append(w.kicks, p)
}
```

`Peer.Close` закрывается через `sync.Once`, причина хранится в `atomic.Pointer[string]`: «побеждает первая причина», сколько бы горутин ни пыталось закрыть соединение. Горутина записи видит закрытый `Peer`, дописывает то, что уже в очереди, и закрывает соединение. Пакета отключения с причиной медленный клиент не получает: его очередь полна, класть некуда. Такой пакет кладёт только `World.kick` — при NaN/Inf во вводе и при остановке сервера, когда очередь обычно свободна. Это будит и горутину чтения, заблокированную в `Read`.

**Тик без аллокаций (урок 06).** В установившемся режиме тик не выделяет память. Пачка клиента берётся из `sync.Pool` и возвращается горутиной записи после отправки, очередь событий тика `w.out` переиспользуется через `[:0]`, кодировщики пишут в стиле append, метрики с метками получены заранее. Одна деталь видна только из escape analysis. Событие перемещения лежит в поле мира `w.moveEv`, а не в локальной переменной: указатель на локальную переменную, переданный в метод интерфейса `Protocol.Append`, «убегает» в кучу, потому что компилятор не знает, что сделает с ним реализация (ловушка ниже). `TestStepAllocsSteadyState` проверяет через `testing.AllocsPerRun`, что тик с 20 игроками без событий не аллоцирует, и пропускается под `-race`: детектор нарочно выбрасывает часть объектов из `sync.Pool`. Нагрузку с движением мерит бенчмарк худшего случая — 200 Minecraft-игроков в одной зоне видимости, все двигаются, каждое перемещение уходит 199 зрителям:

```sh
cd labs/gameserver && go test -run='^$' -bench=Tick200 -benchmem ./internal/mc
# BenchmarkTick200-12   2769   430833 ns/op   2990 B/op   0 allocs/op   (Apple M4 Pro)
```

Это около 0,4 мс из бюджета 50 мс и ноль аллокаций на тик. Байты на операцию — амортизированный рост переиспользуемых буферов.

**Чанки и interest management (урок 07).** Мир — квадрат ±512 блоков, зона видимости — квадрат `(2R+1)²` чанков вокруг чанка игрока (`GAME_VIEW_DISTANCE`, по умолчанию R = 6). Когда игрок меняет чанк, фаза обновления выгружает чанки вне нового квадрата, шлёт новый центр (Set Center Chunk) и строит план загрузки: недостающие чанки, отсортированные по расстоянию, ближние первыми. Отправляется не больше `ChunksPerTick` (8) чанков за тик: телепорт не должен забить исходящую очередь и сделать игрока «медленным». У всех один радиус, поэтому отношение «видит» симметрично, и видимость пересчитывается только для тех, кто сменил чанк: пары с ними обновятся с обеих сторон. Перемещения рассылаются дельтой от последней разосланной позиции: в Minecraft это Update Entity Position в 1/4096 блока в `int16`, а дальше 8 блоков — Teleport Entity (`appendMove` в `mc/encoder.go`). Плоский мир почти весь одинаковый, поэтому базовые секции чанка, карта высот и свет кодируются один раз при старте, а готовые сжатые пакеты чанков кешируются по позиции и версии чанка.

| Событие | Получатели |
| --- | --- |
| перемещение, поворот | те, кто видит игрока (кроме тех, кто увидел его в этом тике: им ушло появление с актуальной позицией) |
| появление, исчезновение | при входе в квадрат и выходе из него, парами в обе стороны |
| чат игрока | автор и те, кто его видит |
| вход, выход (список игроков, системные сообщения) | все |
| изменение блока | те, у кого загружен этот чанк |

**Пространственный хеш (урок 08).** `grid.go` — 50 строк: `map[ChunkPos][]*Player`, ячейка равна чанку, удаление — обменом с последним. Вопрос «кто рядом?» превращается из перебора всех игроков в обход `(2R+1)²` = 169 ячеек вокруг, и при 200 игроках на большой карте это десятки проверок вместо 200.

**Проверка ввода (урок 09).** Клиент присылает желаемое («я теперь здесь», «я сломал этот блок»), а сервер решает, возможно ли это, и правила одинаковы для обоих протоколов. NaN или Inf в координатах или углах — сразу отключение `bad_input`: NaN «проходит» любые сравнения. Скорость проверяется «бюджетом пути»: он пополняется на `MaxSpeed/20` блока за тик и копится не больше чем на секунду, так что два пакета в одном тике из-за джиттера проходят, а телепортация — нет. Превышение — телепорт назад на последнюю верную позицию (`too_fast`), и перемещения игнорируются, пока клиент не подтвердит телепорт. Чат и действия с блоками ограничены ведром токенов, время в котором — номер тика (`ratelimit.go`), поэтому тесты проверяют лимиты без `sleep`. А лимиты частоты стоят в горутинах чтения и считаются по `time.Now`: у Minecraft — 100 пакетов в секунду с запасом 300, у WebSocket — 40 сообщений в секунду с запасом 80 и отдельно 80 кадров в секунду с запасом 160 (этот считает и ping, и пустые фрагменты, которых лимит сообщений не видит). Это защита соединения, она живёт вне детерминированного мира и отключает флудера ещё до того, как его пакеты займут место в `inbox`.

**Снапшоты и остановка (урок 10).** Каждые 30 секунд тик спрашивает `Store.Busy()`: если прошлое сохранение ещё пишется, снапшот пропускается (`gameserver_snapshots_total{result="skipped"}`), и состояние даже не копируется — незачем делать копию, которую некуда отдать. Иначе тик копирует сохраняемое состояние (правки блоков относительно генератора и позиции игроков по нику) и отдаёт копию неблокирующим `Offer`. Число правок ограничено `GAME_MAX_BLOCK_EDITS` (по умолчанию 100 000), поэтому копия в тике не растёт без предела. Горутина сохранения пишет JSON во временный файл в том же каталоге, делает `fsync`, переименовывает его поверх старого и делает `fsync` каталога. Упади процесс посреди записи — на диске останется прошлый целый снапшот. Остановку собирает `app.Run`. `SIGTERM` от `docker stop` отменяет контекст через `signal.NotifyContext`. Дальше по порядку: `/readyz` начинает отвечать 503, слушатели закрываются, мир досчитывает тик, шлёт каждому игроку «Server is shutting down» и отдаёт финальный снапшот, соединениям даётся до 5 секунд дописать отключение, и снапшот пишется на диск синхронно. `TestGracefulShutdownSaves` (`app/app_test.go`) перезапускает сервер и проверяет, что блок на месте, а игрок появляется там, где вышел.

**Симуляция и боты (урок 11).** `world/world_test.go` гоняет мир без сокетов и горутин: тики вызываются вручную (`Step`), часы фейковые, а тестовый протокол `textProto` записывает события строками. Среди тестов есть свойство видимости на случайных блужданиях: клиент, который собирает картину только из `spawn`/`despawn`, в каждом тике видит ровно тех, кто в радиусе. `e2e/e2e_test.go` — главная автоматическая проверка совместимости. Бот `go-mc/bot` делает пинг списка серверов, входит, разбирает чанки парсером go-mc, а второй бот и браузерный игрок видят друг друга, переписываются в чате и замечают выход. Нагрузочные боты `cmd/bots` написаны на своём `mcproto` и на WebSocket. Сжатые пакеты (чанки) они не распаковывают, чтобы не отнимать CPU у сервера на той же машине.

**Протокол и состояния (уроки 01–03).** `mcproto.FrameReader` читает длину кадра VarInt не длиннее 3 байт, проверяет её до выделения буфера и держит разные пределы на разных фазах: 1 КиБ до входа (handshake, status, login), 4 КиБ в configuration, 32 КиБ в игре. До входа в игру клиент может прислать не больше 128 пакетов (`maxPrePlayPackets`), а на весь вход есть 10 секунд (`LoginTimeout`): иначе он мог бы держать слот соединения, присылая пакеты, которые configuration пропускает. После Set Compression (порог 256 байт) распакованный размер обязан не превышать предел и совпасть с заявленным — это защита от zip-бомбы. Сжатый пакет короче порога — нарушение протокола. Состояния — обычный код сверху вниз в `mc/server.go`: `handle` читает handshake и идёт в `status` или `login`, `login` включает сжатие, шлёт Login Success, ждёт Login Acknowledged и переходит в `configure`, а оттуда в `play`. Горутина на соединение позволяет писать автомат состояний прямой последовательностью вызовов — без колбэков и без `async`.

**Что из go-mc и почему.** Из [go-mc](https://github.com/Tnze/go-mc) (MIT) взято то, что писать руками бессмысленно: номера пакетов (`data/packetid`), таблица состояний блоков 1.21.1 (`level/block`), реестр типов сущностей (`data/registryid`), а в тестах — бот и парсер чанков. `TestPacketIDs` сверяет номера с таблицей протокола 767, чтобы обновление go-mc сломало тест, а не клиента. Кадрирование, сжатие, состояния, игровой цикл и рассылка — свои: это предмет модуля, и здесь нужны свои лимиты и свой контроль над буферами. Фреймворк `go-mc/server` написан под протокол 764 и не используется. Отдельная история — реестры. В фазе configuration клиент 1.21 ждёт данные реестров: типы урона, биомы, измерения. Полное их содержимое — данные Mojang. С 1.20.5 сервер может предложить **известный набор данных** (known pack) `minecraft:core` нужной версии. Клиент с ванильными данными отвечает, что набор у него есть, и тогда Registry Data несёт только имена записей с флагом «данных нет» (`mc/registries.go`). Поэтому в репозитории лежат только списки идентификаторов, а клиент без ванильных данных получает отказ. Отдельная ловушка совместимости — Game Event 13 «start waiting for level chunks»: без него клиент 1.20.3+ навсегда остаётся на экране «Загрузка ландшафта».

**Одно кодирование на протокол.** Мир не знает ни Minecraft, ни JSON. Он порождает нейтральные события (`world.Event`), а превращает их в байты интерфейс из трёх методов:

```go
type Protocol interface {
	Begin(dst []byte) []byte              // начать пачку тика для клиента
	Append(dst []byte, ev *Event) []byte  // дописать событие (можно ничего)
	End(dst []byte, st *BatchStats) []byte // завершить; пустая пачка не отправляется
}
```

Реализаций две: `mc.Encoder` (бинарные пакеты, общий `PacketWriter` с буфером тела и zlib, кеш пакетов чанков) и `gateway.Encoder` (JSON, написанный вручную в стиле append: `encoding/json` с рефлексией аллоцировал бы на каждое событие). Экземпляр один на все соединения своего типа и вызывается только из горутины тика, поэтому кеши внутри него обходятся без блокировок. Широковещательное событие кодируется **один раз на протокол** и копируется в пачки всех получателей (`appendEncoded`): при 200 зрителях одного перемещения это два вызова кодировщика вместо двухсот. Кеш — срез из записи на протокол, который сбрасывается перед каждым событием. Пример и задача урока — об этом механизме.

**Свой WebSocket.** Стандартная библиотека Go WebSocket не умеет, а документация `golang.org/x/net/websocket` сама отсылает к более развитым пакетам (`github.com/coder/websocket`, `gorilla/websocket`). Шлюзу нужно маленькое подмножество RFC 6455: текстовые сообщения, ping/pong, close, лимит размера, без расширений и подпротоколов. Это меньше 500 строк в `websocket/` с тестами на фрагментацию, управляющие кадры между фрагментами, коды закрытия, UTF-8 и маскирование, плюс fuzz-тест `FuzzReadMessage`. permessage-deflate не поддержан нарочно: сжатие — отдельный класс атак, а браузер работает и без него. Свои лимиты есть и у шлюза: сообщение не больше 4 КиБ, кадров — не больше 80 в секунду (`AllowFrame` вызывается на каждый кадр, включая ping и пустые фрагменты; превышение — close 1008), а на первое сообщение `hello` — абсолютный дедлайн 5 секунд, который ни ping, ни фрагменты не продлевают. Запись в `websocket.Conn` идёт под мьютексом: pong из горутины чтения не должен перемешаться с кадрами горутины записи.

**Сборка (`app/app.go`).** Вся композиция — в одной функции `Run`, явно и в порядке использования, как в модуле 10: свой реестр Prometheus, загрузка снапшота, мир, два кодировщика, три слушателя, служебный порт с `/metrics`, пробами и pprof. Остановка идёт в обратном порядке. Интеграционные тесты вызывают тот же `Run` с адресами `127.0.0.1:0`.

### Метрики

| Метрика | Как читать |
| --- | --- |
| `gameserver_tick_duration_seconds` (гистограмма) | MSPT. p99: `histogram_quantile(0.99, rate(gameserver_tick_duration_seconds_bucket[1m]))`. Бюджет — 50 мс |
| `gameserver_tick_duration_max_seconds` | максимум за последние 5 секунд: пики, которые сглаживает гистограмма |
| `gameserver_tps` | частота по последним 20 тикам, не больше 20. Пока сервер успевает, около 20 (19,9x — дрожание таймера) и ничего не говорит; меньше — уже перегрузка |
| `gameserver_ticks_total`, `gameserver_ticks_skipped_total` | тики и списанный долг |
| `gameserver_disconnects_total{reason}` | `quit`, `timeout`, `slow_consumer`, `rate_limit`, `bad_packet`, `bad_input`, `shutdown`. Набор меток фиксирован: произвольные значения раздули бы метрики |
| `gameserver_rejected_input_total{reason}` | отклонённый ввод: `too_fast`, `out_of_bounds`, `not_finite`, `chat_rate`, `block_reach`, `block_limit` (в мире уже `GAME_MAX_BLOCK_EDITS` правок)… |
| `gameserver_inbox_length` | очередь команд в начале тика. Растёт — мир не успевает разбирать ввод |
| `gameserver_bytes_out_total{proto}` | исходящий трафик по протоколам |
| `gameserver_chunk_cache_hits_total`, `…_misses_total` | кеш готовых пакетов чанков |
| `gameserver_snapshots_total{result}` | сохранения: `ok`, `skipped`, `error` |

Prometheus профиля labs собирает их как job `gameserver`. Рядом — `go_*` и `process_*`: паузы GC, горутины, память. В compose стоит `GOMEMLIMIT=400MiB` при `mem_limit: 512m` (урок 13-runtime/05): у потолка GC работает чаще, а не ловит OOM-killer.

### Отчёт ботов

```sh
docker compose --profile labs run --rm gamebots                          # 200 ботов, 60 с
docker compose --profile labs run --rm gamebots -n 8 -duration 5s -ramp 2s
```

Сервис `gamebots` живёт в профиле `loadtest`, поэтому `up` его не запускает, а `run` включает профиль сам. По умолчанию — 200 ботов: 75% по протоколу Minecraft (150), 25% через WebSocket (50). Каждый ходит со скоростью 4,3 блока в секунду к случайным точкам в квадрате ±160 блоков (`-spread`), шлёт позицию каждый тик и примерно раз в 20 секунд пишет в чат. Прогон идёт так: подключение за `-ramp` (10 с), 3 секунды на загрузку чанков, замер `-duration`. Каждую секунду боты снимают `/metrics` сервера. Вот прогон с ноутбука автора сервера (Apple Silicon, Docker Desktop):

```
=== gameserver load report: 200 bots, 1m0s ===
players online      min 200
TPS                 avg 20.00  min 19.97   (target 20)
ticks               1200 (20.0/s), skipped 0
MSPT                p50 1.47 ms  p99 5.63 ms  max 23.61 ms   (budget 50 ms)
traffic out         11.80 MB/s
bots                joined 200, failed to join 0, dropped 0, moves 3995/s, packets in 299024/s, chat recv 965/s
server corrections  0 teleports to bots, 0 rejected inputs
server disconnects  none
verdict             PASS: the server holds 20 TPS
```

- **TPS avg/min** — среднее и минимум ежесекундных снятий `gameserver_tps`. Ниже 20 — тик не укладывается в 50 мс или цикл списывает долг.
- **MSPT p50/p99** — квантили по **приросту** гистограммы за время замера, с линейной интерполяцией внутри корзины, как у `histogram_quantile`. `max` — наибольшее снятие `gameserver_tick_duration_max_seconds`. Одиночный пик в 20–30 мс — обычно пауза машины или GC. Он не опасен, пока p99 далеко от 50 мс.
- **traffic out** — главная статья расхода: перемещения 200 игроков, каждое уходит всем, кто видит. Это квадратичная часть нагрузки, и на ней виден interest management.
- **dropped, server disconnects** — в здоровом прогоне 0 и `none`. `slow_consumer` здесь значит, что машина не успевает вычитывать трафик ботов.
- **server corrections** — поправки позиции ботам. Боты ходят медленнее предела, поэтому должно быть 0.
- **verdict** — критерий этапа: TPS avg ≥ 19.5, min ≥ 18.5, p99 < 50 мс, нет списанных тиков, все боты вошли и не отвалились. Код выхода 0 — PASS, 2 — FAIL: прогон годится для CI.

Числа зависят от машины и её загрузки: сравнивайте направление, а не значения. Боты и сервер на одной машине делят CPU, поэтому по-честному нагрузку дают с другой машины (урок 11).

### Ограничения

- **Протокол — подмножество.** Нет шифрования и online-режима, скинов (свойства профиля пустые), команд (`/…` игнорируются), инвентаря и предметов (кроме выбора блока для постройки), сущностей, кроме игроков, физики и столкновений на сервере, воды, света от блоков, метаданных сущностей, Update Tags, других измерений и пакета Transfer.
- **Один процесс — один мир.** Мир живёт в одной горутине одного процесса, и горизонтально он не делится. Прокси перед несколькими серверами и перенос игроков между мирами (урок 12) здесь не сделаны.
- **Мир плоский и конечный** (±512 блоков). Правки хранятся в памяти как отличия от генератора, и их не больше `GAME_MAX_BLOCK_EDITS` (100 000): дальше новая правка получает отказ `block_limit` и сообщение «World edit limit reached», а вернуть блок как было можно всегда. Проверка перемещения — по скорости и границам, а не по столкновениям: сквозь блоки пройти можно (в креативе клиент это и так позволяет).
- **Изменение блока рассылается перебором игроков**: O(N) на изменение при лимите 10 изменений в секунду на игрока. Для большого сервера нужен обратный индекс «чанк → кто загрузил» из урока 07.
- **Снапшот копирует все правки** — O(правок) в тике, их число ограничено `GAME_MAX_BLOCK_EDITS`. Для большого мира понадобятся грязные чанки и copy-on-write (урок 10).
- **Ник — это личность** в offline-режиме: сервер годится только для своей машины.

### Попробуйте сами

Настройки меняются вторым compose-файлом, например `game.yml`:

```yaml
services:
  gameserver:
    environment:
      GAME_QUEUE_LEN: "2"        # исходящая очередь, тиков (по умолчанию 64)
      GAME_VIEW_DISTANCE: "10"   # радиус зоны видимости, чанков (2–16)
      GAME_MAX_PLAYERS: "1000"
      GAME_MAX_CONNS: "1000"
      GAME_WS_MAX_CONNS: "512"
```

```sh
docker compose -f docker-compose.yml -f game.yml --profile labs up -d gameserver   # пересоздаётся только gameserver
docker compose --profile labs up -d gameserver                                      # вернуть как было
```

- **Маленькая очередь.** С `GAME_QUEUE_LEN: "2"` клиенту достаточно на 100 мс отстать с чтением, чтобы стать «медленным». Прогоните ботов и ищите `slow_consumer` в строке `server disconnects` и в журнале сервера (`docker compose logs gameserver | grep slow`). Сколько отключений будет, зависит от машины. Без нагрузки можно приостановить свой клиент Minecraft (`kill -STOP` процесса Java, вернуть — `kill -CONT`): когда сокетные буферы ОС заполнятся, очередь переполнится, и сервер отключит вас, не задержав остальных.
- **Больше ботов до провала TPS.** Поднимайте `-n` ступенями: 300, 600, 1000. Лимиты по умолчанию — 256 игроков, 512 соединений Minecraft и 256 WebSocket, поэтому без файла выше лишние боты получат отказ во входе (`failed to join`). Смотрите, что сломается первым: p99 MSPT, TPS min или `dropped`. Без Docker на ноутбуке автора сервера 600 ботов давали p99 MSPT 8,8 мс при 20 TPS.
- **Плотность.** `-spread 30` собирает ботов в одну зону видимости: трафик и MSPT растут квадратично. `-spread 400` разводит их, и оба падают. То же с `GAME_VIEW_DISTANCE`: зона 21×21 вместо 13×13 — больше зрителей у каждого перемещения и больше чанков на вход.
- **Профиль тика.** Во время прогона ботов: `go tool pprof -top 'http://127.0.0.1:25590/debug/pprof/profile?seconds=20'`. Ищите `world.(*World).broadcast`, `appendEncoded`, кодировщики и zlib. Трасса планировщика: `curl -o trace.out 'http://127.0.0.1:25590/debug/pprof/trace?seconds=5' && go tool trace trace.out` (урок 13-runtime/12). pprof слушает только служебный порт на `127.0.0.1`: стеки и профили — не для всех.
- **Тесты и fuzz.** `cd labs/gameserver && go test -race ./...`, затем, например, `go test -run='^$' -fuzz=FuzzFrameReader -fuzztime=30s ./internal/mcproto`.

### Пример: тик в миниатюре

Песочница не видит `labs/`, поэтому пример — модель тика в одном процессе: пять игроков, два вида клиентов, два кодировщика и одно кодирование на протокол. Кодировщик Minecraft пишет настоящие кадры перемещения протокола 767: дельту `0x2E` в пределах 8 блоков и телепорт `0x70` дальше (чат упрощён). Браузерный кодировщик пишет JSON-массив с `tick` в конце. В первом тике Alice шагает на 2 блока, Bob (браузер) прыгает на 20 блоков, Carol пишет в чат. Доставок 10, а кодирований — по три на протокол. Dave стоит далеко и не получает ничего: Minecraft-клиенту без событий пачку не шлют, а браузерному шлют каждый тик. У Eve очередь на одну пачку, которую никто не читает. Во втором тике её отключают как `slow_consumer`, а в начале третьего убирают из мира. Ввод передаётся функцией, а не каналом, чтобы вывод не зависел от планировщика.

## Как это в C#

- **WebSocket.** В .NET он встроен: `app.UseWebSockets()` и `HttpContext.WebSockets.AcceptWebSocketAsync()` в ASP.NET Core, `ClientWebSocket` для клиента. В Go стандартная библиотека WebSocket не умеет, и выбор — библиотека (`github.com/coder/websocket`) или своё подмножество RFC 6455, как в labs. Зато рукопожатие в Go заканчивается перехватом соединения (`http.NewResponseController(w).Hijack()`): дальше у вас в руках `net.Conn`, и дедлайны, лимиты и горутины те же, что у TCP-соединения Minecraft.
- **Рассылка.** Тот же приём на .NET: событие пишут один раз в `ArrayBufferWriter<byte>`/`IBufferWriter<byte>` на протокол (`BinaryPrimitives.WriteInt16BigEndian` для дельт, `Utf8JsonWriter` для JSON без рефлексии), готовый `ReadOnlyMemory<byte>` копируют в пачки, пачки берут из `ArrayPool<byte>.Shared`. Исходящая очередь — `Channel.CreateBounded` с `BoundedChannelFullMode.Wait` и `TryWrite` из тика: при полной очереди он возвращает `false`, и отключение решает мир. Входящая — тот же канал, но с `await WriteAsync`, то есть с обратным давлением.
- **Владелец мира и тик.** На .NET мир крутят в выделенном потоке или долгоживущей задаче, а тик — на `PeriodicTimer` (урок 04: пропущенные тики он склеивает в один, догонять приходится самому) или на `Stopwatch` и своём расписании. Вместо `signal.NotifyContext` и ручного порядка в `app.Run` — `IHostApplicationLifetime.ApplicationStopping` и `BackgroundService.StopAsync` с `HostOptions.ShutdownTimeout`. В Go граф объектов и порядок остановки видны в одной функции, а не в контейнере.
- **Экосистема.** Серверы Minecraft Java — в основном Java (ванильный сервер, Paper, Minestom). На C# есть открытые реализации протокола (например, Obsidian), а в сетевом коде игр на Unity interest management делают компонентами: в Mirror есть пространственный хеш, в Netcode for GameObjects — управление видимостью объектов для клиентов. Идеи те же: зона видимости, дельты, отправка без ожидания. Различие в модели: там `async`-методы и колбэки движка, здесь — синхронный код в горутине на соединение и одна горутина-владелец мира.

## Ловушки

### Кодирование для каждого получателя

```go
for q := range p.visible {
	q.batch = q.proto.Append(q.batch, ev) // 199 одинаковых кодирований на одно перемещение
}
```

При 200 игроках в одной зоне это 40 000 вызовов кодировщика за тик вместо 200 (по одному на перемещение, если все в Minecraft), а у Minecraft-кодировщика внутри ещё и zlib для крупных пакетов. Кодируйте событие один раз на протокол в отдельный буфер и копируйте байты в пачки получателей. Сбрасывайте этот кеш перед каждым событием: иначе второму событию достанутся байты первого.

### Указатель на локальную переменную в метод интерфейса

```go
ev := Event{Kind: EvMove, Player: &p.PlayerInfo, From: p.sentPos, To: p.Pos}
c.buf = proto.Append(c.buf[:0], &ev) // moved to heap: ev — аллокация на каждое перемещение
```

Компилятор не знает, какая реализация стоит за `Protocol`, и считает, что указатель может сохраниться: `go build -gcflags=-m` говорит «moved to heap: ev». В тике это аллокация на каждое событие, и `AllocsPerRun` перестаёт быть нулём. В labs событие перемещения и статистика пачки лежат в полях мира (`w.moveEv`, `w.endStats`) и перезаписываются для каждого игрока: указатель на поле объекта, который и так в куче, новых аллокаций не даёт.

### Дельта дальше 8 блоков

```go
dx := int64(math.Round(to.X*4096)) - int64(math.Round(from.X*4096))
b = binary.BigEndian.AppendUint16(b, uint16(int16(dx))) // 8 блоков вперёд = 32768 → -32768
```

Преобразование целых в Go не проверяет переполнение и не насыщается: 32768 в `int16` становится −32768, и на экранах остальных игрок прыгает на 8 блоков назад. Клиент складывает дельты, поэтому сдвиг остаётся до следующего телепорта. Диапазон `int16` несимметричен: −8 блоков (−32768) помещаются, а +8 — уже нет. Проверяйте, что дельта по каждой оси лежит в `[math.MinInt16, math.MaxInt16]`, и шлите абсолютный телепорт, если нет, как `appendMove`. Дельту считайте между округлёнными позициями — последней разосланной и новой, — тогда ошибка округления не копится на клиенте.

## Задание

Напишите раздачу событий тика — фазу «рассылка» из `world.broadcast`: игроки с разными протоколами, адресаты событий и одно кодирование на протокол.

```go
type PlayerID int32

type Event struct {
	Kind    string
	Subject PlayerID
	Text    string
}

type Stats struct {
	Tick   uint64
	Events int
}

type Protocol interface {
	Begin(dst []byte) []byte
	Append(dst []byte, ev *Event) []byte
	End(dst []byte, st Stats) []byte
}

type Audience uint8

const (
	ToOne     Audience = iota + 1 // одному игроку Target
	ToAll                         // всем, кроме Exclude
	ToViewers                     // тем, кто видит Subject (и самому Subject, если Self)
)

type Item struct {
	Event   Event
	To      Audience
	Target  PlayerID
	Exclude PlayerID
	Self    bool
}

type Batch struct {
	Player PlayerID
	Data   []byte
}

var (
	ErrBadPlayer     = errors.New("bad player")
	ErrDuplicate     = errors.New("player already added")
	ErrUnknownPlayer = errors.New("unknown player")
)

func NewHub() *Hub
func (h *Hub) Add(id PlayerID, p Protocol) error
func (h *Hub) Remove(id PlayerID) bool
func (h *Hub) SetVisible(a, b PlayerID, visible bool) error
func (h *Hub) Emit(it Item)
func (h *Hub) Flush(tick uint64) []Batch
```

Ошибки проверяются через `errors.Is`. `Hub` используется из одной горутины (владельца мира); блокировки не нужны.

- `Add`: если `id <= 0` или `p == nil` — `ErrBadPlayer`; если игрок с таким `id` уже есть — `ErrDuplicate`; иначе игрок добавлен (никого не видит) и `nil`. Протоколы сравниваются как значения интерфейса (`==`): два игрока с одним и тем же экземпляром — один протокол, два разных экземпляра — два протокола. Тесты передают указатели.
- `Remove` удаляет игрока вместе со всеми парами видимости, где он участвует, и возвращает `true`; для неизвестного `id` — `false`. Игрок, добавленный снова с тем же `id`, никого не видит.
- `SetVisible`: если `a == b` — `ErrBadPlayer` (эта проверка первая); если `a` или `b` нет — `ErrUnknownPlayer`. Иначе при `visible` пара становится видимой **в обе стороны**, без `visible` — невидимой в обе стороны (если пары не было — ничего не меняется). Ошибка `nil`.
- `Emit` ставит копию `it` в очередь тика. Получатели определяются во `Flush` — по игрокам и видимости на момент `Flush`.
- `Flush(tick)` раздаёт все события, накопленные с прошлого `Flush`, ровно один раз, и очищает очередь:
  1. Для каждого текущего игрока ровно один раз вызывается `Begin` его протокола с `dst` длины 0 — `nil` или пустым срезом, допустимо и то и другое. Результат — начало пачки игрока.
  2. События — в порядке `Emit`. Получатели: `ToOne` — `Target`, если такой игрок есть; `ToAll` — все игроки, кроме `Exclude` (0 или неизвестный id — никого не исключает); `ToViewers` — если игрок `Subject` есть: все, кого он видит, и он сам, если `Self` (дублей не бывает: `SetVisible(a, a)` запрещён, поэтому `Subject` никогда не входит в число тех, кого видит сам); если `Subject` нет — никто, даже при `Self`. Событие с другим значением `To` никому не доставляется. Событие без получателей не кодируется.
  3. Для `ToOne` вызывается `Append(пачка адресата, &ev)` протокола адресата ровно один раз; результат — новая пачка. Для `ToAll` и `ToViewers` `Append` вызывается **ровно один раз на каждый протокол, у которого есть хотя бы один получатель этого события**, и ни разу для протоколов без получателей. Байты, которые дописал этот вызов, копируются в конец пачки каждого получателя с этим протоколом. Каждый получатель встречается в списке не больше одного раза. При широковещании `dst` этого единственного вызова — на ваш выбор: пачка одного из получателей или отдельный буфер (в том числе пустой); протокол только дописывает в конец и от содержимого `dst` не зависит, поэтому в пачки идут именно дописанные им байты. `ev` указывает на событие с теми же полями, что `Item.Event`; протоколы событие только читают и не меняют, так что один указатель можно передавать всем.
  4. Событие засчитывается получателю, если в его пачку добавился хотя бы один байт. Если `Append` не дописал ничего (событие протоколу не нужно), получателю не добавляется ни байт и ни одно событие.
  5. Для каждого игрока ровно один раз вызывается `End(пачка, Stats{Tick: tick, Events: число засчитанных ему событий})`. Результат — готовая пачка.
  6. Возвращаются пачки с `len(Data) > 0`, по возрастанию `Player`; игроки с пустой пачкой пропускаются. Нет ни одной — `nil` или пустой срез.
- Порядок вызовов между разными игроками не задан. Задан только порядок байт внутри пачки каждого игрока.
- `Data` принадлежит вызывающему: пачки разных игроков не делят память друг с другом и с буферами `Hub`, а следующие вызовы не меняют уже возвращённые пачки. Обеспечивает это `Hub`: тестовые протоколы возвращают срез, выросший из переданного `dst`, и своих буферов между вызовами не держат, так что достаточно давать каждому игроку на каждый `Flush` свой новый буфер и копировать в него байты из кеша кодирования (если какая-то память может оказаться общей — копируйте).
