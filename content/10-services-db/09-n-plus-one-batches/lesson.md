**N+1** — один запрос за списком и ещё по запросу на каждый элемент: заказы, а потом в цикле позиции каждого. На тестовой базе с пятью заказами незаметно, на проде с тысячей заказов это тысяча и один round trip до базы — секунды вместо миллисекунд, плюс нагрузка на пул соединений. В EF Core N+1 обычно приходит неявно, через ленивую загрузку навигационных свойств. В Go неявной загрузки нет, и N+1 всегда виден в коде: это `QueryContext` внутри `for`. Именно поэтому его легко пропустить на ревью — цикл выглядит невинно, особенно если запрос спрятан в методе репозитория `ItemsByOrder(id)`.

**Два лекарства.** *Второй запрос со списком id*: заказы одним запросом, затем все их позиции — `WHERE order_id IN (?, ?, ?)` (SQLite, MySQL) или `WHERE order_id = ANY($1)` с `[]int64` одним параметром (PostgreSQL через pgx, урок 11), — и раскладка по заказам через `map[id]индекс`. Запросов два при любом N. *JOIN*: один запрос, но данные заказа повторяются в каждой строке позиции; при широких родительских строках и многих детях объём ответа растёт как произведение («cartesian explosion» в терминах EF Core). Для нескольких независимых коллекций (позиции *и* платежи) JOIN перемножает их — там нужен отдельный запрос на коллекцию. `LEFT JOIN` — чтобы не потерять заказы без позиций (их столбцы придут как `NULL`).

**`IN` без инъекции.** Значения в текст SQL не вставляют никогда, даже числа: текст собирают из нужного числа плейсхолдеров (`strings.Repeat("?, ", n)`), значения передают отдельным `[]any`. Пустой список — отдельный случай: `IN ()` в PostgreSQL и MySQL — синтаксическая ошибка (SQLite его пропускает), поэтому при пустом входе запрос не делают вовсе. sqlc умеет это сам: `WHERE id IN (sqlc.slice(ids))` для SQLite и MySQL разворачивает плейсхолдеры во время выполнения (а пустой список — в `IN (NULL)`); для PostgreSQL пишут `= ANY(@ids::bigint[])`.

**Лимит параметров.** У одного запроса число параметров ограничено: в SQLite — 32 766 (так с версии 3.32; проверено на 3.53 из `modernc.org/sqlite`: 32 767 → `too many SQL variables`), в PostgreSQL — 65 535 (поле Int16 в протоколе; pgx ещё до отправки отвечает `extended protocol limited to 65535 parameters`), в MySQL — те же 65 535 плейсхолдеров у подготовленного запроса (`Error 1390`) и размер пакета `max_allowed_packet` (64 МБ по умолчанию в 8.4). Поэтому и длинный `IN`, и пакетную вставку режут на пачки — `slices.Chunk` (Go 1.23). Пачка обычно меньше лимита: сотни–тысячи значений, иначе разбор и план запроса начинают стоить дороже, чем сэкономленные round trip.

**Пакетная вставка.** `INSERT` по строке в цикле — тот же N+1, только на запись. Многострочный `INSERT INTO items (order_id, sku, qty) VALUES (?, ?, ?), (?, ?, ?), ...` вставляет пачку за один запрос; пачки — в одной транзакции, чтобы вставка была атомарной (и в SQLite быстрой: один коммит вместо тысячи). В PostgreSQL есть способы лучше: `pgx.Batch` отправляет много разных запросов за один round trip, а `CopyFrom` (протокол `COPY`) грузит сотни тысяч строк быстрее любого `INSERT` — оба в уроке 11.

**Счётчик запросов — метрика.** Чтобы N+1 не вернулся при следующем рефакторинге, его проверяют тестом: функции принимают маленький интерфейс (`QueryContext`/`ExecContext` — тот же `DBTX`, что и у sqlc), тест подставляет обёртку, которая считает вызовы, и проверяет «не больше двух запросов на любой N». В продакшне то же число видно в трейсинге (OpenTelemetry-инструментация `database/sql` даёт по спану на запрос) — длинная «лесенка» одинаковых спанов и есть N+1.

## Как это в C#

- **Ленивая загрузка EF Core** (`UseLazyLoadingProxies`, `virtual` навигация) — классический источник N+1: обращение к `order.Items` в цикле делает запрос. В Go неявных запросов нет: N+1 — это видимый `QueryContext` в цикле, и ловится он ревью и тестом-счётчиком.
- **`Include(o => o.Items)`** → JOIN одним запросом (по умолчанию — single query, отсюда cartesian explosion); **`AsSplitQuery()`** → второй запрос по ключам — ровно вариант с `IN` из этого урока. В Go стратегию выбираете вы и пишете её руками (или sqlc-запросом с `sqlc.slice`).
- **`ids.Contains(o.Id)` в LINQ** транслируется в `IN (...)` или в параметр-массив — в Go текст `IN` с плейсхолдерами или `= ANY($1)` собирается явно. Лимит параметров (у SQL Server — 2100) одинаково бьёт в обоих мирах.
- **`AddRange` + `SaveChanges`** пакетирует вставки сам (EF Core группирует команды), **`SqlBulkCopy`/`NpgsqlBinaryImporter`** — аналоги `COPY`. В Go пакетирование — ваш код: многострочный `INSERT` пачками, `pgx.Batch`, `CopyFrom`.

## Ловушки

### Запрос, спрятанный в методе

```go
for i := range orders {
	orders[i].Items, err = repo.ItemsByOrder(ctx, orders[i].ID) // N+1
	if err != nil {
		return nil, err
	}
}
```

Каждый метод по отдельности выглядит правильно, а вместе они делают N+1. Давайте репозиторию метод на множество — `ItemsByOrders(ctx, ids []int64) (map[int64][]Item, error)` — и закрепите число запросов тестом-счётчиком.

### Незакрытые `Rows` и вложенные запросы

```go
rows, _ := db.QueryContext(ctx, `SELECT id FROM orders`)
defer rows.Close()
for rows.Next() {
	rows.Scan(&id)
	items, _ := db.QueryContext(ctx, `SELECT ... WHERE order_id = ?`, id) // второе соединение
	...
}
```

Пока первый `Rows` не дочитан, он держит соединение — запрос внутри цикла берёт из пула второе. При `SetMaxOpenConns(1)` (или под нагрузкой, когда пул исчерпан) он ждёт вечно: самоблокировка. Сначала дочитайте и закройте первый результат, потом делайте второй запрос — или один запрос со всеми id.

### `IN` без верхней границы

```go
q := `SELECT ... WHERE id IN (` + placeholders(len(ids)) + `)` // ids пришли от клиента
```

Список из 70 000 id упадёт на лимите параметров (`too many SQL variables`, `Error 1390`), а 30 000 — пройдёт, но медленно и с огромным текстом запроса. Ограничьте размер входа на краю API и режьте список на пачки `slices.Chunk(ids, 500)`.

## Задание

Функции работают со схемой `Schema` из шаблона (таблицы `orders(id, customer)` и `items(id, order_id, sku, qty)`; создают её тесты, драйвер `modernc.org/sqlite` импортируют тоже тесты). Шаблонная `LoadOrders` работает, но делает N+1 — перепишите её, и напишите `InsertItems`.

```go
const (
	MaxIDsPerQuery = 500
	MaxParams      = 999
)

type Querier interface {
	QueryContext(ctx context.Context, query string, args ...any) (*sql.Rows, error)
}
type Execer interface {
	ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
}

type Item struct {
	SKU string
	Qty int64
}
type Order struct {
	ID       int64
	Customer string
	Items    []Item
}

func LoadOrders(ctx context.Context, db Querier, ids []int64) ([]Order, error)
func InsertItems(ctx context.Context, db Execer, orderID int64, items []Item) error
```

Тесты передают обёртки, которые считают вызовы `QueryContext`/`ExecContext` и число параметров в каждом, и пул из одного соединения. Значения — только через плейсхолдеры `?`, `ctx` передаётся в каждый запрос (с отменённым контекстом — ошибка, для которой `errors.Is(err, context.Canceled)`), ошибки базы возвращаются обёрнутыми через `%w` или как есть.

`LoadOrders(ctx, db, ids)`:

- возвращает заказы, чьи `id` есть в `ids`, по возрастанию `ID`; каждый заказ — один раз, даже если его id повторяется; несуществующие id пропускаются; если ни одного заказа не нашлось — срез длины 0 (`nil` допустим);
- `Items` — позиции заказа по возрастанию `items.id`; у заказа без позиций — срез длины 0 (`nil` допустим);
- пустой `ids` — без единого запроса;
- без N+1: разные id делятся на пачки не больше `MaxIDsPerQuery`, на каждую пачку — не больше двух запросов, и ни в одном запросе нет больше `MaxIDsPerQuery` параметров (1200 разных id — не больше 6 запросов);
- при ошибке любого запроса возвращает её; в любом случае к возврату все `Rows` закрыты и соединение вернулось в пул.

`InsertItems(ctx, db, orderID, items)`:

- вставляет позиции заказа `orderID` в порядке `items` (их `items.id` идут по возрастанию в том же порядке) многострочными `INSERT`;
- в одном запросе — не больше `MaxParams` параметров, а запросов — минимально возможное число: ⌈`len(items)` / 333⌉ (по 3 параметра на строку); пустой `items` — без запросов, `nil`;
- первая ошибка запроса прекращает вставку: функция возвращает её, следующие пачки не отправляются (атомарность — забота вызывающего: он передаёт `*sql.Tx`).
