Самая частая ошибка конкурентного кода с базой выглядит невинно: прочитать остаток, проверить в Go, записать новое значение. Две транзакции читают одно и то же `qty = 10`. Первая пишет `10 - 3`, вторая — `10 - 4`. Обе фиксируются без ошибок, а в базе 6 вместо 3: списание первой **потерялось**. Уровень Read Committed (по умолчанию в PostgreSQL) от этого не защищает: каждая транзакция честно видела зафиксированные данные, просто к моменту записи они устарели. Пример урока воспроизводит это на настоящем PostgreSQL 18 и лечит тремя способами.

**Пессимистичная блокировка: `SELECT ... FOR UPDATE`.** Чтение с `FOR UPDATE` блокирует найденные строки до конца транзакции. Вторая транзакция, которая хочет прочитать ту же строку с `FOR UPDATE` или изменить её, **ждёт**. Когда первая фиксируется, вторая на Read Committed перечитывает строку и видит уже 7. Обычный `SELECT` без `FOR UPDATE` при этом не ждёт: MVCC отдаёт ему снимок. Варианты:

- `FOR UPDATE NOWAIT` — не ждать, а сразу получить ошибку `55P03` (`lock_not_available`). Подходит, когда лучше ответить «занято, попробуйте позже», чем держать запрос.
- `FOR UPDATE SKIP LOCKED` — пропустить занятые строки. Это инструмент для очередей: воркеры берут `... ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED` и получают разные задачи, не мешая друг другу (так устроен relay в уроке про outbox). Для остатка конкретного товара он не годится: занятая строка просто «исчезнет».
- `SET LOCAL lock_timeout = '2s'` — предел ожидания блокировки в этой транзакции, ошибка `55P03` по истечении. Ожидание блокировки не ограничено ничем, кроме `lock_timeout`, `statement_timeout` и контекста запроса, — ставьте хотя бы контекст с дедлайном.
- Блокируя несколько строк, берите их в одном порядке (`ORDER BY id`): иначе две транзакции захватят строки крест-накрест, и PostgreSQL прервёт одну из них ошибкой дедлока `40P01`.

**Оптимистичная блокировка: версия строки.** Не блокировать при чтении, а проверить при записи, что строку никто не трогал: `UPDATE stock SET qty = $1, version = version + 1 WHERE id = $2 AND version = $3`. Если между вашим чтением и записью строку изменили, версия уже другая, и запрос не затронет ни одной строки: `RowsAffected() == 0` — конфликт. Нужно перечитать и повторить. Это дёшево, когда конфликты редки (редактирование карточки товара, профиля), не держит блокировок между запросами и работает даже между HTTP-запросами: версию отдают клиенту и принимают обратно (ETag и `If-Match`). При частых конфликтах на одной горячей строке повторы съедят выигрыш — там лучше ждать на блокировке или считать атомарно.

**Атомарный `UPDATE`.** Если новое значение вычисляется из старого простой формулой, не нужно ни читать, ни блокировать: `UPDATE stock SET qty = qty - $1 WHERE id = $2 AND qty >= $1`. Проверка и изменение — один оператор, и база сама сериализует конкурентные `UPDATE` одной строки (второй ждёт блокировку строки и пересчитывает условие по новой версии). `RowsAffected() == 0` значит «не хватило». Это самый простой и быстрый путь — начинайте с него. Когда логика между чтением и записью сложнее формулы (скидки, лимиты по нескольким таблицам), берите `FOR UPDATE` или версию.

**Повторы.** Конфликт версии, `40001` (сериализация на Repeatable Read и Serializable) и `40P01` (дедлок) — нормальные ответы базы под нагрузкой, их повторяют. Правила:

- повторяется **вся операция** — новая транзакция, новое чтение, новое решение, а не упавший запрос: решение принималось по устаревшим данным, а в PostgreSQL прерванная транзакция годна только для отката;
- число попыток ограничено; когда они кончились — ошибка наверх (409 или 503 клиенту);
- пауза между попытками растёт экспоненциально и выбирается случайно в этих пределах (**полный джиттер**): `rand(0, min(base·2^(n-1), max))` — иначе проигравшие повторяют одновременно и сталкиваются снова;
- повторяются только конфликты: «нет товара» или нарушение ограничения повтор не исправит;
- повторяемый блок не имеет внешних эффектов (письма, вызовы API) или идемпотентен — иначе повтор их удвоит.

Изоляцию Repeatable Read и Serializable, write skew и повтор по `40001` подробно разбирает урок о MVCC в PostgreSQL.

## Как это в C#

- **Concurrency token.** В EF Core оптимистичная блокировка объявляется на сущности (`[ConcurrencyCheck]`, `[Timestamp]` для `rowversion` в SQL Server, `IsConcurrencyToken()`), а `SaveChanges` сам добавляет условие на исходное значение в `UPDATE` и бросает `DbUpdateConcurrencyException`, если строк затронуто 0. В Go условие пишут в SQL явно и проверяют `RowsAffected` — механизм тот же, только виден целиком.
- **Пессимистичные блокировки.** У EF Core для них нет API: `FromSql("SELECT ... FOR UPDATE")` внутри транзакции в PostgreSQL или подсказка `WITH (UPDLOCK, ROWLOCK)` в SQL Server. В Go это обычный запрос через `tx`.
- **Повторы.** В .NET их делают Polly (`ResiliencePipeline` с `Retry`, экспонентой и джиттером) или стратегия повторов EF Core (`EnableRetryOnFailure` — она повторяет ошибки, которые провайдер считает временными: сбои соединения, дедлоки, а у Npgsql ещё `40001` и `55P03`; но не конфликт версий — `DbUpdateConcurrencyException` остаётся вам). В Go библиотека не обязательна: цикл с ограничением попыток и паузой — десяток строк, и его легко тестировать, внедрив функцию сна.

## Ловушки

### Повтор одного запроса вместо всей операции

```go
for range 3 {
	_, err = tx.ExecContext(ctx, `UPDATE stock SET qty = $1 WHERE id = $2`, qty-n, id)
	if !isSerializationFailure(err) {
		break
	}
}
```

После ошибки `40001` транзакция PostgreSQL прервана, и каждый следующий запрос в ней получит `current transaction is aborted, commands ignored until end of transaction block`. Даже в базах, где транзакция продолжилась бы, `qty` прочитан до конфликта и устарел. Повторяемая единица — функция, которая сама начинает транзакцию, читает, решает и фиксирует: `retry(ctx, func(ctx) error { return withTx(ctx, db, reserve) })`.

### `FOR UPDATE` вне транзакции

```go
var qty int
db.QueryRowContext(ctx, `SELECT qty FROM stock WHERE id = $1 FOR UPDATE`, id).Scan(&qty)
db.ExecContext(ctx, `UPDATE stock SET qty = $1 WHERE id = $2`, qty-n, id)
```

Без явной транзакции каждый запрос — своя транзакция в автокоммите: блокировка снимается сразу после `SELECT`, и между чтением и записью может вклиниться кто угодно. К тому же запросы через `db` могут уйти в разные соединения. Блокировка живёт до конца транзакции, поэтому `SELECT ... FOR UPDATE` и `UPDATE` должны идти через один `tx`.

### Проверка остатка в Go без условия в `UPDATE`

```go
if s.Qty < n {
	return ErrInsufficient
}
db.ExecContext(ctx, `UPDATE stock SET qty = qty - $1 WHERE id = $2`, n, id) // без AND qty >= $1
```

Проверка в Go и запись разнесены во времени: две горутины одновременно убедятся, что 5 ≥ 3, и обе спишут — остаток станет −1. Атомарная формула `qty = qty - $1` спасает от потери обновления, но не от нарушения инварианта. Условие должно жить в том же операторе (`AND qty >= $1`), в ограничении базы (`CHECK (qty >= 0)`) — лучше и там, и там.

## Задание

Напишите резервирование товара с оптимистичной блокировкой и повторами. Задача решается и проверяется на SQLite без PostgreSQL. Схема, тип `Stock` и ошибки даны в шаблоне:

```go
type Stock struct{ ID, Qty, Version int64 }

var ErrNotFound, ErrInvalid, ErrInsufficient, ErrConflict error

func Get(ctx context.Context, db *sql.DB, id int64) (Stock, error)
func Save(ctx context.Context, db *sql.DB, s Stock) error
func TryReserve(ctx context.Context, db *sql.DB, id, n int64) error

type Retry struct {
	Attempts int
	Backoff  func(attempt int) time.Duration
	Sleep    func(ctx context.Context, d time.Duration) error
}

func (r Retry) Do(ctx context.Context, fn func(ctx context.Context) error) error
func Reserve(ctx context.Context, db *sql.DB, r Retry, id, n int64) error
func ExpBackoff(base, maxDelay time.Duration, rnd func() float64) func(attempt int) time.Duration
```

Таблицу `stock(id, qty, version)` создают тесты (драйвер SQLite подключают тоже они). Ошибки можно оборачивать — тесты проверяют `errors.Is`. Все запросы — с `ctx` и плейсхолдерами.

- `Get` возвращает строку `id` с её `qty` и `version`; строки нет — `ErrNotFound` и нулевой `Stock{}`.
- `Save` записывает `s.Qty` и увеличивает версию на 1, **только если** версия строки в базе равна `s.Version`; иначе (версия другая или строки нет) — `ErrConflict`, и база не меняется. Другие строки не меняются никогда.
- `TryReserve` — одна попытка: `n <= 0` — `ErrInvalid` без обращения к базе; строки нет — `ErrNotFound`; `qty < n` — `ErrInsufficient`; иначе записать `qty - n` через `Save` (конфликт — `ErrConflict`). Транзакция не нужна.
- `Do` вызывает `fn(ctx)` не больше `Attempts` раз (`Attempts < 1` — один раз). Перед каждой попыткой: если `ctx` отменён — вернуть `ctx.Err()`, не вызывая `fn`. Если `fn` вернула не `ErrConflict` (в том числе `nil` или обёрнутую другую ошибку) — сразу вернуть её. Если `ErrConflict` и попытки остались — пауза `Sleep(ctx, Backoff(k))`, где `k` — номер неудавшейся попытки (1, 2, …); без `Backoff` пауза 0; ошибку `Sleep` вернуть как есть. После последней попытки паузы нет: вернуть ошибку с `errors.Is(err, ErrConflict)`. Если `Sleep` не задан, ждать `d` по-настоящему, но прерваться при отмене `ctx` с его ошибкой.
- `Reserve` повторяет `TryReserve` целиком через `r.Do`. Одновременные `Reserve` из многих горутин (тесты: пул из одного соединения, 20 горутин, хватает на 15, попыток в `Retry` — с запасом) дают ровно столько успешных списаний, сколько позволяет остаток; остальные — `ErrInsufficient`, версия растёт на 1 с каждым списанием.
- `ExpBackoff` возвращает функцию паузы с полным джиттером: для попытки `k` (значения меньше 1 считать 1) предел — `min(base·2^(k-1), maxDelay)`, пауза — `rnd()` × предел, где `rnd()` возвращает число из [0, 1). Считайте, что `base > 0` и `maxDelay ≥ base`; на любых `k`, включая очень большие, пауза не отрицательна и меньше `maxDelay`.
