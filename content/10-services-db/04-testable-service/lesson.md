Сервис с хранилищем за маленьким интерфейсом тестируется на двух уровнях. **Логику сервиса** — проверки, переходы статусов, перевод ошибок, повторы — гоняют на **фейке**: рабочей реализации интерфейса в памяти (map под мьютексом). Такие тесты быстрые, не требуют Docker и проверяют результат («после `Place` заказ читается из хранилища»), а не то, какие методы и сколько раз вызваны. Моки с ожиданиями (gomock, mockery) уместны, когда вызов и есть поведение — письмо отправлено, кеш не пошёл в источник, — в остальных случаях они ломаются от каждого рефакторинга (об этом — урок 07-testing/09).

**Хранилище** — это SQL, и проверять его можно только на базе. Мок `database/sql` (sqlmock) с ожиданием текста запроса проверяет, что строка не изменилась, но не то, что запрос верен: опечатка в имени колонки, неверный `ON CONFLICT`, нарушенный `CHECK` и коды ошибок драйвера на нём не видны. Поэтому SQL не мокают — его запускают.

Связывает уровни **контрактный набор**: функция `testStore(t, newStore func(t *testing.T) Store)` с подтестами на всё, что обещает интерфейс, — включая ошибки, состояние после неудачного вызова и отмену контекста. Её вызывают для каждой реализации: для фейка, для SQLite, для PostgreSQL. Если фейк разойдётся с базой (забыл про уникальность имени, вернул не ту ошибку, не уважает отмену), упадёт его прогон, и тестам сервиса на фейке снова можно верить. Фабрика вместо готового значения нужна, чтобы каждый подтест начинал с пустого хранилища и убирал за собой через `t.Cleanup`.

Изолировать тесты с базой можно тремя способами:

- **SQLite в памяти на тест** — база создаётся за миллисекунды. С `:memory:` у каждого соединения своя база, поэтому `db.SetMaxOpenConns(1)` (или `file::memory:?cache=shared`, или файл в `t.TempDir()`, если нужен пул из нескольких соединений). Годится для кода, который пишет переносимый SQL; диалектные вещи (`jsonb`, `FOR UPDATE SKIP LOCKED`, коды ошибок PostgreSQL) так не проверить.
- **Транзакция на тест** — схема создаётся один раз, а каждый тест работает в транзакции, которую `t.Cleanup` откатывает. Быстро и без уборки; поэтому хранилище принимает `DBTX` — общее у `*sql.DB` и `*sql.Tx` (у pgx — `pgx.Tx` и `*pgxpool.Pool`). Не подходит, если код сам открывает транзакции (вложенных в PostgreSQL нет — только `SAVEPOINT`) или тест проверяет конкурентность нескольких соединений.
- **Отдельная база или схема на тест** — дороже, но честно: `CREATE DATABASE test_<случайное>` и `DROP` в `t.Cleanup`. Так делает runner этого курса для каждого запуска примера.

**Настоящий PostgreSQL** тест берёт по DSN из окружения: нет переменной — `t.Skip` с подсказкой, как поднять базу, и `go test ./...` у разработчика без Docker остаётся зелёным. В CI базу поднимает сервис job'а, а поднимать её прямо из теста умеет **testcontainers-go**: `postgres.Run(ctx, "postgres:18", postgres.BasicWaitStrategies())` из модуля `modules/postgres` стартует контейнер (стратегию ожидания готовности модуль сам не задаёт — без неё тест может подключиться раньше, чем база готова) и отдаёт DSN через `ctr.ConnectionString(ctx, "sslmode=disable")`, а `testcontainers.CleanupContainer(t, ctr)` удаляет его в конце теста. В песочнице Docker нет, поэтому в коде урока его нет. Пример урока — контракт склада на трёх хранилищах; прогон на PostgreSQL выполняется, если включён профиль labs (`docker compose --profile labs up`), иначе он пропускается.

## Как это в C#

- **Moq/NSubstitute** → фейк руками. Интерфейс в Go маленький и объявлен у потребителя, поэтому фейк — десяток строк, а не сотня `Setup(...)`. Генераторы моков (gomock, mockery) есть, но идиоматичнее начинать с фейка и оставлять мок для случаев, где проверяется сам вызов.
- **Абстрактный базовый класс с `[Fact]` и наследники под каждую реализацию** → функция `testStore(t, newStore)`, которую вызывают из `TestMemStore`, `TestSQLiteStore`, `TestPostgresStore`. Подтесты `t.Run` дают те же имена в отчёте, что и методы базового класса.
- **`TransactionScope` для отката после теста** → явная транзакция: `tx := db.BeginTx(...)`, `t.Cleanup(func() { tx.Rollback() })`, хранилище получает `tx` как `DBTX`. Неявной «окружающей» транзакции в Go нет — это и плюс: видно, какой код в какой транзакции работает.
- **EF Core InMemory-провайдер** — та же ловушка, что и фейк без контракта: LINQ исполняется в памяти, без SQL, ограничений и транзакций, и тесты зелёные там, где база упадёт. Microsoft сама советует для этого SQLite или настоящую базу. В Go аналога нет — сравнивайте фейк с базой контрактом.

## Ловушки

### Фейк, который никто не сверяет с базой

```go
func (m *MemStore) Create(_ context.Context, name string, qty int) (int64, error) {
	m.lastID++
	m.items[m.lastID] = Item{ID: m.lastID, Name: name, Qty: qty} // а в схеме name UNIQUE
	return m.lastID, nil
}
```

Тесты сервиса на таком фейке зелёные, а в проде второй товар с тем же именем даёт `500` вместо `409`: база возвращает ошибку уникальности, которой фейк не знает. Фейк — тоже реализация интерфейса, и проходить он должен тот же контракт, что и SQL-хранилище.

### Транзакция теста от `t.Context()`

```go
tx, _ := db.BeginTx(t.Context(), nil)
t.Cleanup(func() {
	if t.Failed() {
		dumpTable(t, tx, "stock") // иногда: sql: transaction has already been committed or rolled back
	}
	tx.Rollback()
})
```

`t.Context()` отменяется **перед** вызовом функций `t.Cleanup`. А отмена контекста, переданного в `BeginTx`, откатывает транзакцию в фоновой горутине `database/sql` — и всё, что `Cleanup` делает в этой транзакции, успевает или получает `ErrTxDone`, как повезёт. Для ресурсов, которые живут до `Cleanup`, берите `context.Background()`.

### Тесты делят одну базу

```go
func TestCreate(t *testing.T) { store.Create(ctx, "лампа", 1) /* ... */ }
func TestList(t *testing.T) {
	items, _ := store.List(ctx)
	if len(items) != 0 { t.Fatal("ожидался пустой склад") } // зависит от порядка тестов
}
```

Общая база на пакет — тот же глобальный state: тесты проходят по отдельности и падают вместе, а с `-shuffle=on` или `t.Parallel` — через раз. Каждому тесту — своё хранилище из фабрики: своя база в памяти, своя транзакция или своя схема.

## Задание

В `task.go` дано хранилище товаров `SQLiteStore` на SQLite. Напишите фейк `MemStore` — хранилище в памяти, которое ведёт себя так же. Открытые тесты содержат контрактный набор `testStore` и гоняют его на обеих реализациях; скрытые добавляют краевые случаи — тоже на обеих.

```go
var (
	ErrInvalid      = errors.New("invalid argument")
	ErrNotFound     = errors.New("not found")
	ErrDuplicate    = errors.New("duplicate name")
	ErrInsufficient = errors.New("insufficient stock")
)

type Item struct {
	ID   int64
	Name string
	Qty  int
}

type Store interface {
	Create(ctx context.Context, name string, qty int) (int64, error)
	Get(ctx context.Context, id int64) (Item, error)
	Reserve(ctx context.Context, id int64, qty int) error
	List(ctx context.Context) ([]Item, error)
}

func NewMemStore() *MemStore // *MemStore реализует Store
```

Поведение (его же реализует `SQLiteStore` — сверяйтесь с кодом):

- Каждый метод сначала проверяет контекст: если он отменён — возвращает ошибку, для которой `errors.Is(err, context.Canceled)`, раньше любых других проверок, и ничего не меняет.
- `Create`: если `name == ""` или `qty < 0` — `(0, ErrInvalid)`. Если товар с таким же `name` уже есть (сравнение точное, с учётом регистра) — `(0, ErrDuplicate)`, существующий товар не меняется. Иначе сохраняет товар и возвращает его `id`: у первого товара `1`, дальше по порядку; неудачный `Create` номер не тратит.
- `Get`: товар по `id`; если нет — `(Item{}, ErrNotFound)`.
- `Reserve`: если `qty <= 0` — `ErrInvalid` (даже для несуществующего `id`); нет товара — `ErrNotFound`; остаток меньше `qty` — `ErrInsufficient`; иначе уменьшает остаток на `qty`. При ошибке остаток не меняется.
- `List`: все товары по возрастанию `id`; пустое хранилище — срез длины 0 (`nil` допустим). Изменение возвращённого среза не влияет на хранилище.
- У каждого `MemStore` своё состояние; все методы безопасны для вызова из многих горутин (тесты идут с `-race`): 100 одновременных `Reserve(id, 1)` при остатке 50 дают ровно 50 успехов и 50 `ErrInsufficient`.
