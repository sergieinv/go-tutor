В EF Core схема выводится из модели: `dotnet ef migrations add` сравнивает классы со снимком и генерирует C#-миграцию, `Database.Migrate()` её применяет, а LINQ превращается в SQL во время выполнения. В Go обычно идут в обратную сторону: **источник правды — SQL**. Схему меняют пронумерованные SQL-миграции, запросы пишут руками в `.sql`-файлах, а Go-код для них генерирует `sqlc`. ORM есть (GORM), но в сервисах на Go чаще выбирают явный SQL: видно, что именно уходит в базу, и нечему «магически» сделать лишние запросы.

**Миграции goose.** Каждая миграция — файл `00002_stock.sql` (число — версия) с двумя разделами: `-- +goose Up` и `-- +goose Down`. goose ведёт таблицу `goose_db_version`: какие версии применены. По умолчанию каждая миграция выполняется в своей транзакции: упала посередине — откатилась целиком, версия не записана. Тело из нескольких операторов с `;` внутри (функция PL/pgSQL, триггер) оборачивают в `-- +goose StatementBegin` / `-- +goose StatementEnd`; операции, которые нельзя выполнять в транзакции (`CREATE INDEX CONCURRENTLY` в PostgreSQL), — помечают `-- +goose NO TRANSACTION`. Миграции встраивают в бинарник через `//go:embed` и применяют через `goose.NewProvider(dialect, db, fsys)` — у провайдера нет глобального состояния, есть `Up`, `UpTo`, `DownTo`, `Status`, `HasPending`, `GetDBVersion`. Старый API на глобальных функциях (`goose.SetBaseFS`, `goose.SetDialect`, `goose.UpContext`) встречается в коде повсюду и делает то же самое. Тот же набор команд есть в CLI: `goose -dir migrations postgres "$DSN" up`.

**Когда применять.** Два варианта. *При старте сервиса* — просто, но несколько реплик стартуют одновременно и начнут применять одно и то же. goose решает это блокировкой: опция провайдера `goose.WithSessionLocker(locker)`, где `locker, err := lock.NewPostgresSessionLocker()`, берёт advisory lock PostgreSQL (`pg_try_advisory_lock` с повторами) на время миграций, остальные реплики ждут. *Отдельным шагом деплоя* — job в CI/CD или init-контейнер запускает `goose up` до выкатки новой версии, а сервис при старте только проверяет `HasPending` и падает с понятной ошибкой, если схема отстала. Второй вариант надёжнее: у сервиса нет прав на DDL, долгая миграция не тормозит старт, а её сбой не роняет все реплики.

**Обратная совместимость.** Во время rolling deploy одновременно работают старая и новая версии кода, и обе должны работать с текущей схемой. Поэтому несовместимое изменение раскладывают на шаги **expand/contract**: сначала *расширить* (добавить столбец, допускающий `NULL`, или новую таблицу), выкатить код, который пишет в оба места, перенести данные, переключить чтение — и только следующим релизом *сжать* (удалить старый столбец). Переименование столбца одной миграцией сломает все реплики старой версии в момент применения. `Down` пишут, но в продакшне откат схемы — редкость: `DROP COLUMN` уничтожает данные (это видно в примере), поэтому чаще «откатываются вперёд» новой миграцией. golang-migrate — вторая популярная библиотека: каждая миграция — пара файлов `1_init.up.sql` / `1_init.down.sql`, таблица `schema_migrations` с флагом `dirty`, который после сбоя надо снимать руками.

**sqlc.** Вы пишете схему (sqlc читает миграции goose и пропускает разделы `Down`) и запросы с аннотациями, а `sqlc generate` по `sqlc.yaml` создаёт Go-код: модели таблиц, структуры параметров и методы у типа `Queries`. Аннотация задаёт форму результата: `:one` — одна строка (`sql.ErrNoRows`, если нет), `:many` — срез, `:exec` — только ошибка, `:execrows` — число затронутых строк, `:execresult` — `sql.Result`; для pgx есть ещё `:copyfrom` и `:batchexec`. Параметры по умолчанию называются по столбцам, имя задают `sqlc.arg(name)`, nullable-параметр — `sqlc.narg(name)`, список для `IN` в SQLite и MySQL — `sqlc.slice(ids)` (в PostgreSQL — `= ANY(@ids::bigint[])`). Главное: sqlc **разбирает запросы по схеме при генерации** — опечатка в столбце или несоответствие типов ловятся до компиляции, а не в рантайме. `New(db)` принимает интерфейс `DBTX`, который реализуют и `*sql.DB`, и `*sql.Tx`, поэтому транзакция — `q.WithTx(tx)`. С `sql_package: "pgx/v5"` код генерируется под `pgx`/`pgxpool` напрямую (урок 11). В CI запускают `sqlc diff` (сгенерированное совпадает с SQL) и `sqlc vet` (правила проверки запросов).

**Для сравнения.** GORM даёт `db.Where("price > ?", p).Find(&products)`, `AutoMigrate`, хуки и ассоциации — и платит рефлексией и тегами структур (ошибка в теге видна только в рантайме), неочевидным SQL, ленивыми ассоциациями (без `Preload` — N+1, урок 9) и сюрпризами вроде того, что `Updates(struct)` пропускает нулевые значения полей. Query builder (squirrel) склеивает SQL из кусочков — удобен для динамических фильтров, но проверки по схеме нет. sqlx — тонкая надстройка над `database/sql`: сканирование в структуры по тегам `db`. sqlc закрывает статический SQL — а это большинство запросов сервиса; для действительно динамических фильтров рядом пишут код руками или берут builder.

## Как это в C#

- **EF Core Migrations** (`dotnet ef migrations add`, `Database.Migrate()`, таблица `__EFMigrationsHistory`) → goose: миграции пишутся на SQL вручную, снимка модели и автоматического диффа нет. Ближе всего по духу — DbUp и FluentMigrator: «список скриптов + таблица журнала». EF Core 9 научился брать блокировку в `Migrate()` при параллельном старте — в goose это `WithSessionLocker`.
- **`DbContext` + LINQ + change tracking** → `Queries` от sqlc: метод на каждый запрос, без отслеживания изменений — чтобы обновить строку, вызываете `UPDATE` явно. Ближе всего — Dapper, только маппинг не пишется руками и проверен по схеме ещё при генерации.
- **`IDbContextTransaction` и `TransactionScope`** → явный `*sql.Tx`: `q.WithTx(tx)` возвращает те же методы поверх транзакции. Ambient-транзакции нет: что не получило `tx`, в транзакцию не попало.
- **Scaffolding (`dotnet ef dbcontext scaffold`)** генерирует классы по живой базе; sqlc генерирует по файлам схемы и запросов — генерация воспроизводима и проверяется в CI.

## Ловушки

### Правка уже применённой миграции

```sql
-- 00002_stock.sql уже применён на проде, а его «чинят» на месте:
-- +goose Up
ALTER TABLE products ADD COLUMN stock INTEGER NOT NULL DEFAULT 0;
CREATE INDEX products_stock_idx ON products (stock, name); -- было (stock)
```

goose не хранит контрольных сумм: версия 2 записана в `goose_db_version`, и изменённый файл больше никогда не выполнится. На свежих базах (тесты, новый стенд) индекс будет новым, на проде — старым, и схемы тихо разойдутся. Применённая миграция неизменна; исправление — новая миграция `00003_...`.

### Переименование столбца за один шаг

```sql
-- +goose Up
ALTER TABLE customers RENAME COLUMN name TO full_name;
```

Миграция применилась до выкатки нового кода (или после — неважно): какое-то время работают реплики, которые читают `name`, и все их запросы падают. Expand/contract: добавить `full_name`, писать в оба столбца, перенести данные (`UPDATE ... SET full_name = name`), перевести чтение на `full_name`, а `DROP COLUMN name` — следующим релизом.

### DDL в MySQL не откатывается

```sql
-- +goose Up
CREATE TABLE coupons (id BIGINT PRIMARY KEY);
ALTER TABLE ordrs ADD COLUMN coupon_id BIGINT; -- опечатка: Error 1146
```

В PostgreSQL и SQLite транзакция goose откатит и `CREATE TABLE`. В MySQL каждый DDL-оператор неявно фиксирует транзакцию: `coupons` останется, версия 2 не запишется, и после исправления опечатки повторный `up` упадёт уже на первой строке — `Error 1050: Table 'coupons' already exists` (проверено на MySQL 8.4). Для MySQL — одна DDL-операция на миграцию и `IF NOT EXISTS` там, где это возможно.

## Задание

Напишите миграции схемы и обёртку над goose, которая приводит базу к заданной версии. Всё работает с SQLite (`goose.DialectSQLite3`); драйвер `modernc.org/sqlite` импортируют тесты.

```go
var ErrBadTarget = errors.New("migrate: неизвестная версия")

var Migrations = fstest.MapFS{ /* 00001_customers.sql дан */ }

func Migrate(ctx context.Context, db *sql.DB, fsys fs.FS, target int64) ([]int64, error)
func Pending(ctx context.Context, db *sql.DB, fsys fs.FS) ([]int64, error)
```

Миграции (в `Migrations` добавьте два файла в формате goose, у каждого — `Up` и `Down`):

- `00002_orders.sql`: таблица `orders` со столбцами по порядку `id INTEGER PRIMARY KEY`, `customer_id INTEGER NOT NULL` — внешний ключ на `customers(id)`, `total INTEGER NOT NULL` с ограничением `total >= 0`; индекс `orders_customer_idx` на `orders (customer_id)`. `Down` удаляет индекс и таблицу;
- `00003_customer_email.sql`: шаг expand — столбец `email TEXT`, допускающий `NULL`, в конце `customers`. `Down` удаляет столбец, остальные данные `customers` сохраняются.

`Migrate(ctx, db, fsys, target)` приводит схему к версии `target`, используя миграции из `fsys` (не обязательно `Migrations` — тесты передают и свои):

- `target` — `0` (откатить всё) или версия одной из миграций в `fsys`; иначе — `nil` и ошибка с `errors.Is(err, ErrBadTarget)`, а база не тронута вовсе (не создаётся даже таблица версий goose);
- если `target` больше текущей версии — применяет миграции до неё включительно; если меньше — откатывает до неё (сама `target` не откатывается); если равна — ничего не делает;
- возвращает версии выполненных миграций в порядке выполнения: при применении — по возрастанию, при откате — по убыванию; если делать нечего — срез длины 0 (`nil` допустим);
- если миграция упала — возвращает ошибку, в которой через `%w` доступна ошибка goose (`errors.As(err, &partial)` для `*goose.PartialError` работает), и версии миграций, успешно выполненных до сбоя (goose кладёт их в `PartialError.Applied`, а `UpTo`/`DownTo` в этом случае возвращают пустой список результатов). Сломанная миграция откатывается целиком (goose выполняет каждую в транзакции);
- контекст передаётся goose: с отменённым контекстом — ошибка, миграции не применяются.

`Pending(ctx, db, fsys)` возвращает версии миграций из `fsys`, ещё не применённых к базе, по возрастанию; если всё применено — срез длины 0 (`nil` допустим). Для пустой базы — все версии.
