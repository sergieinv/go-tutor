Индекс в PostgreSQL — отдельная структура рядом с таблицей, и планировщик сам решает, использовать ли её. Решение видно в `EXPLAIN`: дерево **узлов**, каждый получает строки от детей и отдаёт родителю. `EXPLAIN` показывает план и **оценки** (`rows` — сколько строк ожидается, `cost` — условная стоимость), `EXPLAIN (ANALYZE)` ещё и выполняет запрос и добавляет **факт**: `actual rows` и `loops`. С 18-й версии `ANALYZE` по умолчанию включает `BUFFERS` (сколько страниц по 8 КБ прочитано), фактическое число строк печатается дробным (это среднее на цикл: `rows=0.50 loops=2`), а у индексных узлов появилась строка `Index Searches` — сколько раз сканирование спускалось по дереву. Для программ есть `FORMAT JSON`: те же поля с ключами `"Node Type"`, `"Plan Rows"`, `"Actual Rows"`, `"Actual Loops"`, `"Index Name"`, `"Plans"` — пример разбирает его `encoding/json`.

Как читать план: снизу вверх, от листьев. Главные узлы чтения — `Seq Scan` (вся таблица), `Index Scan` (индекс, затем строка в таблице), `Index Only Scan` (только индекс), `Bitmap Index Scan` + `Bitmap Heap Scan` (собрать из индекса список страниц, потом прочитать их по порядку — для «многих, но не всех» строк). Первым делом сравнивайте оценку с фактом: если планировщик ждал 1 строку, а пришло 80 000, он выбрал план под другую задачу (вложенный цикл вместо хеш-соединения). Оценки берутся из статистики, которую собирает `ANALYZE` (и autovacuum); после массовой загрузки запускайте `ANALYZE` сами. Стоимости и время в выводе зависят от машины и кеша — их сравнивают внутри одного плана, а не между запусками.

Какие индексы бывают:

- **B-tree** — по умолчанию: равенство, диапазоны, `ORDER BY`, `LIKE 'abc%'`. Составной `(a, b)` отсортирован сначала по `a`: запрос с `a = $1` и сортировкой по `b` идёт по нему идеально, а запрос только по `b` — дорого (в примере — весь индекс, 390 страниц). PostgreSQL 18 умеет skip scan: если у первой колонки мало значений, он спускается по дереву для каждого (3 спуска, 12 страниц в примере). `LIKE` по префиксу в базе с лингвистической сортировкой (`en_US.utf8`) работает только с индексом `text_pattern_ops` или `COLLATE "C"`.
- **Частичный** — `CREATE INDEX … WHERE status = 'new'`: индексирует только нужные строки, мал и быстр; используется, когда условие запроса подразумевает условие индекса.
- **Покрывающий** — `INCLUDE (total)`: дополнительные колонки лежат в листьях индекса, и запрос получает `Index Only Scan`, если карта видимости актуальна (её обновляет VACUUM, урок 12).
- **GIN** — для значений-коллекций: `jsonb` (`@>`, `?`), массивы (`@>`, `&&`), полнотекстовый поиск (`tsvector`), триграммы `pg_trgm` для `LIKE '%abc%'`.
- **BRIN** — крошечный индекс «минимум/максимум на диапазон страниц»: хорош для огромных таблиц, где значение растёт вместе с физическим порядком (время вставки в журнале событий). Он неточный — `Bitmap Heap Scan` перепроверяет строки, поэтому число строк у `Bitmap Index Scan` по BRIN условно.

Каждый индекс замедляет запись и занимает место; индексы под реальные запросы, а не «на всякий случай», проверка — по `EXPLAIN (ANALYZE)` на данных правдоподобного объёма.

pgx добавляет свой слой. По умолчанию (`QueryExecModeCacheStatement`) запрос с параметрами при первом вызове готовится на сервере (`Parse` с именем `stmtcache_…`), а дальше выполняется по имени — экономия разбора и один сетевой обмен. Кеш живёт на серверном соединении, и это ломается за PgBouncer в режиме `pool_mode = transaction`: следующая транзакция может попасть на другое серверное соединение, где выражения нет. Варианты: `DefaultQueryExecMode = QueryExecModeExec` или `QueryExecModeSimpleProtocol` (без именованных выражений; оба выводят типы параметров из Go-типов, поэтому, например, структуру в `jsonb` придётся передавать строкой JSON), `QueryExecModeCacheDescribe` (кеширует на клиенте только типы параметров и колонок и выполняет запрос безымянным выражением за один обмен — с пулером совместим, но после изменения схемы первый запрос может упасть), либо PgBouncer 1.21+ с `max_prepared_statements` — он сам отслеживает выражения уровня протокола; с 1.24 это включено по умолчанию (200). Режим можно задать в DSN (`default_query_exec_mode=exec`) или первым аргументом отдельного запроса.

## Как это в C#

- Индексы, `EXPLAIN` и статистика — одинаковые: это PostgreSQL. Если вы привыкли к SQL Server: кластерного индекса в PostgreSQL нет — таблица всегда куча, `INCLUDE` и фильтрованные индексы (`WHERE`) работают так же, а аналог «Actual Execution Plan» из SSMS — `EXPLAIN (ANALYZE)`.
- Подготовка запросов — наоборот. Npgsql по умолчанию на сервере ничего не готовит: только явный `cmd.Prepare()` или автоподготовка `Max Auto Prepare`. pgx готовит всё по умолчанию. Поэтому сервис, переписанный с C# на Go, может впервые «встретиться» с PgBouncer в режиме transaction.
- EF Core генерирует SQL сам, и узнать, какой индекс нужен, можно только из логов SQL и `EXPLAIN`. В Go SQL написан руками (или в `query.sql` для sqlc) — его же и анализируют.

## Ловушки

### Функция над колонкой выключает индекс

```go
// индекс orders_email (email) не поможет: индексировано email, а не lower(email)
pool.Query(ctx, `SELECT id FROM orders WHERE lower(email) = lower($1)`, email)
```

Индекс используется, когда условие сравнивает саму индексированную колонку. Нужен индекс по выражению — `CREATE INDEX ON orders (lower(email))` — и тот же вид выражения в запросе. Та же история с `created_at::date = $1` (пишите диапазон `created_at >= $1 AND created_at < $1 + interval '1 day'`) и с неявным приведением типа параметра.

### Обобщённый план подготовленного выражения

```go
// status = 'new' — 1% строк, status = 'done' — 99%
for _, s := range statuses {
	pool.Query(ctx, `SELECT id FROM orders WHERE status = $1`, s) // pgx: одно подготовленное выражение
}
```

Для подготовленного выражения PostgreSQL первые пять выполнений строит план под конкретные значения, а затем может перейти на обобщённый (generic) план, если тот не выглядит дороже. На перекошенных данных обобщённый план хорош для одних значений и ужасен для других. Признак — запрос то быстрый, то медленный при тех же индексах. Лечение — `plan_cache_mode = force_custom_plan` для роли или сессии, либо `QueryExecModeExec` для такого запроса.

### `EXPLAIN ANALYZE` выполняет запрос

```go
conn.Exec(ctx, `EXPLAIN ANALYZE DELETE FROM orders WHERE created_at < $1`, cutoff) // строки удалены!
```

`ANALYZE` честно выполняет запрос, включая `INSERT`, `UPDATE` и `DELETE`. Изменяющие запросы разбирайте внутри транзакции и откатывайте её (`BEGIN; EXPLAIN ANALYZE …; ROLLBACK`), а на проде помните, что запрос под `EXPLAIN ANALYZE` нагружает базу так же, как настоящий.

## Задание

Напишите анализатор плана из `EXPLAIN (ANALYZE, FORMAT JSON)`, который находит последовательные сканирования больших объёмов и узлы, где оценка числа строк расходится с фактом:

```go
var ErrBadPlan = errors.New("bad plan")

type Finding struct {
	Kind      string  // "seq-scan" или "misestimate"
	Node      string  // "Node Type"
	Relation  string  // "Relation Name", "" если нет
	Estimated float64 // "Plan Rows"
	Actual    float64 // "Actual Rows"
}

type Options struct {
	MinSeqScanRows    float64
	MisestimateFactor float64
}

func Analyze(plan []byte, opts Options) ([]Finding, error)
```

Вход — JSON-массив, первый элемент которого — объект с ключом `"Plan"` (корневой узел). Узел — объект с полями `"Node Type"` (строка), `"Relation Name"` (строка, может отсутствовать), `"Plan Rows"`, `"Actual Rows"`, `"Actual Loops"`, `"Rows Removed by Filter"` (числа, возможно дробные; любое может отсутствовать — отсутствующее `"Plan Rows"` и `"Rows Removed by Filter"` считаются нулём) и `"Plans"` — массив дочерних узлов. Остальные поля игнорируются.

- Если вход — не JSON, не массив, пустой массив, или у первого элемента нет `"Plan"`-объекта (`null`, не объект) — вернуть `nil` и ошибку, для которой `errors.Is(err, ErrBadPlan)`.
- Узлы обходятся в прямом порядке: сначала узел, затем его `"Plans"` по порядку, рекурсивно.
- Узел проверяется, только если у него есть и `"Actual Rows"`, и `"Actual Loops"`, и `"Actual Loops" > 0` (обычный `EXPLAIN` и невыполнявшиеся узлы пропускаются, но их дети обходятся).
- **seq-scan**: `"Node Type"` равен `"Seq Scan"`, `opts.MinSeqScanRows > 0` и `(Actual Rows + Rows Removed by Filter) × Actual Loops >= opts.MinSeqScanRows`.
- **misestimate**: `opts.MisestimateFactor > 0` и `max(e, a) / max(min(e, a), 1) >= opts.MisestimateFactor`, где `e` — `"Plan Rows"`, `a` — `"Actual Rows"`.
- Порог `<= 0` отключает свою проверку.
- Находки идут в порядке обхода; если узел дал обе, сначала `seq-scan`, потом `misestimate`. В `Finding` — тип узла, имя таблицы (или `""`), `"Plan Rows"` и `"Actual Rows"` узла как есть. Нет находок — срез длины 0 (`nil` допустим), ошибка `nil`.

С профилем labs скрытый тест получает настоящий план PostgreSQL 18: до создания индекса анализатор должен найти `seq-scan`, после — ничего.
