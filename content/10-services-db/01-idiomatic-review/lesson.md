Компилятор Go строг к мелочам (неиспользуемые импорты и переменные — ошибка), а `gofmt` снимает споры о форматировании. Всё остальное — договорённости сообщества, собранные в [Effective Go](https://go.dev/doc/effective_go) и [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments). На ревью Go-кода по ним и спорят: код с такими замечаниями работает, но хуже читается, теряет причины ошибок, не отменяется и течёт горутинами. Самые частые замечания:

- **Имена.** `GetUser`, `user.UserService`, `this`, `IStore`, пакет `utils` → `User`, `user.Service`; receiver — одна-две буквы от типа, одинаковые во всех методах; интерфейс без префикса; пакет назван по смыслу.
- **Ошибки.** `%v` вместо `%w`, текст `"Failed to load."`, лог и возврат одновременно, `_ = f()` → `fmt.Errorf("load order %d: %w", id, err)`; текст строчными и без точки — его допишут в середину чужой фразы; логирует тот, кто обработал.
- **context.** `context.Background()` посреди запроса, `ctx` в поле структуры или не первым параметром → `ctx context.Context` — первый параметр каждой функции, которая ждёт ввода-вывода, и передаётся вниз до `QueryContext`.
- **Интерфейсы.** Большой интерфейс рядом с реализацией «для моков», функция возвращает интерфейс → маленький интерфейс объявляет потребитель; «accept interfaces, return structs».
- **Нулевое значение.** Обязательный конструктор для простого типа → `var b strings.Builder`, `var mu sync.Mutex` работают сразу — так стоит проектировать и свои типы.
- **Паника.** `panic` в библиотеке на плохом вводе → ошибка; `panic` — для невозможного состояния и `Must…` при старте.
- **Ресурсы.** `Close` без `defer`, забытый `rows.Close()` → `defer` сразу после успешного открытия.
- **Горутины.** `go func() { for { ... } }()` в конструкторе → у каждой горутины есть владелец, способ остановки (`ctx`, закрытый канал) и ожидание (`WaitGroup`, `errgroup`).

Пример — функция до и после ревью: обе возвращают имя пользователя, но первая теряет причину ошибки (`errors.Is` не находит `ErrNotFound`), пишет в лог за вызывающего и не замечает отмены. Полный список проверок с разделами про HTTP, базы данных и тесты — на странице [чек-листа ревью](/review/): у каждого пункта ссылка на урок, где он разобран. Остальные уроки модуля разбирают пункты подробно.

## Как это в C#

- **Имена.** В .NET — `PascalCase` для всего публичного, `GetUserAsync`, `IUserRepository`, `_camelCase` для полей и `this`. В Go экспорт задаёт регистр первой буквы, имя пакета — часть имени (`user.Service`, а не `UserService`), геттеры без `Get`, у receiver короткое имя вместо `this`, аббревиатуры одним регистром: `userID`, `HTTPClient`, а не `UserId`/`HttpClient`.
- **Ошибки.** `throw new LookupException("...", inner)` и фильтр `catch ... when (ex.InnerException is NotFoundException)` → `fmt.Errorf("...: %w", err)` и `errors.Is`/`errors.As`. Исключение несёт стек само; в Go контекст ошибки — это текст обёрток, поэтому каждый слой добавляет к ней, *что* он делал.
- **Отмена.** `CancellationToken ct` — последним параметром, часто со значением по умолчанию. `ctx context.Context` — всегда первым и без значения по умолчанию: функция, которой не дали контекст, получает его явно — `context.Background()` в `main` или `t.Context()` в тесте.
- **Интерфейсы и DI.** В .NET интерфейс объявляют рядом с реализацией, чтобы зарегистрировать в контейнере и подменять в тестах. В Go реализация неявна, поэтому интерфейс из одного-двух методов объявляет тот, кому он нужен, а конструктор возвращает конкретный тип — потребитель сам решит, через какой интерфейс на него смотреть.

## Ловушки

### Залогировать и вернуть

```go
if err != nil {
	log.Printf("load order %d: %v", id, err) // запись № 1
	return fmt.Errorf("load order %d: %w", id, err)
}
// ...а выше по стеку обработчик пишет запись № 2, и так на каждом слое
```

Одна ошибка порождает три-четыре записи в логе с разной долей контекста, и по ним уже не понять, сколько было сбоев. Правило: ошибку либо обрабатывают (логируют, отвечают клиенту, повторяют), либо возвращают с контекстом — но не то и другое сразу. Логирует край: HTTP-обработчик, воркер очереди, `main`.

### `context` в поле структуры

```go
type Repo struct {
	ctx context.Context // контекст первого запроса или Background
	db  *sql.DB
}

func (r *Repo) Order(id int64) (Order, error) {
	return r.scan(r.db.QueryRowContext(r.ctx, q, id)) // дедлайн и отмена запроса сюда не доходят
}
```

Структура живёт дольше запроса, а контекст — ровно запрос: из поля он либо уже отменён (и все запросы падают), либо `Background` без дедлайна (и отмена клиентом ничего не обрывает). Контекст передают параметром в каждый метод. Исключение из правила — редкое: тип, который сам и есть одна операция (как `*http.Request`).

### Горутина без владельца

```go
func NewCache(ttl time.Duration) *Cache {
	c := &Cache{ticker: time.NewTicker(ttl)}
	go func() {
		for range c.ticker.C { c.clear() }
	}()
	return c
}

func (c *Cache) Close() { c.ticker.Stop() } // горутина осталась висеть
```

`Ticker.Stop` не закрывает канал `C`, поэтому `for range` после него ждёт вечно, а каждый созданный и «закрытый» `Cache` оставляет горутину. Горутину должен останавливать тот, кто её запустил: канал `done` (или `ctx`) в `select` рядом с `<-ticker.C`, а `Close` закрывает его и ждёт выхода через `sync.WaitGroup`. Ещё лучше — не запускать горутину в конструкторе, а дать вызывающему метод `Run(ctx)`: тогда он сам решает, в какой горутине и до какого момента тот работает.

## Задание

В `task.go` — каталог цен с кешем: цены берутся из источника `Source` (в сервисе это база), кеш раз в `ttl` очищается фоновой горутиной. Код работает и открытые тесты проходят, но ревью он не прошёл бы: в нём шесть замечаний из чек-листа. Исправьте их, не меняя сигнатур. Каждое замечание проверяет свой скрытый тест.

```go
var (
	ErrNotFound   = errors.New("not found")
	ErrInvalidSKU = errors.New("invalid sku")
)

type Source interface {
	Price(ctx context.Context, sku string) (int64, error)
}

func NewCatalog(src Source, ttl time.Duration) *Catalog
func (c *Catalog) Price(ctx context.Context, sku string) (int64, error)
func (c *Catalog) Total(ctx context.Context, skus []string) (int64, error)
func (c *Catalog) Close()
```

Требования к исправленному коду:

- `NewCatalog` запускает фоновую очистку кеша раз в `ttl`. `Close` (вызывается один раз) останавливает её и возвращается, когда фоновая горутина завершилась.
- `Price`:
  - пустой `sku` — `0` и ошибка, для которой `errors.Is(err, ErrInvalidSKU)`; паники нет, источник не вызывается;
  - если цена в кеше — возвращает её, не обращаясь к источнику; иначе вызывает `src.Price` **с контекстом, переданным в `Price`**, и кладёт успешный результат в кеш;
  - ошибка источника не кешируется и возвращается обёрнутой: `errors.Is` находит исходную ошибку (`ErrNotFound`, `context.Canceled`…), текст содержит `sku`, начинается со строчной буквы и не заканчивается точкой; результат — `0`.
- `Total` возвращает сумму цен (для пустого списка — `0, nil`). На первой ошибке `Price` прекращает подсчёт и возвращает `0` и ошибку, обёрнутую так же: `errors.Is` находит причину, текст содержит `sku`.
- Каталог ничего не пишет в лог (ни `log`, ни `slog`): ошибки только возвращаются.
- Все методы безопасны для вызова из многих горутин.
