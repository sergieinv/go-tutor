# Сервисы и базы данных

Обзор модуля для показа команде: как пишут Go-сервисы в продакшне и как они работают с PostgreSQL и MySQL.

---

## Ревью: что замечают чаще всего

- Имена: `GetUser`, `IStore`, пакет `utils` → `User`, `Store`, пакет по смыслу.
- Ошибки: `fmt.Errorf("load order %d: %w", id, err)`, текст строчными; логирует тот, кто обработал, а не каждый слой.
- `context` — первым параметром, а не в поле структуры.
- Интерфейсы маленькие и объявлены у потребителя; у каждой горутины есть владелец.

---

## Раскладка и сборка без DI-контейнера

- Нет `dotnet new webapi` и обязательной структуры: `cmd/` и `internal/`, пакеты по смыслу, а не по слоям.
- Зависимости собираются руками в функции `run`, которую можно вызвать из теста.
- Доменные ошибки (`ErrNotFound`, `ErrConflict`) переводятся в HTTP-статус в одном месте — на краю.
- Остановка: сначала перестать принимать запросы, потом воркеры, потом закрыть базу.

---

## `*sql.DB` — это пул

- Свободных соединений нет и лимит исчерпан — запрос ждёт в очереди до возврата соединения или отмены `context`.
- Соединение возвращают `rows.Close()`, `Scan` у `Row`, `Commit`/`Rollback`. Почти все проблемы пула — утечки.
- Пул из десяти переживает девять утечек и встаёт на десятой — в случайном запросе.

## Транзакция передаётся явно

```go
func withTx(ctx context.Context, db *sql.DB, opts *sql.TxOptions, fn func(tx *sql.Tx) error) error {
	tx, err := db.BeginTx(ctx, opts)
	if err != nil {
		return err
	}
	defer tx.Rollback() // после Commit ничего не делает
	if err := fn(tx); err != nil {
		return err
	}
	return tx.Commit()
}
```

Невидимой «текущей транзакции», как у `TransactionScope`, нет. Запрос через `db` внутри `tx` уходит в другое соединение.

## Потерянное обновление

- «Прочитать, проверить в Go, записать» теряет списания даже на Read Committed.
- Три лекарства: `SELECT … FOR UPDATE` (`NOWAIT`, `SKIP LOCKED`), версия строки, атомарный `UPDATE … WHERE qty >= $1`.
- Повтор — всей транзакции, с ограничением попыток и backoff с джиттером.

## SQL — источник правды

| .NET | Go |
| --- | --- |
| миграции EF Core из модели | SQL-миграции goose |
| LINQ во время выполнения | запросы в `.sql`, код генерирует sqlc |
| ленивая загрузка → неявный N+1 | N+1 виден: `QueryContext` внутри `for` |

N+1 лечат вторым запросом с `IN (...)` / `= ANY($1)` или JOIN.

## Outbox: событие в той же транзакции

- Запись в БД и в брокер — двойная запись без общей транзакции: событие теряется или появляется без заказа.
- Событие пишут в таблицу `outbox` в той же транзакции, что и заказ.
- Relay забирает пачку с `FOR UPDATE SKIP LOCKED` и публикует. Доставка at-least-once — потребитель идемпотентный.

## pgx и MySQL

- `pgxpool` — родной API: массивы, `jsonb`, `Batch`, `COPY`, `LISTEN/NOTIFY`. Ошибки сравнивают по коду `*pgconn.PgError`: `23505`, `40001`.
- MVCC: долгая транзакция держит горизонт `VACUUM`, и таблицы пухнут.
- MySQL: DSN собирают через `mysql.Config`, а не `Sprintf`; `parseTime`, `utf8mb4`, gap locks и дедлок `1213`.
- Уроки на настоящих базах — профиль labs: `docker compose --profile labs up --build`.

---

## Что запомнить

- Ошибку оборачивают с `%w` и логируют один раз.
- Каждый `Rows` закрывают, транзакцию начинают с `defer tx.Rollback()`.
- Проверку «хватает ли» — в условие `UPDATE` или под блокировку, а не в Go.
- SQL не мокают: контрактный набор тестов гоняют на фейке и на настоящей базе.
