# Аудит безопасности локальной песочницы

Проверялся локальный режим (`RUNNER_MODE=local`, без gVisor) — тот, в котором
учебник запускают на машине разработчика: `docker-compose up` →
http://localhost:8080. Дата аудита — 2026-11-09/10, машина — macOS на arm64,
Docker Desktop, образ `go-tutor/runner:dev` (Go 1.27.2), `RUNNER_SLOTS=4`.

Каждая гипотеза проверялась пробой, а не только чтением кода: программы
отправлялись в `/api/run` так же, как их отправляет сайт.

## Модель угроз

Учебник работает на машине разработчика и доступен только с `127.0.0.1`.
Защищаем:

- **машину** — от кода в песочнице (свой или присланный коллегой по ссылке
  «Поделиться»: ученик может запустить чужой код, не вчитываясь);
- **другие запуски** — один запуск не должен видеть и ломать соседние;
- **сервисы профиля `labs`** — программа не должна получать к ним больше,
  чем задокументировано;
- **браузер ученика** — чужая страница не должна дотянуться до runner и
  служебных портов, хотя они и слушают только loopback.

Вне модели: злонамеренный владелец машины (у него и так root), защита самого
контента учебника от ученика (эталоны отдаёт `/api/solution` по условию
владельца), и сеть — порты публикуются только на `127.0.0.1`, runner наружу
не выставлен вообще (проверено: `docker ps` показывает у `runner` только
внутренний `8081/tcp`).

## Что проверено и как

### Браузер → runner

| Проба | Результат |
| --- | --- |
| POST со своей страницы (`Origin` и `Sec-Fetch-Site: same-origin`) | 200 |
| «Простой» запрос `text/plain` с чужой страницы | 403 |
| Form POST (`application/x-www-form-urlencoded`) с чужой страницы | 403 |
| JSON с `Origin: http://evil.example` | 403 |
| JSON с `Sec-Fetch-Site: cross-site` без `Origin` | 403 |
| `Sec-Fetch-Site: same-site` (поддомен) | 403 |
| Preflight `OPTIONS` с чужой страницы | 405, ни одного заголовка `Access-Control-Allow-*` |
| DNS rebinding: `Host: evil.example` | соединение закрыто (nginx `return 444`) |
| Тело 2 МБ | 413 (nginx `client_max_body_size 1m`) |
| `GET /api/health` с чужой страницы | 200 — отдаёт только `{ok, lessons}` |
| Запрос без `Origin` и `Sec-Fetch-Site` (не браузер) | 200 — см. принятые риски |

Защиту дают три независимых слоя: `http.CrossOriginProtection` в runner,
проверка `Content-Type: application/json` (простой запрос браузера такой
заголовок без preflight не поставит) и `server_name` в nginx. WebSocket и
других путей через nginx нет: проксируется только `/api/`, остальное —
статика.

Игровой сервер модуля 15 (профиль `labs`, `ws://127.0.0.1:25580/ws`)
проверяет `Origin` по списку `GAME_WS_ORIGINS`
(`labs/gameserver/internal/websocket/handshake.go`) — чужая страница
WebSocket не откроет.

### Песочница → контейнер и хост

Проба изнутри песочницы (`uid 20001`, `CapEff: 0000000000000000`,
`Seccomp: 2` — профиль Docker включён):

- кеш сборки `/var/cache/go-build`, кеш модулей `/go/pkg/mod`, кеш buf и
  снимок базы уязвимостей — **только для чтения**: запись отвергается
  (`permission denied`). Отравить сборку следующих запусков нельзя;
- `/tmp/runner` (корень рабочих каталогов, `0711`) **не перечисляется**, а
  каталог запуска теперь `0700` и принадлежит uid слота: имя соседа нужно
  угадать, и даже угадав, прочитать его не получится;
- `/proc/1/environ` (окружение runner с паролями `labs`) — `permission
  denied`; окружение самой программы содержит только `PATH`, `HOME`,
  `TMPDIR`, `GOMEMLIMIT` и DSN своей базы;
- `..` и `/` в именах файлов запроса отвергает `Files.Validate`,
  `//go:embed ../../content/...` — ошибка сборки (`invalid pattern syntax`),
  `//go:generate` при сборке не выполняется, `import "C"` отвергается;
- присланный `go.mod` с `toolchain go1.99.0` ничего не скачивает
  (`GOTOOLCHAIN=local`), `replace` на каталог контейнера требует там `go.mod`
  и в `/content` его нет; `buf.yaml` переписывается в каноническом виде,
  `buf.gen.yaml` и `buf.lock` всегда свои (плагины — это программы, которые
  buf запускает от имени runner);
- Docker API (`/var/run/docker.sock`) в контейнере нет.

### Сеть песочницы

- интернета нет: `1.1.1.1:443` — `network is unreachable` (сеть `sandbox`
  помечена `internal`);
- базы профиля `labs` доступны только когда профиль запущен (иначе имена не
  резолвятся); `kafka`, `gameserver`, `valkey` сервисов и `postgres-shard1` в
  сеть `sandbox` не входят и недоступны;
- `site:8080` отвечает закрытием соединения: `Host: site:8080` не проходит
  `server_name` nginx;
- **API runner изнутри песочницы доступен** (`runner:8081` и
  `127.0.0.1:8081`) — см. находку 2.

### Исчерпание ресурсов

Проверено нагрузочным тестом (`docs/load-test.md`, сценарий `abuse`) и
отдельными пробами: бесконечный цикл, fork-бомба, миллион горутин, выделение
памяти, бесконечный вывод, заливка tmpfs. Все удержаны: обычные запросы
продолжали обслуживаться, контейнер ни разу не упал, `pids_limit` (1024) не
был близок (пик 37), память контейнера — 628 МБ из 2 ГБ.

### Утечки между запусками

После прогонов (включая abuse и таймауты): процессов uid'ов слотов — 0,
`/tmp/runner` пуст, в PostgreSQL и MySQL нет баз, схем и пользователей
`run_*`, в Valkey не осталось ACL-пользователей запусков.

## Находки

### 1. Из песочницы читались скрытые тесты и эталоны всех задач (исправлено)

**Критичность:** средняя (ломает проверку знаний, не безопасность машины).
**Воспроизведение:** `POST /api/run` с программой
`os.ReadFile("/content/02-basics/01-for/task/hidden_test.go")` — файл
читался, как и любой `solution.go`; `os.ReadDir("/content")` перечислял
модули. Причина: `COPY content /content` оставляет файлы доступными всем, а
программа работает от имени uid слота.
**Исправлено:** `runner/Dockerfile` — `RUN chmod -R go-rwx /content`. Сам
runner работает под root и читает контент как раньше.
**Проверка:** та же проба даёт `permission denied` на всех трёх путях и на
`ReadDir`; `/api/health` по-прежнему видит 203 урока, e2e и
`go test ./runner/...` проходят.

### 2. Программа из песочницы вызывает API runner (риск принят)

**Критичность:** средняя.
**Воспроизведение:** программа в песочнице делает
`POST http://runner:8081/api/solution {"lesson":"02-basics/01-for"}` и
получает эталон (HTTP 200). Так же доступны `/api/run`, `/api/test` и
остальные: присланный по ссылке код может вытащить эталоны всех задач или
занять слоты рекурсивными запусками.

Технически это не дырка в сети: программа работает **внутри контейнера
runner**, то есть в его сетевом пространстве имён. Ни `internal`-сеть, ни
отдельные сети, ни адрес прослушивания тут не помогают — нужен либо netns на
слот, либо аутентификация запросов. Защита от браузера (`CrossOriginProtection`,
`Content-Type`) не мешает: программа — не браузер и просто не шлёт
`Sec-Fetch-Site`.

**Рассмотренные варианты** (владелец выбрал первый — принять):

1. *Принять.* Эталоны и так отдаются по `/api/solution` без ограничений (это
   решение владельца: «учебник для своей команды»), а занять слоты можно и из
   браузера. Ничего, кроме содержимого курса и слотов, через API не достать.
2. *Общий секрет от nginx.* nginx добавляет `proxy_set_header X-Runner-Token
   …` из переменной окружения, runner требует этот заголовок. Программа
   секрет не прочитает (окружение runner ей недоступно — проверено). Цена:
   dev-сервер Astro проксирует `/api` прямо в runner
   (`site/astro.config.mjs`, `RUNNER_URL`), и ему тоже нужно передавать
   токен; `curl` к runner без токена перестанет работать.
3. *Netns на слот.* Самое честное, но требует `CAP_SYS_ADMIN` в контейнере —
   то есть ослабления изоляции самого контейнера. Не рекомендуется.

### 3. Не был включён `no_new_privileges`, в образе были setuid-программы (исправлено)

**Критичность:** низкая.
**Воспроизведение:** программа в песочнице читала `/proc/self/status` —
`NoNewPrivs: 0`, и находила 10 setuid-root программ базового образа
(`su`, `mount`, `passwd`, `newgrp`, `chsh`, `gpasswd`, `sg`, `umount`,
`chfn`, `ssh-keysign`). Прав они сами не дают, но это лишняя поверхность для
повышения прав из песочницы.
**Исправлено:** в `runner/Dockerfile` биты setuid/setgid сняты
(`find / -xdev -type f -perm /6000 -exec chmod ug-s {} +`), в
`docker-compose.yml` у `runner` добавлен `security_opt:
[no-new-privileges:true]`. Смена uid слота идёт не через execve, а через
`SysProcAttr.Credential`, поэтому запуск не ломается.
**Проверка:** та же проба даёт `NoNewPrivs: 1` и «всего setuid-программ: 0»;
тесты в образе (включая fork-бомбу и лимиты) проходят.

### 4. Каталог запуска был доступен на чтение всем (исправлено)

**Критичность:** низкая (нужно угадать имя каталога).
Было `chmod(dir, 0o755)` при `0711` на корне: угадав имя `run-…`, сосед по
контейнеру прочитал бы чужие файлы. Теперь `0700` и владелец — uid слота;
запись программы в свой рабочий каталог (уроки про файлы) работает.
**Проверка:** программа видит у своего каталога `drwx------` и успешно в него
пишет; `ReadDir /tmp/runner` — `permission denied`.

### 5. RLIMIT_AS ломал программы случайным образом (исправлено)

**Критичность:** средняя — это не дырка, а порча результата: примерно один
запуск из ста падал с «фатальной ошибкой рантайма» или **молча печатал
испорченный вывод**, и ученик видел это как ошибку своего кода.

**Воспроизведение.** Урок `06-stdlib/16-temp-files` (программа создаёт и
удаляет временные файлы), 8 потоков, 810 запусков: 6 неудач — `SIGSEGV`,
`fatal error: traceback did not unwind completely`, а один раз вывод был
таким:

```
CreateTemp:                                  %!(EXTRA bool=true, bool=true, bool=true)
```

то есть у программы испортилась строка формата. Чтобы отделить причину от
окружения, та же программа гонялась в контейнере напрямую, 8 × 120 запусков:
с `runner launch -as 1073741824` — 8 сбоев, без `-as` — ни одного. Причина
подтвердилась: рантайм Go не переживает отказ `mmap` по `RLIMIT_AS` — он
резервирует гораздо больше адресного пространства, чем использует, и отказ
получает в неожиданном месте.

**Исправлено:** `RLIMIT_AS` заменён на `RLIMIT_DATA` (`-data`,
`MemoryBytes*2`), который считает только отображённые данные.
Побочный выигрыш: раньше `-as` приходилось **полностью отключать** для
`-race` (детектор резервирует терабайты теневой памяти), и запуски с
детектором гонок шли без предела памяти вообще; `RLIMIT_DATA` работает и
с `-race`.
**Тесты:** `TestRunMemoryLimit` (был), `TestRunMemoryLimitWithRace` (новый).
**Проверка:** тот же урок, 8 потоков, 1209 запусков — 0 неудач.

### 6. Таймаут очереди обрывал сборку, и корректный код выглядел несобирающимся (исправлено)

**Критичность:** средняя (доступность и доверие к проверке).
**Воспроизведение:** 16 клиентов `runnerload`, 90 с — запрос `/api/test` с
эталонным решением вернул `buildFailed: true` и текст «сборка не уложилась в
1m0s». Причина: `queueTimeout` (30 с) оборачивал **весь** запрос, а не только
ожидание слота, и наследовался лимитом сборки.
**Исправлено:** ожидание слота ограничивает `sandbox.Config.QueueTimeout`
внутри `acquire`, а обработчики API передают контекст запроса; текст таймаута
сборки теперь говорит, что runner перегружен.
**Тесты:** `TestQueueTimeoutLimitsOnlyWait`, `TestQueueTimeoutBusy`.

### 7. Заливка общего tmpfs ломала соседние запуски «ошибкой компиляции» (частично исправлено)

**Критичность:** низкая в этой модели угроз (один пользователь, локальная
машина), но симптомы были обманчивыми.
**Воспроизведение:** программа пишет файлы по 8 МБ в свой каталог и забивает
общий tmpfs (512 МБ) за ~0,4 с, затем спит. В это время другие запросы
получали `HTTP 500 внутренняя ошибка runner`, а при неудаче на этапе сборки —
`buildFailed` с текстом `write prog: no space left on device`; один запуск
получил `SIGSEGV` из частично записанного бинарника.
**Исправлено (симптомы):** нехватка места — отдельная временная ошибка
`sandbox.ErrNoSpace`; и при создании рабочего каталога, и при неудачной
сборке (проверкой свободного места через `statfs`) runner отвечает `503 в
песочнице кончилось место, попробуйте ещё раз`.
**Тесты:** `TestFreeBytes`, `TestFailStatuses`.
**Не исправлено:** предела на объём, который пишет один запуск, нет —
см. принятые риски.

### 8. Программа убитая сигналом не объясняла себя (исправлено)

Запуск, убитый сигналом без своего вывода, возвращал только `exitCode: -1` и
пустой `stderr`. Теперь runner дописывает «программа убита сигналом …».
**Тест:** `TestRunKilledBySignalIsExplained`.

## Принятые риски

1. **Запросы не из браузера проходят** (`curl` к `127.0.0.1:8080/api/run` без
   `Origin` и `Sec-Fetch-Site` — 200). Так и задумано: `Sec-Fetch-*` защищает
   от чужой страницы в браузере, а не от процессов на машине, у которых и так
   есть права пользователя. Порт — только `127.0.0.1`.
2. **`/api/solution` отдаёт эталон без условий** — решение владельца: условие
   «после успеха или трёх попыток» проверяет интерфейс.
3. **Скрытые тесты видны изнутри своего же запуска.** `/api/test` кладёт
   `hidden_test.go` в рабочий каталог, и решение ученика может его прочитать
   и напечатать. Иначе тесты не запустить; после находки 1 это единственный
   путь, и он требует намеренных действий.
4. **Пароли профиля `labs` лежат в репозитории**, а программа работает в
   одной сети с базами. Проверено пробами: суперпользователи не входят из
   сети песочницы (PostgreSQL — `pg_hba.conf rejects`, MySQL — `Access
   denied` для `root`), `COPY ... TO PROGRAM` запрещён. Но ролью `runner`
   программа входит и может: создавать базы (`CREATE DATABASE` прошёл),
   видеть имена баз других запусков и — поскольку эта роль их и создала —
   удалять их; в MySQL у неё `CREATE USER`, `PROCESS`, `CONNECTION_ADMIN` и
   полные права на `run_%`; в Valkey песочницы администратор `default` с
   паролем из репозитория пускает `FLUSHALL` и `ACL` (проверено). То есть
   программа ученика может помешать **другому уроку на той же машине** и
   занять память баз. Данные в `labs` учебные и живут в tmpfs, профиль
   включается вручную, поэтому риск принят. Закрывается генерацией паролей
   при старте стека (программа окружение runner не читает); владелец решил
   оставить пароли в репозитории.
5. **Один запуск может забить общий tmpfs рабочих каталогов** на время своей
   работы (до 10 с). Соседи получают понятный `503` (находка 7), после
   запуска место освобождается. Отдельный tmpfs на слот потребовал бы
   фиксированного числа слотов в compose (сейчас `RUNNER_SLOTS` настраивается)
   или `CAP_SYS_ADMIN` для монтирования изнутри; при одном пользователе на
   машине это не стоит усложнения.
6. **Кеш сборки растёт** от запусков учеников: 1,2 → 1,7 ГБ за ~6 минут
   нагрузки. Он живёт в слое контейнера: `docker-compose up -d
   --force-recreate runner` возвращает его к состоянию образа, а Go сам
   выбрасывает записи, которыми не пользовались 5 дней. Лимита на кеш нет.
7. **`/api/fmt` не занимает слот** (форматирование идёт в процессе runner,
   `go/format` код не исполняет). Тело ограничено 1 МБ, у `go/parser` есть
   предел вложенности, так что это только процессорное время runner.
8. **Память контейнера под нагрузкой доходит до лимита.** В прогоне 4
   клиентов зафиксирован пик 1,57 ГБ из 2 ГБ, а `memory.events` показал 2708
   срабатываний `max` без единого `oom_kill`. Запас небольшой: если поднимать
   `RUNNER_SLOTS`, нужно поднимать и `mem_limit` (на слот — до 512 МБ
   программы по `RLIMIT_DATA` плюс сборка).

## Решения владельца и служебные порты labs

- **Находка 2** (вызов API runner из песочницы) — риск принят: эталоны и так
  открываются в интерфейсе, учебник локальный.
- **Риск 4** (пароли `labs` в репозитории) — оставлены, риск принят.
- **Служебные порты labs** (замечено по ходу аудита, исправлено):
  `POST /admin/features` «Заказов» (`127.0.0.1:8190`) теперь обёрнут в
  `http.NewCrossOriginProtection` — запрос с чужой страницы получает 403
  (`labs/orders/internal/features`, тест `TestFeaturesRejectsCrossOrigin`);
  служебный порт игрового сервера (`127.0.0.1:25590`, `/metrics` и
  `/debug/pprof`) отвергает фоновые запросы с `Sec-Fetch-Site:
  cross-site`/`same-site`, а переход по ссылке пропускает
  (`labs/gameserver/internal/app`, тест `TestOpsRejectsCrossSite`). Prometheus
  и `curl` этот заголовок не шлют и работают как раньше.
