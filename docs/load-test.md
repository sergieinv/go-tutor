# Нагрузочный тест runner

`tools/runnerload` гоняет по локальному стенду те же запросы, что делает сайт
(`/api/run` примеров, `/api/test` эталонов, `/api/gotest`, `/api/trace`), и
сверяет вывод с `example/output.txt`. Это не бенчмарк: цель — показать, что
под нагрузкой «команда на одной машине / один ученик с десятком вкладок» и под
злоупотреблением runner остаётся **корректным** и не падает.

## Как запустить

```sh
docker-compose up -d --build site runner

# обычная нагрузка: 8 клиентов, 90 секунд
go run ./tools/runnerload -clients 8 -duration 90s

# со «злыми» запросами (20 % — бесконечный цикл, fork-бомба, память, вывод)
go run ./tools/runnerload -clients 8 -duration 90s -scenario abuse

# плюс запрос, забивающий общий tmpfs рабочих каталогов (ломает соседей — см. ниже)
go run ./tools/runnerload -clients 8 -duration 90s -scenario abuse -fill-tmpfs
```

Флаги: `-url` (по умолчанию `http://127.0.0.1:8080`, то есть через nginx),
`-content`, `-clients`, `-duration`, `-scenario`, `-abuse-share`, `-timeout`,
`-verify`, `-fill-tmpfs`, `-seed`. Запросы идут с заголовками страницы
учебника (`Content-Type: application/json`, `Origin`, `Sec-Fetch-Site`) —
без них runner отвечает 403.

Набор запросов строится из контента: берутся уроки с `example/main.go`, кроме
тех, которым нужен профиль `labs` (их вывод зависит от настоящей базы).
Пример с `_test.go` идёт в `/api/gotest`, урок с `task/solution.go` — в
`/api/test` (эталон обязан пройти), уроки модуля 05 — ещё и в `/api/trace`.

Отчёт: число запросов и пропускная способность, коды ответов, по каждому виду
запроса — количество, ошибки и перцентили задержки, а также `ожид.p90` —
p90 от «задержка минус время запуска в песочнице» (ожидание слота, сборка,
сеть). Ошибки группируются по видам с номером урока.

`docker stats` снимается рядом, в отдельном окне:

```sh
while :; do docker stats --no-stream --format \
  '{{.Name}} cpu={{.CPUPerc}} mem={{.MemUsage}} pids={{.PIDs}}' go-tutor-runner-1; sleep 3; done
```

## Критерии прохождения

Инструмент печатает их сам в конце отчёта:

1. **Нет 5xx, кроме 503.** `503` — честный ответ «все песочницы заняты» или
   «кончилось место»; `500` и 502/504 — провал.
2. **Обычные запросы корректны.** `stdout` примера совпадает с
   `example/output.txt` (у `go test` время тестов маскируется), эталон задачи
   проходит тесты, пример собирается и укладывается в лимиты.
3. **«Злые» запросы удержаны лимитами** (сценарий `abuse`): каждый такой
   запрос получает 200 (или 503), а программа убита по таймауту, лимиту
   вывода или памяти — успешное завершение считается провалом.
4. **После прогона не остаётся мусора** (проверяется рядом, командами ниже):
   нет процессов uid'ов слотов, `/tmp/runner` пуст, рост кеша сборки
   ограничен слоем контейнера.

```sh
docker exec go-tutor-runner-1 sh -c \
  'ps -eo uid,comm | awk "\$1+0 >= 20000"; ls /tmp/runner; du -sh /var/cache/go-build; df -h /tmp/runner'
```

## Результаты

Машина: MacBook на arm64, macOS 25.6, Docker Desktop; контейнер runner —
`cpus: 2`, `mem_limit: 2g`, `pids_limit: 1024`, `RUNNER_SLOTS=4`, tmpfs
рабочих каталогов 512 МБ. Дата — 2026-11-10, образ после исправлений аудита
(`docs/security-audit.md`). **Числа машинозависимы** и сильно зависят от
прогретости кеша сборки: в прогонах ниже контейнер был только что создан,
поэтому часть сборок шла «с нуля».

### Обычная нагрузка

| Клиентов | Длительность | Запросов | Запр/с | Ошибок | p50 `run` | p90 `run` | p99 `run` | Пик памяти |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 4 | 60 с | 233 | 3,9 | 0 | 767 мс | 2,4 с | 4,1 с | 184 МБ |
| 8 | 90 с | 228 | 2,5 | 0 | 2,4 с | 5,1 с | 19,0 с | 317 МБ |
| 8 (кеш прогрет) | 90 с | 538 | 6,0 | 0 | 2,1 с | 3,0 с | 3,9 с | 237 МБ |
| 16 | 90 с | 365 | 4,1 | 0 | 4,3 с | 7,9 с | 14,2 с | 423 МБ |

Все четыре критерия выполнены. Видно главное: слотов 4, поэтому с ростом
числа клиентов задержка растёт, а пропускная способность — нет; ожидание
слота (`ожид.p90`) при 16 клиентах доходит до 7 с. `503` не было ни разу:
ожидание слота не дотягивало до 30 с.

### Нагрузка со злоупотреблением

8 клиентов, 90 с, 20 % «злых» запросов (`-scenario abuse`): 250 запросов,
**0 ошибок**, все критерии выполнены. Обычные запросы продолжали
обслуживаться (p90 `run` — 4,6 с), контейнер не падал: пик памяти 628 МБ из
2 ГБ, процессов — 35 из 1024.

| «Злой» запрос | Чем удержан |
| --- | --- |
| бесконечный цикл | таймаут реального времени (10 с) |
| fork-бомба | `RLIMIT_NPROC` 64 на uid слота, затем `killall` слота |
| миллион горутин | `RLIMIT_DATA` и `GOMEMLIMIT` |
| выделение 4 ГБ | `RLIMIT_DATA` (512 МБ) |
| бесконечный вывод | лимит 64 КБ, программа обрывается, не дожидаясь таймаута |

После прогона: процессов слотов — 0, `/tmp/runner` пуст, баз и
ACL-пользователей `run_*` в сервисах `labs` не осталось (проверялось с
поднятым профилем `labs`).

### Заливка общего tmpfs

С `-fill-tmpfs` сценарий **намеренно не проходит** критерии 2 и 3 — это и есть
находка 7 аудита: предела на объём, который пишет один запуск, нет. Один
запрос забивает 512 МБ общего tmpfs за ~0,4 с, и пока он работает, соседние
запросы получают `503 в песочнице кончилось место, попробуйте ещё раз` (до
исправления они получали `500` и ложные «ошибки компиляции»). После
окончания запуска место освобождается само.

## Что нагрузка нашла и что исправлено

Подробно — в `docs/security-audit.md`, находки 5–8. Коротко:

- `RLIMIT_AS` ломал программы примерно в одном запуске из ста (случайные
  `SIGSEGV` и испорченный вывод) — заменён на `RLIMIT_DATA`; заодно лимит
  памяти стал работать и с `-race`;
- таймаут очереди (30 с) обрывал сборку, и корректный код выглядел
  несобирающимся — теперь он ограничивает только ожидание слота;
- нехватка места в tmpfs превратилась из `500 внутренняя ошибка` в `503` с
  понятным текстом;
- программа, убитая сигналом, больше не возвращает пустой вывод без
  объяснения.
